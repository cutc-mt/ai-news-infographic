Fable-6級の性能を引き出す評議会ワークフロー

エージェントが自分の仕事を自分で採点する問題に悩んだ末、PandaCodeに「Council（評議会）」を搭載。設定・レビュワー視点・差し戻しルールから、25ラウンドに及んだスキル管理機能の実録まで丸ごと解説

📅 2026年11月17日／AI Code King（@aicodeking）／AIエージェント実践解説

①はじめに：今日のテーマ

  • エージェント開発の悩みは「作った本人（AI）が自分の仕事を採点してしまう」こと。自己評価では甘くなりがち。
  • その解決策として、オープンソースツールPandaCodeにCouncil（評議会）機能を自作した話。
  • タイトル通り、このワークフローでFable-6級の成果物品質を狙う、というのが本動画の主張。
「AIに作らせて終わり」では届かない——審査を仕組み化するのが今回の主役なの

②PandaCodeとは

  • 作者が公開しているコーディングツールで、リポジトリはgithub.com/aicodeking/pandacode。
  • エージェントに作業を任せて進めるタイプのツールで、この動画用にCouncil機能を実装して組み込んだ。
  • 既存の「AIが作ってAIが自己チェック」な運用のどこが危ないかを、実装を通じて見せていく回。
使ったツールは全部公開済み——自分の手元でも再現できるのが偉いの

③問題点：自己採点の甘さ

  • 作業を作ったエージェント自身が品質を判定すると、自分の仕事に甘い点がつきやすい。
  • 作った本人は自分の設計意図を知っているため、抜けや破綻に気づきにくい。
  • 対策はシンプル：独立したレビュワーに、作った本人の自己評価へ異議を唱えさせること。
採点者と作業者を分ける——人間の世界と同じ鉄則をAIにも当てはめるの

④Council（評議会）の基本設計

  • Councilでは目標スコアラウンド上限レビュワー人数の3つを自分で設定する。
  • ワークフローは「実装 → レビュー → 修正 → 再レビュー」の繰り返し。目標に届くまで周回する。
  • スコアの基準を先に決めておくので、「なんとなく良し」で終わらせられない。
品質のゴールを数字で宣言させる——これが全体の土台なの

⑤レビュワーの「レンズ」

  • 各レビュワーにはレンズ（専門の見地）が割り当てられ、それぞれ違う観点から採点する。
  • 例えばセキュリティリリース品質事実の正確さといった具合に、関心を分離。
  • レンズはラウンド1の終了後は固定。以降の周回では同じ観点で一貫した採点が続く。
全方位レビューは幻想——一人一つの「見る窓」を割り当てるのがコツなの

⑥平均ではなく「最低スコア」を採用

  • Councilの判定に使うのは平均点ではなく全レビュワーの最低スコア。
  • 一人でも厳しい評価があれば全体が引き下げられるので、弱い観点の見落としが致命傷になる設計。
  • 「他が高評価だから良し」という帳消し運用を構造的に禁止できる。
品質は最弱のリンクで決まる——鎖の強さと同じ理屈なの

⑦毎ラウンド「新しい顔」で審査

  • 各ラウンドには毎回新しいレビュワーが参加。前の周回の審査員を引き継がない。
  • レビュワーには目標スコアも過去のスコアも見せない。先入観なしの白紙採点。
  • 「前回9点だったから今回は少し甘く」のような基準のすり寄りを防ぐのが狙い。
審査員に記憶も目標も持たせない——清廉な採点のための工夫なの

⑧目標未達なら「完成拒否」

  • PandaCodeは目標スコア未満での完了を拒否する。途中で手を上げて終わる、を許さない。
  • 代わりにリードへブロッカーの修正を指示させ、次のラウンド召集を命令する。
  • つまり「直して出し直す」ループがツール側で強制される。人間の目が離れても回り続ける。
「まあいっか」を封じるのがこの機能の存在意義なの

⑨実録：スキル管理機能のレビュー

  • 題材はPandaCode自身のスキル管理機能。実装後、Councilのレビューラウンドをどう通過したかを追う。
  • 結果は上限の25ラウンド到達で終了。目標は9.5、最終スコアは9.0。
  • 目標に届かぬまま打ち切りとなり、「続けるか、ここで受け入れるか」は人間の判断に委ねられた。
9.0と9.5の差0.5を追うのに25周——理想と現実の距離も見せてくれるの

⑩セキュリティレビューの発見

  • セキュリティのレンズで審査すると、実装者が想定していなかった脆弱性・リスクが具体的に挙がった。
  • 発見事項はレビュー結果として修正ブロッカーとしてリードに渡り、次ラウンドの課題になる。
  • 「動くけど危ない」コードが完成扱いで紛れ込むのを防げるのがこの視点の価値。
機能しただけで安心、をやめてくれる一番ありがたいレビュワーなの

⑪リリース品質レビューの発見

  • リリースのレンズでは公開に足る状態か（文書・整合性・仕上がり）が問われる。
  • README等の説明と実装のずれや、公開前に直すべき粗が指摘された。
  • 「自分ならこれを公開できるか？」という第三者の公開基準が自動で入る効果。
出荷検査を毎回やってもらえる——品質保証部門を丸ごと借りる感じなの

⑫事実の正確さレビューの発見

  • 事実確認のレンズでは、UIに表示する文面や数値が正確かを審査。
  • 実装者が書いた説明文の嘘・誇張・古い情報が具体例として挙がった。
  • 「それっぽい文章」をそのまま出すAIの癖を、事実照会の視点で叩く意味は大きい。
もっともらしい嘘を見抜く係——地味だけど効くレンズなの

⑬UIレビューを成功させるコツ①

  • UIを審査させるときは具体的な目標と状態を名指しで指定する（「この操作ではこう表示される」等）。
  • あわせてスクリーンショットによるレビューを要求。見た目の事実を確認させてから採点させる。
  • 抽象的な「いいUIにして」ではレビュワーも判断基準を掴めず評価が空転する。
審査員への指示も仕様書レベルで書く——ここが分かれ道なの

⑭UIレビューを成功させるコツ②

  • 審査は見た目（appearance）と操作の挙動（interaction）に分離する。
  • 見た目の採点と、クリックや遷移といった振る舞いの採点を別々にやらせると指摘が鋭くなる。
  • 混ぜて審査すると片方の問題がもう片方の点数に波及して原因が見えなくなる。
「綺麗か」と「動くか」は別の質問——分けると答えが変わるの

⑮コスト面：プラン消費と伸び悩み

  • Councilはプランの使用量をその分余計に食う。レビュワー分の消費は避けられない。
  • スキル管理の例では大半のラウンドでスコアがほとんど動かなかった＝伸び悩み（収穫逓減）が実在する。
  • 目標を際限なく上げるより、現実的な目標設定と打ち切り判断が大事。
品質追求は料金と引き換え——無限に上がるわけじゃないのも事実なの

⑯ミックスモデルのススメ

  • Panda Routerをオンにすると、各レビュワーに異なるモデルを割り当てようとする。
  • 同系モデルばかりだと指摘が似るため、多様な視点＝多様なモデルで判定の偏りを減らせる。
  • レビュワーだけじゃなく実装側とのモデル組み合わせも含めたミックス運用を推奨。
審査員が全員同じ脳みそだと意味が薄い——多様性が強さなの

⑰正直な評価：スコアは「味」ではない

  • 作者の判定は「Councilはかなりイケてる」。自己採点問題への実効性ある一手。
  • ただしスコア＝品質の全てではない。9.5を取っても「味」や使用感が良いとは限らない。
  • いつ止めるか・受け入れるかの最終決定は常に人間。ツールは判断材料をくれるだけ。
数字が良くても使って心地いいかは別物——最後は自分の舌なの

  • 導入の肝は目標スコア最低点採用新規レビュワーの3セットで回すこと。
  • 自分のエージェントの仕上がりに満足できていないなら、審査側を強化する発想が次の一手。
