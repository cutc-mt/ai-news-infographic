Cluster Health ScannerでTPU/GPUクラスタを健康診断

大規模AIクラスタのネットワークやハードウェアの不調を、稼働を止めずに事前検知する診断ツール「Cluster Health Scanner（CHS）」をGoogle Cloud Techが紹介。GKE・Slurm・TPU VMで動く仕組みと、NCCL・DCGMなどの検査内容を18カードにまとめました

📅 2026年11月21日／カレーちゃんのAIニュース／Google Cloud Tech 動画より

①本日のピックアップ

  • Google Cloud Techが2026年11月20日に「Cluster Health Scanner」の紹介動画を公開。
  • TPU・GPUクラスタのネットワークとハードウェアの問題を検出する非破壊の診断テストを前倒しで実行するツール。
  • 本体はGitHubのGoogleCloudPlatformリポジトリで公開されているオープンソース。
「クラスタの健康診断」を自動でやってくれるツールが登場したのだ

②CHSとは何か

  • TPU・GPUハードウェアの健全性・性能・信頼性を評価するエンドツーエンドの診断ツール。
  • 基盤の差異を吸収し、同じツール・同じコマンド・同じレポート形式で検証できる。
  • 単一ホストの故障切り分けからマルチノードのトポロジとネットワークの検証までスケールする。
クラスタ版の「人間ドック」だと考えればわかりやすいのだ

③なぜ今必要なのか

  • LLM学習は数千〜数万アクセラレータ規模に巨大化し、1台の不調が学習全体を足止めする。
  • 原因はGPU本体だけでなくノード間ネットワークの劣化・遅延にも潜伏する。
  • CHSは問題が起きる前に前倒し（プロアクティブ）で健康チェックできる。
「学習が止まってから探す」から「事前に見つける」への転換なのだ

④非破壊診断・セーフ設計

  • プレフライトチェックが対象を検証し、アイドル状態のノードだけをテスト。
  • そのため実行中のワークロードは妨げられない——動画の見どころ「non-disruptive」。
  • 「Safe by default」が設計思想で、誤って稼働中ノードを壊す心配が少ない。
健康診断のために業務を止めない、が大きな売りなのだ

⑤TPUもGPUも統一

  • TPUとGPUを同一ツール・同一レポート形式で検証できる統一性。
  • 次世代アーキテクチャにもday-zeroで対応する方針。
  • プラグイン構造でユーザー独自のテストを追加できる拡張性も備える。
環境ごとに道具がバラバラ、という悩みを一本化したのだ

⑥GKE・Slurm・TPU VMで動く

  • ネイティブ対応はKubernetes（GKEを含む）・Slurm・スタンドアロンのTPU VMの3環境。
  • スケジューラとアクセラレータの機種を自動判別——利用者が指定不要。
  • Kubernetesならkubectlアクセスのある任意のマシンやCloud Shellから実行可能。
「どの環境でも同じ診断」が現実になっているのだ

⑦実行は3段階

  • Preflight：対象環境を検証し、同じアクセラレータのアイドルノードだけを選択。
  • Execution：選んだ診断テストを対象ノード群で一括実行。
  • Evaluation ＆ Reporting：結果をベースラインと比較し、レポートを生成。
選別→実行→判定の流れが明快で、迷わないのだ

⑧NCCLチェック：ノード間の網

  • NVIDIA Collective Communications Library（NCCL）でGPU間のネットワーク通信を検証。
  • ノードペアで通信を実測し、平均帯域がしきい値以上なら合格。
  • セカンドパスで健康・不健康ノードの再ペア検証を行い、誤検知を低減。
学習の命綱「ノード間ネット」をくまなく検査するのだ

⑨GPUチェック：DCGM診断

  • NVIDIAのData Center GPU Manager（DCGM）診断で個別GPUの健全性を検査。
  • エラー検出がなければ合格——メモリエラー（Xid）などの前兆も拾える。
  • 公式ドキュメントではerror_idや深刻度と対処法（ドレイン＆リセット等）が案内される。
GPU一本一本の具合を丁寧に診るのがDCGMなのだ

⑩Straggler（足手まとい）検出

  • ノード間のSendRecvテストで遅いノード＝Stragglerを特定する検査。
  • トラフィックパターンはLLM学習のパイプライン並列に近い形を再現。
  • 結果はヒートマップで可視化——遅延のしきい値（既定8ミリ秒）超えが赤く浮かぶ。
「誰が列を遅らせているか」が一目で分かるのが秀逸なのだ

⑪NeperとTinymax

  • NeperチェックはLinuxのネットワーク性能ツールでノード内の帯域を評価。
  • TinymaxはOSSのLLMフレームワークMaxTextで小規模な学習を実際に回す検査。
  • 「部品は正常でも実際のML学習が完走するか」を実地で確認できる。
模擬試験を本番さながらに走らせる発想なのだ

⑫明確な判定を出す

  • 各指標をアクセラレータごとに事前キャリブレーションしたベースラインと比較。
  • 生のログではなくテストごとに明快な合否（health status）を提示。
  • 運用担当者がログ解析をしなくても結論が読めるのが特徴。
「たぶん大丈夫」ではなく「合格／不合格」で返すのだ

⑬成果物はBill of Health

  • 人が読めるインタラクティブな健康レポート（bill_of_health.html）を生成。
  • 同時に機械可読なbill_of_health.jsonも出力。
  • GCSバケットを設定すれば成果物を自動アップロードも可能。
診断結果が「診断書」として手元に残る仕組みなのだ

⑭対応するGPUマシンタイプ

  • 対応はA4X Max・A4X・A4・A3 Ultra・A3 Mega・A3 High。
  • GKEまたはSlurmでオーケストレーションされたGPUクラスタならプロビジョニング方式を問わず利用可。
  • テストはジョブが動いていないノードに限る——繁忙ノードでは実行不可。
最新のAI向けマシン系がずらりと並ぶのだ

⑮TPUスライスにも対応

  • Kubernetes上の動的・静的どちらのTPUスライストポロジもオーケストレーション対応。
  • 1回の実行で並列テスト可能な上限はTPU7xで4×4×4、TPU v6eで16×16まで。
  • スライスをまたぐテストは非対応——各スライスは独立に検査。
TPUの格子構造を理解した設計がされているのだ

⑯導入と必要な権限

  • 導入はPythonパッケージ（pip）かコンテナイメージの2方式。TPU VMのCOSならコンテナのみ。
  • 必要IAMロールはKubernetes Engine DeveloperとCompute Viewer（GCS連携時はStorage Object Admin）。
  • 動画の案内ではGoogle担当者に連絡してオンボーディングすれば詳細なクラスタ健康レポートを生成開始。
権限設計まで丁寧にドキュメント化されているのだ

⑰クイックスタート

  • chs list suites / chs list testsで定義済みスイートとテスト一覧を表示。
  • chs run --nodepools=… --suite=lite（またはstandard）で診断実行。
  • chs resultsでレポートの場所を確認、chs cancelで実行中止とリソース掃除。
数コマンドでクラスタの健康診断が回せるのだ

⑱今日の持ち帰り

  • 今日の一手：大規模GPU/TPU運用者はCHSのGitHub READMEとドキュメントを一読する価値あり。
  • 結論：クラスタ障害対策は事前診断＋非破壊テスト＋明確な判定の三段構えへ。
  • 詳細は元動画とGoogle Cloud ドキュメント「Test clusters」を参照。
AI基盤の信頼性を支える縁の下の力持ちなのだ
