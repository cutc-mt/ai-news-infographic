Opus 5リリースと概要

① Opus 5がリリース: Anthropicの最新モデル

  • AnthropicがOpus 5を正式リリース — Fableレベルの機能を半額で提供すると約束
  • ベンチマークテストの結果もその約束を裏付けている
  • リリースから約1日間、複数の小さなプロジェクトで実際に使用して検証
  • 公式ベンチマークだけでなく、デモプロジェクトで裏付けられた個人的な感想もお届け
ベンチマークだけじゃ分からない — 実際に使ってみた感想が重要！

② ベンチマークの限界: 実際の開発では感覚が違う

  • 日常的にモデルを使っている人なら誰でも、ベンチマークには限界があることを知っている
  • 実際に時間をかけて開発すると、モデルに対する直感的な感覚が強くなっていく
  • 「削除すべきでないファイルまで削除してしまうか？」「誰も求めていない機能を追加していないか？」
  • 「あなたにただ同意するのではなく、反論する意思はどれくらいあるか？」
ベンチマークの数字より、使ってみた「手触り」が大切！

③ Opus 5の使用感: Opus 4.8とほぼ同じ

  • 約1日使ってみた感想として、Opus 5での作業はOpus 4.8での作業と非常に近いと感じた
  • ブラインドテストだったら区別できなかっただろうというレベル
  • 一方で、Fable 5はOpus 5よりも私の指示にずっとよく従っているように感じる
  • 現在制作中のゲームの画像を2枚並べて比較すると、明確な違いが分かる
ブラインドテストで区別できないって... 進化はどこにある？

4モデル対決の実験設定

④ 4モデル対決: 同じタスクで比較実験

  • 直感的な判断に構造を持たせるため、4つのモデルに全く同じタスクを実行させた
  • 参加モデル: Opus 5 · Fable 5 · GPT 5.6 Sol · Sonnet 5
  • 課題: クマが障害物や体力回復アイテムがある斜面を滑り降りるエンドレスランナー型スノーボードゲーム
  • エンドレスランナーの定番要素をすべて盛り込んだゲームを開発
同じ課題で4モデルをガチ対決 — これが一番信頼できる！

⑤ ワークフロー: バックドライブ開発手法

  • モデルを一度で完成させるのではなく、バックドライブ開発というワークフローを採用
  • ステップ1: Claudeに詳細な仕様書を作成させる
  • ステップ2: その仕様書をコードに渡して、個々のタスクに分解させる
  • この手法で各モデルの仕様書の質と実装力を比較
# バックドライブ開発フロー
Step 1: 詳細仕様書を作成 (CLAUDE.md)
Step 2: 仕様書 → 個別タスクに分解
Step 3: 各タスクをコードに変換
仕様書の質で、モデルの「思考力」が分かる！

⑥ 仕様書の比較: 行数に大きな差

  • Fable 5: 仕様書は227行 — 詳細でしっかりした内容
  • Opus 5: 456行 — Fable 5のほぼ2倍のボリューム
  • GPT 5.6 Sol: 約1,500行 — 圧倒的に最も詳細な仕様書
  • Sonnet 5: わずか167行 — 最小限の仕様書
でも長い ＝ 良いとは限らない... 次で検証！

仕様書の質と実装結果

⑦ 仕様書の長さ ≠ 質: 無意味な情報で埋めることも

  • 仕様書が非常に長いからといって、必ずしも優れた仕様書であるとは限らない
  • 単に大量の無意味な情報で埋め尽くすこともできる
  • Solは1,500行だったが、詳細すぎるが有用かは別問題
  • 重要なのは実際に何が作られたかで判断すること
行数より中身！結果で比べるのが一番公正だよね

⑧ デモ1「Snow Bear Rush」: Sonnet 5が制作

  • AキーとDキーで移動、ジャンプ中にShiftキーで加速できる
  • 操作の反応速度が非常に速い — スピード感があって楽しい
  • バックグラウンドに奇妙なノイズ音が流れる問題あり
  • 金貨・茶色いコイン・魚のアイテムの区別が不明確
  • アニメーションは非常に良い — 速度上昇を示す線エフェクトも優秀
音さえ直せば、一番遊んでいて楽しいかも！

⑨ デモ2「Powder Bear」: GPT 5.6 Solが制作

  • 設定画面で音量や音質を変更可能 — 全画面表示にも対応
  • ゲームのテンポがやや遅い — その後少し速くなる
  • 山が空中に浮かんでいるように見える奇妙な描写
  • たった一度のジャンプで命を落としてしまうバランスの悪さ
  • スタート画面は良かったが、ゲームプレイは一番気に入らなかった
1,500行の仕様書なのに、ゲームプレイはイマイチ...

残りのデモと総合結果

⑩ デモ3「Powder Bear」: Fable 5が制作

  • スペースキーでスタート — 素敵なBGMが流れる
  • トリックを決めると追加ポイントを獲得できる
  • たくさんの木が配置され、ゲームプレイの質がかなり良い
  • 効果音も良く、前回より断然良いと評価
  • 難易度は高いが不可能ではなくない — ちょうど良いバランス
  • ただし障害物の配置が適切でない部分あり
Fable 5のゲームバランス、さすが！

⑪ デモ4「Powder Bear」: Opus 5が制作

  • スタート画面を見ると、以前のプロジェクトと比較して断トツで最も醜い
  • ただし始めてみるとそれほど悪くない
  • クマの顔も見えるし、動いた時の音も良かった
  • 速すぎず遅すぎず、ちょうど良いスピード感

  • 死んだ時の明確なフィードバックがない
スタート画面が一番醜いのは痛い... でも中身は悪くない

⑫ 総合評価: 勝者を決めない、それぞれに良さあり

  • 正直なところ、ここで勝者を決めたいとは思わない
  • Sonnet 5のデモは非常に速い操作感が好き
  • GPT 5.6 Solはスタート画面が良かったがゲームプレイは一番気に入らなかった
  • Opus 5とFable 5はかなり拮抗していた
  • どちらかを選ぶならスピンアニメーションの反応が最も良かったFable 5に軍配
一長一短 — モデルごとに得意分野が違う！

結論と今後の使い分け

⑬ 結論: ベンチマークでは差が見えないが...

  • ベンチマークの結果ではそれほど差が見えないものの、実際に使うと違いが分かる
  • 個人の意見としては、Fable 5は依然としてOpus 5をわずかに上回っている
  • 進行中のゲームプロジェクトの画像を比較すると、左側（Fable）の方が右側（Opus）よりはるかに優れている
  • 単一の課題ではなく、進行中の作業の積み重ねで差が明確になる
ベンチマーク ＝ テストの点数、実開発 ＝ 実務の力

⑭ 今後の使い分け: Fable 5とOpus 5の役割分担

  • 趣味のプロジェクトにおける作業手順は変わらない — 両方を使い分ける
  • 難しい部分はFable 5に任せる — 計画立案や例外的なケースへの対応
  • Opus 5は主力として活用 — 日常的なコーディング作業を担当
  • 2つのモデルを適材適所で使い分けるのが最適な戦略
# おすすめの使い分け
Fable 5  → 計画立案・例外処理・難しいタスク
Opus 5   → 主力コーディング・日常的な実装
競合ではなく、チームメイトとして使うのが正解！

⑮ トークン消費の注意: Opus 5を雑に使うと枯渇する

  • Opus 5を主力として使う際はトークン消費に注意が必要
  • 難しい部分をOpus 5に任せると、トークンをあっという間に使い果たしてしまう
  • だからこそ難しい部分はFable 5に任せる戦略が理にかなっている
  • Opus 5はコストパフォーマンスの良い日常作業に集中させる
Fable 5が半額だからって、Opus 5を無駄遣いしないで！

詳細比較とインサイト

⑯ Fable 5が勝るポイント: 指示への従順さ

  • Fable 5はOpus 5よりも指示にずっとよく従っていると感じる
  • 仕様書の行数は少ない（227行 vs 456行）が、内容の質が高い
  • ゲームの完成度ではスピンアニメーションの反応が最も良かった

仕様書が短くても、的確なら勝ち！

⑰ Opus 5の立ち位置: Opus 4.8の進化版

  • Opus 5の作業感はOpus 4.8と非常に近い — ブラインドテストでは区別困難
  • 仕様書は456行と詳細で、Fable 5の2倍の情報量
  • ゲームのスピード感はちょうど良い — 速すぎず遅すぎず
  • ただしカメラアングルやUIの見た目に課題あり
  • Fableレベルの機能を半額で提供という価格メリットは大きい
値段半分でFable並み — でも細かいところで差あり

⑱ まとめ: ベンチマークを超えた実機レビューの重要性

  • ベンチマークでは差が見えなくても、実際の開発では明確な差が存在する
  • 4モデル対決の結果、Fable 5が依然として独自の地位を築いている
  • ベストプラクティスはFable 5とOpus 5を使い分けること
  • 難しい部分はFable 5、主力作業はOpus 5 — これが最適なワークフロー
  • ただしトークン消費には要注意 — 雑に使うとあっという間に枯渇
実際に使ってみた感想こそが、一番信頼できるベンチマーク！
