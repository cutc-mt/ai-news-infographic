Anthropicの公式発表

① 公式発表: システムプロンプトを80%削除

  • AnthropicのTariq氏がXで投稿: 最新モデル向けにClaude Codeのシステムプロンプトを約80%削除したと発表
  • 性能低下はなし — むしろ改善したという結果
  • この投稿はXで大バズりし、多くの開発者が注目
  • システムプロンプトの書き方やスキル、CLAUDE.mdに関する学びを公開
8割削っても性能が落ちないって、すごくない？

② ログ解析で発見: 指示の矛盾が原因

  • AnthropicがClaude Codeの利用ログを読み返して発見した問題
  • 1回のリクエスト内で同じ指示同士が矛盾していた — 例: 「ドキュメントを残せ」と「コメントを書くな」が同時に存在
  • Claudeは意図を汲んで正解に近づけるが、矛盾を解くために余計に考える必要があった
  • 結論: 賢いモデルには指示を足すより矛盾を減らす方が効く
量ではなく「ぶつかっていないか」が問題だった！

③ 量より整合性: 新しいモデルの特性

  • Opus 5やSonnet 4.5など新しい世代のモデルでは、指示を減らす方が効く
  • 以前は「念のため」に同じ指示を複数箇所に繰り返し書くのが推奨されていた
  • しかし新しいモデルでは重複や矛盾がマイナスに作用する
  • 方針は「量を減らす」ではなく「ぶつかりをなくす」
モデルが賢くなったから、指示の書き方も進化する！

6つの変更点

④ 禁止から基準へ: ルールをやめて判断を任せる

  • 以前: 「複数行のコメントブロックは絶対に書くな」 「最大でも1行」 などの強い禁止
  • 現在: 「周囲のコードと同じように読めるコードを書け」という基準
  • 禁止を書くこと自体がダメなわけではない — 事故防止の「これはやらない」は残す価値あり
  • 禁止を10個並べるより、判断基準を1個書く方が今は効く
「禁止リスト」より「判断基準」を1つ書く方が効く！

⑤ 例を見せるより渡し方を設計する

  • 以前はサンプルを1234と並べて示すのが第一のルールだった
  • しかしOpus 5やSonnet 4.5では、例を並べると逆に探索の幅を狭めてしまうことが判明
  • 公式のTodoツール例: 状態は「未着手・作業中・完了」の3つだけ — これで使い方が伝わる
  • 「作業中の項目は常に1つ」という制約を1つ書くだけで運用が決まる
例文を並べるより、選択肢と決まりを設計する！

⑥ 全部先に渡さず、必要な時に読ませる

  • 以前はコードレビューや検証手順をシステムプロンプトに常時載せていた
  • 必要な時だけ呼び出せるスキルに切り出して、使う前は場所を取らないように
  • ツールも同様: 探索させてから定義を読み込む方式に変更
  • コンテキストウィンドウの消費を抑えて、トークンを節約
「段階的開示」 — 必要な時に必要な分だけ読ませる！

⑦ 同じことを2回書かない

  • 以前のモデルは同じ指示を繰り返す必要があり、文脈の末尾の指示に強く従う傾向があった
  • ツールの説明文とシステムプロンプトに同じ内容を両方に書いていた
  • 新しい世代では重複を排除 — 使い方はツール説明文に、方針はシステムプロンプトに
  • この項目が実環境で一番効いた削減ポイント（後述）
「念のためもう一度書く」はもう不要！

⑧ 自動メモリーの導入: CLAUDE.mdは記憶の置き場じゃない

  • 以前はホットキーでCLAUDE.mdに書き込んで記憶を育てる運用が推奨されていた
  • 現在のClaudeは作業内容や自分に関わる記憶を自動で保存するようになった
  • 誤解しやすいポイント: 作業ログをマークダウンやHTMLに残すこと自体は否定されていない
  • やめるべきはCLAUDE.mdを記憶の置き場にすること — ファイルに残す作業記録は続けて問題なし
手で記録を書く必要がなくなった — でも作業ログは別！

⑨ 使用書はマークダウンじゃなくてもいい

  • マークダウン形式の使用書が定着していたが、さらに広がったという話
  • Artifactで作ったHTMLを使用書として渡せる — 認知的負荷が低くて良い
  • 詳細なテストの認識や、別プロジェクトの移植元関数も使用書になる
  • 評価基準の表を渡すと、検証用AIに照らし合わせて確認させられる
  • 自分の好みの物差しをHTMLにまとめておくと、AIが好みに沿って作業してくれる
HTMLの使用書なら人間もAIも分かりやすい！

コンテキストの4つの置き場所

⑩ 置き場所1: システムプロンプト

  • これは製品の文脈で、Claude Codeを使う側は基本的に触らない
  • 自分でAIエージェントの土台そのものを作る場合に重要になる
  • 方針と役割を書く場所 — ツールの使い方はここに書かない
一般のユーザーは触らない領域 — でも知っておくべき！

⑪ 置き場所2: CLAUDE.md

  • 大半をプロジェクトの固有の落とし穴に使うのが正解
  • できるだけ軽く保つことを意識する
  • ここからスキルを参照させる設計にする
  • 当たり前のことは書かず、固有の文脈だけを書く
プロジェクトの「落とし穴」だけを書く場所！

⑫ 置き場所3: スキル

  • 手順書、固有の知識、意見、作法をスキルとして呼び出す
  • 過剰な制約は避ける — 縛りすぎない
  • 必要な時にだけ読まれるので、置き場を取らない
  • 木のような構造で整理して、必要な時に読まれるファイルにする
使う時だけ読み込まれるから、コンテキストを圧迫しない！

⑬ 置き場所4: 使用書・モックアップ・コード

  • 説明文よりもコードやHTMLの方が分かりやすく伝わる
  • モックアップや実コードを直接渡す
  • 評価基準の表を渡して、検証AIに判定させる使い方も可能
  • これら4つの置き場所でコンテキストを組み立てるのが全体像
説明100文字より、コード10行の方が伝わる！

実践結果と検証

⑭ 実践: CLAUDE.mdを147個から16個へ

  • プロジェクト全体のCLAUDE.mdを数えたら147個もあった
  • うち68個は見出しだけの空っぽファイル
  • 整理して16個まで減らした — 131個を削除
  • 話し方のルールが3箇所に重複、スキルの説明文だけで2万トークン超
147個って...気づかないうちに溜まりすぎ！

⑮ 驚きの結果: ファイル削除はトークン0削減

  • CLAUDE.mdを131個削除したのに、毎回のトークンは1つも減らなかった
  • 理由: CLAUDE.mdは作業フォルダとその親を辿って読まれる — 遠くのファイルは読まれない
  • 全体削減率はわずか6.3%
# 内訳
話し方ルール重複まとめ: -653 トークン
スキル説明文の短縮:     -554 トークン
記憶の重複まとめ:       -129 トークン
CLAUDE.md 131個削除:     ±0 トークン
目立つけど効かない場所を掃除していた...！

⑯ 本当に効いた場所: スキルの説明文

  • 削減余地が一番残っていたのはスキルの説明文だった
  • スキルの説明文は1万トークン超 — CLAUDE.mdの2倍以上
  • スキルの中身（25万トークン）は呼ばれた時だけ読まれるが、説明文は毎回のやり取りで必ずついてくる
  • ここを削ると全部の会話に効く — 1336トークン削減に成功
毎回ついてくる部分を削るのが一番効く！

残すべきもの・足すべきもの

⑰ 残すべき3種類: 事故防止・好み・過去の失敗

  • 事故防止の指示: 勝手にコミットしない、外部に送信しない — 必ず残す
  • 自分やチームの固有の好み・作法: チームのルールなど
  • 過去に問題が起きたから書かれた記述: 同じ失敗を繰り返さないための1行 — 重要
  • 全部削れという話ではなく、足すものを足してから削るのが正解
削る前に「足すべきもの」を先に確認！

⑱ むしろ足すべき: メタ認知の4要素

  • 作業前に自分のバイアスを申告させる — これだけでAIの動きが変わる
  • 与えられた前提を疑う — 鵜呑みにしない
  • 曖昧な両論併記で終わらせない — 結論を出す
  • 局所ではなく全体を見る — 全体最適を意識
  • これらはOpus 5でも効いている実感あり — むしろ積極的に足すべき
削るだけじゃない — メタ認知は足していく！
