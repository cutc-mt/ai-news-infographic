Claude 5世代のコンテキストエンジニアリング新原則

Anthropic公式ブログから読み解く、プロンプト設計のパラダイムシフト
2026年8月1日

①公式ブログ: コンテキスト設計が変わった

  • Anthropic公式がClaude 5世代に向けた新しい設計思想を発表
  • プロンプトの書き方が根本的に見直された
  • モデルが賢くなった分、人間側のアプローチも進化が必要
これまでの常識が通用しなくなった時代の幕開け！

②システムプロンプトを80%削除

  • Claude Code内のシステムプロンプトが80%以上削除された
  • にもかかわらず評価の低下はなし
  • 「削っても問題ない指示」が実は大量にあった
コンテキストをスリムにするほどモデルが賢く動く、という逆転現象！

③プロンプトはコンテキストの一部

  • 出力は単一プロンプトだけで決まらない
  • CLAUDE.md + システムプロンプト + スキル + ユーザー指示
  • これらがすべて組み合わさって出力が決まる
プロンプトを単体で最適化するのはもう意味がない。全体設計が鍵！

④コンテキスト内の矛盾が起こる

  • システムプロンプト「ドキュメントを残せ」
  • スキル「コメント追加するな」
  • CLAUDE.md「中間文章を作るな」
  • → モデルはどれに従えばよいか分からない
指示同士がケンカしていると、モデルはどれも中途半端に実行してしまう… 😵

⑤「ルール」から「判断」への転換

  • 以前: 「コメント書くな」「計画書を作るな」等のルール
  • 現在: 「周囲のコードに合わせて判断して」
  • 理由だけを添えて、後はモデルに任せる方針へ
「禁止ルール」より「判断基準」を与える方が性能が伸びる時代に！

⑥判断を任せれば5世代は上手くやる

  • モデルが賢くなり、状況を読み取って適切に対応できる
  • 「判断の余地」を与えると柔軟に動く
  • 逆に細かく縛ると性能が落ちてしまう
信じて任せると期待以上の結果が返ってくる。まさに部下育成と同じ！

⑦具体例を与えすぎない

  • 以前: 具体例（few-shot）を大量に与えるのが正解
  • 現在: 具体例に縛られて制度が落ちる
  • モデルが「例の形」に過剰に合わせようとしてしまう
例は「参考」程度にとどめ、自由度を残すのが今の正解！

⑧具体例ではなく「構造」を伝える

  • TODOアプリの例で解説
  • 「ステータスは pending / 進捗中 / 完了」
  • 「制約はこれだけ」と構造とルールだけを伝える
完成品を見せるより「骨組み」を伝える方が、賢いモデルには効く！

⑨プログレッシブ・ディスクロージャー

  • 最初に全部を渡さないのが原則
  • 必要な時に、必要な分だけ読み込む
  • 段階的に情報を開示する設計思想
一度に全部説明するとコンテキストが埋まってしまう。少しずつが正解！

⑩読み込みタイミングを設計する

  • 「この時はここを読んでね」を明示
  • 足りなければモデルが自分で探しに行く
  • 情報の入り口だけ設計すればよい
全てを手渡すより、「どこにあるか」を教える方が効率的！

⑪重複を減らして役割を分ける

  • CLAUDE.mdをログ倉庫にするのは危険
  • 何でも書き込むと肥大化して矛盾が生まれる
  • 記録はオートメモリー機能を信頼して任せる
「とりあえずCLAUDE.mdに書いとこ」は一番やってはいけないパターン… 😱

⑫オートメモリーに記録を任せる

  • 記録はオートメモリーが自動で管理
  • CLAUDE.mdへの過剰な書き込みは停止
  • 「設定ファイル」と「記録」を明確に分離
人間が手動で書くからズレる。自動化に任せるのが安全！

⑬設計仕様書はもう不要

  • plan.md や spec.md 等の大量MDファイルは不要
  • 「参考資料があれば十分」な時代に
  • ドキュメント作成の手間を大幅に削減
「先に完璧な設計書を」というプレッシャーから解放される！

⑭アセットを適切に読み分ける

  • コード + テスト + mock + rubric
  • 既存のアセットから適切に読み分けて取得する能力が向上
  • モデルが文脈に応じて必要なものを自律選択
「これも読んで」「あれも読んで」と指示しなくても、自分で取捨選択してくれる！

⑮各コンテキストの役割を明確分離

  • システムプロンプト: 基本振る舞い
  • CLAUDE.md: プロジェクト固有の設定
  • スキル: 再利用可能な手順
  • リファレンス: 参照用ドキュメント
役割が重なると混乱する。1つ1つの持ち場を明確に！

⑯矛盾が起きても優先順位がつく

  • 役割が分かれていれば矛盾が起きても解決できる
  • 「どの指示を優先すべきか」が明確になる
  • コンテキスト間の階層構造を意識
責任分担が決まっていれば、迷わず最適な判断ができる！

⑰/doctorで不要なコンテキストを削除

  • /doctorコマンドでコンテキストを健康診断
  • 重複や矛盾を精査するだけでも制度が向上
  • 定期的なメンテナンスが効果的
コンテキストも定期健断が必要。放置すると静かに性能を下げる！

⑱「まずは減らしてみよう」

  • 同じ指示が複数箇所にないか確認
  • 細かく縛るほど性能が落ちる
  • 「削れるところから削る」が新しい最適化
5世代の最適化は「足す」ではなく「引く」。シンプルイズベスト！
