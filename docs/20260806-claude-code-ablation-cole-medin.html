Claude Codeの「AIレイヤー全削除」が意味するもの

CLAUDE.md・スキル・フックを捨てて、モデルを裸で試す — Boris Chernyの提案とCole Medinの実測

第一章：問題提起と背景

①「全部消せ」という過激な提案

  • Claude Codeの生みの親 Boris Cherny が放った一言
  • 数ヶ月ごとに CLAUDE.md スキル フック を全部消せ
  • 何もない状態で、モデルが どう振る舞うか を観察する
  • 衝撃的ながら、根拠のある練習
「設定が肥大化したら、一度ゼロに戻して、本当に必要なものだけ残す」
最小化の思想

②80%削っても賢くなった事実

  • AnthropicはOpus 5で、Claude Code自身の システムプロンプトの80% をカット
  • 結果：モデルは 逆に賢く なったと報告
  • 指示が多いほど、モデルが 混乱 しやすくなる現象
  • 「プロンプト＝指示書」という思い込みへの挑戦
指示を減らしたら賢くなった。
これは多くの人の 常識の逆 だよね。

③「でも本当に全部消していいの？」

  • Cole Medin「Borisは ある程度 は正しいが、ニュアンスがある」
  • 鵜呑みにすると 見えない損 を生む可能性
  • そこでColeは 実際のコードベース で自分のベンチマークを走らせた
  • 通用する所と、壊れる所を分けて確認する方針
動画の核心は「何を消し、何を残すか」の判別法にある。

第二章：アブレーション＝削るだけじゃない

④アブレーションは「評価」の手法

  • アブレーション＝単なる削除 ではない
  • 正体は 評価（Eval） の一種
  • 手順：削除前の性能を計測 → 削除 → 削除後を計測
  • 差を見て 意味の有無 を判断する
「消してみた」だけでは 評価 にならない。
数字を比べるのが本物の練習だよ。

⑤過剰指示（オーバースペック）の罠

  • ルールを 細かく書きすぎる と逆効果
  • 「こう書け」「こう呼べ」を並べると ノイズ に
  • モデルは文脈を十分に読める — 過剰な指定は 邪魔
  • 「書かなくても分かる事」は削る候補
指示が多い ＝ 親切、ではない。
むしろ モデルの判断を奪う こともある。

⑥アブレーションが「高くつく」理由

  • 正しく評価するには 複数回 の実行が必要
  • 1回のテストでも トークンと時間 を消費
  • ルールの数だけ 組合せ が増えて爆発する
  • 現実には、コストと効果の 按分 が必要
「全部消して試す」は、
実は 結構な出費 なんだ。

第三章：AIレイヤーを分類する

⑦「無限トークン予算」の問題

  • CLAUDE.mdは 毎ターン 読み込まれる — つまり 定額課金
  • 巨大なファイルは コンテキストを食う
  • モデルの注意力が 薄まる（干渉効果）
  • 「書く価値」より「消す価値」が大きい事も
長いCLAUDE.mdは、毎回 利子を取られる借金みたいなもの。

⑧AIレイヤーは「スペクトラム」

  • 左端：有効 — 今も効いているルール
  • 中央：期限切れ — モデルが変わってもう不要
  • 右端：有害 — むしろ邪魔になっている
  • 「全部同じ」ではなく 分けて考える
ルールにも 賞味期限 がある。
古いモデル向けの設定は、今では 邪魔 かも。

⑨Borisに「賛成」できる所

  • 古い回避策・ワークアラウンドは 迷わず捨てる べき
  • 「昔は必要だった」＝ 消す候補
  • 過剰指示・重複ルールも 整理の対象
  • 定期的な「棚卸し」の価値は本物
Borisの提案は、片付けの基本 としては大正解。
ただし「全部」には例外がある。

第四章：Archonで実測してみた

⑩Archonで「完全アブレーション」を試す

  • Archon＝Coleが作った 実際のコードベース
  • AIレイヤーを 全部 消して、素の状態で作業させる
  • 同じタスクを複数回走らせて 差を計測
  • 「無くても動くか」を数字で確認
実際の開発現場で、
「全部消す」の正体を 検証 した稀有な例。

⑪「構造」は持ちこたえた

  • アーキテクチャ系のルールは 残っていた方が良かった
  • フォルダ構成・責務の分割・依存の方向
  • これらは プロジェクト固有 の知識
  • モデルが 推測できない 情報 — 残す価値あり
「構造」はゼロから推測できない。
だから 消してはいけない 部類だ。

⑫「慣習」は壊れた

  • 命名規則・コーディング規約系は 壊れた
  • モデルが勝手に 別の流儀 を持ち込む
  • 一貫性が 失われる — レビュー負荷が増える
  • 「無くても動く」≠「無くても良い」
コードは動いても、書き方がバラバラ になる。
これが「見えない損」の正体。

第五章：何を消し、何を残すか

⑬消していいルールの特徴

  • 古いモデル向けの 回避策
  • モデルが 自明 だと判断できる内容
  • 重複・矛盾する指示
  • 「一般論」ばかりの長文
  • 消しても 計測上の差 が無いもの
モデルが進化しても、古い対応策を
放置している人、意外と多いよ。要整理！

⑭残すべきルールの特徴

  • プロジェクト固有 の構造と前提
  • 命名・配置の 一貫性 に関わる規約
  • 依存関係・境界の 暗黙の取り決め
  • 消すと 品質が目に見えて落ちる 設定
  • 計測で 効果が証明 されたもの
「モデルが推測できない事」こそが、
CLAUDE.mdの 本領 だよ。

⑮「動く」≠「良い」 — 見えない損

  • 表面上は 動作する ので気づきにくい
  • レビュー時間の 増加
  • 複数人・複数ターンでの スタイルの乱れ
  • 負債は ゆっくり 蓄積する
  • だからこそ 計測 が要る
「とりあえず動く」に騙されないで。
長い目 で評価しよう。

第六章：実践編

⑯スポンサー：CodeRabbit

  • AIコードレビュー を自動で行う道具
  • PRに対して、文脈を踏まえた 指摘 を返す
  • レビュー負荷を 下げる 一助に
  • 本編の主題ではないが、一貫性維持に有用
規約が減っても、
レビューで 安全網 を張れる例。

⑰アブレーション・スキルの存在

  • Coleはこの一連の手順を スキル として公開
  • リポジトリ：coleam00/skills
  • コーディング用エージェント 全般 で使える設計
  • 手順：計測 → 削除 → 再計測 → 比較
「スキル」自体もAIレイヤーの一部。
でも 計測のため のスキルは残す、という面白さ。

⑱まとめ：正しい「片付け」の道筋

  • 計測 から始める（消す前に現状を知る）
  • 古い 回避策 を真っ先に消す
  • 固有の構造 は必ず残す
  • 規約系 は慎重に、差を見て判断
  • 定期的に 棚卸し を習慣化する
Borisの「全部消せ」は 出発点。
本当の答えは 計測の先 にある。
