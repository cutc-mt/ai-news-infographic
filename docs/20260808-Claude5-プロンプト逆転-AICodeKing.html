新しい考え方
「コンテキスト設計」

  • ユーザーのその場の指示だけじゃない
  • システムプロンプト・設定ファイル
  • メモリや参照データも含む
  • AIに渡す全材料を設計する仕事
「書く技術」から
「渡す材料を設計する技術」へ！
Context Engineering

3つの「逆転」した
指示の書き方

  • 例を見せる → 選ばせ方を設計
  • 禁止を並べる → 判断の材料を渡す
  • 1ファイルに全部 → 必要な時だけ呼ぶ

② 3つの「逆転」を深掘り

逆転① 例を見せる
→ 選ばせ方を設計

  • 例を3つ見せると探索範囲が狭まる
  • 代わりに「選び方」のルールを決める
BEFORE
例を3つずらっと提示
→ 似た形に固定される
AFTER
状態を3つだけ定義
着手・作業中・完了
「答えの形」じゃなく
「判断の軸」を渡す！

具体例: 状態を
3つだけにする

  • 着手 まだ手をつけていない
  • 作業中 今まさに進行中
  • 完了 終わって確認済み
# 状態の選択肢を限定する
status: todo | doing | done
# ← AIが自由に選べる軸だけ残す
選択肢を絞ると、
ブレない答えが出る！

逆転② 禁止を並べる
→ 判断の材料を渡す

  • 「コメント書くな」は場面で間違いになる
  • 「長い説明書くな」も同様
  • 代わりに基準だけ渡す
BEFORE
禁止リストをずらりと
→ 状況で裏目に出る
AFTER
「周りコードと同じ
読みやすさ」基準だけ
「ダメ」より
「何を正解とするか」を！

逆転③ 全部1ファイル
→ 必要な時だけ呼ぶ

  • これまで: 倉庫（全部詰め込む）
  • これから: 図書館（必要時に取りに行く）
  • 確認・レビュー手順はその都度参照
倉庫方式
常に全部読み込み
→ 文脈が太る・遅い
図書館方式
必要な巻だけ取出
→ 軽くて速い
いつでも全部、じゃなく
「今、何が要るか」を！

③ モデル選びも逆転

安い順ではなく
賢いモデルから始める

  • 賢いモデルはやり直しが少ない
  • 結果、トータルコストが安く収まる
  • 小さい模型で失敗すると原因切り分けが困難
旧・発想
まず安い模型で試す
→ 失敗の原因が不明
新・発想
まず賢い模型で通す
→ 手戻り最少
最初の1手で「正解」を
見せられるかが鍵！

Claudeの4つのクラス

Haiku 安い・速い
Sonnet 万能バランス
Opus 考え深い
Fable 長時間・自律
  • 目的に合わせて使い分けるのが前提
  • 今回のOpus 5が最上位
速さ・深さ・自律性で
4段階そろってる！

④ 何を残し、何を消すか

消せるのは「添え木」
＝ モデル支援の跡

  • 昔の模型が弱かったから出していた補助の文章
  • 「〜してください」「〜を忘れないで」の類
  • 今の模型には不要なもの
消せる例 「必ず○○の順で」「絶対に短く」「コメント禁止」など、模型を補正していたルール群
木が大きくなったら、
添え木は外せる！

残すべきは「誰も
代わりに知らないこと」

  • 仕事の前提（なぜやるか）
  • 落とし穴・注意点
  • 外から見えない事情
残す例 「この関数は夜間バッチ前提」「外部APIは0.1%失敗する」「〇〇の判定は人間が最終OK」など、現場しか知らない文脈
模型が自力で分からない
「現場の鍵」こそ残す！

矛盾チェック：
指示を盛るのは不安

  • 指示が多いのは書いた人の不安の表れ
  • 矛盾する指示が混入しがち
指示A
「ドキュメントを残せ」
指示B
「コメント書くな」
この2つ、両立しない。
書きっぱなしで放置しない！

⑤ 実践と持ち帰り

80%削減でも
性能を保てた理由

  • 模型が賢くなり余計な補助が不要に
  • 重複・矛盾する指示が整理された
  • 文脈が軽くなり速く・正確に
性能 ≒ 量は減らしても質は保つ
減らす＝手抜きじゃなく
「最適化」なんだ！

持ち帰り: 一度
読み返す癖をつける

  • AIに渡している文を全部読み返す
  • 矛盾がないか探す
  • 当たり前の事を探して削る
  • 残すのは現場しか知らない事だけ
書いたら終わり、じゃなく
「書いて見直す」が新常識！

指示の「健康診断」
3つのチェック項目

  • これ、模型は自力で分かる?
  • 別の指示とぶつかってない?
  • 「念のため」じゃない?
3つに「はい」と言えたら
その行は削除候補！
