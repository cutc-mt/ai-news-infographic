Claude Code｜PR説明、もう毎回ゼロから書かなくていい

Skillsに「説明の型」を渡せば、1コマンドで肩からスタート

2026.08.14 ／ あきらパパ

PR説明の「あるある」課題

  • 毎回ゼロから書き始めるのが重い
  • 変更点・確認手順・リスクを
    その場で全部ひねり出す
  • 「何を書けばいいか」迷って時間が消える
  • 人によって説明の深さがバラつく
ゼロ起しの回数だけ、
認知のムダが積もるのが問題！

初心者と上級者の差

VS
  • 初心者：その場で変更点確認手順リスクを毎回考える
  • 上級者：Claude Code に説明の型を Skills として渡す
  • 上級者は1コマンドで肩から書き始められる
差は「才能」じゃなく、
型を渡しているかどうか！

Claude Codeの Skills とは

  • Markdownに手順を書いておく仕組み
  • 書けばSlash Commandのように呼び出せる
  • プロジェクト単位で保存して使い回し
  • 毎回の指示を「型」として再利用
Skills ＝ AI に渡す
「専用の手順書」！

スキル用 Markdown の書き方

  • 見出しで目的を明示
  • 手順は番号付きで順序を固定
  • 必須項目を箇条書きで指定
  • 判断基準も併記（これが後述の鍵）
# PR説明 を作るスキル
## 必須項目
1. 変更点
2. リスク
3. 確認手順

Slash Command で即呼び出し

  • Markdown を置くだけでコマンド化
  • タイプ量が劇的に減る
  • 毎回同じ構造で説明が出る
// Claude Code 上で
/pr-description
→ 型に沿ったPR説明を生成
コマンド1つで
肩から書き始められる！

スキルフォルダーの構成

  • プロジェクト内のSkills フォルダーに配置
  • .mdファイル単位で管理
  • Git で版管理 → チームへ波及
.claude/
  skills/
    pr-description.md
    commit-message.md

変更点は「何を・なぜ」

  • 何を変えたか（ファイル・関数単位）
  • なぜ変えたか（背景・意図）
  • 影響範囲を一言で添える
「何を・なぜ」の
2点を型化しておく！

リスクは「何が壊れうるか」

  • 既存機能への影響を書く
  • 後方互換の注意点
  • データ移行や副作用の有無
リスクを書かないと
レビューが「賭け」になる！

確認手順は「再現可能」に

  • 動かし方を順番で書く
  • 確認するポイントを明示
  • 期待結果もセットで記載
1. ローカルで起動
2. /settings を開く
3. 値が反映されるか確認

判断基準こそ最大の鍵

  • 基準なし → 説明が薄くなる
  • 「重大度の基準」を書いておく
  • プロジェクトごとに基準を設定
基準を書かないと、
AI の説明が無味無臭に！

秘密情報は絶対入れない

  • API Key・パスワードは書かない
  • 本番データへの言及も避ける
  • スキルは Git に乗る前提で書く
Skills は共有される。
秘密は外に出さない！

スキル化で時短になる理由

  • 起動が1コマンドで済む
  • 認知の負荷がごっそり減る
  • 品質が安定する
  • 同じ説明の型が回数分効く

実践例：PR説明スキルの中身

  • ファイル名：pr-description.md
  • 必須項目を3つ固定
  • 判断基準を末尾に添える
# PR説明 を生成
## 必須項目
1. 変更点（何を・なぜ）
2. リスク（影響範囲）
3. 確認手順（再現手順）

## 判断基準
- 破壊的な変更は必ず明記
- 軽微な変更は1行で可
この1ファイルが、
あなたの「型」になる！

チームで共有する利点

  • Git に置けば全員が使える
  • PR の説明の質が揃う
  • レビュー時間が短くなる
  • 新人も型を真似できる
Skills は個人の道具、
そしてチームの資産！

PR 以外にも応用できる

  • Commit Message の型化
  • Bug 報告テンプレ
  • README の自動生成
  • Test ケースのひな型
「毎回書くもの」は
全部 Skills 候補！
