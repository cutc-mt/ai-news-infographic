BrowseComp とは？

  • AIエージェントのWeb検索・閲覧 能力を測る評価ベンチ
  • OpenAI自身が作った、高難易度のタスク群
  • ここで「安くて賢い」Lunaが結果を出したのが注目点

04:10

84% vs 84.4% の対決

84% GPT-5.6 Luna
コスト $1.33
84.4% GPT-5.5 xhigh
コスト 約$33
  • 正答 率はほぼ同等（差はわずか0.4ポイント）
  • なのにコストは約25倍も差がついた
同じ点数なら、Lunaにend-to-endで任せた方が 投資 対 効果が高い！

1/25コストの意味

  • $33 → $1.33。25分の1で同じレベルの問題 解決
  • 低コストモデルに任せられる仕事の質と量が拡大
  • DeepSeekなどで巻き取れる範囲も、さらに広がっている
「とりあえず最上位」の時代は、もう一段落かも？
③ reasoning effort の使い分け
05:23

「とりあえずxhigh」はやめよう

  • これまでの癖: とりあえず最上位＋高effortで回す
  • 今はタスク次第。簡単なものは low / medium に落とすべき
  • 速度もeffortの影響が大きい。スピード要否でも選ぶ
「全部xhighでOK」ではなく、賢く切り替える時代です

Claude系でも体感あり

  • Claude Fable や Opus でも effort を下げると
  • 体感できるほどトークン消費が激減
  • Claudeのハーネスでは、スキルのYAML内でモデル/effort指定が可能
  • 「このスキルはこのモデル＋このeffort」と固定する運用が有効
スキル側に設定を書いておくと、ムダな燃焼を防げます！

指定のしかた（イメージ）

  • タスクに合わせて model と effort を明示
  • 同じタスクでも、速さ重視ならlow、確度重視ならhigh
# タスク別の使い分けイメージ
result = client.responses.create(
  model="gpt-5.6-luna",
  reasoning={ "effort": "low" }  # かんたんな抽出はlowで
)
# 難しい設計だけ effort="high" に上げる
「どちらも行けるなら安い方」——この判断が節約の基本！
④ 「1タスクいくら」で考える

85点 vs 90点の割り切り

  • スマートなトークンで 85〜90点を取れる道がある
  • 例: 10倍のトークンをかけて、やっと92点に
  • その差に見合うかは、タスク次第で判断を
最後の数点のために10倍払う？ — ここが腕のみせどころ

1タスクあたりのトークン

  • 単価（1Mトークン単価）だけでは見えない
  • 「仕事を最後まで終わらせるのに何トークンかかったか」が本質
  • 例: Lunaは入力 $0.2 / 出力 $1.2（1Mトークンあたり）
  • 品質レベル × トークン量 で測る癖をつけよう
掴みの単価より、「完成までの総コスト」で比べる！
⑤ Sol / Terra / Luna の実力マップ
07:39

3兄弟の立ち位置

  • Sol: 最上位。能力は高いが、コストも人が良い…じゃなく高め
  • Terra: 中堅ゾーンで良い位置。速度とコストのバランス型
  • Luna: 安くて賢い。コスパの主役
さらにeffortの指定で、1つの中でも段階を作れる！

コーディング・ベンチの地図

  • Artificial Analysis のコーディング系ベンチで確認
  • Terra を max にすると、Sol の低めのeffort相当に到達
  • Luna を max にすると、かなり上の方まで到達可能
  • Luna の xhigh ≒ GPT-5.5 の xhigh クラス
「クオリティライン」に届く組み合わせが、ぐっと増えました！
⑥ 中の仕組み：圧縮・エージェント・キャッシュ
09:21

compaction（圧縮）対応

  • GPT-5.6は compaction（会話の圧縮）や
  • マルチエージェント協調、決定論 寄せの要素もセットで訓練
  • トークン効率向上と、AGI系ベンチのスコア伸びも報告
長い作業でも、履歴を圧縮して賄えるように設計されている！
09:48

Programmatic Tool Calling

  • Programmatic Tool Calling: 昔から話題の仕組み
  • 高度な判定をはさみ、AIエージェントには要点だけを見せる
  • OpenAIが力を入れる、トークン効率のための中間機構
  • マルチエージェント呼び出しのAPIも同梱（Ultraと同様の仕組み）
出力を「スプーンで一口」にして渡すイメージ。ムダが減る！

呼び出し側のサンプル

  • モデルは「何体呼べばいいか」を直感的に判断
  • 呼ぶ条件をコード側で縛ることも可能
# マルチエージェント呼び出しの雰囲気
run = client.responses.create(
  model="gpt-5.6",
  tools=[{
    "type": "multi_agent",
    "agents": [luna, terra],  # 呼ぶ相手を指定
    "condition": "task_complexity > 0.7"
  }]
)
1トークン → どんな結果が返るかも、モデルが理解している！

harness engineering を学ぶモデル

  • 界隈で良いとされる知見をモデルがどんどん取り込む
  • つまり モデル自体が harness（操作系）に詳しくなっていく
  • Fable や Grok 4.4.6 登場時の「ハーネスを学ぶ」流れと同じ
  • 最適化は人間側の工夫から、モデル側の実装へシフト
使う側も、最適化の複雑さから少しずつ解放されるかも！

まとめ：見直しのススメ

  • 5.5の頃は「最上位＋高effort」で回しがちだった
