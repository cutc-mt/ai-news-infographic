#02

課題: 修正が混ざってしまう

同じ作業場のリスク

  • 1つのフォルダで2件の変更が混在する
  • どの変更がどの修正ぶんか、わからなくなる
  • 差分の確認に時間がかかってしまう
// おなじ作業場だと…
fix-A の変更 と fix-B の変更が
同じフォルダでまざり合う
「これはAの変更？ Bの変更？」と迷う時間がもったいない！
#03

Worktree とは

1つのリポジトリ、複数の作業場

  • Git のworktree機能で作業場を追加
  • ブランチごとに別フォルダを用意できる
  • リポジトリは1つのまま、部屋だけふやす感じ
// worktree のイメージ
リポジトリ/
 ├─ main/  … 本線
 ├─ fix-A/ … 修正Aの作業場
 └─ fix-B/ … 修正Bの作業場
#04

利点: 差分が追いやすい

分ければ見える

  • 作業場がわかれるので変更が混ざらない
  • 修正A・修正Bの差分を分けて確認できる
  • レビューの見通しがぐっと良くなる
「どこを変えたか」がはっきり見えるのが最大の利点！
今日試すこと
#05

入口だけ確認する

  • 今日はWorktree の入口を確認するだけ
  • 開始ブランチの選び方も一緒に見る
  • むずかしい操作は今日は不要
まず入口を知る。小さく試すのが毎日の型！

#07

開始ブランチの入口

どこからはじめるか

  • 作業場の元になる開始ブランチを指定
  • main から出すか、別の枝から出すか決める
  • 入口さえ押さえれば、あとは Codex が整える
「どこからはじめるか」だけ決めれば、あとは任せてOK！
#08

並列作業のイメージ

2つの線が並走する

  • 修正Aは fix-A の作業場で
  • 修正Bは fix-B の作業場で
  • おたがいに干渉せずすすむ
  • それぞれの差分を別々にレビュー
前提条件と秘密ファイル
#09

前提: Git repository

大切な条件

  • 対象は Git repository のプロジェクト
  • Git 管理されていることが前提条件
  • Git でない project では使えない
まず「Git 管理かどうか」を確認するのが最初の一歩！
#10

秘密ファイルの扱い

自動では全部コピーされない

  • .env などの秘密ファイルは要注意
  • 新しい作業場に自動で全部はコピーされない
  • 必要なものだけ.worktreeinclude に書く
「必要なものだけ明示」が安全に使うコツ！
#11

.worktreeinclude の書き方

コードで見る例

  • リポジトリのルートに置く設定ファイル
  • 1行に1つ、パスを書き並べるだけ
  • 書いたものだけ作業場へコピーされる
# .worktreeinclude の例
.env.local
config/secrets.yml
keys/service-account.json
#12

自動コピーの範囲

どこまで入り、どこが入らないか

  • Git 管理のファイルは自動で用意される
  • Git から外れた秘密ファイルは対象外
  • 入れたいものは .worktreeinclude に追記
「入るもの・入らないもの」を知っておくと安心！
仕組みと深掘り
#13

差分レビューが楽になる理由

きれいな差分のながれ

  • 変更が混ざらないので差分がきれい
  • 「この修正で変わった範囲」が明確
  • 確認の手間と時間がへる
レビューが楽になると、修正を恐れず試せるようになる！
#14

sandboxing との関係

安全に動かす仕組み

  • Codex はsandbox の中で動く
  • 作業場がわかれると影響範囲も限定される
  • Worktree と sandbox で二重に安心
「わける」ことで、安全も一緒に手に入る！
