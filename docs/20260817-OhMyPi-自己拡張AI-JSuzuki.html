Oh My Pi（OMP）と「自己拡張AI」の実像

Pi との違いと、人が手綱を握る承認設計

2026年8月17日 ／ Jun Suzuki（AIエージェント・ラボ）の音声解説動画（17分25秒）より

#OhMyPi #Pi #AICodingAgent #自己拡張 #承認設計

便利すぎるエージェントに、いつのまにか主導権を渡しがち。Pi と OMP という二つの道具立てから、「使い続けられるAI」の条件をひもときます。

はじめに：主導権を取り戻す カード 1 〜 3
01

エージェントの主導権

  • AIコーディング環境は、いつのまにか複雑になりすぎる
  • 任せきりにすると、何をしているか見えなくなる
  • この動画の問い＝主導権を人に取り戻すには？
便利さと引き換えに、
見えなくなったものは何か。
そこが出発点です
02

「自己拡張」の定義

  • 足りない機能を、エージェントに拡張として書かせる
  • 書いたら再読み込みして、すぐ使えるようにする
  • 人の意図を離れてコアを書き換え続ける、という意味ではない
誤解されやすい言葉。
ここを先に確認！
03

PiとOMP、二つの道

  • Pi ＝ 最小構成のターミナル型コーディング・ハーネス
  • OMP ＝ Pi を基にした実務向けフォーク
  • 共通点は、使い手が主導権を持つ設計

まず Pi の思想から見ていきます

同じ根から出た、
二つの枝です
Pi — 最小コアの思想 カード 4 〜 6
04

Piの最小コア

  • 最初から小さい。余計なものをそぎ落とす
  • 何が入っているか把握しやすい
  • 自分の開発環境を組み立てる土台になる
小さいからこそ、
中身を全部知れる！
05

標準ツールは4つだけ

  • read（読む）／ write（書く）
  • edit（直す）／ bash（実行）
  • 少ないからこそ、挙動が予測できる
# Pi の標準ツール
read  /  write
edit  /  bash
基本の道具はたった4つ。
あとは自分で足す！
06

必要な分だけ足す

拡張の4つの枠組み

  • extensions — 機能の拡張
  • skills — 技能の追加
  • prompt templates — 雛形
  • packages — 部品の導入
「全部入り」を買うより、
必要な分だけ選ぶ
OMP — 実務向けの拡張 カード 7 〜 10
07

実務向けワークフロー

  • OMP は Pi の考え方を実務に持ち込むフォーク
  • 仕事で使うための流れや作法をまとめている
  • 最小から育てる方向性は Pi と同じ
思想は Pi、
現場向きの道具立てが OMP
08

LSPとデバッグ

  • LSP ＝ 定義ジャンプや補完を支える仕組み
  • デバッグの道具もそろっている
  • コードの理解と修正がはかどる
エージェントがコードを
読み違えにくくなる！
09

透明な道具箱

  • 何の道具が入っているか見える
  • 隠された処理がない
  • 見えることが信頼の土台になる
黒箱ではなく、
ガラス箱であってほしい
10

書いて、再読み込み

  • 足りない部品はエージェントに書かせる
  • /reload-plugins で読み込み直す
  • 書く → 読み込む → 使う、の循環
# OMP での流れ
1. 不足をエージェントに書かせる
2. /reload-plugins で再読み込み
3. すぐ新しい道具として使う
道具が育っていく
感覚がここにあります
承認設計 — 人が手綱を握る カード 11 〜 14
11

人が手綱を握る

  • ツール実行の前に、人が承認する場面を作る
  • これが AI を便利な道具として使い続ける鍵
  • すべて任せない、が前提
手綱を離さない。
それが使い続けるコツ
12

read・write・execの境界

  • 読み取り — ファイルを見る
  • 書き込み — ファイルを変える
  • コマンド実行 — 動かす
  • 境界を見える形にして、どこまで許すか選ぶ
「読むのは良いけど、
書くのは待って」ができる
13

3つの承認モード

  • always-ask — 毎回、人に確認
  • write — 書き込みは許可しておく
  • yolo — 確認なし。危険も増える
# approval mode（イメージ）
always-ask  ← 全部確認
write       ← 書き込み許可
yolo        ← 確認なし
yolo は速いけど、
慎重に使おう！
14

最後に検証するのは人

  • 承認しても、動作の確認は人がする
  • 検証まで含めて「使う」ということ
  • 任せきりにしない姿勢が品質を守る
ゴールは承認じゃなく、
動いたと確認できた瞬間！
選び方と、これから カード 15 〜 18
15

PiとOMP、どちらを選ぶ？

  • まず最小で試すなら Pi
  • 実務の作法が欲しいなら OMP
  • どちらでも主導権は使う側にある
正解は1つじゃない。
自分の作業に合う方を
16

こんな人に向けた内容

  • 環境が複雑になりすぎたと感じる人
  • 最小構成から組み立てたい人
  • 承認と検証を大切にしたい人
「道具を選び直したい」
人への後押しになる話
17

公開形態と費用の注意

  • Pi／OMP 本体の公開形態と、モデル契約は別もの
  • API 利用料はプロバイダー側で確認
  • 利用条件と費用は自分でチェックを
道具が無料でも、
頭脳の利用料は別枠です
18

まとめ：主導権のある道具づくり

  • 最小コア＋必要な分だけ自分で足す
  • 承認設計で安全を保つ
  • 最後の検証は人間が担う
  • 詳しくは一次資料（GitHub の README）へ
AIは道具、主導権は人。
その型がここにあります！
