AIネイティブSDLC エージェント開発 ツール非依存 スターターパック無料
第1章: いま起きている「生産性の幻想」
①

衝撃の結果: 19%も遅くなった

  • ランダム化された試験 で検証(10:43)
  • AIを使った開発者は タスク完了が 19% 遅く なった
  • なのに本人たちは 「20% 速くなった」 と錯覚
  • 体感と実データが 正反対 という結果
体感:  +20% 速い ⬆
実測:  −19% 遅い ⬇
→ 「生産性の幻想」
「AIに任せた気持ちよさ」が 数字を裏切っていた…!
②

原因はモデルじゃない

  • モデルの性能は 十分すぎる ほど上がっている
  • 悪いのは 「システム」の欠如
  • そして チーム標準 が共有されていないこと
  • 個人バラバラの使い方では チーム最適にならない
  • 解決策は 道具の入れ替え ではなく 仕組みづくり
「強いAI」より先に 「整えた土台」が必要なんだ
③

エージェント開発者への移行

  • 「AIコーディング」の先にある エージェント型 の開発へ(1:45)
  • 人間の役割は 指示と検証 にシフト
  • 書く時間より 設計する時間 が増える
  • 求められる技能も 変化の途中
コードを書く人から エージェントを率いる人へ!
④

フレームワークじゃなく テンプレート

  • フレームワーク は縛りが強く 自由が効かない(5:45)
  • テンプレート なら自分のチームに 合うよう改造できる
  • 使う部品だけ残して 取捨選択 が自由
  • まず 「層（レイヤー）」 を足す発想から始める
framework = 強い枠
template = 自由な型
→ 型を借りて 自分たち流に!
完成品を「削って」使うのが いちばん早い!
第2章: 多くのチームの現在地
⑤

いま普通のチームは こう使っている

  • 各自が自分のプロンプトを ひみつの兵器に(12:33)
  • 共有される ルール も スキル もない
  • 設計書とコードが つながっていない
  • やり方は人によって 毎回バラバラ
「うちのチームだけ特別」実は ぜんぶこれかも…?
⑥

相手はブラウンフィールド

  • 対象は 既存のコードベース ＝ ブラウンフィールド(15:22)
  • まっさらな グリーンフィールド ではない
  • 初期状態: ルール・スキル・接続 がゼロ
  • それでも 2時間のワークショップ で組み切る
before: 既存コード + AI設定ゼロ
after:  SDLC全体がAIネイティブ
(作業時間: 約2時間)
新規サービスじゃなく 「いま動いてる現場」を変える話!
⑦

Vibeコーディングの 禁じ手

  • 中身を確認せず そのままマージ(18:21)
  • テストなし で通してしまう
  • 設計の文脈（コンテキスト）を 与えないまま丸投げ
  • 「なんか動いた」で 品質を見ない
  • 対処法: ルール + 計画 + 検証 の型に入れる
気分で進めるVibeコーディングは 現場では爆弾だよ!
⑧

AIネイティブSDLCの 設計図

  • 出発は Confluence上のPRD(22:00)
  • ゴールは CIがレビュー済みのPR まで
  • 途中の PM・開発者・QA を全て網羅
  • 設計書 ⇄ チケット ⇄ コード ⇄ レビューが 一本の糸でつながる
PRD → チケット → 計画 → 実装
 → PR → CIの自動レビュー → 完了
(全工程にエージェントが同行)
上流から下流まで 「一人も落ちない」設計図!

グローバルルールと スキルの棚

  • グローバルルール: チーム共通の約束事(33:33)
  • スキルライブラリ: 手順を なんども使える形で保存
  • /create-rules を実行して ルールを自動生成(37:04)
  • 一度書けば 何度も使える 資産に
> /create-rules
 → コードと対話しながら
   ルール案を起草してくれる
ルールは手書きじゃない AIと一緒に起草する時代!
⑪

AIレイヤーの 6つの構成要素

  • グローバルルール — 共通の行動規範(39:44)
  • スキルライブラリ — 手順の部品置き場
  • コネクション — 外部サービスとの接続
  • ほか 計6要素 でレイヤーが完成
AI layer = rules
          + skills
          + connections
          + ... (6要素)
6つの部品をそろえれば どのリポジトリもAI仕様に!
⑫

CLAUDE.mdは 短く保つ

  • ルールファイルは 簡潔に一覧 が鉄則(41:32)
  • 長すぎると コンテキストを圧迫
  • 詳細はスキル側に逃がして 本体はスリムに
  • 結果: 応答が速く 命中率も上がる
CLAUDE.md
├─ 言語 / 品質の基本方針
├─ テストとlintの約束
└─ 詳細 → skills/ へ移す
説明書は「薄く」が美德。 詳細は棚にしまう!
第4章: チーム全員に届ける仕組み
⑬

AIレイヤーは ソース管理へ

  • AIの設定を リポジトリの中 に置く(44:52)
  • クローンしただけで 設定の手間ゼロ
  • 使う全エンジニアが 同じルールを継承
  • ルール変更も レビューで管理 できる
git clone → ルール入手完了
(各自の設定ファイルは不要)
「新人が1日目からベテランと 同じ型で書ける」のが最大の効果!
⑭

PMの仕事: PRDから チケットへ

  • Confluenceの PRD を読み込ませる(49:01)
  • エージェントが Jiraチケット を起草
  • 要件の抜けも 自動で指摘
  • PMは 確認と承認 だけに専念
Confluence PRD
  ↓ 読み取り & 分析
Jira チケット群
  ↓ PMが承認
開発の-readyな状態へ
PMの「書き写し作業」が 消えて判断だけ残る!
⑮

エージェントとMCPの 接続

  • MCP でJira等の外部サービスと直結(53:49)
  • AIコーディングには 5つの段階 がある(57:01)
  • 段階が上がるほど 自律と信頼 が増す
  • まずは低い段階から 着実に登る
Level 1: 補完
Level 2: 対話しつつ生成
Level 3: 指示して一括生成
Level 4: 計画→実行
Level 5: 自律ループ
いきなり頂上を狙わず 「今いる段」を確かめよう!
⑯

開発者の番: R-PIVループ

  • まず チケットを準備 してから着手(1:05:04)
  • R-PIVループ で回す(1:09:14)
  • 作り手の意図を 対話で共有
  • 成果物は 検証しては戻す 繰り返し
R: Read the ticket
P: Plan with agent
I: Implement
V: Verify
(→ 検証結果で計画へ差し戻し)
「一回で完璧」を捨てて 小さく回すのがコツ!
第5章: 計画からCIまで、走り切る
⑰

インタビュー → 計画 → 実行

  • 実装前に エージェントへインタビュー(1:11:36)
  • 回答をもとに 構造化プラン を作る(1:16:52)
  • 実行は 新しいセッション で(1:23:49)
  • おすすめ: 自律エージェント構築の Archon も紹介(1:36:21)
1. agent に質問攻め
2. 回答で計画を構造化
3. 新しい session で実行
   → 計画と実行を分離!
書く前に「質問」させる。 この一手で手戻りが減る!
⑱

CIが自動でPRを レビュー

  • CI上のエージェント がPRを自動チェック(1:41:43)
  • ルール違反を 機械が検出
  • システムは固定せず 育て続ける(1:46:00)
  • まとめ: SDLC全体 をAIネイティブに(1:47:52)
push → CI: agent が diff を検査
  ├─ ルール違反?
  ├─ テスト十分?
  └─ review comment → 修正 → merge
人のレビューは「判断」に集中。 単純チェックはCIへ任せよう!
