MAIN TOPIC

GitHubのAI修正に弱点

今日いちばん大事なニュース

  • CopilotなどAIによるコード自動修正が当たり前に
  • でも“直った顔”で別の問題を生むことがある
  • 見た目は直っていても、挙動まで正しいかは別
  • AIの修正を“信じ込みすぎない”運用が急務
AIが書いた diff（変更差分）をパッと流し見してマージ、じゃ危ない日もある…！
WHY ?

弱点の正体をひもとく

なぜAIの修正はくせもの？

  • 表面的な修正にとどまり、原因は残ったまま
  • 直したファイルが、よその処理を巻き込んで壊す
  • テストが足りない場所では静かに失敗
  • 「直しました」の説明がまばらで、判断がむずかしい
大事なのは 「なおった理由」を自分の言葉で説明できるか、だね。
今日の一歩

人が見る手順を“1つ”決める

AI任せにしない、小さく強い習慣

  • AIの修正結果を人が見る手順を、まず1つだけ決める
  • 例：朝イチで「未チェックのPR」を開く
  • diff を読み、動かして、納得してからマージ
  • 完璧でなくてOK。1つ決めて回すのが一歩
3児のパパでも続けられる「小さく1つ」ルール。今日から試してみよう 🌱
RECIPE

チェック手順のレシピ例

マージ前3分のながれ

diff を読む ローカルで動かす テスト実行 マージ
  • 変更が“意図どおりか”を1文でメモする
  • 画面を実際に触って、前と同じ挙動か見る
  • 迷ったらマージは待って、一晩 sleep させる
# 朝3分のやることリスト
for pr in unchecked_prs:
    read_diff(pr)      # 1. 変更を読む
    run_app()          # 2. 動かす
    run_tests()        # 3. 検証
    merge_if_ok(pr)    # 4. 判断
コーヒーがさめる前に終わる量にしておくのが続くコツ ✍️
