②
全体像

Cloudflare OS とは

  • Cloudflare が社内利用のために開発した AI 生産性向上環境。
  • エンジニアから営業まで、社員の大部分 が毎日の仕事で使っている。
  • 2026 年 8 月に Apache 2.0 でオープンソース公開。
  • 公開直後から 8.6k スター・952 フォーク（2026 年 8 月時点）。
狙いは「他社がコピーして自社向けに育てること」。Cloudflare OS をそのまま使うのではなく、「御社の OS」を作ってもらうという発想なのだ。
③
命名の意図

「OS」という名前の意味

  • 従来のコンピューター用 OS ではない、と明言されている。
  • 意味 1: AI と 安全 に生産的になるための仕事環境。セキュリティチームが夜ぐっすり眠れる状態が目標。
  • 意味 2: ワークロードを管理する 伝統的 OS との類推。
マーケティングだけの名前ではなく、技術的な対応表も本当にあるのだ（⑰で詳しく）。
④
3 つの柱

提供する 3 つの機能

  • 1. エージェントチャット UI — 会社の運用知識をあらかじめ読み込ませて、タスクを依頼できる。
  • 2. サンドボックス化されたアプリ開発 — ガジェット という小さな個人アプリを安全に作って共有。
  • 3. Gatekeepers — エージェントにもアプリにもガードレールをかけるセキュリティの枠組み。
非技術者のユーザーが安心して思いっきり使っても、悪いことが起こらないようにする — それがこの 3 本柱の狙い。
⑤
クイックスタート

まず動かしてみる

  • pnpm を入れて pnpm run-local だけでローカル実行できる。
  • ブラウザで localhost:8787 を開けば OK。スタック全体が wrangler と workerd 上で動く。
  • 試せる例：「顧客との会議用スライドを作って」（内蔵ブループリントを使用）。
  • 「三目並べを作って」「この GitHub リポジトリの課題ダッシュボードを作って」なども。
$ pnpm run-local
→ http://localhost:8787
（本番運用向けではないが、
 動きを確かめるには十分）
「作って」と頼むだけで、テストまでエージェントがやってくれるのだ。
⑥
Gadgets

ガジェットとは

  • スライド 1 枚を作るときも、その人専用のアプリ のコピーが用意される。
  • SaaS のようにクラウド上の共有ソフトを呼ぶのではなく、プライベートインスタンス が動く。
  • 全員が別々の サンドボックス で実行される。
「コネクター付きのチャットボット」ではなく、ソフトウェアの新しい考え方 — これが Cloudflare OS の中心にある発想。
⑦
サンドボックス

安全にコードを変えられる

  • サンドボックスがアクセスを全部管理するので、漏洩系のバグ が入りにくい構造。
  • 機能が足りなければ エージェントに追加を頼める。安全だから改造も自由。
  • ガジェットは明示的に許可しない限り 外部ネットワークと通信できない（Dynamic Worker と Bindings で制御）。
「自分専用のコピーだから壊しても影響なし」— これが大胆な改造を可能にするのだ。
⑧
使い心地

オフィススイートのような体験

  • 基本の使い心地は Google Docs のようなオンラインオフィスに近い。
  • ただし「文書・表計算・スライド」ではなく、各ファイルが AI が書いた独自アプリ になり得る。
  • ドキュメントと同じく 非公開がデフォルト。思いつきで何個でも作れる。
  • テンプレートにあたるのが ブループリント — 中身はアプリ全体のコード。
「ファイルを開く」の延長で、自分専用アプリが手に入る感覚なのだ。
⑨
Blueprints

ブループリントで共有

  • ガジェットそのものではなく 設計図（コードのコピー） を共有すると、相手は自分のコピーを作れる。
  • モバイルアプリのように、使う人全員が自分のソフトを持つ 形。
  • 機能追加の要望を出す代わりに、エンドユーザーが AI で自分の問題を解決できる。
  • 個人開発者がオンラインサービスを維持する苦労から解放される側面も。
ここ 25 年のクラウド／SaaS の中心モデルからの大きな転換 — AI が誰でも機能を足せる時代には、中央集権型が合わなくなってきた、という主張。
⑩
共同作業

リアルタイム共同編集

  • ガジェットはドキュメントのように共有できる（特定ユーザー指定 or 共有リンク）。
  • 共同作業者の操作が リアルタイムで見える。
  • 仕組みは Durable Object — Cloudflare のステートフルなサーバレス部品。
あまりに簡単なので、コーディングエージェントが頼まれなくても標準で組み込んでくれるのだ。
⑪
Gatekeepers

Gatekeepers とは

  • エージェントやガジェットを外部リソースにつなぐとき、仲介役 として立つ仕組み。
  • README いわく 「強化版 MCP サーバー」 のようなもの。
  • 実装は 独立した Worker。1 つ 1 つが別々に動く。
  • 将来は OS インスタンスとは別に配備・運用する構想（詳細はまだ調整中）。
外部サービスとの接続窓口を、専用の番人に任せてしまう発想なのだ。
⑫
5 つの役割

Gatekeeper の役割

  • サービスの API をラップして、きれいな Cap'n Web API を提供。
  • OAuth などの認可を処理。
  • ユーザーが意図した リソースだけ にアクセスを制限。
  • ガジェットとエージェントの 全操作をログ に記録。
  • 副作用のある操作は人間の 承認・却下 機会を用意。
⑬
非同期承認

止まらない承認フロー

  • 従来の human-in-the-loop は同期式。エージェントが承認待ちで 停止 してしまう。
  • コーヒーを取りに行って戻ると、最初の一歩で止まったまま…という事態に。
  • Gatekeeper は承認が必要な操作をローカルで シミュレート。エージェントはそのまま先へ進める。
  • 結果の読み取りにはシミュレーション結果を返し、あとで まとめて or 個別に承認 できる。
面倒で「自動承認」や --dangerously-skip-permissions に頼ってしまうのが人の性。それに頼らずにすむ、というのが大きな前進。
⑭
権限モデル

ケイパビリティ型の権限管理

  • エージェントもガジェットも、デフォルトでは何にもアクセスできない。
  • リソースごとにユーザーが 「紹介」 して初めて権限が与えられる。
  • エージェント側から「このリソースが必要」と 申請 することも可能。
  • MCP サーバーを事前一括設定して常時全権限を与える方式とは、ここが違う。
「今の仕事に必要な分だけ」を都度わたす。合鍵の管理に似た発想なのだ。
⑮
対応サービス

対応している外部サービス

  • GitHub ・ Google ・ Cloudflare の各 API。
  • Supabase ・ Notion ・ Confluence。
  • Email Workers ・ Home Assistant ・ Slack ・ Spotify ・ ZoomInfo。
  • 各 Gatekeeper パッケージに セットアップ手順 が同梱。
OAuth クライアント資格情報の取得など、設定はやや手間。対象が開発者向けに作られているサービスが多く、意図的に簡単にしていない面もある。
⑯
技術基盤

Workers チームが作った Workers アプリ

  • 基盤は Cloudflare Workers。Durable Objects・Dynamic Workers・Facets を特に多用。
  • ワークスペースごとに独立した Durable Object、ガジェットは Dynamic Worker の Facet で実行。
  • 開発主体は Workers を作った本人たち。Dynamic Workers や Facets は OS のためにランタイムへ追加された機能。
  • workerd 自体がオープンソースなので、自社サーバー上でも丸ごと動かせる。
ソースを読むと「Workers チーム流の正しい使い方」が学べる、という読書素材としての価値も大きいのだ。

⑱
まとめ

エージェントの実力と今後

  • コーディングエージェントは汎用。Code Mode — コードを書いて即実行する方式。
  • LLM は主要プロバイダー・自己ホストから 自由に選べる。
  • プラットフォーム密着のおかげで、同じモデルでも 少ないトークンで速く 動きやすい。
  • アプリには標準で エージェント向け API が付き、MCP サーバーの構築が不要。
  • v2 は全面的な書き直し。2026 年 8 月時点では 早期アクセス 状態で、粗い部分も多い。
