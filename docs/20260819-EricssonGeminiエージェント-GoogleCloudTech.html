Ericsson×Gemini で通信網の
問題解決を数時間から数分へ

Gemini Enterprise Agent Platform と OSS/BSS を統合した、プロアクティブなクローズドループの実例

2026年8月18日公開　 Google Cloud Tech（New Way Now）

RCA が数時間 → 数分に エージェントが問題を特定・解決 Google Cloud でデータ基盤構築 クローズドループ自動化 ROI とサービス立ち上げを加速

背景と課題 —— 通信の事業者が抱える壁

テレコム業界の現実

Ericsson が挑む領域

  • 世界各地の通信の事業者（テレビ電話会社）にネットワーク機器とソフトウェアを提供するEricsson。
  • その顧客である事業者は、何百万もの加入者に24時間サービスを提供し続ける使命がある。
  • ネットワークは巨大で複雑。障害の原因を突き止めるのは、昔から大変な作業だった。
通信網が止まると、加入者の生活も仕事も止まる。だからこそ原因究明は急ぎの案件！

RCA の属人化と低速

根本原因を分析する壁

  • ネットワークで問題が起きたとき、その根本原因を分析する作業（RCA）はベテランエンジニアの経験と勘に頼ってきた。
  • 膨大なログと警報を目で追うため、原因特定に数時間かかることも珍しくない。
  • 知識が特定の人に偏る属人化が進み、担当者が不在だと解決がさらに遅れる。
  • 同じような障害が起きても、毎回の手作業で調査のやり直しに。
「原因不明のまま復旧して、また再発」の繰り返しから抜け出したい！

対応が後手に回る構図

リアクティブな運用の限界

  • 多くの運用は、障害が起きてから動くリアクティブ（受身の対応）方式。
  • 警報が鳴る → 調査 → 対応という流れでは、加入者が被害を受けてから復旧作業が始まる。
  • エンジニアの時間は調査に取られ、新サービス開発に回せないジレンマも。
「起きてから直す」ではなく「起きる前に防ぐ」運用への転換が鍵！

OSS/BSS ポートフォリオ

通信運用の土台となるシステム群

  • OSS（運用支援システム）はネットワークの監視・設定・障害管理を支える仕組み。
  • BSS（業務支援システム）は契約・課金・顧客管理などを担う仕組み。
  • Ericsson はこの OSS/BSS ポートフォリオと Gemini Enterprise Agent Platform を統合。
  • 既存の運用システムを壊さず、その上にAIエージェントの層を重ねる設計。
すでに動いている通信の基幹システムと、新しいAIをどう組み合わせるかが勝負どころ！

第1段階 —— Google Cloud でデータ基盤をつくる

ネットワークデータを濾す

フィルタリング

  • ネットワークからは、警報・ログ・性能データなど膨大なデータが絶えず流れてくる。
  • Google Cloud のツールでノイズを除き、意味のあるデータだけを取り出す。
  • この下ごしらえがあるからこそ、AIエージェントが正確に判断できる。
# データの下ごしらえ（イメージ）
raw_network_data
  → filter: 雑音を除去
  → いる信号だけを残す
料理と同じで、素材の下ごしらえが味を決める。AIの精度はここから！

データをまとめて集約

重ね合わせて一枚岩に

  • 機器ごと・システムごとに散らばっていたデータを、Google Cloud 上に集約。
  • 別々の形式で保存されていた情報を、扱いやすい形に整えて統合。
  • ネットワーク全体を一望できるデータ基盤ができあがる。
ばらばらの情報を1か所に集めるだけで、見えてくる問題の全体像がある！

データ同士を関係づける

相関化で原因が見える

  • 「この警報と、この機器のログはつながっている」という関連付け（相関化）をデータ側で表現。
  • 個別のイベントを並べて読み解くのではなく、因果のつながりとして捉えられる。
  • この相関の糸をたどれば、根本原因に一気に近づける。
点のデータを線でつなぐと、「なんとなく変」が「ここが原因」に変わる！

エージェントの土台完成

判断できる状態への準備

  • 濾す・集約・関係づけの3ステップで、分析可能なデータ基盤が完成。
  • この土台の上でなら、AIエージェントは迷わずデータを読んで推理できる。
  • 基盤づくり → エージェント構築 → 自動解決、という順番が重要。
いきなりAIに全部任せるのではなく、まずは足場を固めるのが正攻法！

第2段階 —— エージェントを構築・指揮する

Gemini Enterprise Agent Platform

企業向けエージェント基盤

  • Google が企業向けに提供する、AIエージェントを構築・運用するための基盤。
  • エンタープライズ向けのガバナンスやセキュリティの仕組みを備える。
  • Ericsson はこの上に、ネットワーク運用に特化したエージェント群を構築。
遊びのAIではなく、企業の基幹運用に耐えるエージェント基盤である点が要点！

問題を特定するエージェント

自律的な原因の突き止め

  • データ基盤上の情報を自ら読み、根本原因を特定するエージェント。
  • 警報とログの相関を追いかけ、人のように推理して結論を出す。
  • これまで数時間かかっていた RCA が、数分に短縮。
  • ベテランの経験に頼らず、誰がいても同じ品質の分析が可能に。
「数時間 → 数分」は単なる高速化ではなく、対応の質そのものが変わる進化！

問題を解決するエージェント

特定したら、次は修復へ

  • 原因を特定するだけでなく、解決まで実行するエージェントも用意。
  • 復旧処理や設定変更などを、手順に沿って自動で処理。
  • 「調べて、直して、確認する」の一連の流れを人手を介さず完結。
「発見」と「修復」を別々のエージェントが分担するのが、この仕組みの肝！

オーケストレーション

エージェントたちの指揮者

  • 複数のエージェントの動きを、プラットフォーム上で指揮・調整（オーケストレーション）。
  • どのエージェントが何を担当し、結果をどう渡すかの流れを設計。
  • 特定の役割ごとにエージェントを用意し、分担して連携させる。
  • 指揮者のもと、楽団のように息を合わせた自動運用が実現。
エージェント1体の賢さより、指揮系統の設計が全体の性能を決める！

第3段階 —— クローズドループが生む成果

プロアクティブなクローズドループ

先回りの自動改善サイクル

  • 監視 → 原因特定 → 解決 → 学習を循環させるクローズドループ（閉じた環）。
  • 障害を待つのではなく、先回りして検知・対処するプロアクティブ運用へ。
  • 回すほどに賢くなる、自己改善の仕組み。
「起きてから直す」から「起こる前に整える」へ。環が回り続けるのが強み！

ROI 向上の構造

投資の効果が上がる理由

  • RCA の所要時間が激減し、エンジニアの工数が解放される。
  • 障害の早期解決で停止損失を抑制し、収益を守る。
  • 属人化の解消で研修コストを圧縮、品質も安定。
  • 浮いたリソースを新サービスに再投資でき、ROI が高まる好循環。
「時間を買う」投資として、プラットフォーム導入費用を回収していく発想！

新サービスの立ち上げ加速

運用が軽くなると開発が進む

  • 調査・復旧の自動化で、エンジニアが新しい価値づくりに集中できる。
  • 新サービスの立ち上げ（トライアル展開）も加速。
  • 通信の事業者はより速くイノベーションを起こせるようになった。
「守り」が自動化されたぶん、「攻め」に人の知恵を回せるのが最大の副産物！

加入者への好影響

サービス提供に集中できる

  • 障害の影響が小さく短くなり、加入者は安定した通信を楽しめる。
  • 事業者は障害対応に追われず、サービス提供に集中できるように。
  • 問題を自律解決できる通信網は、顧客満足の土台そのもの。
果ては加入者の「つながるあたりまえ」を守る話。地味だけど価値は巨大！

まとめ —— 他業界への示唆

成功の型を分解する

Ericsson がたどった3歩

  • Google Cloud のツールでデータを濾す・集約・関係づけし、基盤をつくる。
  • Gemini Enterprise Agent Platform でエージェントを構築・指揮する。
  • 特定と解決を自動化し、クローズドループで回し続ける。
# 成功の型（要約）
data_platform()   # 1. データ基盤
build_agents()    # 2. エージェント構築
closed_loop()     # 3. 自動改善サイクル
「基盤 → エージェント → 自動化」の3段構えは、どの業界にも当てはまる型！
