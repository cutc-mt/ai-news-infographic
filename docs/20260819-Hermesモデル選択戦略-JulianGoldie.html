Hermes Agent の最適モデルの選び方

タスクで選ぶ ローカル×API LM Studio ハードウェアの制約

その1：モデル選びの軸

01

タスクの要求からモデルを選ぶ

  • 「書く・調べる・まとめる」など、まず種類を分ける
  • 複雑な手順がいる作業には、強いモデルを割り当てる
  • 単純な作業は軽いモデルで十分なことが多い
  • 「何を求めるか」を先に決めると、選ぶのが速くなる
タスク分析 要求を先に 使い分け
モデル選びは「このタスクに何を求めるか」から始まるよ!
02

Claude はオーケストレーションの定番

  • 複数の作業をまとめる「指揮する役」には Claude が定番
  • 複雑な手順を分けて、指示を出すのが得意
  • 長い文脈を読みながら、判断を続けられる
  • 大事なワークフローの土台として安心感がある
Claude まとめ役 定番の選択
まとめ役（指揮）は Claude に任せると安心だね!
03

DeepSeek V4 Pro という選択肢

  • Agentic OS の操作向けに、効率の良いもう一つの軸になる
  • 動きの軽さを活かして、繰り返しの作業と相性がいい
  • 費用を抑えたい場面で、まず検討する価値がある
  • Claude との使い分けで、全体のバランスが取れる
DeepSeek V4 Pro 効率タイプ もう一つの軸
「強さ」だけでなく「効率の軸」も持っておこう!
04

Hermes のモデルプロファイル機能

  • Hermes では、用途ごとにモデルのプロファイルを登録できる
  • 「執筆用」「調査用」など名前をつけると管理が楽
  • 複数のプロファイルを試して、合う組み合わせを探す
  • 設定はあとから何度でも書き換えられる
Hermes プロファイル 試して育てる
まず仮のプロファイルを作って、試しながら育てるのがおすすめ!

その2：ローカルとAPIの使い分け

05

ローカルモデル（Qwen など）の役割

  • Qwen など、手元の機材で動くモデルを補助に使える
  • 通信がなくても動くので、小さな作業を任せられる
  • 外に出したくない内容を扱うときに安心
  • 速い返事が欲しい雑用と相性がいい
Qwen ローカル実行 秘密のデータ
「メインはAPI、雑用はローカル」の分担が使いやすいよ!
06

APIモデルとの動的な切り替え

  • Hermes の中で、ローカルとAPIのモデルを切り替えられる
  • タスクの重さに合わせて、その場で最適な方へ
  • 大事な作業は強いAPIモデル、日常は軽いモデル
  • 「どちらを使うか」の基準を決めておくと迷わない
動的な切り替え API 基準を先に
切り替えの「基準」を先に決めておくのがコツ!
07

ハードウェアの制約を知る

  • 大きなモデルを手元で動かすには、それなりの機材が必要
  • メモリの量が、動かせるモデルの大きさを決める
  • 無理な設定では動きが止まるので、最初に確認
  • 自分の環境の「ここまで動く」という線を把握する
メモリ VRAM 限界ライン
「どのサイズまで動くか」を先に調べると、失敗が減るよ!
08

Mac でローカルLLMを動かす

  • Mac はメモリが大きめなので、ローカルLLMと相性がいい
  • 統合メモリの仕組みを活かして、大きめのモデルも試せる
  • 発熱やバッテリーへの影響も見ながら使う
  • 長時間の運用では、冷却の様子もチェック
Mac 統合メモリ まず試す
Mac は「まず動かして試す」環境にぴったり!

その3：環境を整えて確かめる

09

PC 構成で考えること

  • GPUの有無とVRAMの量が、快適さを大きく左右する
  • 電源と冷却も、長く使うなら大事な要素
  • Windows と Linux で使えるツールが違うこともある
  • 小さめのモデルで動作を確認してから、大きくしていく
GPU VRAM 冷却
「GPU → メモリ → 冷却」の順で確認すると迷わないよ!
10

LM Studio で相性を確かめる

  • LM Studio を使うと、モデルの相性を手軽に確認できる
  • 動くかどうか、まず小さく試してから本番へ
  • 読み込みでエラーが出たら、形式や容量を疑う
  • 軽量化の形式への対応も一緒に見ておく
LM Studio 相性チェック 事前チェック
「動くか分からない」は LM Studio で先に確かめよう!
11

モデルを評価する手順

  • かんたんなタスクを3つほど用意する
  • 同じタスクを複数のモデルで回して比べる
  • 「速さ・丁寧さ・費用」の3つの軸でメモを取る
  • 良かった組み合わせはプロファイルに残す
比較テスト 3つの軸 記録
「比べるくせ」をつけると、選ぶ目が育っていくよ!
12

コストと性能のバランス設計

  • 最強のモデルを全部に使うと、費用が一気に増える
  • 重要な2割に強いモデル、残りは軽いモデル
  • 「ここだけは強く」という場所を決めておく
  • 毎月、費用を見ながら配分を少しずつ直す
費用の配分 2割に集中 毎月の点検
全体の費用を見ながら、「力の入れどころ」を決めよう!

その4：設定して運用する

13

プロファイル切り替えのサンプル

  • 用途ごとに名前をつけたプロファイルを並べる
  • どの場面でどれを使うか、コメントで書いておく
  • 値は自分の環境に合わせて書き換えて使う
# サンプル（イメージ）: 実際の値は環境に合わせて
profiles:
  orchestration:   # まとめ役・重要な作業向け
    provider: api
    model: "<強めのAPIモデル名>"
  daily:          # 日常の軽い作業向け
    provider: api
    model: "<軽めのAPIモデル名>"
  local_helper:  # 手元で動かす補助役
    provider: local
    model: "<ローカルモデル名>"

default_profile: daily
# タスクに応じて切り替えて使う
YAML プロファイル 見本
これは「形の見本」。自分の環境に合わせて書き換えよう!
14

運用で気をつけること

  • モデルを替えると、出方のくせが変わる
  • 設定の変更は少しずつ、反映を確認しながら
  • APIの使った量と残高は、こまめに点検
  • ローカルの重いモデルは、熱と音にも注意
替えた直後 使った量 点検
替えた直後こそ、出力を必ずチェックしよう!
15

モデルの組み合わせ戦略

  • まとめ役（Claude）と、実行する役割の二段構え
  • 効率を上げたい部分に DeepSeek V4 Pro を混ぜる
  • 秘密にしたい作業は Qwen などローカルでカバー
  • 組み合わせは固定せず、毎月のように見直す
二段構え 役割の分担 月1の見直し
「1つで全部」より「役割で分ける」方が強くなるよ!

その5：運用を安定させて、これからへ

16

トラブルシューティング

  • 動かない → メモリ不足の可能性。小さいモデルへ
  • 遅い → 通信か、モデルが大きすぎる場合を疑う
  • 変な出力 → プロファイルの指定ミスを最初に確認
  • 切り替え不能 → 設定の反映と保存をもう一度
動かない 重い 再確認
トラブルは「小さく試す」のが解決への近道!
17

今後のモデル戦略

  • 新しいモデルは「小さく試してから」採用を決める
  • 評価の手順が決まっていれば、乗り換えも速い
  • 特定の1社だけに頼りすぎない構成にする
  • 毎月1回、プロファイルを見直す習慣を
小さく試す 乗り換え 月1の見直し
「選ぶ考え方」があれば、新モデルが出ても迷わない!
18

まとめ：選び方の型

  • 選ぶ基準は「タスクの要求」から
  • まとめ役は Claude、効率なら DeepSeek V4 Pro
  • 細かい仕事は Qwen などローカルで
  • 相性と限界は LM Studio で確認
  • 試しながらプロファイルを育てるのが近道
使い分け 試しながら 育てる
「完璧な1つ」を探すより「組み合わせを育てる」が正解!
