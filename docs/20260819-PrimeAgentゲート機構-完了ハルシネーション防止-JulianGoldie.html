セクション1: 「できました」は本当か? — 完了ハルシネーションの痛み
01

完了ハルシネーションとは

  • AIが実際には失敗しているのに「タスク完了」と宣言する現象
  • 報告はそれっぽいのに、中身が動いていない
  • 「完了したつもり」の報告ほどタチが悪い
  • エージェントを信頼できなくなる原因の代表格
#完了ハルシネーション #DoneButNotDone
「はい、完了しました!」…本当に?
02

全エージェント勢の共通の痛み

  • 動画内でも「every agent user knows its pain」
  • AIの「完成!」を鵜呑みにして起きる提出事故
  • 確認したら「やっぱり動いていなかった」が日常
  • 発見が遅れるほど、手戻りの被害は拡大する
#AgentPain #信頼の崩壊
罠なのは、報告が超・自信満々なことなんだ
03

従来の対処①: 全手動確認

  • 通常のツールでは毎回すべて自分で確認するしかない
  • ファイル・ビルド・動作をひとつずつ目視チェック
  • エージェントの数が増えると確認作業が破綻
  • 「AIに任せたはずが、人間が一番忙しい」
#手動確認 #スケールしない
結局、検査役が自分になるジレンマ…
04

従来の対処②: 確認ループを回す

  • 「直して」→「できました」→再確認を延々ループ
  • ループのたびにトークンと時間を消費
  • 嘘完了のたびに人間のレビューが挟まる
  • 直る保証はなく、運任せの側面があった
#ループ手法 #非効率
回し続ける管理も、それなりにひと手間なんだよね…
セクション2: Prime Agent の「gate（ゲート）」機構
05

Prime Agent とは

  • 自律実行を前提としたエージェント環境
  • autonomous mode（自律モード）を搭載
  • 動画は「ユースケース #6: the gate」の紹介回
  • 嘘完了対策の決定打として紹介される機能
#PrimeAgent #AutonomousMode
今回の主役は「gate」という関所の仕組みだよ
06

gate（ゲート）とは

  • 完了宣言の前にパス必須の検証コマンド
  • 「チェックコマンド」をタスクにアタッチできる
  • コマンドが通らない限り完了とみなされない
  • 合格＝本物の証拠 / 不合格＝作業続行
#gate #検証コマンド
名前の通り「関所」。通行証は実行結果だけ！
07

ゲートの動作フロー

  • ① エージェントが作業を終え、完了を宣言
  • ② gate の検証コマンドが自動で実行される
  • ③ 失敗すると失敗内容がセッションへ送り返される
  • ④ エージェントは失敗を受け取り、仕事を続行
#自動検証 #FailAndContinue
検査 → 差し戻し → 再作業が、全部自動で回る！
08

口先では越えられない

  • “It literally can't talk its way past the bar.”
  • 言い訳や弁明はハードルとして無効
  • 合格/失敗はコマンドの結果で機械的に決定
  • ごまかしの余地が構造的に存在しない
#ProofOverPromise #機械的判定
「頑張りました」は0点。「通りました」だけが合格！
セクション3: バウンド（境界）された自律実行とスキル
09

gate の設定イメージ

  • タスクごとに検証コマンドを定義
  • 例: テスト実行 / ビルド / lint / 形式チェック
  • 失敗出力はそのままセッションへフィードバック
  • コマンド選びが信頼性を左右する
# gate の概念例（イメージ）
task:
  goal: "テストを全件グリーンにする"
  gate:
    command: pytest -q         # 完了前に必ず実行
    on_fail: send_to_session   # 失敗は差し戻し
#GateConfig #CI的発想
「テストが通らないとマージできない」と同じ発想！
10

ラン全体がバウンドされる

  • 自律実行ラン全体が明確な境界で囲まれる
  • 無限に働き続けるリスクを排除
  • 上限に到達したランは強制終了
  • 「暴走」ではなく「委任」になる設計
#BoundedRun #暴走防止
自由すぎない自律、が安心のポイントなんだ
11

上限①: ターン数

  • エージェントが取れるターン数に上限を設定
  • 動画では「kind of like goal mode」と表現
  • ゴールモード的な打ち切りで無限ループを防止
  • 上限はタスクの規模に合わせて調整
#MaxTurns #GoalMode類似
「あと1ターンだけ」の連チャンを防ぐガードだよ
12

上限②③: トークンと時間

  • 消費トークン数に上限を設定
  • 総実行時間にも上限を設定
  • コストと納期の想定が立てやすい
  • 「いつまでも終わらないタスク」を排除
#TokenCap #TimeCap
予算と締切のある自律実行、それがバウンド！
セクション4: スキルの考え方と実践メリット
13

スキルは「実行可能な形」で

  • Prime Agent へのスキルは「手順の説明」ではない
  • 読んで解釈する曖昧さ・解釈ミスが減る
  • 再現性のある実行資産として蓄積される
  • gate と組み合わせて品質を固定化
#ExecutableSkills #再現性
「レシピを読む」より「ボタンを押す」が確実だね
14

メリット: 成功率が大幅 UP

  • 複雑なマルチステップ自動化の成功率が大幅に向上
  • 失敗→修正が自動で回り、手戻りが減る
  • 嘘完了による事故・手直しが激減
  • 「放置してよいエージェント」に近づく
#成功率UP #マルチステップ
長く複雑なタスクほど、gate の効果が出るんだ
15

メリット: 確認作業からの解放

  • 毎回すべてを自分で確認する必要がなくなる
  • 確認ループを回す運用からもおさらば
  • 人間は例外処理と最終レビューに集中
  • 見るべきは gate の合格結果だけで OK
#作業削減 #役割分担
検査は機械、判断は人間。すっきり分担！
16

ユースケース

  • コード生成 → テスト gate で品質保証
  • サイト構築 → ビルド＆リンク切れチェック gate
  • データ処理 → 件数・スキーマ検証 gate
  • レポート作成 → 必須項目チェック gate
#ユースケース #自動品質保証
「完了の定義」をコマンドにできる仕事すべて！
セクション5: ベストプラクティスとまとめ
17

ベストプラクティス

  • gate は客観的に判定できるコマンドにする
  • テスト・ビルド・lint など CI 資産をそのまま流用
  • 上限（ターン/トークン/時間）は段階的に調整
  • gate が甘いと意味がないので、厳しめに設定
#GateDesign #段階導入
「絶対に嘘をつけないコマンド」を選ぶのがコツ！
18

まとめ: 証明なき完了はない

  • 完了は「宣言」ではなく gate 合格で決まる
  • 失敗は自動で差し戻し → エージェントが継続
  • バウンド（ターン/トークン/時間）で暴走防止
  • スキルは実行可能な形で与えて再現性を確保
#PrimeAgent #gate #ProofOfWork
「信じて」ではなく「証明して」が新しいルール！
