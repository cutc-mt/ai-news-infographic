Prime Agent サブエージェント・チーム構築

セクション1：チームとは何か — 1人から部門へ

1人を部門に変えるギア

  • 動画の核心は「team」の話題。ここが1 worker → 部門への変換ギア
  • 単一ワーカーの管理だけなら、ふつうのツールで足りる
  • Prime Agentが作れるのは、まるごと1つの部門（department）
  • 並列で動くエージェント集団が、自律的に仕事を進める
「1人の助手」ではなく
「組織」を丸ごと動かす発想!
departmentがキーワードだよ

メインagentがsub-agentを生成

  • メインエージェントがsub-agentをスポーンできる
  • それは「見せかけ」ではなく、real separate agents（本物の独立agent）
  • 親・子の階層で、組織図のように広がっていく
  • メインagentは「管理者」としてふるまう
偽物の分割じゃなくて
本当に別々のagentが
動いちゃうのがスゴい点✨

各自が持つ「自分だけの」資産

  • 自分自身のsessionを持つ
  • 自分専用のworkspace（作業場所）を保持
  • 自分だけの履歴（history）を持つ
  • コードの中に、それぞれの記憶が残っていく
session・workspace・history
の3点セットが「自分だけの
部屋」みたいなもの🏠

「採用」は1回の関数呼び出し

  • 新しいagentの「採用」は、文字どおりsingle function call
  • 面談も契約書もなし。1行でチームが増える
  • 人事の手続きコストがゼロになる設計

イメージ

# 「採用」はこれだけ
spawn_sub_agent(
  role="リサーチ担当"
)
人の採用は数週間지만
こっちは一瞬で完了!
1 call = 1 採用

セクション2：呼び出しは「待たない」— 並列実行のしくみ

呼び出しが待たない（非同期）

  • 決定的に重要な詳細：spawnの呼び出しはwaitしない
  • メインagentはsub-agentを発射したら、即座に自分の作業を続行
  • 完了をじっと待つ「ブロック」が存在しない
  • メインagentが遊んでる時間をゼロにできる
「投げたら待たない」
ノンブロッキング設計が
すべての高速化の起点📡

並列実行 & 結果の返信

  • sub-agentたちはparallel（並列）で走る
  • 結果はmessageとして、終わった時点で返ってくる
  • 「いつ終わるか」を気にせず、届いたものから処理できる
  • メインagentは受信箱で結果を回収するだけ
終わった順にメッセージで
「できました!」と返ってくる。
順番待ちの列が存在しない📬

具体例：3人のsub-agent

  • 1人目：競合リサーチ — 今四半期に競合サイトへ入った変更を調査
  • 2人目：FAQ抽出 — 顧客メールから一番多い質問を取り出す
  • 3人目：コンテンツ案 — 来月分のアイデアをドラフト
  • この3つを同時に走らせるのがポイント
「spin up three sub-agents」
の一言で3人態勢が出動。
仕事の分担がそのまま組織になる💼

すべてを1つのレポートに統合

  • 3つの結果をcombine（統合）して1つのreportへ
  • バラバラの調査・抽出・草案が、1本の成果物にまとまる
  • あなたがやるのは「まとめて」という指示だけ
分業して、最後に合流。
人間のチームと同じ流れを
コマンド1つで実現📄

セクション3：たった1コマンドで回る組織の数字

3 workers ＋ 1 manager ＋ あなたの1コマンド

  • 3 workers — 同時に走るsub-agentたち
  • 1 manager — 結果を組み立てるメインagent
  • 1 command — あなたが打つのは最初の1回だけ
  • 少ない指示で、大きな成果が出る構図
入力は1、働き手は3、
まとめ役が1。レバー比率が
ムチャクチャ良い構造👃

セクション4：消えないworker — 永続性の設計

sub-agentは永続的（persistent）

  • Prime Agentのsub-agentで最初に特筆すべき点：persistent
  • 仕事を終えたagentは消えない（doesn't vanish）
  • sessionが生存し続ける
  • 翌日にフォローアップを投げても、すべて記憶している
「昨日のあの調査、ちょっと
続けて」と言えば、続きから
始められるのが嬉しい🎶

30分アイドルで静かに退避

  • 約30分アイドルが続くと、sub-agentは静かにアンロードされる
  • これはmemory を節約するための設計
  • 「退避します」と通知も音もなし。quietlyに退く
  • 退避時の状態は、しっかり保存される
休憩中のスタッフを奥の部屋に
下げる感じ。無駄な常駐を
しない省エネ設計⏳

話しかければ即、元の位置から復元

  • 誰かがそのagentに話しかければ、即座にリロード
  • 復元地点は保存された時のまま（from where it was saved）
  • 「最初からやり直し」ではなく、いなかったことみたいに再開（like it never left）
席を外してた人が、呼んだら
すぐ戻ってきて続きから仕事。
コンテキストのロスが無い🚪

セクション5：誰が誰と話せるのか — 通信の境界

ファミリー内だけの通信

  • 意図的に設けられた境界：agentは自分のfamily内だけにメッセージ可能
  • 例：parent agent＋そのsub-agent＋その下のagentたち
  • 無関係なセッション同士が、勝手に話せない設計
  • この範囲はbuilderがわざと（on purpose）決めている
「部外者と雑談しない」ルール。
組織の外まで話が飛び散らない
のが安心なポイント🏠

無関係なsessionの雑談を防止

  • 境界が無いと、数十の無関係なsessionが予測不能に喋り出す
  • 関係ないagent同士がチャットし合うカオスを防止
  • 自由度と秩序のバランスを、設計段階で調整済み
「全員が全員と話せる」は
一見理想的でも、実際は
ただの騒音になりがち⚠️

直接メッセージで互相きする

  • ファミリー内のagentは直接メッセージを送り合える
  • すべてをあなた経由にしなくてOK（without routing through you）
  • 互いの仕事をステア（誘導）できる
  • 「部門を作ると、その部門が喋る」のが結論
上司（あなた）を毎回挟まず、
現場同士で調整できる。
組織として本物の動き方📣

managerが途中でリサーチを修正

  • managerは、リサーチ中のタスクをmid-task（途中）で修正できる
  • 方向がズレたら、完了を待たずに軌道修正
  • 監督が現場を見ながら指図するのと同じ感覚
  • 手戻りのロスを、実行中に小さく潰せる
「その方向ちがうよ」と
仕事中に直せるのが、
managerの本当の役目✍️

セクション6：長時間処理を現実にする daemon

daemonがすべてのsessionを所有

  • この土台にあるのがdaemon — バックグラウンドサービス
  • daemonが生きているすべてのsessionを所有する
  • sessionはターミナルwindowに紐づかない
  • この仕組みが「長い仕事」を現実のものにする
目に見えない所で回り続ける
エンジン。sessionの命運は
このdaemonが握る🔧

PCを閉じても動き続ける

  • ラップトップを閉じても、エンジンは動き続ける
  • ジムに行っても、散歩に出てもOK
  • 戻ってきたらattachするだけで、現場に復帰

復帰コマンド

$ prime-agent attach
# 立っていた場所に、そのまま戻れる
遊びに行ってる間も仕事が進む。
帰ってきて attach すれば、
続きがそのまま見れる☕
