Zed「Delta」って何？

  • Zed が送り出した新しい単体アプリ（スタンドアロン）
  • Zed の編集器とは別アプリ。AIエージェント向けのGUIへの参入第一弾
  • 発行者は早期アクセス枠を入手して徹底検証
編集器にチャットをくっつけたのとは全然違う。
「会話でコードを作る」ための専用アプリだよ！

スレッドの中でコーディング

  • 横にチャット画面を付けた編集器ではなく、スレッド（会話）が主役
  • AIエージェントとの対話をくり返してコードを作っていく
  • 「編集器に住む」から「会話に住む」への転換
発想の転換だね。コードは会話から生まれるもの、と考える。

土台は「Delta DB」

  • Delta を支える 新しいバージョンの管理レイヤー
  • Zed が以前から予告していた技術が、ついに形になった
  • コミットとコミットの間も取りこぼさず記録
Delta アプリ
   └── Delta DB（管理レイヤー）
          └── Git リポジトリ
下のレイヤーから作り直したのが、このアプリの大きな特徴。

Git とどこが違う？

Git の場合

  • コミットした瞬間のスナップショットだけを保存

Delta DB の場合

  • コミット間で起きたすべての操作を記録
  • それぞれに安定したIDを付与
  • 変更を、それを生んだ会話とひも付け
Git を捨てるわけじゃなく、その上に細かい履歴の層を足すイメージ。

コード行 ⇄ 会話 をたどれる

  • どのコード行からでも、それを形作ったエージェントの会話を特定できる
  • どの会話からでも、その成果のコードへ一発でジャンプできる
  • 「なぜこのコード？」がすぐ分かる
src/app/page.tsx:42
  → op:xyz（安定したID）
      → スレッド #3 の発話とひも付き
あとから理由をたどれるのは、複数人で開発するときに強そう！

「会話こそがソース」

  • Zed の主張：人とエージェントの会話こそ、ソフトの本当のソース
  • 道具の側もそれを前提に設計すべき、という考え方
  • 発行者いわく「なかなか面白い見方」
履歴 = 会話 log じゃなくて、部品そのものとして扱うところが新しい。

マルチプレイヤー対応

  • 内部では CRDT を使用して衝突なしの同時編集を実現
  • 複数の人と複数のエージェントが、同じスレッドに同時に参加できる
  • リンク経由で仲間が参加し、次が可能に：
    • コメントを書く
    • プロンプトを共同で編集
    • 作業をそのまま引き継ぐ
「エージェントの作業を見守る」体制が、そのままチーム作業になる。

ブラウザ版もあり（delta.dev）

  • デスクトップと同じ Rust アプリを WebAssembly にコンパイル
  • インストールは不要。ブラウザですぐ動く
  • 既存の Git リポジトリとの互換をキープ
  • Delta を使わない仲間は、何も変わったことに気づかない
導入のハードルが低いのは助かる。delta.dev にアクセスするだけ。

シェアして協働する

  • 上部のシェアボタンで、スレッドの共有を準備
  • リンクを送るだけで、仲間がスレッドに参加
  • 履歴をすべて見ることも、作業をした同じエージェントと会話することもできる
  • Delta DB が支えているので、スレッドはただのチャット log ではなくバージョンの履歴そのもの
共有リンク＝そのまま「作業の証拠」になるのが面白いところ。

設定：モデルと見た目

  • モデルの選択肢には24種類（サブスク経由で公開）
  • ChatGPT Plus / Pro でサインインして OpenAI のモデルを使える
  • 自分の API キーも登録できる：OpenAI Anthropic OpenRouter Bedrock
  • GitHub Copilot のサインインにも対応 → サブスクに縛られない
  • 外観：ライト / ダーク、diff の色やマーカーも変更できる
  • 行番号、ソフトラップ、diff の基準などの設定もあり
  • 会話中心でありながら本物の編集器を内蔵。ファイルを開くと、シンタックスハイライト付きの画面でスレッドと並べて見られる
モデルに縛られない設計は、地味だけど大きな利点！

実践：曖昧な依頼には質問で返す

  • 「いろいろ編集して、もっと速くして」と依頼してみる
  • いきなり突き進まず、git コマンドでリポジトリの状態を確認
  • 「まだ手つかずのひな形」と判断 → 「速くする」には複数の意味があると3つの選択肢を提示：
A（推奨）軽量できれいな映画のトップ画面 B 検索とウォッチリスト付きの完全なMVP C 速度の改善だけ
  • A と答えると、トップ画面の中身についてさらに質問（また3択）
  • ブラウザのタブを開いてモックアップを作る提案も（まだ新しく、トークンを多く使うと注意付き）
  • 「もう質問しないで作って」と返すと、いよいよ作業開始
曖昧なときは勝手に進まない。この挙動はかなり好感が持てる。

計画 → テスト → 実装の流れ

  • docs フォルダに設計の仕様を書いてコミット（スレッド内に external changes として表示、コミットハッシュ付き）
  • writing plan スキルで184行の実装の計画を書いてコミット
  • executing plan ＋ git worktree スキルを読み込んで作業へ
  • npm install と lint で土台を確認
  • node_modules 内の Next.js 16 の文書を確認（フォント・メタデータ・サーバー/クライアントの部品）
  • テストファースト：「ランディングページが意味的なランドマークを出す」「レイアウトにメタデータがある」「動きの抑制設定を尊重」などのテスト契約を先に書いてコミット
規律のあるエンジニアみたいに、計画 → 確認 → 実装の順で進む。

エージェント専用の分離クローン

  • パスを見ると、delta clones フォルダの中で作業している
  • エージェントにはリポジトリの孤立したコピーが与えられる
  • Delta DB がワークツリーを仮想化 → 起動はほぼ一瞬で、コストもほぼゼロ
  • エージェントがブランチで暴れても、あなたの作業フォルダは無傷
  • 下部のブランチ切替で、main とエージェントが作ったブランチを一覧できる（ファイル表示・パスのコピー・ブランチ名のコピーも）
あなたの作業フォルダ（無傷）
    │  仮想化されたワークツリー
    ├── delta clones/agent-01 ... main と同じ状態
    └── delta clones/agent-02 ... 好きなブランチで自由に
ブランチをいくら作ってもタダ、っていうのが Delta DB の底力。
