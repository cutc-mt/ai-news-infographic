リアルタイム音声AIエージェント「omni-app」への道

「より優れたチャットボット」ではない、双方向ライブマルチモーダルエージェントの全貌と構築ロードマップ

2026年8月20日公開　 Google Cloud Tech（解説: Annie Wang）　 6分26秒

話している最中にリアルタイムで動作 知覚 → 推論 → 表現を1つのループで 全6エピソードの構築ロードマップ Gemini Live API × Google ADK 実際のブラウザを音声で操作

導入 —— 「実際に動く」エージェントと omni-app の概念

①デモ：話すだけで動く

0:00 — 実際に行動するエージェント

  • 動画はデモから始まる。Annie Wang 氏が声でエージェントに話しかける場面。
  • エージェントは声で応答するだけでなく、実際に手を動かして作業する。
  • 「よくできたチャットボット」ではなく、本物に行動するエージェントとの対話。
話しかけたら、聞いて・見て・覚えて・動く。まずはその瞬間を見せるところからスタート！

②テキスト入出力の壁

ほとんどのAIエージェントの限界

  • 世の中のほとんどのAIエージェントはテキスト入力・テキスト出力のみ。
  • 一方このエージェントは、あなたの声を聞き、
  • ページを見て、文脈を記憶し、話し返し、実際のブラウザをリアルタイムで操作する。
「読んで打ち返す」だけとの差が、体験をガラリと変える。あなたが話している最中にも動くのだ！

③omni-app とは何か

0:50 — Annie 氏の命名

  • Annie 氏はこの形のアプリをomni-app（オムニアプリ）と呼ぶ。
  • 音声・視覚・記憶・行動といったすべてのモダリティを1つのアプリに統合。
  • 知覚 → 推論 → 表現という一連のプロセスが、順番に処理されるのではなく1つの開いたループとして実行される。
omni = すべて。入力も出力も対話も、ぜんぶひっくるめて1つのアプリに。それがomni-app！

④チャットボット vs omni-app

1:35 — ワンターン vs ライブループ

  • チャットボットはワンターン（1回ずつの応酬）。入力が来て、返して、また待つ。
  • omni-app は1つのライブループ。会話が途切れず、流れ続ける。
  • この差は「少し良いチャットボット」ではなく、はるかに大きな飛躍だと強調される。
ピンポンの打ち合いではなく、ずっと流れ続ける川のような対話。発想の転換が必要！

⑤「双方向」の本当の意味

2:10 — bidirectional とは

  • 「双方向（bidirectional）」とは、送信と受信が同時に成立すること。
  • あなたが話している最中にも、エージェントはリアルタイムで動作する。
  • 話し終わってから返事を待つ、という順番待ちの前提がなくなる。
電話の全二重通信みたいなもの。お互いに同時に話せて、聞こえる。それがライブな双方向！

⑥ループ：知覚 → 推論 → 表現

2:50 — Perceive → Reason → Express

  • 知覚（Perceive）：声や画面の情報を取り込む。
  • 推論（Reason）：文脈を思い出しながら、次の行動を考える。
  • 表現（Express）：声で応答し、ブラウザを操作する。
# omni-app の心臓部（イメージ）
while True:          # 1つの開いたループ
    perceive()       # 聞く・見る
    reason()         # 考える（順番待ちなし）
    express()        # 話す・動かす
3つの処理を「順番に」実行するのではなく、ループの中で同時に回し続けるのがポイント！

シーズン1前半 —— エピソード1〜3：音声・フレームワーク・ツール

⑦シーズン1：全6エピソード

3:25 — 構築ロードマップの全体像

  • 自分でomni-appを構築するための全6エピソードのロードマップを紹介。
  • 使う技術は Gemini Live API と Google ADK。
  • 音声 → フレームワーク → ツール → ブラウザ → メモリ → ビジョンの順で積み上げていく構成。
この動画はイントロ編。ここから6話にわたって、少しずつ本物のomni-appへ近づいていく！

⑧Ep1·音声：読み上げ vs ライブ

3:55 — text-to-speech vs live session

  • まず比べるのは、テキスト読み上げ（TTS）方式とライブセッション方式。
  • TTSは応答文を書いてから音声化。ライブは音声のやりとりそのものが対話。
  • この選択が、エージェントの体験全体を分ける最初の分岐点。
「しゃべらせる」のと「対話する」のは全然違う。第1話はここから掘り下げる！

⑨Ep1·「中断」が変えるもの

なぜ interruption が界面全体を変えるのか

  • ライブ対話では、ユーザーが割り込める（中断できる）のが自然。
  • この中断への対応が、インターフェース全体の設計を変えてしまう。
  • 応答の途中で止める・聞き直すが当たり前になると、UIの前提そのものを作り直すことに。
人間同士の会話でも「ちょっと待って」は普通。それを機械側で受け止める仕組みが鍵になる！

⑩Ep2·フレームワーク選択

4:30 — GenAI SDK vs Google ADK

  • 素の GenAI SDK で組むか、エージェント開発キット Google ADK を使うか。
  • 比較の軸は「ループを駆動するのはどちらか」。
  • 自前でループを制御したいのか、フレームワークに任せたいのかで設計方針が変わる。
「車を自分で運転するか、運転任せにするか」。第2話はこの選択基準をじっくり比べる！

⑪Ep3·ツールとレイテンシー

5:00 — ライブ会話中の関数呼び出し

  • ライブ会話の途中で関数呼び出し（function calling）を行うのがツールのテーマ。
  • ここで立ちはだかるのがレイテンシー（遅延）問題。
  • 応答を待っている間にライブ感が失われると、体験が崩れてしまう。
# ライブ対話でのツール呼び出し（イメージ）
user_speaks()      # 話している間も…
agent.calls(tool)  # ツールを実行
→ 待ち時間が発生 ⏱ ここの遅延が課題
「ちょっと検索します」で沈黙が続いたら台無し。遅延との戦いが第3話の山場！

シーズン1後半 —— エピソード4〜6と、その先の未来

⑫Ep4·ブラウザに手を与える

5:40 — giving the agent hands

  • テーマは、エージェントに手を与えること。
  • 音声制御によるブラウザ自動操作を実現する。
  • 「話す」だけでなく「操作する」ことで、エージェントが実際に仕事をこなす。
目と耳と口に、最後は手を足す。これでエージェントは画面の向こう側まで働ける！

⑬Ep5·メモリの2層構造

6:00 — facts, vectors, and live recall

  • 構造化ファクト：確定した事実を整理して覚える。
  • ベクトルメモリ：膨大な情報を意味で引き出せる形で保存。
  • ポイントは会話の途中で取得（live recall）できること。
「あれ、さっき何て言ったっけ？」に即答できるのがomni-appの記憶。対話を壊さずに思い出す！

⑭Ep6·ビジョンの選択肢

6:20 — snapshot vs continuous frames

  • スナップショット：必要な瞬間だけ静止画を渡す方式。
  • 連続フレームストリーム：画面を絶えず流し込み続ける方式。
  • 比較の基準は「ライブ感を損なわないこと」。
見すぎると遅くなり、見なさすぎると取り残される。ビジョンの塩梅が最終エピソードの見どころ！

⑮開発者が構築できるもの

6:55 — ロードマップの先にある未来

  • 6エピソードを終えれば、開発者は自分だけのomni-appを構築できる。
  • 音声・ツール・ブラウザ・メモリ・ビジョンを1つのループにつなぐ技術が身につく。
  • 「話しかけると動くアプリ」という新しい体験が当たり前になる未来への招待。
これは入門編にすぎない。ここから先は、自分の手でループを回しにいこう！

構築の道具箱 —— API・SDK・学習リソース

⑯Gemini Live API

双方向ライブ対話の基盤

  • omni-appの音声のライブセッションを支える基盤技術。
  • 話している最中の双方向のやりとりを実現する。
  • ドキュメントは公式ドキュメントで公開中（フッターにリンク）。
ライブ感の心臓部。エピソード1で最初に触る、一番大事な部品！

⑰GenAI SDK と Google ADK

ループを駆動する2つの選択肢

  • GenAI SDK：素のSDK。ループの制御を自分で書きたい人向け。
  • Google ADK（Agent Development Kit）：エージェント開発に最適化されたキット。
  • 動画の「紹介製品」にも、この2つとLive APIの3点セットが挙げられている。
どちらでループを回すか。シリーズを通じて付き合うことになる大きな選択！
