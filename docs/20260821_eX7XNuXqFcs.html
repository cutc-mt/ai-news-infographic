決定論と非決定論
出力がブレる理由

  • 普通のプログラムは決定論：同じ入力なら同じ出力
  • LLMは非決定論：まったく同じ質問でも返しがブレる
  • 確率的に次のトークンを選ぶので、ゆらぎは仕様
  • ブレがもとでハルシネーションも生まれる
入力: 「この関数を直して」
1回目 → 丁寧に修正
2回目 → 作り直し提案
3回目 → 質問返し …ブレる！
「毎回ちがう」は故障じゃなくて、LLMの性質。これを前提に設計するのがはじめの一歩！
⏱ 03:58

ナレッジカットオフ
知識にも賞味期限が

  • モデルの知識は学習データのカットオフ日で止まっている
  • それ以降のニューや新バージョンは知らないまま
  • 最新情報は検索やRAGで外から渡す
  • 「知ってる」と口走るので、うのみにしない注意も
古い地図で今日の道を歩くと迷う地図。新しい情報は毎回、手渡してあげるのがコツです。
⏱ 03:58

コンテキストウィンドウ
作業机の広さ

  • モデルが一度に見れる範囲＝コンテキストウィンドウ
  • 例えるなら作業机。机に乗りきらない資料は読めない
  • トークン数に上限があり、会話を重ねるとすぐ埋まっていく
  • あふれた分は切り捨てか、要約して詰め直すしかない
「窓が大きい＝頭がいい」ではありません。広さと集中力は別の話なんです。
⏱ 06:39

モデル ＋ ハーネス
注意力は有限

  • 注意（アテンション）の総量は有限。窓が広くても集中は分散
  • 人間も長文の途中で読み飛ばすのとおなじ現象
  • 情報を詰め込むほど1つあたりの密度は薄まる
  • だからモデル単体では足りず、ハーネスで支える発想へ
ここが動画の山場！「なぜハーネスが要るのか」の答えが、注意力の有限性にあります。
⏱ 08:29

lost in the middle
真ん中が見えない

  • 長い文脈では中ほどの情報が見落とされやすい研究報告
  • 冒頭と末尾は強く、真ん中が弱点
  • 大事な指示は頭かお尻に置くのが得
  • 関連ファイルを端から端まで読ませる使い方は危険
［結果のイメージ］
先頭 ████████ 読める
中央 ██······· 見落とされがち
末尾 ████████ 読める
「読み込んだのに従わない…」は、真ん中に埋もれたせいかも。置き場所を工夫しましょう。
⏱ 08:29

context rot
文脈がしなびる

  • 会話を長く続けると文脈の鮮度が落ちる＝context rot
  • 昔の失敗やノイズが残って、判断が〈腐って〉いく
  • 余計なやりとりが積み重なると本題が薄まる
  • ときどき初期化して、きれいな状態に戻すのが正解
長く使ったフライパンはこびりつく。会話もこまめに洗うと、おいしい（正確な）料理になります。
⏱ 08:29〜

迎合性（シコファンシー）
いい子になりすぎる

  • ユーザーの言うことに調子を合わせすぎる性質
  • 「いいね」「そのとおりです！」と流されがち
  • まちがった指摘でも否定しないことがある
  • レビューを頼むと甘くなる弱点にもつながる
いつもニコニコ同意する相棒は心強いけど、審判には向きません。対策は後半で！
⏱ 10:20

性質から導く対策
/clear とタスク分割

  • /clear で机をまっさらに。context rot をリセット
  • 大きな仕事は小さいタスクに分割して渡す
  • 1タスク1狙いにすると注意のムダが減る
  • 区切りごとに新鮮な文脈でやり直すリズム
悪い例: 「アプリ全部つくって」
良い例: 1. 画面の設計
        2. API の定義
        3. 通信まわり実装 …と分割
モデルの性質（クセ）から逆算した対策なので、出力のブレにも rot にも効く、これが基本のカタチ！
⏱ 12:13

ハーネスとは
エンジンと車の例え

  • モデル ＝ エンジン（パワーは抜群）
  • ハーネス ＝ 車体。タイヤ・ハンドル・ブレーキ
  • エンジンだけでは走れない。街道を走るには仕組みが要る
  • 同じエンジンでも、車体しだいで走りが変わる
猛者のエージェントが強いのは、エンジンじゃなく車体づくりが上手だった、という話！
⏱ 13:37

王道のハーネス
CLAUDE.md に書くこと

  • プロジェクトのREADME的な心得を置くファイル
  • よく使うコマンド（ビルド・テスト・Lint）
  • コードのスタイル規約と好みの書きぶり
  • フォルダ構成や設計の約束
  • やってはいけないこと（NGリスト）も明記
# CLAUDE.md 例
- test: npm run test
- 命名はキャメルケースで
- src/core は触らないこと
「毎回口で説明する手間」をファイルに吐き出しておく。それだけで出力がぐっと安定します。
⏱ 16:40

Agent Skills
段階的開示の仕組み

  • スキルはフォルダ単位で管理。中に手順書を置く
  • 常時読ませず、必要な名前と説明だけ見せる
  • 使うときに初めて中身を読む＝段階的開示
  • 窓の専有を防いで、注意力のムダを削減
skills/
  ├ pdf-report/
  │   └ SKILL.md ← 必要な時だけ開封
  └ slide-gen/
      └ SKILL.md
「全部渡す」んじゃなく〈いつでも取り出せる棚〉にしまう。机は広く保てます！
⏱ 18:10

hooks
必ず走る決定論的処理

  • 特定のタイミングで確実に発火する仕組み
  • LLMに任せず普通のプログラムで処理＝決定論
  • 例：禁止コマンドをゲートで遮断
  • 保存時にフォーマッタを自動で走らせる
  • ブレない処理はモデルの外に出す、が鉄則
PreToolUse → 危険な操作をブロック
PostToolUse → 成形とLintを自動実行
「お願いすればやってくれる」ではなく〈必ず起きる〉仕組みにする。安心感がちがいます！
⏱ 19:02

subagent
第三者評価と関心の分離

  • 別のコンテキストで動く別働隊エージェント
  • 第三者評価：作った本人じゃなく別枠が審査
  • 関心の分離：調査・実装・検証を役割で分ける
  • 真っさらな窓で見るので迎合性の影響も小さい
  • 結果の要約だけ戻せば、窓も汚れない
作った人のレビューは甘くなりがち。別人格（別コンテキスト）に見てもらうのがミソです。
⏱ 21:14

llm-debate
議論させて磨きをかける

  • 複数のモデルに相互レビューさせる仕組み
  • あえて反対意見を求めて穴を探す
  • たたき合うことで、案の精度が磨かれる
  • 最後は別の視点で判定させると仕上がる
A案 「この設計で行こう」
B役 「この境界条件は危険」
→ 修正を経てより堅い案に
1人で考えても〈自分に都合のいい答え〉になりがち。良いケンカは薬になります！
⏱ 21:14

best-of-n
複数つくって最良を選ぶ

  • 同一タスクをn回（並行）で実行させる
  • 非決定論のブレを逆手に取って多様性を確保
  • できた案から一番良いものを選ぶ
  • コストは増えるが、精度と引き換えにできる
案1 ─┐
案2 ─┤→ 審査 → 最良の案を採用！
案3 ─┘
「1発で当てる」より〈複数引いて選ぶ〉ほうが確実。くじの弱さを数でカバーする戦法です。
