Prism とは何か

  • 分散LLM推論の性能分析ツール
  • スタックの状態を視覚的に見せる設計
  • 推論基盤の設定の最適化を支援
  • どこがボトルネックかを特定できる
数字を「見える化」して、推論スタックの悩みを解決する道具！

母体は llm-d プロジェクト

  • Prism は llm-d の一部として育つ道具
  • Kubernetes 上で動く分散推論の実現が目標
  • コミュニティ主導で開発が進む
  • Webサイト llm-d.ai で情報を公開中
大規模推論をクラウドネイティブにやる、という挑戦の一部！

分散推論のきほん

  • 1台のGPUでは収まらないモデルを複数台で分担
  • 重みの配置や通信の順番が性能を左右
  • 速さの鍵はGPU間の連携の部分
  • 構成次第で得手・不得手が変わる
分散推論の構図
  巨大なモデル
    ↓ 1台では処理しきれない
  複数GPU・複数ポッドで 分担
「GPUを足せば速くなる」は幻想、構成が命！

スループットとレイテンシ

  • スループット：単位時間あたりに捌ける量
  • レイテンシ：1件あたりの応答の速さ
  • この2つはトレードオフの関係
  • サービスの形に合う釣り合い点を選ぶ
使い分けの目安
  チャット検索  → 低レイテンシ重視
  一括処理 バッチ → 高スループット重視
「量を取るか、速さを取るか」で構成が変わる！

ベンチマークを並べて比べる

  • Prism は複数構成の結果を一覧化
  • GPUの数・ポッド数・エンジン設定を軸に比較
  • 数字の違いから傾向が読める
  • 勘ではなく根拠で構成を選べる
比較のイメージ
  構成A（GPU×2）   ██ 遅い
  構成B（GPU×8）   ██████ 速い
  構成C（GPU×16）  ████████ 費用増
条件をそろえて比べるから、意味のある比較になる！

GPUの数とポッド構成

  • GPUを何枚・何ノードで組むかが基本
  • Kubernetes ならポッドの分割も選択肢
  • 台数を増やすと処理の余力は上がる
  • ただしコストも比例して増える
スケールの方向
  ポッド数 ↑ → 同時処理が増える
  GPU/ポッド ↑ → 1件あたりが速い
        （通信のオーバーヘッドに注意 !）
「強さ」と「コスパ」のバランス地点を探す作業！

KVキャッシュという鍵

  • 推論中の計算結果を一時保存する仕組み
  • 使いこなせば再計算が不要になり高速
  • 反面、GPUメモリを大きく消費
  • 量化（量子化）して圧縮する手法もあり
KVキャッシュの恩恵
  トークンを増やすごとに
  計算量が 急増 する問題
    → キャッシュで 再利用 して軽減
メモリと速度の板挟み、その調整が推論の急所！

プリフィックスキャッシング

  • 依頼の冒頭部分が同じなら再利用
  • システム指示や長い前置きが効く
  • 同じ読み込みを省略して応答が速くなる
  • RAG のように前置きが長い用途で効果大
効く場面の例
  「この文書を読んで…」×100件
    → 冒頭の処理を 1回だけ 実施
    → 残りは 再利用 で一気に短縮
同じ聞き方を繰り返すサービスほど、効く技！

選べる推論エンジン

  • vLLM：連続バッチ処理で人気の定番
  • SGLang：高速な応答で注目の選択肢
  • エンジンによって得意な場面が異なる
  • Prism で実際に比べて決めるのが正攻法
エンジン選び
  vLLM   : 実績と安定重視
  SGLang : 速度と構造化出力に強い
      ↓ 同じ条件で計測して比較
エンジン選びも「信仰」ではなく「計測」で決めよう！

スケジューラの役割

  • 来た依頼をどう並べるか決める部品
  • 連続バッチ処理で待ち時間を削減
  • 優先順位の付け方で応答の体感が変わる
  • 設定項目が多く、調整のしがいがある
スケジューラの効果
  依頼が続々 ↓
  まとめて バッチ化
    → GPUの遊び時間が 減る
並べ方ひとつで、同じハードでも結果が変わる！

負荷分散のしくみ

  • 依頼を複数のワーカーに振り分け
  • 振り方次第で待ち行列の長さが変わる
  • セッションの同じ相手に戻す制御も可能
  • 偏ると一部だけ熱暴走気味に
負荷分散の例
  依頼 → ルーター
     ├─ ワーカー1（余裕あり）
     ├─ ワーカー2（ちょうど良い）
     └─ ワーカー3（詰まり気味 → 調整）
「誰に任せるか」の割り振りも、性能の大きな鍵！

分業の3つの型

  • テンソル並列：計算そのものを縦割り
  • パイプライン並列：層を順番に分けて担う
  • エキスパート並列：専門家ごとに分散
  • 実際は組み合わせて使うのが普通
使い分けの目安
  テンソル並列 : 低レイテンシ志向
  パイプライン  : 巨大モデル向き
  エキスパート  : MoE モデルと 好相性
どう分けるかで、速さとコストの絵が変わる！

なぜ「見える化」なのか

  • 数値の羅列より図が伝わる
  • 悪い箇所を早く見つける診断に近い
  • チームで議論するときの共通言語になる
  • 改善 → 計測 → また改善の循環が回る
見える化の循環
  計測 → 可視化 → 気づき
    ↑                ↓
  改善 ← 設定を変えて再挑戦
見えないものは直せない、が性能改善の鉄則！

コストとの付き合い方

  • 1トークンあたりの費用で比較
  • 余剰なGPUは削れる候補
  • 需要に合わせて台数を増減させる手も
  • 速さだけの勝負で費用が爆発しがち
費用の考え方
  性能 ÷ コスト = コスパ
    例: 構成B は構成Aの1.5倍速い
        でも 3倍の費用 → 要再考
「速いけど高すぎ」を避けるのが大人の判断！

最適な構成の探し方

  • まず目指す指標を決める
  • 候補の構成で同じ条件の計測を回す
  • Prism の結果から良さげな圏をしぼる
  • 実運用の流量で確認して仕上げ
探す手順
  ① 目標を決める（例: 応答2秒以内）
  ② 候補を 3〜5案 用意
  ③ Prism で比較 → ④ 実流量で 最終確認
「完璧な1手」より「測って決める習慣」が強い！

Kubernetes での運用

  • llm-d はKubernetes上での分散を想定
  • ポッドを伸び縮みさせて対応
  • 応答を受け持つ入口の設定も重要
  • Prism で運用中の傾向も把握
運用の絵
  利用者 → 入口（負荷分散）
    → ポッド群（vLLM 等）
    → GPU ノード 自动調整※
  ※ 自動スケールの設定次第
クラスタの上で推論を組み立てるのが今の流れ！
