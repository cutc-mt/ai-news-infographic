APIキーとは何か

  • APIを使うための合い言葉のようなもの
  • あなたのアカウントと結びついている
  • 使い方はそのまま課金につながる
  • 他人に知られると自由に使われる
たとえるなら
  APIキー = 家の鍵
  鍵があれば
   → 誰でも 入れてしまう
鍵と同じ。扱いは「合言葉」ではなく「秘密」！

チャットに貼る危険

  • 貼った文は履歴に残り続ける
  • 履歴はサーバー側にも保存される
  • 画面共有やスクショで写り込む
  • ログを送る・見せるとき一緒に出る
貼った瞬間に起こること
  プロンプトに入力
   → 履歴に保存
   → 送信先の数だけ コピーが増える
   → 自分では消しきれない
一度貼ると「どこにあるか分からない」状態に！

漏れたときの実害

  • 知らない人に勝手に使われる
  • 使い放題で費用がふくらむ
  • 気づくのが数日後になることも
  • 対処のために仕事が止まる
被害の流れ
  キーが漏れる
   → 見知らぬ場所から利用
   → 請求が跳ね上がる
   → 全キーの 作り直し へ
「自分は大丈夫」が一番の落とし穴！

うっかり貼るあるある

  • 動作確認を急いでいるとき
  • エラー対応で丸ごと貼る癖
  • ターミナルの表示をそのまま送る
  • 「場所を決めていない」から手元に来る
うっかりの構図
  キーの置き場所が未決定
   → メモやチャットに 仮置き
   → そのまま 忘れて共有
悪気じゃなく起きる。だから「置き場所」を先に決める！

環境変数とは

  • OSが持つ値の置き場のこと
  • プログラムの外側から渡す仕組み
  • コードに書かなくてよいのが利点
  • CodexなどのCLIツールも読み取れる
仕組みはかんたん
  OS の置き場に値を入れる
   MY_API_KEY=xxxx
   → ツールが 勝手に参照
   → コードは キーなし でOK
「外から渡す」たったこれだけで履歴に載らない！

.envファイルの使い方

  • プロジェクトの設定ファイルとして作る
  • 中身は名前＝値を書き並べるだけ
  • 開発中の手元のPC向きの方法
  • 作ったらGitに乗せないのが鉄則
.env の中身（例）
  # この行は自分のPC限定
  OPENAI_API_KEY=sk-xxxx
  DB_PASSWORD=xxxx
   → ファイル1つで 置き場所を統一
「値はここだけ」を決めるのが第一歩！

Gitに乗せない工夫

  • .gitignoreに追記して除外
  • 代わりに.env.exampleを公開
  • 名前だけ共有し値は各自で入れる
  • うっかり追加したら履歴ごと消す
.gitignore に書く一行
  .env
   → GitHub に上げない
  example は名前だけ
  OPENAI_API_KEY=
   → チームに 形だけ共有
公開するのは「入れ物」だけ。中身は各自で！

Secret Managerとは

  • クラウドが用意する金庫のような場所
  • 値は暗号化して保管される
  • 読める人を権限で絞れる
  • 書き換えの記録も追える
使いどころの目安
  手元のPC → .env
  サーバーやCI → Secret Manager
   → 本番ほど しっかり管理
場面が上がるほど、鍵は金庫へ移すイメージ！

置き場所の使い分け

  • お試し開発は.envで十分
  • 本番やCIはSecret Managerへ
  • チャットとメモは置き場にしない
  • 迷ったら大事な値ほど外へ
使い分けの一行ルール
  動かす場所が上がったら
   置き場所も 一段しっかり へ
   チャットは 常に除外
「どこに置くか」を一行で決めておくのがコツ！

Codexでの実践

  • CLIの起動時に外から渡す
  • シェルの設定で読み込みも可
  • 指示文には値を書かない
  • 動けば成功。貼らなくてよい証拠
ターミナルでの流れ
  export OPENAI_API_KEY=sk-xx
  codex "この機能を追加して"
   → 値は 外から参照 される
   → 会話は キーなし で進む
Codexは環境変数を読める。教える必要がない！

指示文から名前を消す

  • 今の指示文を見直すところから
  • 書いてあるキーの名前を探す
  • その部分を丸ごと消す
  • 参照の仕方だけ残せばOK
書き換えの例
  × sk-xxxx を使ってAPIを呼ぶ
  ○ APIキーは環境変数から
     取得して使って
   → 名前ごと 消す のが正解
値だけでなく名前も消す。ヒントもあげない！

名前を消す理由

  • 名前があると探す起点になる
  • 設定ファイルへの当たりがつく
  • 履歴を真似するとき貼り直しが起きる
  • 名前がなければ刺さりにくい
攻撃者視点で考える
  「OPENAI_API_KEY あり」
   → あとは 値を探すだけ
  名前もなければ
   → 探す手がかりが減る
覗く人に「地図」を渡さないための工夫！

一行ルールを決める

  • 決めるのは一行だけ
  • 「値をどこへ置くか」を書く
  • 決めたらREADMEに貼っておく
  • 迷いが消えて毎回同じ判定に
ルールの書き方の例
  「APIキーは .env に置く。
   チャットには書かない」
   → この一行を いつでも見える場所 へ
決めて見える場所に置く。それだけで迷わない！

漏れたときの対処

  • まずキーを無効化
  • 新しいキーを作り直す
  • 使い方の記録を確認
  • 使える範囲に上限をかける
対処の順番
  ① 無効化（止める）
  ② 作り直し（新しく）
  ③ 置き場所の見直し
   → 「貼ったまま」が 一番悪い
完璧より「止められる」備えが大事！

チームで回すには

  • 共有するのは手順の書き方だけ
  • 値は各自の環境で入れる
  • 共有の場での貼る癖に注意
  • 見直しを習慣にすると強い
共有の型
  README に手順を残す
  ① .env.example をコピー
  ② 自分のキーを入れる
   → チャットに 値は流さない
「入れ物」を共有して「中身」は渡さない！
