Embedding とは何か

  • テキストの意味を数字の並びに置き換える技
  • 「意味が近い＝数字が近い」になるよう調整
  • ベクトルの次元はモデルごとに異なる
  • LLMの最後の層から取り出すのが一般的
たとえると
  「猫」 → [0.21, -0.4, 0.87, …]
  「犬」 → [0.19, -0.38, 0.84, …]
    → 数字がよく似る＝意味が近い
「意味を計算できる形にする」という発想がすべての入口！

なぜ今、必要なのか

  • RAG：外の知識を引いてくる仕組みの土台
  • 意味の検索：言い方が違っても拾える
  • 推薦：好みの傾向を数値で表現
  • 分類やまとめ分けにも活用
活躍の場
  文書検索 / 社内QA / 推薦
   → どれも ベクトル化 から始まる
   → 土台の速度が全体を左右
生成AIの裏方として、需要が急伸している領域！

ベクトル検索のしくみ

  • 似ている度合いを角度で測る（コサイン類似度）
  • 質問も文書も同じ空間に置く
  • 近い順に並べて上位を返す
  • 索引（Index）を使い、探す時間を短縮
流れの絵
  質問 → ベクトル化
  文書 → ベクトル化（事前に）
   → 近い順に 照合 → 答えの材料に
「意味で探す」検索の心臓部分がここ！

大量テキストの壁

  • 文書が増えるほど変換する量もふくらむ
  • 数百万件ともなると時間がかかる
  • 依頼をまとめて処理する流れが必須
  • 単位時間あたりの処理量が勝負
課題の構図
  文書 100万件
   → 1件ずつでは 日が暮れる
   → まとめて流す 工夫 が必要
品質だけでなく「速く安く」が問われる場面！

vLLM とは何か

  • 誰でも使える公開の推論枠組み
  • PagedAttentionによる省メモリが看板
  • もともと文章生成向けに発展
  • エンベディング配信にも対応
特徴まとめ
  高速 / 省メモリ / API付き
   → 生成も 埋め込み も同じ道具で
   → 導入事例が豊富で安心
「速い・安い・使いやすい」で人気の定番エンジン！

PagedAttention の勘所

  • 計算の途中結果を細かく分ける発想
  • メモリのすき間をほぼなくす
  • 同じ容量で同時処理数を増やせる
  • OSの仮想メモリと似た考え
たとえ話
  トラックに荷物を積む
   → すき間なく 詰め込む
   → 1台で運べる量が増える
メモリの使い方を変えるだけで、数字が大きく動く！

エンベディングの配信

  • 起動時にタスクを切替（embedモード）
  • 最終層をまとめて（プーリング）出力
  • API越しにベクトルを返す
  • 生成と同じ運用の型が使える
イメージ
  vllm serve モデル名
    --task embed
  → /v1/embeddings で 受付
  → 文字を入れると ベクトル が返る
生成で培った速さが、そのまま埋め込みでも活きる！

TPU のきほん

  • Googleが育てたAI専用チップ
  • 行列の掛け算を一気にこなす設計
  • 複数チップを束ねて大きな処理へ
  • Google Cloud 上でVMとして借りられる
得意分野
  ニューラルネットの中身
   = 行列 × 行列 の連続
    → 専用回路でまとめて処理
汎用チップでなく「AIのためだけ」に作られた加速装置！

TPU と GPU の違い

  • GPU：幅広い用途に効く万能型
  • TPU：AIの計算に特化した専門型
  • 大規模な学習・推論と好相性
  • 実際は両方試して比べるのが鉄則
使い分けの目安
  画像など多目的 → GPU
  巨大モデルの一括処理 → TPU
  どちらも 計測して比較 を
優劣ではなく「得意分野が違う」とらえ方が正しい！

Cloud コンソールで準備

  • コンソールの画面からTPU VM を作成
  • ゾーンとバージョンを選ぶ
  • SSHでVMに入り作業を開始
  • 利用上限（クォータ）の確認も忘れずに
準備の流れ
  コンソールで TPU を作成
    ↓ SSH で接続
  環境を整えて vLLM を導入
    ↓ すぐ動かせる状態へ
画面を数クリックするだけで、数分で立ち上がる！

TPU VM の起動手順

  • コマンド（gcloud）でも作成できる
  • トポロジーでチップの数を指定
  • 用途に合わせ種類を選ぶ（v5eなど）
  • 手順は公式ガイドに沿って進める
コマンド例（※公式ガイド参照）
  gcloud compute tpus create …
    --zone=…
    --version=…
  → 作成後に SSH で 接続
公式の手順をなぞるだけで、初めてでも迷いにくい！

vLLM を入れて動かす

  • TPU向けの公式ガイドに沿って導入
  • 数行のコマンドで起動までたどり着く
  • モデルは引数で指定して切替
  • 動いたらAPIで試すだけ
イメージ（※公式ガイド参照）
  vllm serve モデル名
    --task embed …
  → API として 待受開始
まず動かす、それから調整！の流れが一番早い！

OpenAI 互換の API

  • /v1/embeddings に依頼を送る
  • 既存のライブラリからそのまま接続
  • 入力は文字列のリストでまとめて送れる
  • 返答の中にベクトルが並ぶ
リクエスト例
  POST /v1/embeddings
  { "model": "…",
    "input": ["文1", "文2", …] }
  → ベクトル のリストが返る
いつもの書き方のままで使えるのは、移行が楽！

まとめ処理で速く

  • 入力をまとめて送ると処理量が向上
  • 積み込む量（バッチサイズ）の調整が鍵
  • 大きすぎるとメモリ不足に注意
  • TPU はまとめた処理が特に得意
効果の絵
  1件ずつ → もたつく
  まとめて → 一気に変換
   → 1件あたりのコストが下がる
「まとめる」だけでも数字が変わる、お手軽な改善！

規模を広げる考え方

  • チップの束（Pod）で並列化
  • 複数VMで分業させる構成も
  • 流量に合わせ台数を増減
  • 入口の負荷分散も組み合わせて設計
構成の絵
  利用者 → 入口（負荷分散）
   → vLLM サーバ
   → TPU VM 群 で分業
   → 文書量に合わせて拡張
小さく始めて、文書が増えたら育てられる設計！

性能を出すこつ

  • まず目指す指標を決める（件/秒など）
  • 文の長さ・次元の数も結果に影響
  • 設定→計測→改善の循環を回す
  • 一度作ったベクトルは再利用も検討
回す手順
  ① 目標を決める（例: 1万件/時）
  ② 設定を 少しずつ変更
  ③ 良いものを 残す → 繰り返し
「完璧な1手」より「測って決める習慣」が強い！
