SGLang×TPUでLLMサービングを速くする
JAXベースの高速推論のしくみ

Google Cloud ｜ LLM serving with SGLang TPU：RadixAttentionとバッチ処理で応答を加速
2026年8月22日

SGLang とは何か

  • LLMを速く届けるためのサービング用枠組み
  • RadixAttentionという独自の仕組みが看板
  • 複雑な指示の流れを制御できる
  • 多数の依頼を同時にさばく力が自慢
「モデルを立てて終わり」じゃなく、速く安く届ける技術！

サービングの悩みどころ

  • 応答が遅いと利用者が離れる
  • 速くすると費用がふくらむ矛盾
  • メモリの使い方が壁になりがち
  • 同時接続が増えると待ちが長くなる
悩みの構図
  速さ ⇄ 費用 の板挟み
  同時利用 ↑ → 待ち行列が伸びる
    → うまく「並べて処理」する必要
モデルそのものより「届け方」で差がつく領域！

TPU のきほん

  • Googleが育てたAI専用の計算チップ
  • 行列の掛け算を得意とする設計
  • 複数チップを束ねて大きな計算へ
  • Google Cloud 上でVMとして借りられる
TPUの得意分野
  ニューラルネットの中身
   = 行列 × 行列 の連続
    → 専用回路で一気に処理
汎用チップでなく「AIのためだけ」に作られた加速装置！

TPU と GPU の違い

  • GPU：幅広い用途に使える万能型
  • TPU：AIの計算に特化した専門型
  • 大規模な学習・推論で好相性
  • TPU は JAX/XLA との組み合わせで本領
使い分けの目安
  画像処理・多目的 → GPU
  巨大モデルの一括処理 → TPU
  どちらも 実際に計測して比較が鉄則
優劣ではなく「得意分野が違う」のが正しい見方！

JAX ベースである意味

  • 計算の内容を自動で最適化してくれる
  • 同じ計算の反復を高速化する jit が強力
  • 複数チップへの振り分けが書きやすい
  • Google のTPUと相性抜群な土台
JAX の強み
  Python で書く
    → XLA が裏で整理
    → TPU 向けの 速い命令 に変換
書き方は素朴なのに、裏では賢い最適化が走る！

XLA という裏方

  • 計算の記述を機械の言葉へ翻訳
  • 余分な処理を切り詰めて軽くする
  • 計算をまとめ直して効率化
  • TPU 専用の命令を自動選択
変換の流れ
  JAX のコード
    → XLA が 最適化
    → TPU ネイティブな命令に
名前は知らなくても、SGLangの速さを支える縁の下の力持ち！

RadixAttention とは

  • 読み込み済みの部分を木構造で共有
  • 共通の冒頭は再計算しない設計
  • 古いものから賢く消す管理も自動
  • メモリをむだなく活用
しくみの絵
  「システム指示」共通
   ├─ 会話A 再利用
   └─ 会話B 再利用
  → 冒頭の計算は 1回だけ
SGLangの代名詞！同じ前置きを何度も処理しない知恵！

プリフィックスキャッシング

  • 依頼の冒頭部分が同じなら再利用
  • 長いシステム指示で効果が大きい
  • 同じ読み込みを省略して応答が速く
  • RAG のように前置きが長い用途で効果大
効く場面の例
  「この文書を読んで…」×100件
    → 冒頭の処理を 1回だけ 実施
    → 残りは 再利用 で一気に短縮
同じ聞き方を繰り返すサービスほど、効く技！

構造化生成の制御

  • 出力を決まった形に整える機能
  • JSON などを壊さず出力
  • 会話の分岐や流れの設計も可能
  • 機械的に処理しやすい確実な応答
活用の例
  「必ず JSON で答えて」
   → 形が たまに壊れる 心配
   → SGLang なら 出力の時点で制御
「後で直す」より「生まれない」ほうが強い、の発想！

バッチの賢いまとめ方

  • 来た依頼をまとめて処理する仕組み
  • 処理中のグループに後から参加させる技
  • チップの遊び時間を減らす
  • 順番の工夫で待ちの偏りを解消
効果の絵
  依頼が続々 ↓
  まとめて バッチ化
    → TPU の稼働率が 上がる
    → 全体の処理量が増える
並べ方ひとつで、同じハードでも結果が変わる！

vLLM との違い

  • vLLM：連続バッチ処理で人気の定番
  • SGLang：RadixAttention と構造化出力に強い
  • GPU 向け中心の vLLM に対し、JAX 版はTPU 直行
  • 実際は比べて決めるのが正攻法
選び方の目安
  vLLM   : GPU で 実績重視
  SGLang : TPU・構造化出力で 得意
      ↓ 同じ条件で計測して比較
エンジン選びも「信仰」ではなく「計測」で決めよう！

TPU VM の準備

  • Google Cloud でTPU VM を作成
  • VM に SSH で入って作業を開始
  • 必要な導入ガイドが公式ページに
  • 認証の設定を先に済ませるのが楽
準備の流れ
  Cloud コンソールで TPU 作成
    ↓ SSH で接続
  JAX + SGLang を導入
    ↓ すぐ動かせる状態へ
公式の導入ガイドが親切なので、初めてでも迷わない！

クイックスタート例

  • SGLang TPU ページにサンプル集
  • 数行のコマンドで起動までたどり着く
  • 動いたら会話を試すだけ
  • モデルの選択も引数で切替
イメージ（※公式ガイド参照）
  python -m sglang.launch_server
    --model モデル名
    --tpu …
  → API として 待受開始
短い手順で試せるのが魅力。まず動かして、それから調整！

モデルの立て方

  • OpenAI 互換のAPI 形式で待受
  • 並列数や最大長などを引数で調整
  • 重みは 事前に保存しておくと速い
  • 複数 VM で分業させる構成も可能
立て方の例
  launch_server を実行
    → ポートで 受付
    → 既存の道具から そのまま接続
いつものクライアントがそのまま使えるのは助かる！

メモリ管理のかしこさ

  • 推論中の結果を一時保存する仕組み
  • 使いこなせば再計算が不要になり高速
  • RadixAttention が共有と削除を自動で
  • 大メモリの TPU と好相性
恩恵の絵
  トークンが増えるごとに
  計算量が 急増 する問題
    → キャッシュ 再利用 で軽減
メモリと速度の板挟み、その調整が推論の急所！

速さを出すこつ

  • まず目指す指標を決める
  • 前置きが共通ならキャッシュを活かす設計
  • 並列数は実際に計測して選ぶ
  • 改善 → 計測 → また改善の循環を回す
回す手順
  ① 目標を決める（例: 応答2秒以内）
  ② 設定を 少しずつ変更
  ③ 計測 → 良いものを 残す
「完璧な1手」より「測って決める習慣」が強い！

Cloud 上での運用

運用の絵

  ※ 設定次第で伸び縮み
クラスタの上で推論を組み立てるのが今の流れ！
