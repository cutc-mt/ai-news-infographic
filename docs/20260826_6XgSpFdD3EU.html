AIコーディングの未来とSlop Apocalypse

〜計画は人間、コーディングはAI。「human on the loop」を目指す道〜
Cole Medin
2026年8月26日
この対談でわかること

ゲストはBMAD創業者

  • ゲスト：Brian Madison（BMAD創業者）
  • 進行：Cole Medin＋Rasmusが共同で進行
  • Dynamousコミュニティの収録を公開
  • 約85分のポッドキャスト形式・質問も多数
人気のコーディングエージェントフレームワーク「BMAD」の中の人に、活用法から業界の行方まで聞いちゃう回だよ！

キーワードはSlop

  • 番組の中心テーマ：Slop Apocalypse
  • 壊れたコードではなくトークン消費とサイクル増加として現れる
  • たどり着く先はhuman on the loop
「スロップ黙示録」はもう来ている、という話から始まる濃い対談！
誕生：拒否されたエージェントループ

マネージャーの悩み

  • Brianは企業で複数チームのマネージャー
  • Cursorなどの補完が「気の利いた補完機能」として人気に
  • でもエージェントループだけは部下に使ってもらえない
経験を積んだエンジニアの verdict は「ゴミだ、自分でやった方が速い」の一択…

宣伝と現実のギャップ

  • 当時のYouTube：「経験ゼロで一晩で百万ドルSaaS！」
  • 現実のベテラン：「これは玩具。使い物にならない」
  • そのギャップが夜のトライ＆エラーという執念になる
「どこまで押し切れるか」毎晩エージェントを回して限界を探ったんだって！

分割の発見

  • ルールを積んでも銀の弾丸にはならないと判明
  • 効いたのは小さな意図（spec/story）に分けて渡すこと
  • アジャイルの「大きな考えを分割する」思想をAIに適用
  • 失敗したら文脈を足して最初から、を繰り返し完成へ近づける
当時は「vibe coding」も「context engineering」も無い言葉だらけの時代。手探りの発見だった！

まず素で試すべし

  • フレームワークもスキルも全部捨てて素のエージェントでどこまで行けるか試す
  • 今なら1発で近くまで行くことも多い
  • 反復を積んでからスキルやフレームワークを拾うのが正しい順番
「まず素で」は今も有効な訓練法。 Brian のおすすめの入口だよ！
哲学：human on the loop

あなたがコントロール

  • BMADの根っこ：あなたが主導、AIは案内役
  • 計画とspec作りは人間が創造の中心
  • コーディングだけをAIに委任する
  • AIは素晴らしい教師・進行役として扱う
「全部任せて」だと気持ち悪くなるのが Brian 流。人間が創造の源だよ！

in から on へ

  • 旧来：human in the loop（人間が作業の輪の中）
  • 目指す先：human on the loop（輪の上から監督）
  • これが「山の頂点」であり、dark factory ではない
輪から出てもコントロールは手放さない。それが成熟した形だって！
進化：モジュール化と入口の自由

6つのスキルから

  • 当初はPRD→アーキ→ストーリー分割→実装の6個
  • アーキ文書は「モデルの暴走」防止用（テスト失敗でDBを新設！等）
  • 今はモジュール化され全スキルがカスタマイズ可能
「この考えを学んで、自分の流儀を作って」というのが最初のメッセージ！

TOMLでカスタマイズ

  • スキンの横にTOMLファイルを置いて調整
  • Jira / Linear 連携もここで設定
  • 企業のガバナンスを報告書に組み込める
  • スキル本体は書き換えないので更新を受け取れる
組織の単位・個人の単位どちらでもOK。調整点は版を跨いで固定されてるよ！

入口は選べる

  • 定番：PRDから入る
  • PR/FAQ（Amazon式：プレスリリースを書いて agent と議論）
  • 軽いプロダクトブリーフだけでも可
  • ブレインストーミングだけでもOK
  • 他フレームワークのスキル（grill me等）で鍛えてから流し込む
PRD が苦手な人も多いと分かって、入口をどんどん増やしたんだ！

BMAD build

  • 旧名 quick dev。軽い案件向けの近道
  • 会話→その場でspec作成→ビルドへ
  • 全部1スキルで完結する、ひとまとまりのループ
  • 受け入れ条件があればレビューの輪が自動で回る
ちょっとした変更なら Claude に直接話すのも全然アリ。使い分けが大事！
v7：2〜3週間後に来る大改修

チーム対応の強化

  • エピックを複数フォルダへ分割
  • ストーリーを別ファイルにして分担しやすく
  • Azure / Linearなどシステムオブレコードと接続
  • 実チームでのパイロット運用で効果を確認済み
「どうすればチームで使える？」という質問が今いちばん多いんだ！

計画の成果物を一か所へ

  • PRD・アーキ・ソリューションデザインを一か所へ
  • Gitが分からないPMやデザイナーも共同で作業できる場に
  • 見つけやすい場所に置くと、spec 生成時に正しい文書を参照
1人がPRD、1人がアーキ、という分業がそのままできるのがミソ！

スキル市場へ分冊で

  • VercelのNPX Skillsに対応
  • Claude marketplaceとCodex marketplaceにも分割して公開
  • クリエイティブ用・PM用・開発ツール用を個別に選択
  • 全部は要らない人も必要な分だけ導入できる
重いインストーラーだった過去と決別。v7より先に来るかも！

自社ツールを接続

  • 視聴者からの質問：「自社のチケット管理を使いたい」
  • 回答は100% イエス
  • MCPやCLIで呼び出せる設計にしていく
  • 特定の道具に縛られない「開かれた」方針
自社の仕事の流れをそのままAIに乗せられるのが理想だね！
チーム導入：二つの壁

インフレクション点

  • まずエンジニアから始めるのが正解（初期の採用者）
  • うちのチームは100%がエージェント活用に
  • しかしその先に右と左の2つの壁が立つ
速くした先に待つ「次の遅い場所」を知っておくのが重要！

右側の壁＝レビュー

  • 開発が速くなりコードレビューが渋滞
  • 対応例：Code Rabbit等のAIレビュー道具
  • レビューを2人→1人に減らす
  • CSS変更などの些細な変更は自動で本番へ
  • ベストな人材を「本当に考えるべき変更」のレビューに回す
「全部2人レビュー」という思い込みを捨てると流れ出すよ！

左側の壁＝specの質

  • 次に詰まるのはビジネス・PM側
  • 機械に入れるのはspec。その質がすべて
  • ゴミを入れればゴミが出る（garbage in, garbage out）
  • エンジニアの仕事は「PMの成果物をどこで受け取るか」の線引きも
BMADがいちばん力を入れるのは実はこの左側。ここが本丸！

AIは増幅器

  • AIはamplifier（増幅器）
  • 良いものだけでなく悪いCI/CD・悪い工程も増幅する
  • 組織の弱点がはっきり見えるようになる現象
  • 見えたらパイプラインを本番まで通して関門を置く改善へ
AIを入れて破綻するなら、それは元からの課題が見えただけ！
組織のかたち：ポッドとエピック

ポッドモデル

  • 5〜8人のスクラムチームを2〜4人のポッドへ分解
  • 1ポッドが1つの問題（エピック）を最初から最後まで所有
  • PMは削られるのではなく役割が変化（より高い方向性の思考へ）
  • 若手エンジニアの育つ場所もまだ残る
「問題と解決を丸ごと所有する」のがポッドの魂だよ！

エピックが作業の単位

  • 2週間スプリントはもう推奨しない
  • 1人が1エピックを小さなアジャイルとして完遂
  • AI時代は仕事が圧縮され、先まで計画できる
チケットをこなす係から「所有者」へ。大きな変化だよ！

システムシンカーを雇え

  • PMでもエンジニアでもsystems thinkerを採用
  • ビジネスの部品がどう繋がるかを考える力
  • 訓練で伸ばせる能力。内製でも育つ
抽象化とシステム思考はほぼ同義。今いちばん価値が上がるスキル！
Slop Apocalypse（スロップ黙示録）

スロップの正体

  • Opus 5がコードに大量のコメントを注入
  • コメントとコードがズレるとどちらが真実かの争いが発生
  • この争いがモデルの注意力を削る
  • AIレビュー道具もしばらく見逃していた
読めば分かる良いコードが好きだった Brian には特に辛い出来事…

壊れない・でも遅い

  • スロップは壊れたコードとして出るとは限らない
  • 実態はトークン消費増とサイクル増
  • エージェント全体がじわじわ遅くなる形で現れる
  • 誰もリファクタリングに戻らないのが原因
「動いてるからOK」の積み重なりが、ゆっくり機械を殺していく話…

dark factory ではない

  • 原義（SF）の dark factory は計画まで全自動の意味
  • specを入れれば完成が出るならsoftware factoryが正確
  • そして頂点はそこではなくhuman on the loop
  • 「火曜の夕方に投げた spec で水曜に炎上せず眠れるか」が試験の基準
自分の software factory を持って本番系で試すのが今の宿題！

80%削除と concise

  • Anthropic がシステムプロンプトを約80%削除
  • 残りは大部分が workflows 関連の機構という分析
  • 新しい出力スタイルconciseは効果を実感中
  • モデルが変わったらagents.md等の駆動部を作り直せ（Boris の言葉）
「全部が良くなる」わけではない。新モデルでは土台から見直そう！
スキル論：prompt 以外の何ものでもない

スキル＝プロンプト

  • スキルも命令も規則ファイルも、全部markdown＝プロンプト
  • 唯一の例外はhook（決定論を追加できる）
  • 「プロンプト技術は死んだ」説は成立しない。機械の核心の primitive
  • 大容量にも書ける（上限は約25MB）が、skill.md は小さく
機械に入れるものが他に何がある？全部プロンプトなんだ！

新モデルは slop スキル

  • Fable・Mythos等の新モデルは良質な学習データがない
  • 動くけど肥大化した slop スキルを書く
  • 人気の30-day スキルは bloat だけど動く（効率と動作の天秤）
  • 最良の作り方：モデルと対話して掘り出し手で仕上げる、または自分で書く
多くの人が使うスキルだから、 lean さへの執念が大事になる！

セルフ改善の罠

  • 自動で自分を更新するスキルは数ラウンドで腐る
  • 決定論にすべきでない部分に決定論のかたまりが積まれる
  • Hermesの自己進化まわりの機能も Brian は使わない
  • 代替：失敗を課題と証拠としてスキル倉庫に記録し、ループを回し直す
  • eval で少しずつ肉付けする手法は有望だが、まだ完成度は今ひとつ
コードを直すより、スキルを直して、もう一回、最初から！

発火の難問題

  • Codexは何でもサブエージェントで処理したがる
  • Claudeは「言われるまでサブエージェント使うな」と抵抗→agents.md で上書き
  • 指揮官（orchestrator）スキルは実行中に顔を背けると発火しない
  • BMAD は説明文を調整して自動で発火しないコマンドのように使う
道具の気まぐれに振り回される日々。複数の階層に同じ指示を置く工夫も！
導入の秘策：許可の問題

2週間の実験

  • スプリント圧力を2週間ゼロにする
  • 全員に任せるのは1つのストーリーだけ（本来3〜4日の仕事）
  • フレームワークもスキルも与えず、素のエージェントで最後までやらせる
  • 成果の条件：エージェントが自力でストーリーを完成させ検証する所まで
「反対者を最初にください」と言い切る自信のテクニック！

朝会を学びの共有へ

  • 朝のスタンドアップで状況の報告は禁止
  • 代わりに学んだ技術の共有をする
  • 3〜4日目に興奮が生まれる
  • 1〜2週間でほぼ全員が同じ結論に自力で到達
課題の管理をAIに任せたり、独自スキルを作り出す創造性が爆発する！

許可の問題だった

  • 多くの技術者は時間が無く反復を積む余裕がないだけ
  • 私たち（動画の視聴者）は熱狂のバブルの中にいる
  • つまりagent の問題ではなく permission の問題
  • 2週間に出荷しなかった分は、その後の加速で簡単に取り戻せる
職人の誇りも尊重。ただ「仕事は移っていく」ことは自覚しよう。

マルチモデル戦略

  • モデルとハーネスが1年で激変し、焼けていく企業が続出
  • 企業はバックアップ＝マルチモデルの必要に気づき始めた
  • BMAD はClaude 専用ではなく Qwen・Codex等でも動く設計
  • 毎日変わる製品に全振りするのは博打
特定の道具の言葉に依存しないスキル書きが保険になる！
まとめ：技術者の価値はどこへ

価値の移り変わり

  • かつての価値：チケットを速くこなすこと
  • これからの価値：システム思考・specの質・何を作るかの判断
  • チームの不安は、上のレベルに上がれば楽しみに変わる
  • コードの趣味（taste）もプロダクトの趣味も人間の仕事
「私の価値は何？」の答えは、もっと上流にあったんだね！

職人という選択

  • CNCがあるのに手道具にこだわる木工の職人と同じ
  • 手で書くことを愛する選択は尊重される
  • ただ仕事は移っていく現実は受け止める
  • 「趣味」と「仕事」を分けるのが心地よさのコツ
愛するものを仕事にしない、という逆説の助言も忘れずに！

頂点はまだ先

  • 道筋：素で試す→スキルを拾う→チームの壁を壊す
  • AIは対話の相手・進行役として使う
  • slop とは付き合いながら、spec の質で勝負する
  • 目指すはhuman on the loop
第3回もやりたい！という結びで終わった濃密な85分でした！
