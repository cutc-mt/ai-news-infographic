まずは前提 — なぜ人はやめるのか、n8nとは何か

入って2週間でやめる人

原因をさぐると

  • ほとんどの場合、コンテンツのせいではない
  • 正体は「静かになったのに、誰も気づかなかった」こと
  • そこで「気づいてくれる仕組み」を自分で作った
  • 大変なのは作ることではなく、そのあとだった
会員が音を消しても、 コミュニティ側は気づかない… これが解約の本丸だよ

n8nとは（ざっくり）

  • まっさらなキャンバスに「ノード」という箱を置く
  • 1つはデータ取得、1つは変換、1つはメール送信…と役割分担
  • 箱どうしを線でつなげば、それがワークフロー
  • ルール・分岐・小さなコードも足せる → おもちゃでなく本物のシステムに
キャンバス
 ├─[ノード] データを取る
 ├─[ノード] 値を変える
 └─[ノード] メールを送る
 （線でつなぐだけ）
箱と線さえ分かれば、 あとは組み立てるだけ！

すべてはトリガーから

目をさまさせる3タイプ

  • スケジュール: 「毎朝8時」のような時刻指定
  • Webhook: 何か起きた時に他アプリが叩くWebアドレス
  • 手動ボタン: 自分で押して起動
trigger の3形態
schedule : 毎朝 8:00 に起動
webhook : URL を他サービスが叩く
manual  : ボタンで自分起点
トリガーが「起こす」、 ノードが「働く」—— この分担がすべての基本！

「1実行」の意味

  • 1実行 = ワークフロー1回ぶんの完全な実行
  • 中のノード数は無関係。15ノードでも3ノードでも1実行
  • クラウド試用版は14日・1,000実行
  • テストには十分な余裕
実行数のまとめ方は 「ノード数」じゃなく 「回数」だから安心♪
作ったもの — 「AI Profit Boardroom Turn Prevention」

ワークフロー全体像

  • 毎朝8時にスケジュール実行
  • Skoolコミュニティから「最近の投稿」と「メンバーリスト」を取得
  • メンバーごとにリスクスコアを計算して保存
  • 静かになった度合いで3つのパスに振り分け
朝8時 投稿+会員 スコア 振り分け 連絡
名前は「Turn Prevention」。 解約まえに引き止める、 毎朝の見張り番だよ

リスクスコアと履歴ログ

  • 各メンバーのリスクスコアを毎日計算
  • スコアを保存し、履歴ログを残す
  • 時間の経過による推移が見える
member   | day1  | day2  | ...
@tanaka  | 12    | 18    | ↑やばい
@suzuki  | 4     | 3     | → 安定
（スコアの推移イメージ）
数字をためておくと 「今・助けが必要な人」が ぱっと見えてくる！

最重要: 3つに振り分ける

  • ここがいちばん間違えやすいポイント
  • 全員を同じ扱いにすると、自動化はただのノイズになる
  • 昨日投稿した人にチェックインは不要
  • 3週間何も開いていない人には、本物の人間からの本物のメッセージを
router node
 ├ watch    → コンテンツ配信メール
 ├ at-risk  → チェックインメール
 └ critical → チームへWhatsApp
「静かさの度合い」で 動きを変える—— ここが肝なんだ！
BRANCH 1

ウォッチ層

  • 役に立つコンテンツの1編をメールで届ける
  • 「構って」感はゼロ。ただ有用なものがinboxに届くだけ
  • 相手に負担をかけないさりげない接触
「まだいますよ」の合図を 毎日はしない。 ちょうどいい頻度で！
BRANCH 2

リスクあり層

  • パーソナライズされたチェックインメールを送る
  • テンプレの一斉送信ではなく、その人向けの一文
  • 「話しかけるきっかけ」を手動で作る層
名前や行動に合わせた 文面で「気にかけてるよ」を 伝えるブランチ！
BRANCH 3

危急層 — 人が入る

  • ここではメールは送らない
  • ワークフローがアラートを組み立て、チームへWhatsAppでping
  • 受け取った人間が介入する
機械の役目は「知らせる」まで。 最後の一歩は人が踏む！

やったことを必ずログに

  • 各ブランチの最後に、何をしたかを記録
  • 「誰に・いつ連絡したか」がわかる状態を保つ
  • 記録がないと「役立っている」のか「静かにスパムしている」のか区別できない
log: branch=at-risk
member=@tanaka
action=checkin_mail
date=2026-08-26
自動化は「やった証拠」を 残さないと振り返れない。 ログが命だよ！
最初の実行ですぐ壊れた — クレデンシャルの壁

AIに作らせたら「完成」…だったが

  • n8n内のAIアシスタントに構築を依頼
  • 全ノード・全接続・全分岐が完成。完成品に見えた
  • ところが実行したら最初のデータノードで即失敗
  • 理由を聞いたら、AIアシスタントは淡々と答えた → 「5つのノードが未設定」
見た目は完璧でも 中身は空っぽ、という 落とし穴があった…

壊れた原因の内訳

  • 投稿・メンバー取得の2ノード → Apifyクレデンシャル未設定（HTTPノードで特定の資格情報型が必要）
  • メール2ノード → SendGrid接続なし。1通も送れない
  • WhatsAppアラートノード → 接続なし。チームにpingが飛ばない
  • さらにリクエストボディにプレースホルダー文字が残存 — 管理者メール・パスワード・コミュニティslugがダミー値のまま
{
  "adminEmail":    "YOUR_EMAIL_HERE",
  "password":      "YOUR_PASSWORD",
  "communitySlug": "your-community"
}  ← このまま動くわけがない
鍵が5本ない家。 玄関は立派でも 開かないんだ…！

教訓: クレデンシャルの壁

  • AIはワークフローの構造なら数秒で組める
  • でもあなたのアカウントにはログインできない
  • クレデンシャルこそが壁。そして全員がぶつかる
  • 接続は自分の手で、1つずつ設定するしかない
AIに任せていいのは 「設計」まで。 「鍵をわたす」のは無理！
AIが指示した「存在しないもの」と処方箋（しょほうせん）

なぜApifyを使う？

  • Skoolは公開APIを提供していない — 開発者ダッシュボードもなく、APIキーも作れない
  • そこで使うのがApify actor: Webサイトからデータを取ってくる小さなプログラムを走らせるプラットフォーム
  • Skool用actorが管理者メール・パスワード・コミュニティslugでログインし、投稿とメンバーをきれいなデータで返す
  • 使うのは自分が管理者のコミュニティだけ。他人のデータではない
正式な入口がなければ、 合法な別入口を 用意すればいい！

指示された設定先が存在しない

2つ目のワークフロー

  • 入会 → Skoolがn8nをping → Gmailでパーソナライズ歓迎メール
  • ワークフロー自体は完成し、Webhookアドレスも発行された
  • AIの指示「Skoolのグループ設定でwebhook / integrationセクションを探して member joined イベントに追加」
  • → そのセクションは存在しない！
  • 現状のSkoolに公開APIも、公式のmember joined webhookもない
ワークフローは正しかった。 ダメだったのは 「もう半分の指示」だった…！

自分の目で確かめる + 3つのドア

  • AIは確認できない部分を、自信たっぷりに埋めてくる
  • 自分でコントロールできないプラットフォーム内の設定を指示されたら、まず自分の目で見に行く

修正の選択肢（同じ結果、別のドア）

  • 歓迎ワークフローを自分でトリガーする
  • ターン防止と同じメンバーデータ取得をスケジュールで回す
  • サインアップ処理からトリガーする
行き先が同じなら、 入り口はいくつあってもいい。 これで午後まるごと節約！

週末を失わない構築順序

  • まず1ブランチだけ作る。デイリートリガー+データ取得1ノード。実行して出力だけを見る
  • ノードは1つずつ追加。クレデンシャルも1つずつ接続して単体テスト。5つ同時につなぐと犯人不明になる
  • 本番の人に向ける前にフェイクデータでテスト。初回実行で全員にメールは最悪
  • WhatsAppは最後に: Meta開発者アカウント・ビジネスID・アクセストークンが必要。メールを先に
  • スケジュールはゆっくり。デイリーで十分 — 人は15分で静かにならない。毎時実行は枠を燃やすだけ
トリガー1つ・取得1つ・ メール1つだけのミニ版から 作り始めるのが近道！
