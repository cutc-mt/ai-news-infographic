Unlazy：AIエージェントの「できました」を証明に変えるスキル

受け入れゲートで「うそつきdone」をなくす、実行可能チェックの仕組み

なぜ必要なのか

最大の悩み：自信満々の「done」

  • エージェントに大きなタスクを任せると、しばらく作業したあと超自信満々のdoneが返ってくる
  • 実際にコードを見ると、半分はプレースホルダーのまま
  • テストは一度も実行されていない
  • 頼んだ5個のうち2個が丸ごと欠落、ということも
「全部実装してテスト済みです！」…この報告、そのまま信じられますか？ これがいまのAIコーディングで一番イライラする問題なんです

Unlazyとは

  • GitHubリポジトリ Unlazy（作者：Leon X LNX）
  • 正体は実行可能チェックで裏打ちされた完了ディシプリン（規律）のスキル
  • 対応エージェント：Claude Code と Codex CLI
  • プレーンなNodeだけで構築、サードパーティ依存ゼロ
  • 必要なのは Node 16+／現行ソースは v2.1.0／MITライセンス
余計なものが何も入らない軽さ。導入のハードルがとても低いのがまず好感ポイント

タグラインがすべてを語る

公式のうたい文句

  • 受け入れ台帳を先に書く（Write the acceptance ledger first）
  • レビュー済みチェックを実行（Execute reviewed checks）
  • 返ってきた仕事を再検証（Re-verify returned work）
  • 証拠が支える範囲だけ報告（Report only what the evidence supports）
エージェント自身のdone報告を信じる代わりに、完了をテスト可能にする。発想の転換です
中核メカニズム：gates.md

gates.md ＝ 受け入れ台帳

  • 本筋の作業の前に、gates.md という台帳ファイルを書かせる
  • 各ゲートは観察可能な成果ひとつぶん
  • CHECK：実際に走るシェルコマンド
  • EXPECT：出力に現れるべき成功マーカー
## Gate: 全テスト合格
CHECK: npm test
EXPECT: all tests passed
「〜であること」ではなく「このコマンドが0で終わって、この文字が出ること」。英語の曖昧さを shell に落とし込むのがミソ

証拠行がないと未達扱い

  • ゲート達成の条件は2つ：終了コード0 ＋ EXPECTが結合出力に一致
  • 合格すると台帳に証拠行が書き込まれる：解決済みシェル・作業ディレクトリ・終了ステータス・パスのフィンガープリント・決定的な出力
  • チェックボックスをポチっとするだけでは完了と認めない（証拠がmissing/pendingなら未達）
力関係がひっくり返る瞬間。もうモデルは自分の宿題を採点できない。台帳が採点するんです

こっそり削除は禁止

  • 実行不可能なゲートだと判明しても、黙って消すことは許されない
  • 代わりに abandon行を追加し、空でない理由が必須
  • その放棄は最終レポートに晒される
「無理でした」と正直に言わせる仕組み。見えないところで帳尻を合わせる逃げ道を、ちゃんとふさいでいる
導入方法とセキュリティ設計

インストールとかんたん起動

  • Vercel Labsのskills CLI経由が一番ラク：npx skills add leongx/unlazy
  • -g でユーザー全体、--all で検出された全エージェントに入る
  • 手動の場合はリポジトリをスキルフォルダへクローン（Claude Codeは ~/.claude/skills、Codexは ~/.codex/skills）
  • 起動は Claude Codeなら /unlazy、Codexなら $unlazy
  • 「tree five gates」「doneになるまで絶対に止まるな」といった自然言句でも発動
$ npx skills add leongx/unlazy
# or: -g / --all
> /unlazy   # Claude Code
> $unlazy   # Codex CLI

--status：見るだけモード

  • まずリーフテンプレートを gates.md にコピーしてゲートを記入
  • --status は報告専用モード。台帳をパースして達成／未達を教えるだけ
  • 何も実行しないことが保証されている
  • CHECK行はシェルコード。READMEは「実行前に全コマンドと、呼ぶスクリプトを必ず読め」と明記
まず安全に状態を見る→人間が読んで判断→それから承認。順序が大切

承認は「Exact」に束ねる

  • 承認記録のないコマンドは実行されず、解決済みコマンド・EXPECT・作業ディレクトリ・シェル・パスを表示して止まる
  • 読んでOKなら --approve で承認→初めて実行
  • 承認は台帳・ゲート・CHECK/EXPECT文言・作業ディレクトリ・シェル・タイムアウト・プラットフォーム・継承パスのすべてに束ねられる
  • どれかひとつでも変われば再承認が必要
  • 記録はリポジトリ外の ~/.unlazy フォルダに保存
怪しいリポジトリの台帳を引き継いで、こっそりコマンドが差し替えられていても勝手には走らない。これは本当に良い設計

--reverify：証拠は賞味期限あり

  • --reverify は完了済みゲートも含めて全ランナブルゲートを再実行
  • 理由はひとこと：古い証拠は再実行ではない
  • この姿勢が、後述のオーケストレーション側で大活躍する
「さっき通ったから大丈夫」を信任しない。状態は変わるので、いまの時点で測り直すのが前提

正直に失敗できるゲートの書き方

  • ドキュメントは正直：「チェッカーは宣言されたコマンドの神託しか証明できない。英語のゲート名とシェルコマンドが同じ意味かは分からない」
  • 指南その1：実物のアーティファクトを読むゲートにする
  • 指南その2：全アサーション合格後にだけ成功専用マーカーを印字する
  • 指南その3：ネガティブチェックを既知のポジティブ対照で試す
  • 指南その4：提示された数値をEXPECTにコピーせず、独立に測定する
「AIを怠けさせないな」というプロンプト系リポジトリがほぼ全部スルーする細部。ここまで書き切っているのは珍しい
大きな仕事のための仕組み

3つの実行モード

  • solo：ここまで説明した単一のゲートファイル方式
  • orchestrated：指揮系統つきで大きなビルドを分解
  • parallel：リーフを並列に走らせるモード
小さな修正はsoloで十分。ビルドが大きくなるほど、上の2つが効いてきます

Depth Tree：タスクを木に割る

  • 起動例：/unlazy tree 5 refactor the payment module and verify every migration path
  • レイヤー1＝依頼タスク。そこからドメインとコンポーネントの本物の境界でリーフへ分割
  • 各リーフは狭い契約・厳密なファイル所有権・独自のゲートファイルを持つ一貫性ある成果物
  • 全体はプロジェクト内の .unlazy スコープフォルダで管理
  • plan.md が、作業を dispatch する前にインターフェース・依存・規約・ファイル所有権を固定
  • ブランチには統合ゲート（インターフェース適合・end-to-end挙動・デグレ）を重ねる
そしてドキュメントはこう書く：「数字を満たすための空の階層を追加するな」。深さが合わないなら、最も正直な分解を宣言して

並列作業のルール

  • リーフは OWNS パス（リポジトリ相対のグロブ）を宣言して、書けるファイルを限定
  • 同時並走の2リーフが同じパスを所有することは絶対禁止
  • 各リーフは実行前にチェッカー経由でパスを主張・確認
  • ディスパッチはローリング。検証済みリーフが他をアンブロックしたら、即次が始まる（無関係な作業を待たない）
  • 親はリーフの「done」を信用せず、--reverify でリーフのゲートを再実行
  • 検証はリーフから上へ流れ、ルート台帳が満たされて初めて最終報告（数値は直前に再測定）
ファイルの縄張りを決めて、衝突を構造で防ぐ。上司（親）は部下（リーフ）の報告書を必ず検証し直す、の図ですね

リーフは4パスで磨く

  • 完全実装：プレースホルダーなしで成果物を全部作る
  • 専門家再レビュー：ドメイン専門家として再評価し、安易な部分を作り直す
  • 欠陥探し：正しさ・統合・移植性・パフォーマンスのバグ狩り
  • 低コスト磨き：仕上げ。改善パスで何も見つからなくなるまで繰り返す
「動けばOK」で止めない。同じ成果物を複数の目で何度も通すループが品質を生む
安全弁、研究姿勢、そして総評

Stop hook：止まるな

  • Claude Code専用のオプション機能。インストールするとセッションの台帳に未達ゲートがある間、hookがblock決定を返す
  • つまりClaudeは途中で止まって勝利宣言することが物理的にできない
  • hook自体はチェックを実行しない（ブロックだけが仕事）
  • 逃し弁あり：6回連続ブロックで台帳進捗ゼロなら解放（無限ループ回避）
  • 同意なしにこのhookを入れることは禁止とスキル自身に明記
「まだ終わってないでしょ」と扉を押さえる係。ただしハマったとき抜け道も用意されていて、抜け目がない

研究セクションの正直さ

  • LLMの怠惰（laziness）、underthinking／overthinking、長期劣化に関する実際の論文を引用
  • SlobCodeBenchでは、テストした最良のエージェントでも長い反復タスクのチェックポイントはわずか約14.8%しかパスせず
  • READMEは率直：「この研究は動機となる失敗モードを裏付けるが、Unlazyが固定の改善を出す証拠ではない」
  • 過去版が引用した社内6回比較の生データはリポジトリに無いと白状し、設計履歴として扱えと明記
  • きちんと再実行できる検証プロトコルファイルまで用意
根拠ゼロで「10倍！」と叫ぶプロンプトリポだらけの中で、この正直さはシェフのキス級（最高）です

総評：賢いが儀式もある

良い点

  • doneの定義をモデルの頭からファイルへ移した、実行可能な証明つきの現在随一のアプローチ
  • 承認システムには本物のセキュリティ思考がある
  • ゼロ依存で、ドキュメントは証明できること／できないことに驚くほど正直

トレードオフ

  • 儀式のコスト。些末な編集やちょっとした質問に台帳は完全に過剰（スキル自身もそう言う）
  • 向き先は長いリファクタ・監査・並列ビルドなど、静かな不完全さのコストが高い本気の作業
  • 注意：承認は同意であってサンドボックスではない。チェックはマシンへのフルアクセスで走る。「承認前に読む」は省略不可
  • いまどきの数時間に及ぶエージェント実行には、本当に良い選択肢
