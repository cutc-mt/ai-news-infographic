AIコーディングの悩み
過剰な設計

  • 日付ピッカーを1つ頼むだけなのに…
  • ライブラリを丸ごと導入
  • ラッパー部品を新規作成

本当はブラウザが1行でネイティブ対応できるのにね！

なぜ AI は
コードを書きすぎる？

  • 抽象化が大好き
  • 誰も頼んでない設定オプションを追加
  • 標準ライブラリにあるものを依存として導入
  • 「多いコード＝多い仕事」に見えるバイアス
本物の現場では「ほとんど読むだけのPR」が一番嬉しいんだよね

中核のアイデア

  • 最小限のルールをエージェントに注入
  • コードを書く前に判断ラダーを上から順に確認
  • 書く量を最小まで絞り込む仕組み
シニア開発者の「削る勘」をそのままルール化した感じ！

判断ラダー
①〜③

  • ① そもそも必要？…不要なら省く（YAGNI）
  • ② コードベースに既存？…書き直さず再利用
  • ③ 標準ライブラリにある？…それを使う
上の段で「YES」なら、それで終わり。新しいコードは書かない！

判断ラダー
④〜⑥

  • ④ プラットフォームの機能？…ネイティブで済ませる
  • ⑤ 導入済みの依存でできる？…それを流用
  • ⑥ 1行で書ける？…なら1行で
6段すべてダメなら、ようやく最小限の新規コードだけ書く！

ラダーを回す前の前提

  • まず関連コードを読む・流れを追う
  • 問題を理解した後にラダーを実行
  • 見栄えのいい謎の1行を書くのは違う
  • 盲目的に削るのも禁止
最小なのは「必要だから」。無理やり圧縮したわけじゃないよ

絶対に削らないもの

  • バリデーション（入力チェック）
  • エラーハンドリング（例外の処理）
  • セキュリティ
  • アクセシビリティ（使いやすさ）
安全性の評価はベンチマークでも100%のまま！

# Codex の場合（ターミナル）

これだけで「怠惰シニア」ルールが常に ON！

約20種の
エージェントに対応

  • GitHub Copilot CLI: プラグイン経由で
  • Gemini CLI: extensions install で
  • Hermes Agent にも対応
  • Devon・Grok Build もOK
  • OpenCode ほか多数
どんな道具を使っていてもルールが乗るのが強い！

ルールファイル方式

  • Cursor rules: フォルダからコピー
  • Windsurf rules: 専用フォルダ付き
  • Copilot instructions ファイルも
  • AGENTS.md を置くだけ（Aider・Zed）
この方式ならNode 不要。ルールが常に ON になるよ

プラグイン版の仕組み

  • Node.js ライフサイクルフックを使う
  • 各ターンの前にルールを自動で注入
  • 生まれるサブエージェントにも同じルールを注入
  • 動かすには Node が必要（PATH 上に）
脇役のエージェントまで「怠惰シニア」化するのが地味に嬉しい

3段階の強度＋停止

  • /ponytail light: ゆるやかなルール
  • /ponytail full: 既定のバランス（おすすめ）
  • /ponytail ultra: 激しい削除モード
  • /ponytail off: 一時オフ
ultra はREADMEいわく「コードベースに恨まれた時用」。
本番では慎重にね！

見つける系コマンド

  • /ponytail review: 現在のdiffをスキャン
  • 過剰な設計を検出し削除案を提示
  • /ponytail audit: リポジトリ全体を調査
  • 長年積もった設計の肥大を一括で発見
古いプロジェクトで audit を走らせると身が引き締まる…（実体験）

記録する系コマンド

  • /ponytail debt: 繰り越し最適化の台帳を作成
  • コード内の小さなコメントをやるべき作業に集約
  • /ponytail gain: 改善のスコアボードを表示
  • /ponytail help: ざっくりリファレンス
  • コマンドはスキル対応ホストのみ動作
ルールファイル方式は常時 ON のかわりにコマンドはなし
