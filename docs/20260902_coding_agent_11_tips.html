Tip 1
エージェント向けに書く

  • 人間向けドキュメントは曖昧さを許す。エージェントには通用しない
  • ファイルパス・番号・コマンド を明示する
  • 目的はエージェントの想定（assumption）を減らすこと
  • 例:「すべてのSQLは database/ フォルダ配下」
CLAUDE.md の書き方 example
# SQL rules
- 全SQLクエリは database/queries/ に置く
- マイグレーションは
  database/migrations/001_init.sql から連番
- 実行は `npm run db:migrate` を使う
「よしなに」が一番の敵。
思い込みのすき間をふさごう。
2

Tip 2
指示ファイルは腐る

  • rule drift: ルールと実際のコードベースが乖離していく現象
  • 研究では4つに1つのリポジトリで古いルールが残っていた
  • 典型は削除済みファイルの参照。エージェントを迷わせる
  • 対策は rules-check-drift スキルで定期監査
ルール追加 コードは成長 乖離 = 腐敗
ルールも食材と同じで、放っておくと腐る。
定期的に棚入れしよう。
3

Tip 3
/compact は使うな

  • 会話を圧縮すると、具体的な詳細は約10%しか要約に残らない（研究）
  • 代わりに ハンドオフ文書 を作る
  • それを持って新しいセッションへ移行する方が良い
handoff.md example
## Handoff (2026-09-02)
- 済み: API スキーマ定義 (src/schema.ts)
- 未了: テスト3件が失敗中 (tests/auth)
- 次の一歩: tests/auth.test.ts の修正から
圧縮は細部を消す。
引き継ぎメモで、新品の頭に乗り換えよう。
4

Tip 4
重要ルールは hooks へ

  • LLM は非決定的。rule は「確率的」にしか守られない
  • テスト実行などの必須プロセスは hook で担保
  • タスク完了時などに自動で実行され、決定的になる
.claude/settings.json hooks example
{
  "hooks": {
    "Stop": [{
      "hooks": [{
        "type": "command",
        "command": "npm test"
      }]
    }]
  }
}
「忘れず実行して」より
「自動で走る」に頼る方が確実。
5

Tip 5
コンテキストは
少ないほど勝つ

  • 詰め込みすぎは逆効果。集中力が散るのと同じ
  • 研究の結論は less context beats more context
  • いまのタスクに必要な情報だけを渡す
多い context 精度 DOWN
絞った context 精度 UP
「たくさん読ませれば賢い」は
思い込みだった、という話。
6

Tip 6
レート制限の
本当の理由

  • rate limit に届く主因はコンテキスト過多
  • 無駄な情報を削れば、制限に届きにくくなる
  • Tip 5（context削減）と表裏一体の話
無駄な context token 消費 rate limit
制限との戦いは、実は
「ダイエット」の問題だった。
7

Tip 7
途中でモデルを
escalate するな

  • タスクの途中で強いモデルへ切り替えるのは損
  • 研究: 途中変更では差の半分以下しか回復しない
  • 切り替えるならセッションの区切りで
途中交代では取り返しがつかない。
次のセッションから乗り換えよう。
8

Tip 8
コーディネーターは
不要

  • エージェントにコーディネーターという役割を与えても…
  • 研究: その命名は結果を改善しない
  • 役割名の「魔法」にかからないこと
立派な名前をつけるだけで
良くなることは、なかった。
9

Tip 9
書いた本人に
レビューさせるな

  • writer と reviewer は必ず分離する
  • 同じセッションで自分を検査すると見逃しが出る
  • 別の頭（新セッション / 別エージェント）で検査する
writer 別の reviewer 見落とし減
作者の目は甘いもの。
検査は別の頭に頼もう。
10

Tip 10
過剰な反復修正は
禁物

  • 「もう一回直して」の連打は品質を下げる
  • 研究: 85% のケースで最終イテレーション前の方が良い答えを持っていた
  • やき直しの前に一度立ち止まる勇気
85%は「1個前」が正解だった。
もう一回、の前に思い出して。
11

Tip 11
検証はシステムで

  • 単発の「今回だけ確認」で終わらせない
  • 検証を仕組み化して毎回自動で走らせる
  • Tip 4 の hooks と組み合わせると最強
その場の確認 hooks で自動検証 品質が常に安定
「たまに確認」を「いつも自動」に。
これが確実さの正体。

研究の裏付け

arXiv 研究からの引用ポイント
  • /compact 圧縮後の要約に残る具体的詳細は約10%

今日から試せる
3つの一手

  • 指示を具体的に書き直す（パス・番号・コマンド）
  • 必須プロセスを hooks に移して自動化
  • rule drift の定期監査を仕組みに入れる
