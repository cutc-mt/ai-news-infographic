実験から本番（Production）へ

企業の共通ゴール

  • 多くの企業は PoC や小規模試験の段階にいる
  • 目指すのは 本番スケール への移行
  • デジタルネイティブ企業はすでに本番運用中
  • エンタープライズは「リスクが高い」と二の足を踏みがち
PoC 小規模試験 本番スケール
ネイティブ企業は当たり前に動かしてる。エンタープライズとの差は「はじめの一歩」の重さなんだ

タイガーチームの罠

一部の精鋭だけに限定する落とし穴

  • 「リスクが高い」からと タイガーチーム（少数精鋭）だけに限定
  • 組織のごく一小部でしかAIに触れない状態に
  • 実験だけを繰り返す企業は「AIの価値が見えない」まま脱落
  • PoC疲れ → 予算も熱量も失われていく
「うちもAIやってる」でも箱庭の中だけ…それじゃ価値の証明が永遠にできない、という話

小さく始めて、速く勝つ

1つのワークロード作戦

  • 小さなワークロード1つをえらぶ
  • それを最後まで 本番 まで持っていく
  • 1つ成功すればその後の展開が一気に容易になる
  • 社内の説得材料＝実績ができる
小さく 本番で成功 一気に展開
最初の1つを通すと、道が開ける。最初がいちばん重いけど、そこは我慢どころ！

モデルの進化が速すぎる

静的デプロイの時代は終わった

  • 新しいモデルが次々と登場する
  • モデルが変わるとアプリの挙動も変わる（良くも悪くも）
  • 銀行システムのような「静的にデプロイして何年も放置」はもう通用しない
  • 変化は「年単位」ではなく「日単位」でやってくる
作ったアプリが“最新”のまま保てる期間が、どんどん短くなってるってことですね

金曜デプロイ、月曜 新モデル

週末ですら置いていかれる

  • 金曜日 にアプリをデプロイしても…
  • 月曜日 には新しいモデルがリリースされている
  • 挙動が良くなることも、悪くなることもある
  • 「様子を見る」運用では追従できない
🪟 金曜デプロイ 🎉 土日 🆕 月曜 新モデル

Adaptive Applications とは？

この動画の核心コンセプト

  • モデルの変化に合わせて継続的にアップデートされるアプリ
  • ビジネスオーナーの期待も「常に更新される」ものへ変化
  • アプリチームの働き方も根本的に変化
  • 「完成して終わり」ではなく「適応し続けること」が仕事に
アプリの“完成形”なんて存在しない。生き物のように環境へ合わせて変わり続ける、それが Adaptive！

更新が“常態”になる

働き方と期待の変化

  • ビジネスオーナー「最新のままであって当然」
  • 開発チームは継続的な適応を仕事にする
  • 「デプロイしたら完了」の旧式マインドセットは終わり
  • 新モデルの評価・差し替えが日常業務に
「リリース後」こそ本番。適応のループを回し続ける体制が大事になるんだね

新しいアプリ × 新しいインフラ

全部盛りモダナイズは不要

  • 全部を一括でモダナイズする必要はない
  • 新しいAIアプリに必要な部分だけインフラを新調
  • データベースの拡張もセットで考える
  • 既存資産は活かしつつ、必要な所だけ入れ替える戦略
「リプレース全部！」はコストが高すぎる。AIのために必要な“一口”だけ新しくする、が賢いやり方

AIへの応答速度の期待

遅ければユーザーは去る

  • AIへの応答性への期待は非常に高い
  • クエリが遅ければユーザーは去ってしまう
  • チャットUIの普及で「すぐ返ってくる」が当たり前に
  • 遅延は体験を壊す最大のリスクの一つ
賢すぎる答えでも、遅かったら「使えない」。速さも機能のうち、ってことだね

Phase 3｜測り方と成功企業の特徴

Cards 12-18

ワークロードベンチマークへ

測る対象が変わる

  • 従来：ハードウェアやモデル単体のベンチマーク
  • これから：実際のワークロード・ユーザー体験を繰り返しテスト
  • アナリストや顧客体験そのものを測定対象に
  • CSAT / NPS 的な次元を重ねるイメージ
「モデルの点数」より「現場の体験」。測る場所がラボから実際の業務へ移ったんだ

金融サービスの成功事例

ステップ削減で効果を測る

  • 金融サービスで特に成功
  • プロセスがどれだけ改善され、何ステップ削減されたかで効果を測定
  • 業務の手順そのものが短くなることを価値とする
  • 体験指標（CSAT / NPS）とセットで評価
業務ステップ数 削減効果 体験スコア
「ステップが3つ減った」は誰にでも伝わる数字。効果の見える化が金融でハマった理由かも

成功の鍵 ①：常に実験

失敗を認める文化

  • 常に実験し続ける文化を持つ
  • 失敗を認めて、従業員を評価する（失敗予算）
  • 前に失敗したものも再訪する（モデルが良くなってるかも）
  • 挑戦の安全網があるから挑戦が続く
「失敗してもいいよ」の一言が、挑戦の回数を増やす。回数が成功確率を上げるんだ

成功の鍵 ②：適材適所

ワンサイズフィットオールは否定

  • ワンサイズフィットオール ではない
  • マネージド offering：Gemini Enterprise 等
  • コンプラ準拠で本番導入しやすい
  • DIY：Kubernetes 上の自由な構築
  • ワークロードごとに使い分ける
便利だからと全部マネージド、もったいないからと全部DIY、どちらも非効率。使い分けが正解！

DIY とマネージドの使い分け

両極端のトレードオフ

  • 全部 DIY → プラットフォーム構築コストが高い
  • 全部 マネージド → 柔軟性に欠ける
  • 結論：ワークロードに合う方をえらぶ
DIY（自由・高コスト） マネージド（楽・固定）
自由が欲しい所はDIY、スピードが欲しい所はマネージド。一枚岩じゃなくてよいのだ

vibe coding の限界と現実

12歳でも作れる時代

  • 12歳の息子でもアプリを作れる時代に
  • でも Salesforce / ERP / HRシステム を置き換えるのは No
  • 安定性・運用負荷の観点で SaaS は残る
  • 店舗固有データを使うチャットボットなど自分専用タスクはDIYが有効
  • 生成されたコードを理解することが重要
$ "いい感じのアプリ作って" → 🎉 動いた！
でも本番ミッションクリティカル？→ 判断は慎重に
作れるのと“運用できる”のは別物。コードを読める子に育てるのが親の役目、だってさ！

安定性 vs 最先端 — 二極化

bifurcation の時代

  • 500人がローン記録を処理する業務ではランダム性は許容されない
  • バックオフィスは安定性（SaaS / 既存システム）重視
  • 顧客向け・適応が必要な部分は最新モデルを追う
  • F1レースカーでスターバックスに行く必要はない
  • 人間は線形は得意だが指数は苦手。2年後のモデルは今が「おもちゃ」に見える（GPT-3.5 を振り返るように）
🏦 安定（バックオフィス） 🚀 最新（顧客向け）
すべてを最先端にする必要はない。用途で使い分ける“二極化”がこれからの標準だよ
