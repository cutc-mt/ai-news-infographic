GPT-6 Astraを使いこなす 6つの方法

〜 設定・スキル・プロンプトで、アプリ開発の結果をぐっと良くする 〜

AI Code King(英語圏チャンネル)の動画を日本語で紹介

2026年9月6日 | 動画の長さ: 12分33秒

GPT-6 Astraは良い仕事ができる一方で、必要以上にコードを書いたり、関係のないスキルを読んで時間を使ったり、 どこにでもあるAI製の見た目のサイトを作ったりすることもある。この動画は「方向付けの工夫」6つをまとめた実践ガイド。

はじめに — この動画が扱うこと

Overview
01

動画の概要

What's this video?

ポイント

  • GPT-6 Astraでアプリ開発するときの、設定・スキル・プロンプトを紹介
  • 作者自身の使い方に基づいた、実践ベースのおすすめ設定
  • 流れ: セットアップ → 推論を上げるタイミング → 出来たアプリのテストと改善
  • 登場ツールの多くはサブチャンネルAIC Kingでも解説済み
Astraは放っておくと暴走気味。
人間側の方向付けで結果が決まる!
02

放っておくと起きる3つの失敗

Why direction matters

あるあるリスト

  • 小さな機能を頼んだのに必要以上のコードが返ってくる
  • 今回の役に立たないスキルを読むことに時間を使う
  • 巨大カード+ランダムなグラデの、どの製品にも似たサイトになる
  • 結論: モデルに任せっ放しにせず、指示を出すのがこの動画の主役
でも大丈夫。このあとの6つの工夫で、全部防げるよ!

方法① Reasoning設定 — 基本はMediumで十分

Reasoning Effort
03

推論設定の基本方針

Start with Medium

作者の使い方

  • 普段はMedium — プランニング(計画)も含めて十分
  • タスク理解 → 計画 → 実装、まで一通りこなせる
  • 高めの設定を既定値にするほどの差は感じなかった
  • まずMediumで始めて、足りない所を確かめるのがおすすめ
高い設定=良い結果、ではない。
自分のタスクで差が出るか見てから!
04

計画を立てさせる前に

Inputs for planning

伝えるべき3要素

  • 何を作るのか
  • 誰のために作るのか
  • 最初の動く版に何が必要か
  • 例: 支出の記録アプリなら「端末内に保存 or 同期」を先に決める

例えるとこんな指示:

個人用の支出記録アプリを作って。
データは端末の中に保存(アカウント同期はなし)。
最初の版は、登録・編集・削除が
動けば十分です。
先に決めることがないと、役に立つ計画は立たない!
05

設定を上げるのは、具体的な問題があるとき

When to go higher

高設定にするタイミング

  • バグ修正が繰り返し失敗するとき
  • 実装の難しい部分が、どうしても良くならないとき
  • その前に、再現手順・エラーメッセージ・試したことを与えてから
  • 解決しない場合のみ高設定へ。同じ材料で比べられる

こんな指示:

フォームは「保存しました」と出るのに、
再読み込みすると古い値に戻ってしまう。
保存のリクエストを追跡して、
新しい値がどこで消えるか特定して。
コードを変える前に、まず問題を再現して。
追加の推論=待ち時間も利用量も増える。
同じ失敗を5回やるのも同じコスト。見合う改善かを比べて。

おまけ — Ponytailで実装をコンパクトに

Keep it minimal
06

Ponytailプラグイン

Simplest solution first

どんな効果?

  • 要件を満たす一番シンプルな解を探すよう促す
  • プロジェクトにすでにあるものを活用。組み込み機能を優先
  • 想像上の将来要件のために作り込まない
  • 必要な検証と例外処理は残す(保存に失敗したとき利用者へ伝える等)
  • 新しい依存は「このアプリの何を解決するか」を説明させてから

設定画面を足す例:

Ponytail を使って実装して。
既存の設定まわりのコードを先に読み、
今の流儀(パターン)に従って、
要件を満たす最小の変更にして。
新しい依存が必要なら理由を説明して。
行数が少ない=速い、ではない!短い関数でも重い検索を呼ぶことはある。速度は⑥で測る。

方法② スキルは「厳選」して使う

Skill Management
07

スキルの読みすぎに注意

Be selective

起きること

  • Astraはスキルを読みたがる。集めすぎると、役に立たない指示の読み込みに時間が消える
  • 指示文はコンテキストを消費する
  • 重複した指示は混乱のもと:「作業を続けろ」vs「計画の相談で止まれ」
  • Codexでは名前と説明から始まり、使うときに詳細が読み込まれる

使い分けの例

  • 画面の作業 → デザイン指示
  • 構造を知りたい → Archify
  • 動いている確認 → ブラウザ試験ツール
08

スキルを絞る指示

Filter the skills

こう伝える

  • 「このタスクに直接役立つスキルだけを使え」
  • 「関連するプロジェクト指示だけ読み、無関係な案内は読み込むな」
  • 予期せず止まるときは「どの指示が原因か」を尋ねる

プロンプト例:

このタスクに直接役立つスキルだけを
使ってください。
関連するプロジェクトの指示を読み、
無関係なガイドは読み込まないで。
直すべきはセットアップ側のルールかも。
プロンプトに段落を足すと、かえって分かりにくくなることも!

方法③ 見た目の指示 — 一番力を入れるところ

Visual Direction
09

「モダンにして」では伝わらない

Close the open decisions

何が起きる?

  • 「モダンな管理画面を作って」→ デザイン判断が全部開いたまま
  • 結果: 巨大カード・ランダムなグラデ・どの製品にも似た画面
  • 顧客に出すアプリでそれは避けたい
  • 目指すのは「製品と使う人について考えた跡」がある画面
大事なのは: 情報が読み取りやすいか・操作の一貫性・画面が小さくなっても壊れないか。
10

視覚リファレンスの渡し方

Show, and tell

手順

  • Dribbbleのスクリーンショット・好きなサイト・自分のデザインを添付
  • 「何が好きか」を言葉で説明する
  • 例: 1枚目のコンパクトな表レイアウトを使え/2枚目の文字と余白を参考にせよ
  • 「色は既存ブランドに寄せる」も有効
  • 「メインの操作が見つけやすいように」も添える

プロンプト例:

1枚目のスクリーンショットの
コンパクトな表レイアウトを使って。
2枚目のタイポグラフィ(文字の扱い)と
余白を参考に。
色は今のブランドに近づけて。
11

リファレンスの注意点と仕上げ

Consistency check

気をつけること

  • 矛盾する参照はNG: 全然違うスタイルを「全部好き」は、結局当てさせることになる
  • 画面の種類を合わせる: 美しい紹介ページ≠100行のデータを扱う管理画面
  • Open Designで主要画面を先に固め、その方向を実装に渡すのも良い
  • Emil Kowalskiスキルも、画面の振る舞いの細部までの指南に役立つ

動き出したら比較させる:

間隔・タイポグラフィ・レイアウトを
スクリーンショットと比較して。
一番大きな違いを直して、
モバイル表示も確認して。
「もっと良くして」を繰り返すより、ずっと具体的!

方法④ Archifyでアーキテクチャ図

Architecture Diagrams
12

実コードを調べてから図を作る

Ground truth first

ポイント

  • プロジェクト全体がどう繋がっているか分からなくなったらArchifyの出番
  • リポジトリを実際に調査させてから図を作らせる(実装を反映した図に)
  • 図に含める: 前端と後端の通信・データの保存先・関わる外部サービス
  • 「検証できなかった点を明示せよ」を忘れずに

プロンプト例:

Archify でこのアプリの構造を
コードに基づいて説明して。
前端と後端がどう通信し、データが
どこに保存され、どの外部サービスが
関わるか示して。
検証できなかった点は明示して。
13

利用者の操作を1つ、端から端まで追う

Follow one user action

例: 支出を保存する

  • どの画面の部品が処理を受け持つか
  • リクエストはどこへ行くか
  • 何がデータベースに書き込むか
  • 更新された情報がどう画面に戻るか
  • 流れを追えると、壊れている場所を指して「そこを調べろ」と指示できる
デバッグの話がぐっと通りやすくなる!
14

引き継ぎと図の更新

Handover & keep it fresh

次の担当者(エージェント)へ

  • 渡すもの: 図 + 重要な決定の短い説明 + 関連コード
  • 理解の出発点になる
  • 構造を変えたら図も更新(保存の仕組みを交換した時など)
  • 図は「コードと繋がったままの文書」として扱う
古い図のままだと、次の担当者が誤った前提で着手しかねない!

方法⑤ Computer Use でライブ試験

Live Testing
15

動いているアプリを、実際に操作させる

Test like a user

やらせること

  • ブラウザ/コンピューターツールで起動中のアプリを開く
  • 試験アカウントでメインの流れを最後まで(絞り込み・編集も含め)
  • 再読み込み後もデータが残るか確認
  • 空のフォーム・無効な値も試す
  • モバイルのレイアウトも確認

プロンプト例:

アプリを開いて、メインの利用者の
流れを最後まで実行して。
再読み込み後にデータが保存されているか、
空フォームと無効な値を試し、
モバイルのレイアウトも確認して。
見つけた問題を直して、
影響のある手順をやり直して。
ビルド成功だけでは分からない!
例: モバイルでボタンが別の要素に隠れる/後端が拒む値をフォームが受け付ける…
16

結果は「報告書」で受け取る

Ask for a report

報告してほしい3点

  • 何を試したか
  • 何が失敗したか
  • 何を確認できなかったか(使えないサービスは「未検証」のまま)
  • 試験の深さは変更の大きさに見合うように(文章修正 ≠ 保存方法の変更)
「実際に観察したこと」を知りたい。確認で問題が出たら、さらに深掘りさせる。

方法⑥ 速さは「測って」直す

Measure Performance
17

測定を明示的に指示する

Measure → Fix → Compare

サイクル

  • 初期の読み込みと一番遅い操作を測定
  • 主なボトルネックを特定
  • 的を絞った修正だけ行う
  • 同じ条件で再測定 → 前後比較を報告

原因によって修正が違う

  • 同じデータの重複リクエスト
  • 大きすぎる画像(小さく足りる場面)
  • 後端の応答が遅い
  • 公平な比較: キャッシュ前後で比べない。十分な回数繰り返す

プロンプト例:

この画面が遅い原因を測定して、
主な原因を直して、
同じ条件で前後を比較して報告して。
(通信・性能の記録・サーバーの
所要時間を確認して)
速くなっても絞り込みが古いデータのままならまだ未完成。影響のある流れを最後にもう一度!

まとめ — 全部組み合わせた実践例

Put it together
18

まとめ — 全部組み合わせた実践例

The all-in-one prompt

組み合わせ

  • 推論はMediumのまま
  • 関係するスクショを添付
  • 既存実装を調査・流儀に従い・Ponytailで最小に
  • ブラウザでPCとモバイル両方試して直す
  • 完了の定義を伝える(下の吹き出し)

6つの方法 ふり返り

① Reasoning+ Ponytail② スキル厳選③ 視覚の指示④ Archify⑤ ライブ試験⑥ 測定

  • まずMediumで始めて、出来上がったアプリを確認。まだ足りなければ、初めて改善すべき具体案が手に入る
  • 方向付けしだいで、Astraはかなり良い相棒になる

メインの指示:

このアプリに「支出の編集」の流れを追加して。
既存の実装を調べて、その流儀に従って。
Ponytail で変更は最小に。
関係するスキルだけ読んで。
フォームのレイアウトと余白は
添付の参照画面に従って。
利用者が支出を編集・保存し、
再読み込み後に新しい値が見えること。
保存に失敗したら役立つメッセージを。
PCとモバイルの両方で試して、
失敗を直して。

遅いときは別件で:

この画面が遅い原因を測定して、
主な原因を直して、
同じ条件で結果を比較して。
完了条件の例:「ローカルで実装して検証するまで。細かい判断は合理的に決めて、前提を報告して。結果が大きく変わる質問だけ、私に尋ねて。」
