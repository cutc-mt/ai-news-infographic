その1：GPT-6 Astra で「変わった癖」と対策

01

確認を求めてくる癖

いちばん大きな変化はここ

  • 以前なら勝手に進めていた場面でも、その一歩手前で確認を求めてくるように
  • いわゆる証人待ち（確認待ち）が増える挙動
  • 対策としてAGENTS.mdなど各所に「自立的に動いて」と明示するのが定番
ひと呼吸おいてから動く感じ、
じつは書き方しだいで直せるよ！
02

AGENTS.md の指示追従

「1分で止まる」問題への対処

  • 書いてあると1分で止まってしまう指示の追従が強く出る場面がある
  • 矛盾の除去と、よけいな記述を削って整理しよう
  • Fable 発表時にも「見直そう」という話があったのと同じ流れ
  • コンパクションまわりの記述があれば、そこも調整が必要
矛盾があるとモデルが迷子になる。
きれいにしてから使うのがコツ ✓
03

スキルと優先順位

追従が強い分、階層を明示

  • スキル・AGENTS.md への追従が強め。だから優先順位をはっきり書く
  • ユーザーの指示はスキルの指針より優先すると明記するのがおすすめ
  • 迷いが出る箇所は、あらかじめ順位づけしておくと安心
「誰の言うことを聞く？」
を先に決めておく感じかな
04

質問がきても止まらない

裏で回しつづける技

  • 質問がきても作業が止まらないように設計できる
  • サブエージェントで裏側を走らせるのは Fable でも体験済みのパターン
  • 回答待ちの間に、答えに依存しない部分を先に進める
  • ほどよく質問してくれるので、待ち時間もむだにならない
聞きながら、進める。
二刀流みたいな動き方 🌀
05

コンパクション → ノート

内部の仕組みが変わった

  • コンパクションの部分がノートに置きかわっていく
  • コンパクション前提で書いていた部分は調節が必要
  • 停止条件と再開条件を見直すのが重要（いまは切捨て式らしい）
  • 今後さらに変わっていきそうなので、要ウォッチ
「ここで休む・ここから再開」
の目印を書いておこう 📌

その2：公式ガイドが教える「書き方」

06

コピペOKの公式文面

そのまま使える一文

  • 公式ドキュメントにコピーできる文章が掲載されている
  • 意図と範囲を推測して行動し、目標が終わるまで続ける方向の一文
  • 質問する前に、すでに許可されている作業を終わらせてレビューできる形にする
  • 動画の概要欄に公式ガイドへのリンクあり
# 公式ガイドの文面イメージ
意図と範囲を推測して行動し、
目標が終わるまで続けよ。
質問する前に、既に許可された
作業を終わらせ、レビューできる
形にせよ。
「推測してよし」と
一言添えるだけで動きが変わる ✨
07

おもしろい公式の一文

デバッグ用の切り札

  • 「できることは作業指示として扱う」という一文が公式にある
  • スキルのせいで止まる時は読んだスキルを要約して該当の一文を引用せよ
  • なぜ止まったかのデバッグ用として使える発想
「なんで止まったの？」を
自分で説明させるのが面白い！
08

リストとマークダウン

出力の形をコントロール

  • リスト表が多すぎる場合は、段落を基準にした書き方へ
  • 禁止語を列挙しておくのも一つの手
  • リストは本当に必要な時だけ使うのが公式の考え方
  • 専門語をつらつら書かず、やさしい言葉で。技術の詳細は必要な部分だけ
箇条書きだらけの回答、
ちょっと食傷気味かも…？
09

サブエージェント活用

並列化の指示を書こう

  • 期待よりサブエージェントの呼び出しが少ないときがある
  • 並列化できるならちゃんと任せる、と書いておくのが大事
  • ただし無理に並列化しなくてもOK。最近のモデルは単独でもうまい
  • まさおさん: 時間か質が上がるなら並列化、と自分の運用にも書いている
エージェント一人でも
強いのが OP 系のいいところ 👍
10

テストの書きすぎ注意

範囲より広いテストを防ぐ

  • 一致直すのに10分のテストを回してしまうことがある
  • 影響の小さい変更にテストを書くなと AGENTS.md などへ書くのが有効
  • 本当に必要なテストだけ書く、というニュアンスで公式ガイドにも記載
  • 検証の重さもリスクで分けるのがよいパターン
ちいさな直しに大きな試験は
つり合わない、という話 ⚖️
11

AIスロップ対策

文章のくせを直す

  • AIスロップ語（英語圏で問題になっている言葉づかい）を避ける
  • 例: 菊切り・手当てなどの語は一般的でない → 影響が出る・対応方法に言いかえ
  • スロップ検知をフックで仕掛ける方法もある
  • スクリプトで一括バリデーションする手も。まさおさんも対策を作成中
人が読んで自然か。
これが一番の物差し 📏
12

報告も人が読む前提で

出力の質につながる心得

  • エージェント間のメッセージも人が読む前提で書く、と明示する
  • 人が読まない前提で書いていると、最後の出力まで人が読まないものになりがち
  • 「見られる」ことを意識すると文章の質が上がる
途中経過もきれいに、
だと最後もきれい、かも ✉️

その3：価格・エフォート・運用のコツ

13

ベース価格は高め

Artificial Analysis の比較

  • Artificial Analysis のコスト比較で、Sol より Astra は高い
  • Fable よりは効率が良い（スマートでトークン効率も良い）
  • サブスクの枠は溶けていく。Sol 利用より消費が早い
  • ファストモードだとさらに溶けやすいので注意
「Fable より安い」だけで、
じつは高め、という立ち位置 🍷
14

$20プランの生存術

枠が消えやすいときの使い分け

  • 20ドルプランだと Astra で速攻で枠が消える可能性も
  • エフォートを調節して消費をおさえる
  • できることは Sol・Luna に任せる使い分けが大事
  • API で使うと結構もつ、という声も
使い分けの図
  • Astra: 最後の仕上げ・高い描写力が欲しい時
  • Sol / Luna: 日常的な処理はこちらで
全部 Astra にしない。 適材適所が鍵 🔑
15

エフォートの選び方

Low / Medium / High / XHigh

  • 規定はミディアム。難しい所だけハイに引き上げる
  • ローでも十分賢い。輪郭がしっかり決まる・点を打つ所がうまい
  • リッチな結果が欲しい時は High / XHigh
  • 状態管理・リトライが絡む処理はハイで
  • アプリ組込み・速度重視ならロー採用例も海外で話題
難問を解く最初の直感、
ローがなんかいい感じらしい 🧠
16

リスク階層で書く

AGENTS.md とシステムプロンプト

  • 低リスクは勝手に進め、影響の大きいものは先に聞けと書く（まさおさんなら AGENTS.md 派）
  • 情報源の優先順位も明示して順位づけ
  • 賢いモデル前提でも「優先順位」は曖昧になりがち → 察しづらい物は明示へ
  • 再現しづらい挙動はミクロ部分で効いてくるので、書いておくと安心
# リスク階層の書き方イメージ
低リスク → 勝手に進めてよい
影響大   → 先に確認せよ
情報源   → 公式 > 記事 > 推測
信号を先に決めておくと、
モデルが迷わないんだ 🚦
17

マネージャーループ

長い作業の回し方

  • 長い時間の作業はループで回す設計がおすすめ（公式の記述より）
  • チェックを作成 → フェーズに分割 → 実装役のサブエージェントへ1個渡す
  • 完了の報告を受けて、次のフェーズへ。この繰り返しが長時間に効く
  • /goal などと合わせると、すぐ始められるパターンに
ちまちま確認、こまめに報告。
長丁場はこの形が安定 🔁
18

総まとめ

得意分野と今後の注目点

  • SVG・Blender の描写力が非常に高い。デモでも再現済み（素材・イラスト作成例も続々）
  • Fable に近い使用体験で、よりスマートに問題解決。ただし Humanity's Last Exam で負ける場面も
  • Codex は大量に使える（リセットあり）。Fable を大量に課金している組には嬉しい変更点
  • API 仕様の変更点は公式のマイグレーション案内を活用。カットオフは2026年4月末
  • まさおさんは Fable・Claude ハーネスから Codex を呼ぶ形で継続予定
ハーネスの作り込みは課題、
でも「めっちゃええモデル」 🍇
