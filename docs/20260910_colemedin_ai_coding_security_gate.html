AIコーディングのセキュリティ

📅 2026.09.10 ／ 🎥 動画 17:45 ／ 🛡️ 実演つきのワークフロー解説
本命は 決定的なゲート（deterministic gates）

Phase 1：速さの裏で、どこで落ちるのか

01

速い。でもセキュリティで落ちる

売りは速さ、弱点は安全
  • AIコーディングの支援はとにかく速い
  • 読み比べると、いちばん弱いのはセキュリティ
  • 使い回し・ドキュメント・パフォーマンスより先に落ちる
  • AIが書いたコードの怖い話はあとを絶たない
コール：速いだけで選ぶと、怖い話の主役になるんです。
02

混入する入り口は2つ

コードか、ライブラリか
  • 入り口①：エージェントが直に脆弱なコードを書く
  • 入り口②：CVE持ちのサードパーティ製ライブラリを入れてしまう
  • どちらも気づきにくいのがやっかい
入り口は2つ。でも中身はぜんぶ「人の目が届かない」ことから始まるのよ。
03

入り口①：直に書き込まれる

SQLインジェクションのような典型
  • クエリを文字列の連結で済ませてしまう
  • 動けばOKで、穴のある書き方がそのまま通る
  • 昔からある典型的な穴が、新鮮な顔で入ってくる
# NG: 文字列を直にくっつけただけ
q = "SELECT * FROM users
     WHERE name='" + name + "'"
# → 動くのに、穴が開いている
動くコードと、安全なコードは別ものなのだ。
04

入り口②：CVE持ちのライブラリ

入れるだけでリスクが増える
  • エージェントが勝手にパッケージを追加する
  • その奥に既知のCVEが眠っていたら…
  • 入れた本人すら把握しないまま増えていく
$ pip install some-old-lib
# → 依存の奥に CVE つきが
#   こっそり連れてこられる
誰が選んだか分からない荷物が、勝手に部屋に増えるのよ。
05

サブ依存の連鎖が見えない

トップレベルしか見ていない
  • エージェントが確認するのは直近の依存まで
  • その奥のサブ依存のチェーンまでは追えない
  • CVEはその深いところにこそ潜む
木のてっぺんだけ見て、根っこを確認していない状態なのよ。
06

CVEリストは大きすぎる

コンテキストに載りきらない
  • CVEの数は膨大で、まだ増え続けている
  • LLMのコンテキストには載りきらない
  • 知らないものは、そのまま見逃される
全部覚えて判定するのは、もう人間にも無理なのだ。
07

速さ優先で手を抜く

学習データにも脆弱なコード
  • LLMは速く出す方向に倒れている
  • 学習データ自体に、人が書いた脆弱なコードが混ざる
  • 「ここは省略」が、そのままコーナーカットにつながる
「早く出す練習」をしてきたモデルに、安全を丸ごと任せちゃダメなのよ。

Phase 2：静かなパターンと、効かない解

08

静かに混入するパターン

気づいていても、直さない
  • エージェントは穴に気づいていることもある
  • でも直さず、PRの説明に「後で対応」と書くだけ
  • そのまま混入して終わる
コール：気づいてた、がいちばんタチ悪いんですよね…。
09

誘われる解：プロンプトの関所

PRのあとに別エージェントで審査
  • 実装のあと、レビュー用エージェントを通す
  • 確かに、それなりには機能する
  • でも判定は確率的。外れるときは外れる
「安全を確認して」とプロンプトでお願いする方式ね。
10

なぜ見逃すのか

同じ穴を、同じ目で見る
  • 実装側が見逃したものを、審査側も見逃す
  • 両者は同じ土台のLLM
  • 「たぶん大丈夫」で通ってしまう
片方が直せないものを、もう片方も直せない。なら、違う仕掛けが要るのよ。

Phase 3：本命解 決定的なゲート

11

決定的なゲートとは

プロンプトの関所 お願いして審査する
確率的・同じ盲点
決定的なゲート スクリプトが関所を固める
決定的・赤は通さない
  • 赤なら通さない。緑だけ通す
  • 判断をコードに任せる。確率に任せない
「お願い」を「関所」に変えるのが、今回の肝なのよ。
12

Archon で組む

同じ著者のOSSハーネスビルダー
  • Archon でワークフローを組み立てる
  • ノードをつなげて流れを作る
  • 中で動かすエージェントは好きに選べる
コール自作のビルダー。Claude Code なども組み込めるのよ。
13

SonarQube で検査

SonarQube Cloud でスキャン
  • コードを静的に検査して穴を拾う
  • 判定は赤か緑かではっきり返る
  • セキュリティの評価（A〜）も出る
判定を下すのはツール。エージェントの気分じゃないのよ。
14

bashノードからAPIを呼ぶ

エージェントじゃなく、スクリプトが保証
  • bashノードから SonarQube API を叩く
  • 赤ならPRを作らせない
  • 実装エージェントに直しに戻す
# bashノード（抜粋）
curl -s "$SQ_URL/api/qualitygates/\
project_status?projectKey=$REPO" \
 | jq -e '.projectStatus.status=="OK"'
# 赤 → ノード失敗 → 修正へ戻る
関所はbash。プロンプトに一文字も頼っていないのよ。
15

赤なら戻すループ

全部緑になるまで続く
  • スキャン → 赤が出る
  • エージェントが修正
  • 再スキャン
  • 全緑で、ようやくPR作成
人が見なくても、緑になるまで出られないループなのよ。

Phase 4：実演と、自分の流れへの入れ方

16

実演：3つの脆弱性

検出 → 修正 → 評価A → PR
  • 直書きのパスワードなど3件を検出
  • エージェントが修正
  • 再スキャンで全緑・評価A
  • その後、はじめてPR
実際に動くところを、動画でそのまま見せてくれるのだ。
17

全体の流れ

GitHub issue から全緑まで
  • issue → 分類 → 計画
  • 実装 → PR
  • Sonarスキャン → 修正
  • 再スキャン → 全緑で完了
どのエージェントでも組める「型」として配っているのよ。
18

まとめ：guide, verify, solve

Sonar のマントラ
  • guide：エージェントを導く
  • verify：スキャンで確かめる
  • solve：赤を直して、緑にする
  • Claude Code などどんなエージェントにも転用できる
コール：セキュリティは「速さ」の隣じゃなく、「関所」に置く。それが答えです。
