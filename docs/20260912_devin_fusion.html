04
核心

リードとサイドキック

リード（親・強い） サイドキック（子・安い）
  • リードが新鮮なコンテキストを渡す
  • サイドキックはそれをもとに、実際の仕事をどんどんこなす
  • 見た目はサブエージェントと同じ。でも中身が違う
強い親 + 安い子の
シンプルな2枚看板だね 親子セット
05
役割分担

渡すのは「ブリーフ」だけ

  • リード: 計画、曖昧な部分の解釈、レビュー
  • サイドキック: 探索、実験、テスト
  • 渡すのは制約と完了の条件つき指示書＋結果のフィードバック
  • 会話は渡さない! 何でもかんでも渡さない
brief = {
  goal: "この機能を直す",
  constraints: [...],   // 制約
  done: "全テストが通る", // 完了の条件
  edge_cases: [...],    // 境界ケース
}
// 会話の履歴は渡さない!
余計な文脈を渡さないから
子が溺れずに動ける!
06
構成

コストは下げて、点数はキープ

Fable（親） + SWE-2（子）
  • 親にFable、子にSWE-2という組み合わせ
  • コストはしっかり下がるのに、スコアはほぼキープ
  • Astra + SWE-2だと落ち幅が出てしまう、という比較も
「安くしたのに点数が落ちない」
が今回の売り文句!
前史: スマートフレンドの教訓
07
前史

スマートフレンドとは

弱い主役 賢い相談役
  • Cognitionが以前出した設計: 安い主役がふだんの仕事を担当
  • 困った時だけ、強いモデルにアドバイスをもらいに行く
  • Claude Codeのアドバイザー機能も同じ形式と言われる
「安い子が主役、強い先生は呼ぶだけ」
発想はとても美しい…
08
弱点

弱い主役のジレンマ

  • 弱いモデルは自分の弱さが分からない
  • つまりいつ聞きに行くべきかが判断できない
  • 「その判断力を訓練で鍛える」方向も検討された
「分からない時に分からない」と
気づけないのが一番つらい… メタ認知の壁
09
課題

横のつながりの問題

  • 並走する別の子に、発見が届かない問題
  • 受け手に全コンテキストを渡すと、溺れてしまう
  • SWE 1.5の時代から指摘され、1.6でも未解決だった老課題
渡しすぎても溺れ、
渡さなさすぎても伝わらない。
コンテキストのさじ加減が肝!
10
転換点

主役の交代

弱い主役（訓練で鍛える） 強い主役が安い子を使う
  • 方向転換: 強いモデルを主役に据え直す
  • 計画や曖昧さの解釈、レビューを強い側に任せる
  • 制約と完了の条件を渡して、実行はサイドキックへ
訓練で直すより
「構図を逆に」で解決! 目からうろこ
数字で見るFusion
11
検証

Opus → Fableで総額9%減

  • リードをOpusからFableに変えたら、総額9%ダウン
  • 単価はOpusのはずなのになぜ? → 動き方が違った
  • Opusは口出しが過剰気味。Fableは本来のマネージャーっぽい振る舞い
  • ターン数も無駄が少なく、トークンもスマート（5 vs 4.8の比較）
「単価の安さ」より
「任せ方の上手さ」が総額を決める!
12
検証

スコアも負けていない

  • Frontier Code 1.1での比較で、Opus 4.8よりFableが高得点
  • 1タスクあたりのコストも低下
  • リードの入力トークンもスマートに
  • 安いのに賢く解く → 結果として総額も安い、という構図
点数もコストもターン数も
いいとこ取り! 三拍子
13
検証

サイドキックも「強い方が安い」

  • 単価の比較: GPT-5.6 Luna ≒ 0.2 vs SWE-2 ≒ 0.75
  • それでもFrontier Codeのスコアと1タスクのコストはSWE-2が優位
  • 安い子が手数で迷子になるより、賢い子が一発で決めた方が結果的に安い
単価の安さ ≠ 総額の安さ
「解決力」が効いてくる!
さっそく使ってみる

  • 解説者のおすすめリードはFable一択
設定はたったこれだけ。

実戦

  • 子側も色々なモデルから選べる構成
  • 解説者の選択はSWE-2 (M または High)
  • Devin CLIからも、もう早速 使える
  • Devin契約だとSWEが無料枠で使える点も魅力
CLI勢も今日からFusion!
無料枠なら試さない理由がない
16
注意

読み方の注意点

  • 難しめの課題では、まだスコアが微妙な場面も
  • 数値はあくまでDevinの自社測定
  • Claude Codeとは設定が違うため、単純比較は禁物

数字の条件を確認してから
自分の環境に持ち込むのが吉!
自作ハーネスへの教訓
17
設計指針

相談ではなく「任せる」

  • 弱い主役が聞きに行く形はやめて、任せる形へ組み換え
  • 会話は渡さず、制約・境界ケース・完了の定義だけ書いて渡す
  • 弱いモデルのメタ認知に頼らない。計画に効く探索はメインで担当
  • ディベート・評価・反論は強いモデルで行う。弱い子には反論させない
// フレッシュな子への渡し方
delegate({
  brief: [制約, 境界ケース, 完了の定義],
  history: null,        // 会話は渡さない
  planner: "強い側で計画",
  executor: "安い側で実行",
});
自作ハーネスにも
そのまま持ち帰れる指針! 設計の教科書
18
まとめ

本質はシンプル

高いモデル = 計画・評価 + 安いモデル = 実行
  • 結局のところ、シンプルなサブエージェント運用の延長線
  • プランナーと評価は高い側、生成は安い側でも試せる使い分け
  • 「任せていく型」のサブエージェントが、いちばんはまりやすいという示唆
  • 兄弟間での情報の渡し方は今回の設計では未着手の論点。今後に注目
強い親と安い子を熔かして
ひとつに。それがFusion! 面倒な取りまとめは親に任せよう
この動画、ひとことで

熔鉱炉に学ぶ、エージェントの任せ方

  • 主役は強い方: 計画・曖昧さの解釈・レビューはFableのような強いモデルに
  • 実行は安い方: 探索・実験・テストはSWE-2のような専用モデルに
  • 渡すのはブリーフだけ: 会話を渡さず、制約と完了の条件で動かす
  • 結果: コスト9%減・スコア維持・ターンもトークンもスマート
自作ハーネスにもすぐ反映できる。
