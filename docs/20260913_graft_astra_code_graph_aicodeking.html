① なぜコードグラフなのか

#01

エージェントの「毎回探索」問題

あるある風景

  • プロジェクトを開いて小さな修正をお願いするだけ…
  • エージェントは数分かけてファイル検索とimport の読み解きを繰り返す
  • 次のタスクでも同じ探索をやり直し…トークンが溶けていく
「つながり」を毎回ゼロから調べるのが、もったいない!
#02

GRAFT がやること

コードグラフ構築OSS

  • ソースコードを読んで関数やimportを記録
  • それらのつながり(呼び出し関係)をグラフ化
  • 「どこで実装?」「この関数を誰が呼ぶ?」をクエリで即答
  • エージェントが理解を始める時の出発点が良くなる
「単語検索で1件ヒット」より「関係ごと取ってくる」方が、 修正の見落としが減るんだよね
#03

2つのレイヤー構造

ここ大事な区別

  • 基本ビルド: tree-sitter でコード構造を解析。AIのAPIキーは不要!
  • deep ビルド(任意): AIが書いたサマリーと概念ノードを追加
  • deep 層は設定したプロバイダ利用なのでAPIコスト発生あり
  • 今回は構造レイヤーだけで全て再現可能
「グラフのクエリが無料」=「コーディングエージェント自身が無料」では ないよ。モデルの利用料は別かかり!
#04

ライセンスと運用

気軽に試せる設計

  • MIT ライセンスのオープンソース
  • 別途のDBサーバーは不要。生成物は .graft/ フォルダ内に
  • ビルド時にフォルダをgitignore に自動追加(コードから再生成できるから)
# セットアップ(動画では v0.18.0 / node 22)
npx @nanonets/graft  # node 20+ が必要
生成物はいつでも作り直せる。だからリポジトリには置かない、という思想

② Verdent エージェントで実演

#05

Verdent の基本ワークフロー

今回の舞台

  • プロジェクトのフォルダを開きタスク作成→やりたいことを記述
  • ファイル検査・編集・コマンド実行まで進捗つきで表示
  • プランモードやモデル選択も装備
  • 編集後は差分ビューとレビュー機能で変更を確認
  • 大きい仕事はマネージャーがサブタスク化してワーカーへ分配
同じワークスペースのタスクはファイルを共有。隔離じゃないから注意!
#06

接続は CLI で( MCP もあり)

統合の選び方

  • GRAFTには今のところVerdent専用の登録はなし
  • 実演では Verdent に CLI を実行させる方式
  • GRAFT の MCP サーバーも存在(今回は未使用)
  • テレメトリはデモ用にオフに設定
# 動画内の流れ
1. node のバージョン確認
2. graft をローカルにインストール
3. ツール用フォルダでバージョン固定
正確なコマンド一式は補足ノートにまとめてあるよ
#07

お題: ドキュメントサービスの権限バグ

わざと仕込んだ不具合

  • 登場人物: owner / editor / viewer / 無関係ユーザー
  • viewer は共有文書を読める(これは正しい挙動)
  • CSV のexport は editor 以上のはずなのに…viewer に成功してしまう
viewer の export
が成功(バグ)
読むだけは

合成データでローカル実行。本番アカウントは関係なしの安全な例
#08

ベースラインのテスト

修正前の状態

  • テストは 9 個、うち 8 パス・1 失敗
  • 失敗内容: viewer の export が 403 ではなく 200 を返す
  • サンプルを直接叩いても同じ挙動を確認(読む○・編集×・export○)

③ graft コマンドで調査する

#09

graft build でグラフ構築

最初の一步

  • リポジトリ内で graft build を実行
  • この手順ではプロバイダキー不要
  • 結果: 29 ノード・66 エッジ(9 個の JS ファイル・テスト込み)
  • ※小さい題材の数字なのでスケール比較ではないよ
$ graft build
✓ 9 files indexed
✓ 29 nodes / 66 edges
構造レイヤーだけでここまで動くのが便利!
#10

graft map で全体像と質問

概要をつかむ

  • graft map でコードベースの見取り図を取得
  • 「export の権限はどこでチェック?」と質問 → --source フラグ付き
  • 結果: exportDocument 関数 / 権限ヘルパー / ルートハンドラ / 文書ロード関数
  • 検索は決定的な取得。追加のモデル呼び出しゼロ
ソースを渡すのが GRAFT、読んで正しいか考えるのは Verdent の仕事
#11

graft skeleton でAPIの輪郭

シグネチャ一覧

  • 権限ファイルに graft skeleton を実行
  • 出るもの: checkRole / read / edit / export の各判定シグネチャ
  • 本文を会話に流し込まないのでコンテキスト節約
# permissions.js の skeleton
canRead(user, doc)
canEdit(user, doc)
canExport(user, doc)   // owner/editor のみ許可
ファイルのAPIがパッと見える。中身は必要な時だけ読めばいい
#12

callers 追跡でバグ発見

決定打となった問い

  • 「exportDocument を呼ぶのは?」深さ2で追跡 → ルート→デモ/テスト
  • 同じ問いを権限ヘルパーに…呼び出し元がテストだけ!
  • つまりポリシーは存在し試験も通るのに、本筋の経路が未使用
canExport の callers:
  - tests/permissions.test.js  ✓
  - services/export.js        ✗ 呼んでない!
ヘルパー単体の試験が合格でも、使われなければ機能は壊れたまま

④ 直して、確かめる

#13

原因のたどり着き方

読み取り権限だけ通ってしまう

  • export サービスは読み取り判定つきの関数で文書を取得
  • viewer は読み取り可なのでそのチェックは通過
  • そのままより厳しい export 権限を確認せず CSV 化 → 失敗テストと欠けた接続の両方を説明
「読める」権限と「書き出せる」権限を混ぜたのが根本原因だった
#14

修正は小さく・鮮やかに

エージェントへの指示

  • 権限ヘルパーを import
  • エラー型も読み込む
  • export 不可ならリクエストを拒否
  • 既存テストは一切いじらない
// services/export.js への修正イメージ
import { canExport } from './permissions';
import { ForbiddenError } from './errors';

if (!canExport(user, doc)) {
  throw new ForbiddenError();
}
方針が明確なら、修正 diff は本当に数行で済んだ
#15

graft check と自動リフレッシュ

編集後の再構築が楽

  • 編集後に graft check → 古い(stale)と判定・変更ファイルを特定
  • 再質問すると1 ファイル変更を検知して自動リフレッシュ、新しい権限チェックがソースに現れる
  • canExport の callers にexportDocument が新登場(修正前に無かった接続!)
  • 追いかけの鮮度チェックはcurrent(最新)と報告
コミット前の編集でも反映されたよ。別コピーで追試しても同じ挙動
#16

テスト再実行: 9/9 合格

ふたたび走らせる

  • 全 9 テスト合格(8 → 9 に改善)
  • viewer の export は 403 に。editor は今どおり export 成功
  • viewer の読み取り権限は温存(望んだ挙動を壊さない)
  • グラフは接続発見に役立ち、試験が挙動を保証。両方残すのが正解
Tests: 9 passed, 9 total   // ← 8 passed から改善
viewer  export → 403 Forbidden
「新しい呼び出しがグラフに載った」だけでは実装の正しさの証明にはならない。あくまで組で検証!

⑤ 可視化・限界・そして費用

#17

インタラクティブ可視化と限界

見て、触って、知る

  • グラフを書き出して Verdent のブラウザパネルで表示
  • グラフ⇔ファイル輪郭の切替、関数を選ぶと依存の双方向を確認(修正前後の両方を同梱)

静的解析の限界

  • 動的な挙動は苦手。言語別の対応深度にも差がある
  • 結果があいまいなら自分の目でコード確認を
  • 自動リフレッシュは構造のみ。有償AIサマリーは都度再生成しない
  • 更新失敗時は既存グラフへフォールバック。通知を見逃さないで
  • deep 層は本当に生成されたかを要確認(成功表示だけでは不足)
便利な文脈であって、万能の真実ではない。使いどころを選ぼう
