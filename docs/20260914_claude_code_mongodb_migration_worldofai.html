① 実データベースへの委任

序盤: イントロ
  • 数万件の顧客レコードを抱える稼働中アプリの制御をClaude Codeに委任 — ルールは「何も壊すな」の1つだけ
  • 既存システムの理解、データ設計のやり直し、全顧客の移行、アプリ更新、喪失ゼロの証明まで一気通貫で実行
  • MongoDB提供のAgent SkillsとMCP Serverでワークフローを2段階アップグレード（MongoDBスポンサー動画）
理解 再設計 移行 証明
本番さながらのDBをAIに任せてしまうんだ…！こわいけどワクワクする挑戦！

② スキルとMCPの役割分担

序盤: 2つのアップグレード
  • MongoDB Agent Skills — MongoDB専門のエンジニアリング指針を与える「プレイブック」
  • MongoDB MCP Server — デプロイを検査・操作する制御付きアクセス、いわば「目と手」
  • Claudeがワークフローを調整する構図はそのまま、重要ステップは人間が承認
スキル＝知識 MCP＝実操作 安全な委任
「プレイブック」と「目と手」の分担、なるほどって感じ！頭と体が分かれてる！

③ Northstarのシナリオ

序盤: 課題設定
  • 大規模ECマーケットプレイスのプラットフォームチームを想定 — 製品の進化で顧客データがコレクション間に分散
  • インポートによる名前・メールの不整合、古いビジネスルールが残した非対応ステータスが蓄積
  • Northstarがその状況を合成データで再現 — 顧客モデル移行・問題解決・アプリ継続動作を要求
データ分散 不整合 移行課題
実際の現場で起こりそうなデータのぐちゃぐちゃ感、よく再現してるなあ！

④ レガシー顧客モデルの問題

序盤: 現状分析
  • 顧客プロファイルには本人情報・住所・連絡設定・注文サマリーが常にまとめて必要
  • レガシー版はこの一体のデータを3つの顧客コレクションに分散 — アプリは注文コレクションも参照
  • 目指すはCustomer 360 — よりクリーンな統合顧客体験への再設計
3コレクション分散 統合ドキュメントへ
一緒に読むことが多いデータは、一緒に置くべき…設計の基本だね！

⑤ 24個のエッジケース

序盤: 合格条件
  • 移行には意図的に仕込まれた24件のエッジケースが待ち受ける — 不規則な名前の空白、大文字メールアドレス
  • 新モデルが認識しない古いVIPステータスも混入
  • 合格条件は移行元と先の一致・全ドキュメントのルール準拠・アプリの継続動作
一致 準拠 動作 合格
わざと罠を仕込んでるのが良いテストになってる！単純な移植じゃ勝てない…！

⑥ セットアップ手順

序盤〜中盤: 導入
  • Claude Code内の/pluginコマンドまたはNPXスキルコマンドでMongoDB Agent Skillsをインストール
  • MCP設定ファイルにMongoDB接続文字列を貼り付け、MCP Serverを追加
  • 動画ではローカルMCPを使用も、AtlasマネージドMCP（リモート完全ホスト型）も登場 — サーバー運用不要でAtlasに接続
/plugin または NPX skillコマンド
→ MongoDB Agent Skills導入
MCP設定に接続文字列を追記
導入自体はコマンドひとつで済むんだ！ハードル低くていいなあ。

⑦ 読み取り専用での偵察

中盤: 安全策
  • まずMCP接続の有効性と公式スキルの認識を確認
  • この段階のMCPサーバーは意図的に読み取り専用モード — スキーマ・インデックス・件数・ドキュメントの検査のみ可能
  • 書き込みツールはまだ登録すらされていない — 段階的な権限昇格の設計
接続確認 読み取り専用偵察 後から書き込み許可
最初から全部の権限を渡さない設計がこのワークフローの肝だね！

⑧ スキーマ設計スキルで分析

中盤: 問題の両面を調査
  • スキーマ設計スキルで問題の両面を分析 — 「MongoDBに何が入っているか」と「アプリがどう読むか」
  • 後者が重要: コレクション名だけではモデルを決められず、実アクセスパターンにスキーマを合わせるべき
  • 発見: 1万件の住所・1万件の設定・約5万件の注文 — 住所と設定は常に顧客と一緒に読まれ、注文履歴は無限に成長
格納データ 読み取り方 最適モデル
「どう保存するか」より「どう読むか」から決めるの、DB設計の王道だね！

⑨ 埋め込みと参照の推奨

中盤: 推奨アーキテクチャ
  • 重要な推奨: 全部を1つの巨大ドキュメントに入れないこと
  • 一緒に読むことが多い有界な情報は埋め込み（Embed）、成長し続ける注文履歴は参照で保持
  • 不整合なレガシーフィールドと、新アクセスパターンが必要とするインデックスも検出
埋め込み＝いつも読むもの 参照＝伸び続けるもの
巨大ドキュメント地獄を避ける判断、エージェントがちゃんとできてる！

⑩ レビュー用の移行計画

中盤: 計画フェーズ
  • 書き込みを実行する前に、まずレビュー可能な移行計画を作成 — 元のIDを保持し明示的なスキーマバージョンを追加
  • 氏名と連絡先を明確なオブジェクトに分離、住所と設定を埋め込み、注文集計を保存 — 元の注文は専用コレクションに残置
  • 検証ルールも計画に定義: ID一致・件数・重複なし・許可ステータスのみ・メール正規化・24警告の保全・インデックス
計画を作る 人間がレビュー 実行へ
いきなり動かさず計画書を先に出させるの、エージェント運用の鉄則！

⑪ 元コレクション無変更

中盤: 安全設計
  • 重要な設計: 古いコレクションは一切変更しない — 移行先は新しいcustomers_v2コレクションのみ
  • カットオーバーはアプリ側の変更なので、ロールバックはレガシーモードに戻すだけ
  • 作成された詳細計画を確認し「妥当」と判断してから次の段階へ
元を温存 新コレクションへ移行 駄目なら差し戻し
元データが無事ならいつでも引き返せる！安心設計は大事…！

⑫ 書き込み権限の段階的付与

中盤: 可視の安全キー
  • これは本番データではなく分離デモへの書き込みのみ許可 — 可視の安全キーとして段階的に解放
  • 作成・更新操作のみ有効化し、MCP削除カテゴリとAtlas管理ツールは無効のまま
  • 権限を得ても指示により操作ごとに正確な説明と承認待ちが必須
  • 実際のオンライン移行ならバックアップ・デュアルライト・CDC・ローリングカットオーバー・監視も必要と明示
読み取り専用 作成・更新のみ 承認付き実行
削除ツールは最後まで渡さない！権限の渡し方って本当に設計なんだね。

⑬ サーバーサイド集計で移行

中盤〜後半: 実行フェーズ
  • 数万件のドキュメントをモデルに読み込んで1件ずつ書き換えるのではなく、サーバーサイド集計パイプラインを構築
  • MongoDBが配置内で結合と変換を実行し、結果をcustomers_v2へマージ書き込み
  • 役割分担が重要: LLMは計画と指揮、MongoDBがバルク処理 — 期待件数10,000件を確認しレガシーコレクションは無変更
LLM＝設計・指揮 DB＝バルク実行 高速移行
モデルが1件ずつ書き換える想像してたけど、賢い！得意なことにだけ集中させる！

⑭ MCPが暴く24件の警告

後半: データの真実
  • 件数一致だけでは移行の正しさは証明されない — MCPサーバーできれいなデモが隠していた情報を表示
  • 24件の移行元レコードに大文字メールアドレス・不整合な空白・VIP customerステータスを発見
  • 安易にドロップすればターゲットはきれいになるが実情報を喪失 — 他のデータは非エッジケースと同一のまま保全
件数一致 完璧の証明 中身の検証が必要
見た目きれいでも中身が欠けてたら意味ないもんね…！MCPの目、頼りになる！

⑮ アプリ側のリファクタリング

後半: DB移行は半分
  • DB移行は仕事の半分 — アプリは旧モデルのままなので顧客リポジトリをリファクタへ
  • 意味のある変更は小さい: リクエスト時に都度結合していたのをv2顧客ドキュメントを読む方式に変更 — ダッシュボードAPI契約は無変更
  • アプリを再読み込みするとスキーマv2で稼働 — 10,000件の顧客を表示し、24件の警告は消されるのではなくレビュー対象として保全
旧モデル参照 v2参照へ APIはそのまま
API契約を変えずに中身だけ入れ替えるの、プロの仕事っぽい…！

⑯ 独立検証で全合格

後半: 検証フェーズ
  • 移行とは別に独立した検証を実行 — 移行元と先の件数比較、欠落IDの検索
  • 全不変条件で合格: 10,000対10,000・欠落IDゼロ・重複顧客番号ゼロ・全警告保全・アプリ稼働中
  • Claudeは見事にミッションを完遂 — 「何も壊さない」ルールを守り切った
件数 欠落0 重複0 合格
欠落も重複もゼロって、地味だけど一番嬉しい結果！お見事！

⑰ 実測ベースの最適化検証

後半: パフォーマンス
  • 実測された最適化エビデンスを使用 — 公式クエリオプティマイザースキルとMCPを活用
  • 新しい連絡先メールインデックスに対する実際の検索を確認 — 出力からインデックス使用を確認
  • 劇的な高速化倍率を捏造せず、実証を出す誠実な姿勢 — 新インデックス不要と判明し、レガシー経路より速いとは主張しない理由も説明
実測エビデンス 誇張しない結論

⑱ なぜ成功したのか

結末: まとめ
  • 無制限の制御を渡したわけではなく、制約付きの段階的委任だったからこそ成功 — 調査・設計・移行・リファクタ・検証をDBありきで管理
  • 移行元は不変を維持し、アクセス権は複数段階で切り替え、書き込みには承認を要求、最終結果は独立検証
  • スキル＝専門プレイブックでスキーマ・クエリ判断を改善し、MCP＝推論と実配置の接続で助言から制御可能な行動へ
