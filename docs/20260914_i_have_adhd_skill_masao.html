①i-have-adhdとは: 今話題のSkill

まずは正体から
  • i-have-adhd は、AIエージェントの出力を「結論 first・短文・すぐ動ける形」へ整形する Claude Skill です。
  • 実態はシンプルな SKILL.md で、出力の前提を置き換えるだけで動作します。
  • 名前のインパクトもあって一気にバズり、今週のトレンド入りの話題になりました。
  • 「魔法のテクニック」ではなく、読み手負荷の設計が主役な点が特徴です。
読み込ませる 前提が変わる 出力が即戦闘態勢に
「私にはADHDがあります」とAIに伝える体で前提を置く、のが名前の由来です。

②なぜ話題に: 刺さる人が多すぎた

バズの構造
  • 「AIの長文返信を読み飛ばしてしまう」人はADHD診断がなくても大量にいます。
  • 実際に試した人が「自分向けの表示になった」と実感し、口伝えで広がりました。
  • 課金してでも読みやすい出力が欲しい層に、安価なセルフ設定として刺さりました。
  • 「これで仕事が回るように」という実感 report がSNSに蓄積しています。
長文読みのストレス（万人ある）
 ＋ 数行の設定で解決
 → 「自分ごと」化して拡散
要するに「読みやすさのニーズ」が一手に集まった形なんですね。

③認知負荷とは: 頭の作業机の混雑

基礎概念
  • 認知負荷とは、ものを考える時に使う作業記憶の占有量のことです。
  • 頭の中は作業机のようなもので、一度に置ける道具は少数しかありません。
  • 長文は「読む」だけで机を埋めるため、判断する余地が残らないのです。
  • 対策の基本は情報を減らし、並べ替えること。Skillはまさにこれをやります。
机が散らかっていると、何から手をつけるかすら決められない、という話です。

④相性の悪さ: 丁寧な長文が仇になる

問題の構造
  • LLMは丁寧に答えようとして、前置き・背景・補足を全部盛りしがちです。
  • 読む側は結論を待てず、途中で読むのを諦める現象が起きます。
  • 読み飛ばした結果、同じ質問を繰り返し、トークと費用が膨らむ悪循環も。
  • 「正しさ」と「読みやすさ」は別で、後者は意図的に指定しないと得られないと動画は指摘します。
長文 読み飛ばし 再質問 さらに長文
親切心の長文が、そのまま負担になる。せつあるあるですね……。

⑤設計思想: 結論ファースト一辺倒

Skillの哲学
  • 出力の先頭に「結論・次の action」を必ず置くのが、このSkillの柱です。
  • 本文は箇条書き主体で、段落の壁を作らない方針が貫かれています。
  • 「読んでから考える」ではなく、「見た瞬間に動ける」ことを最優先にします。
  • 丁寧さは落とさず、情報の並び順だけ変えるのがミソと解説されていました。
結論（1行）
 ↓ 次の action（1行）
 ↓ 詳細（必要な分だけ箇条書き）
情報を捨てるのではなく、順番を入れ替えるだけ。これが Points です。

⑥前提の置き方①: 冒頭に結論を1行

ルールその1
  • まず 「いま何が起きたか」を1行で宣言させる書き方を指定します。
  • 「〜について説明します」のような前置きの挨拶を禁止するのが効きます。
  • 結論の先頭1語は動詞か判定詞で始めると、さらに読み取りが速くなります。
  • 「詳細は下へ」の一言があるだけで、上だけ読んで済む安心感が生まれます。
NG: 今回はデプロイについて説明します…
OK: デプロイは成功。警告が1件のみ。
1行目で「読むべきか読まないか」が分かるのが理想形ですね。

⑦前提の置き方②: 次の行動を必ず添える

ルールその2
  • 報告の末尾に 「次に取るべき行動」を明記させるのが二つ目の柱です。
  • 選択肢を提示する時は最大3つに絞り、推奨案の1つを先頭に置きます。
  • 判断が必要な時は「AかBか、返信は1語でOK」のように返信コストも下げます。
  • 行動にはコマンド例やリンクを付け、コピペで動く状態にします。
読んだ 選ぶ 貼る 完了
「で、何すればいいの？」をAI側が先回りして答えてくれる形です。

⑧前提の置き方③: 情報量そのものを減らす

ルールその3
  • 1項目は1行・約20〜30字に収める指示が基本となります。
  • 詳細は折りたたみや「詳細は聞いて」に退避させ、表面を軽く保ちます。
  • 強調は太字を最小限に。全部太字なら何も強調されない理屈です。
  • 「書けること」ではなく「必要なこと」だけ書く態度を指示に埋め込みます。
1項目 = 1行（20〜30字）
詳細は畳む／要求された時だけ
強調（太字）は各ブロック1箇所
短くする勇気。ここが一番むずかしい、というのが率直な感想です。

⑨SKILL.mdの書き方: 箇条書きの命令で

実装の入口
  • 中身は SKILL.md 1枚でOK。フロントマター＋命令の箇条書きという構成です。
  • 冒頭には name と description を書き、呼び出し条件を明確にします。
  • 命令は「必ず〜せよ」の肯定形の断定で書くほうが従順に動くと解説されています。
  • 良い例・悪い例を1組だけ添えると、揺らぎが大きく減ります。
---
name: i-have-adhd
description: 出力を結論ファーストに整形
---
- 冒頭1行は結論のみ
- 挨拶・前置きは書かない
- 次の行動を末尾に1行
プログラムではなく「お願いごと」を書く感覚。ハードルは低めです。

⑩命令は具体的に: 曖昧語を殺す

文章術のコア
  • 「簡潔に」「分かりやすく」のような曖昧な指示は効きにくいと動画は断じます。
  • 代わりに「3行以内」「字数上限」「項目数」など、数値で縛ります。
  • 出力の型（テンプレ）を先に示すのが、一番強い指定になります。
  • 指示を変えたら同じ質問で前後比較して、効きを必ず確認します。
NG: 簡潔に答えて
OK: 1行目に結論、2行目に理由、
    3行目に次の行動。各行30字以内。
「簡潔」の解釈は人によって違う。数値と形で固定するのが正解でした。

⑪スマートな実装①: 最小構成で回す

実装の軽さ
  • まずは3〜5行の最小ルールから始めるのが、動画の推奨する入り方です。
  • 困った時だけルールを1行追加していく、育てる運用が前提になります。
  • 指示が短いほどコンテキストの消費もトークンも軽く、お財布に優しい利点も。
  • 巨大な指示は矛盾を起こすので、削る方向で調整するのが定石です。
最小で作る 使う 足りない時だけ足す
最初から完璧に書かない。スキルも植物と同じで、少しずつ育てます。

⑫スマートな実装②: 出力テンプレ固定

型の力
  • 「結論→理由→次の action」の3段テンプレを、Skill側に直接書いて固定します。
  • 型が決まると出力のぶれが消え、目が慣れて読む速度が上がります。
  • 用途別に報告用・レビュー用・相談用と型を分ける技も紹介されました。
  • スマホで読む想定なら、行を短く区切る指定を入れておくと良いそうです。
[結論] 1行
[理由] 最大3行
[次の行動] 1行（コマンド例つき）
毎回同じ形で来る安心感は、地味にでかい効果でした。

⑬活用例①: 朝のデイリー整理

日常へ組み込む
  • 朝にエージェントへ「今日やることを3つ」と聞くと、優先順位つきの短い一覧が返ります。
  • 溜めたメモや未読を投げると、要約と次の行動に圧縮してくれます。
  • 「起動して3分で全体像」が実現するので、始動の重さが消える効果が大きいと動画は述べます。
  • 通知文そのものを短く整形させれば、スマホの通知も落ち着きます。
朝いちばんの意思決定コストを、AIに肩代わりしてもらう構図です。

⑭活用例②: コード修正の報告を整える

開発現場
  • 修正が終わった時の報告を 「何を変えたか・影響は・次は」の3点に限定させます。
  • 差分の説明もファイルごと1行に圧縮すると、レビューが速くなります。
  • リスクは先頭の結論行に含めるよう指示すると、見落としが減ります。
  • 検証コマンドをコピペで動く形で貼らせるのも定番の合わせ技です。
結論: バグ修正済み・テスト12/12成功
影響: 認証まわりのみ。他機能は無傷
次: pnpm test で確認 → マージOK
開発報告、ここまで整うとレビューがぐっと楽になります。

⑮組み合わせ術: 他のSkillと併用する

発展形
  • short-mem やメモ取得系と組むと、過去の文脈も短く要約して持ってこられます。
  • タスク管理系と組めば、一覧→即チェックの流れが一本化されます。
  • 出力整形はどのスキルの末尾にも効くので、土台として常時読み込みにする手もあります。
  • ただし他の整形指定と矛盾しない確認を忘れずに、と注意がありました。
文脈取得 処理 i-have-adhd で整形して出力
最後の「見せ方」を司るskill。組み合わせの出口として優秀です。

⑯注意点: 向かない場面もある

落とし穴
  • 学習や調査など読み込む前提のタスクでは、短縮が逆効果になります。
  • 削りすぎて根拠が消えると、誤読のリスクが増すので注意が必要です。
  • 名前はADHDを冠していますが、医学的な効果を保証するものではない点も強調されていました。
  • 用途によってオン／オフを切り替える運用が、現実的な落とし所です。
「常に最適」ではなく「目的に合わせて着脱」が正しい使い方ですね。

⑰自作への道: 自分専用に調整する

カスタムのコツ
  • まずは配布物をコピーして1行ずつ書き換えるのが、最速の自作ルートです。
  • 自分が読みやすい語尾・記号・絵文字の指定を足すと、一段と手に馴染みます。
  • 朝用・夜用など時間帯でテンプレを分ける小ネタも紹介されていました。
  • 運用して合わない行は迷わず削除。スキルは減らす方が強くなります。
コピー → 1行書き換え → 使う
→ 合わない行を削る → 自分専用版
「自分が読みやすい形」は人それぞれ。自作してこそ完成です。

⑱まとめ: 読み手側に立つ設計を

結論
  • i-have-adhd の本質は、認知負荷を下げる出力設計そのものです。
  • 柱は「結論1行・次の行動・短い箇条書き」の三拍子。
  • 実装は最小のSKILL.mdから育てるのが、スマートなやり方でした。
  • まずは1つコピーして、今日の自分の読みやすさを仕立て直してみましょう。
前提を置く 型で固定 読まずに動ける
