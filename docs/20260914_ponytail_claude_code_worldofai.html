③ AIエージェントのコード膨張問題

00:20 課題背景
  • コーディングエージェント共通の課題は不要なコードの膨張
  • 余分なコードはそのままトークン消費の増大に直結
  • Claude Codeのレート制限に引っかかる場面で特に有効
  • 少ないコードは保守しやすく効率的な成果物になる

④ 「はしご式」最小実装の仕組み

00:48 仕組み解説
  • 書き出す前にチェックリストを実行するのが全体メカニズム
  • 「はしご」のように最小限の選択肢を下から順に確認
  • 条件を満たしたら最初の解で停止——それ以上書かない
  • プロンプトを解決する最小限の出力だけを返す
チェックリスト 最小候補探索 最初の解で停止
「賢く書く」んじゃなく「最初に動いたらやめる」。発想の転換だね。

⑪ 結果1: 81行 vs 14行

04:09 結果発表
  • Ponytail OFF: 2ファイルに81行
  • Ponytail ON: 1ファイルに14行で同等機能を実現
  • OFF側はリッチなドロップダウン、ON側はシンプルな候補表示で機能は達成
  • diffには「登録クリック前に閉じない」ための100msタイマーとmousedown利用が含まれる
OFF 81行 ON 14行 機能は同等
行数は1/6以下！ただし品質の差はある——それがトレードオフ。

⑫ ネイティブHTMLのdatalist活用

04:55 コードの中身
  • ON側が選んだのはプラットフォーム標準のdatalist要素
  • 実装選択肢のはしごは1〜7のリストで、リスト4で解決して停止
  • リスト7（コンポーネント自作）には到達しない——書きすぎを防ぐ仕掛け
<input list="assignees">
<datalist id="assignees">
  <option value="...">
</datalist>
標準機能で済ませるのが達人技。車輪の再発明をやめるだけで行数はぐっと減る！

⑬ 「lazy＝ズボラ」ではない2つの理由

05:30 懸念への回答
  • 理由1: 変更前に必ずコードを読む——触れる範囲のリストを確認してから手をつける
  • 理由2: 重要なものは手抜きしない——バリデーション・セキュリティ・アクセシビリティは省略なし
  • つまり解は最小限、読み込みと品質保証は最大限
読み込みは真剣 書く量は最小 品質は維持
「手抜き」なのは書く量だけ。読みと検証はしっかりやってるのが偉い！
