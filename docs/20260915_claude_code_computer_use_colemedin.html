①新のお気に入り「drive-screen」skill

  • Claude CodeとCodexで毎日あらゆる用途に使っている新のお気に入りskillが「drive-screen」。コーディングエージェントにPC画面を丸ごと操作させます。
  • Claudeプラットフォーム内蔵のコンピュータユースやCodex computer useといった「肥大化して管理が難しい」ツールの超軽量な代替として自作しました。
  • 必要なのはコーディングエージェントだけ。追加インストールもハーネス構築も不要です。
  • Fable 5.1やGPT-6 Astraなど最新LLMは、コマンドラインだけで画面をほぼ何でも操作できる水準に到達。数週間前に試して判明した事実です。
drive-screen 追加ツール不要
「LLM自体がスクリーン駆動に十分」——これがこの動画の大前提なんですね。

②既製コンピュータユースツールを避ける理由

  • Claude内蔵機能、Codex computer use、OSSなど強力なツールは山ほどあるのに、著者は昔から一度もファンになったことがないといいます。
  • ワークフローに組み込むと細かい問題が次々発生するのに、巨大ツールはカスタマイズも微調整も困難。
  • 一貫する思想は「自分のツールを自分でコントロールしたい」の一点。
  • それでもコンピュータユースはあまりに有用で、ここ数週間でその実感が日に日に強まり、skill作成へ踏み切りました。
ツールの自己管理 カスタマイズ性
「強力」より「制御できる」を取る、エンジニアらしい価値観です。

③誕生のきっかけはOSS試用のストレス

  • AI界隈の動向に追いつけないほど多忙で、Kestraのようなオープンソースプロジェクトを次々試したい状態でした。
  • 試したいアプリの多くはUIを持っており、ブラウザ自動化だけでは試せない→コンピュータユースが必要に。
  • とはいえ軽量で管理しやすいものが欲しく、フル規模のコンピュータユースツールは導入したくない。
  • そこでGitHubのURLを渡して「Webを調査→リポジトリを分析→デスクトップアプリを起動→画面を操作して機能テスト→最後に開いたまま残す」と指示してみました。
UIアプリの試用 Kestra
本当に動くのか、本人も半信半疑で放り投げた実験でした。

④結果：ハーネスなしで完走した

  • 大型ツールを入れるでもなく「手動でやって」と拒むでもなく、ターミナルのコマンド実行だけで全工程を完走。
  • 時間はかかったものの、PCの操作を任せきりにして別のデバイスで作業。戻るとすべて完了し、テスト継続中の状態で開かれていました。
  • セッションログは「コマンド実行→クリック→スクリーンショット→結果分析」の連続で、追加ツールは一切なし。
  • WindowsではPowerShell、MacではAppleScriptと、OS標準の機能だけで駆動します。
エンドツーエンド完走 放置して別作業
「美しい光景だった」と本人が振り返る瞬間がここです。

⑤朝のセットアップを自動化

  • 最もわかりやすいクイックウィンは朝の準備。PCを開いたらエージェントに「今日の作業の準備をして」と一声かけるだけ。
  • タスク管理ソフトをCLIやMCPで確認して、今日やるべきことを把握します。
  • ブラウザタブ、Obsidian、デスクトップアプリ、Dockerコンテナなど必要なものを全部起動。
  • これだけで毎朝10〜15分の節約になり、他のクイックウィンとも積み重なっていきます。
morning setup 毎日10-15分節約
使うのはskillとシンプルなコマンドだけ。追加ツールはゼロのままです。

⑥全OS・マルチモニタで動く

  • Mac・Linux・Windowsのそれぞれでテスト済み。どんなOSでも動くように作られています。
  • 複数モニタ構成や異なるディスプレイ設定でも問題なく適応。
  • OSごとに最適な駆動手段（PowerShell、AppleScriptなど）をスキルが使い分け。
  • 「環境を選ばない」からこそ、毎日の仕事に組み込める実用性になります。

⑨まず「画面制御が必要か？」を疑う

  • ワークフローの冒頭は「そもそも画面制御が本当に必要か？」の判断から始まります。
  • ブラウザ自動化など別の手段で済むなら、エージェントはプッシュバックして画面制御を回避できます。
  • 画面制御は「最も適応性が高いが、最も遅く最も信頼性が低い」手段とスキル内に明記。
  • 画面経由のプロンプトインジェクションリスクがあるため、安易な使用を最初から抑制する構造です。
手段の選別 最後の手段としての画面制御
「使える」ことと「使うべき」ことは別、という設計思想です。

⑩同梱のカスタムCLIスクリプト

  • ウィンドウの発見・フォーカス・タイピング・ペーストなどの操作をスクリプト化して同梱。
  • 何時間もテストして見つけたベストプラクティスをパッケージ化し、決定論性を向上。
  • エージェントがリアルタイムでコマンドを考える負担が減り、信頼性と速度が上がるのが狙い。
  • 操作の種類が多くCLIのコマンドと引数も豊富。これが「速く・少ないコマンド数」の理由です。
ベストプラクティス集 決定論性の向上
「エージェントに考える量を減らす」のが信頼性の鍵、というのは面白いですね。

⑪ハードルール：失敗の知識の結晶

  • 最初は単に「PowerShellで画面を操作してXをして」と頼むだけだったのが、動かないケースや失敗パターンが続出。
  • そこで失敗モードを文書化し、ワークフローを定義し、スクリプトも作ってスキル化しました。
  • ハードルールは「使って学んだ困ったパターン」の集積で、信頼性を支える土台です。
  • ミスが出るたびルールを1行追加するだけという保守コストの低さも大きな魅力。
失敗モードの文書化 1行追加の保守
大型ツールだと「待つ」しかない修正も、自分のスキルなら即直せます。

  • 他のコーディングエージェントセッションを駆動する用のCLIもあり、承認待ちなどを監視。
  • 「セッション監視」「自動運転」などの単位で知見が整理されているのが特徴です。

⑰トークン効率：遅さの正体

  • 遅さの原因はトークン消費ではなく、入力待ちなどの待機時間が主。

  • 「速くはないがトークン非効力でもない」という性格を理解して使うのがポイント。
  • 待ち時間が主因と分かれば、並行して別の作業をする運用が自然に決まります。

この動画の要点

最新LLM（Fable 5.1、GPT-6 Astra）はハーネスなしで画面を駆動できる。「コンピュータユースには巨大ツールが必須」という常識はもう古くなりました。

スキルの中身は失敗モードの文書化とカスタムCLI。ミスの修正はルールを1行追加するだけで、巨大ツールにはできない保守性です。

画面制御は「最も柔軟だが最も遅くリスクも高い」最後の手段と位置づけ、まず代替手段（ブラウザ自動化等）を検討させる設計が安全和です。

簡単な用途は軽量スキル、本番用途は大型ハーネスと使い分けるのが、セキュリティと生産性の両立する実践線です。

実務ですぐ使えるチェックリスト

  • コーディングエージェントに任せられる毎日の定型作業（朝のセットアップ、デモの準備など）を書き出し、drive-screen化を検討する。
  • 試したいUI持ちアプリのリストを作り、GitHubのURLを渡して「調査→起動→テスト」を一任してみる。
  • 自分の環境（OS・モニタ構成）で動かし、失敗パターンが出たらスキルにルールとして追記する。
  • コンピュータユースには最新の強いモデルを使い、HiddenLayerのプロンプトインジェクション記事にも目を通す。
  • プロダクション用途には大型ハーネスを検討し、軽量スキルは日次のquick winに限定する。
