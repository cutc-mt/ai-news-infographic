Jevとは何か: 「LLMの次」の正体

「LLMの次」と呼ばれる所以は、文章生成を捨てた設計にあり。次のカードから順を追って見ていこう

②Jevは「System Oneモデル」

TypeSafe AI「Jev」
  • 元OpenAI研究者が立ち上げたTypeSafe AI（typesafe.ai）が公開した新世代モデル
  • 最大の特徴は文章を生成しないこと。流れるようなテキストではなく、型付きの値と信頼度だけを返す
  • 「System Oneモデル」という新カテゴリ。LLMとは根本的に出力の形が違う
  • 返ってきた値をそのままコードの分岐につなげられるのが最大の強み
一言で言えば「非構造の状態を入れると、型付きの確率的な判定を返す関数」。プログラムに組み込めるAI、それがJev

③LLMと決定的に違う点

LLM vs Jev
  • LLM: 文字列を返す → コードで使うにはパース＆バリデートが必須
  • Jev: 型付きの値＋信頼度を返す → そのまま分岐に投入できる
  • 生成方法も違う: LLMは1トークンずつ逐次生成。Jevは全出力を一気に並列生成
  • 位置づけは「人間が書いたIF文とLLMの中間」を埋める存在
「LLMが不要になる」「プログラムが不要になる」話ではない。両者の得意領域の間を埋める、というのが正しい理解

④「残り5%」問題とは

  • LLMで業務の95%は自動化できても、残り5%が邪魔で全体が自動化できない、という課題があった
  • その5%とは「自己申告できない判断」の部分。言葉にできない曖昧さを数値化する手段がなかった
  • Jevは非構造な入力から型付きの確率的判定を返すので、この最後の5%をコードに接続できる
  • 「プログラムで書いたらどう書けばいいか分からない部分に刺さる」（まさお氏）
決定論的なプログラムと非決定論的なLLM。この間の「グレーな判断」を埋めるのがJevの存在意義

爆速・激安・高信頼: 仕組みとコスト

⑤並列生成で一気に返す

仕組み
  • 従来LLM: テキストを1トークンずつ生成 → 文字列として受け取りパース＆バリデート
  • Jev: テキストとプログラムの状態を持って一気に並列生成
  • 出力は型付きの値と確率。文章は捨てられる
  • 実際のリクエストでもレスポンスが一気に返る様子がデモで示された
非構造の状態を入力 並列生成 型付きの値＋信頼度
「逐次に文章を積む」のではなく「結果の形を一括で用意する」。この設計が爆速の源泉

⑥比較で見る爆速ぶり

GPT-5.6-Terra比較
  • デモでの比較: 74.9倍早い
  • コストは 171倍安い
  • この速度があるからこそ、状態をどんどん取りながら次のアクションを起こす使い方が現実的に
  • 公式共有のデモにはシューティングゲーム的な実装も。リアルタイム性が求められる場面で可能性を感じる性能
「速さは新しい機能」の好例。待ち時間ゼロに近いと、AIの判断ループをプログラムに組み込める世界が広がる

⑦とんでもない価格設定

料金
  • 入力: $0.042 / 100万トークン
  • 出力: 無料
  • 世のモデルは1Mトークンあたり$0.2台でも「激安系」と呼ばれる中、桁違いの安さ
  • この価格なら大量呼び出しを前提とした設計（LLMジャッジの多段利用など）も気兼ねなくできる
「高速×激安」は組み合わせて初めて威力を発揮する。何度呼んでも痛くないから、細かい判断を全部任せられる

⑧信頼度スコアの挙動

  • LLMの「確信度」: 過信しがちで不安定。モデルによってバラつきも
  • Jevの信頼度: 高いほど当たるように較正されており毎回返ってくる
  • 信頼度をパラメータとして扱えるので、閾値で処理を分岐する設計が可能
  • 「自信がある時だけ自動、ない時は確認へ」という安全な自動化が作りやすい
デモでは信頼度100を指定しても実際の値は上下し、条件が揃うと高くなる様子が実演された。生の数値が扱えるのは大きい

ベンチマーク性能と、実際の使いどころ

⑨ベンチマーク: Terra級の性能

ベンチマーク
  • ベンチマークスコアは68%。それでいてコストは最安クラス
  • 性能はTerraとほぼ同等。Sonnetともいい勝負、という位置づけ
  • つまり「Sonnet級の判断を桁違いの安さで」というコスパ構造
  • 注意点: プロンプト形式で渡す方式だと精度が下がり値段が上がる図になる。評価の取り方に癖がある
性能インフレ時代の新しい軸「性能あたりのコスト」。Jevはこの軸で現状トップクラスの競争力を持つ

⑩使いどころ: LLMとIF文の間

適材適所
  • 確実に決められる部分 → プログラム（決定論）で書く
  • 自由な文章生成 → LLM（非決定論）に任せる
  • その中間の「曖昧だけど型のある判断」 → Jevの出番
  • 既にLLMで同じことをやっていたパターンをJevへ置き換えるだけでも速度・コスト面で恩恵が出る
IF文（決定論） Jev（確率的判定） LLM（文章生成）
「全部LLMで」でも「全部プログラムで」でもない。3層に使い分けるのがこれのハーネス設計のコツ

⑪LLMジャッジを高速化

  • 「LLMジャッジ」（別モデルの出力をAIに評価させる手法）を高速に実行できるのがJev
  • 具体例: 記事の再評価。"実用性を何%重視するか" "根拠が必要かどうか" を軸に評価器を作ると総合点が変わる
  • 応用例: お問い合わせ文章の内容で担当サポートを振り分けるルーティング
  • 判断を大量に回せるので、評価の粒度を細かく試しながら調整できる
評価関数をどう作るかがAI開発の鍵、という近年の流れにぴったりハマる用途。安いから試行錯誤もはかどる

⑫ハーネスの作りが変わる

まさお氏の展望
  • 面白い使い方: AIエージェントにJev向けプログラムを書かせる
  • 書かれたコードをハーネスの各部分に組み込んでいくことで、小回りの効く自動化を構築
  • ハーネス（AIを制御する枠組み）の設計に新しい選択肢が加わる意味着は大きい
  • まさお氏自身「色々と掘っていきたい」と今後の検証を約束
「AIにAIの部品を書かせる」というメタ構造。エージェント開発の組み立て方が変わる可能性を秘めている

実演デモと、注目すべき理由

⑬デモ①: 文章で照明を操作

スマートホーム制御
  • 「リビングを暗くして映画を見たい」と文章で指示 → 照明の明るさを25%にすると解釈
  • 「明るくして」系の指示では暗くならず、文章の内容に応じて動作が変化
  • 「寝室を暗くして」では対象部屋を正しく認識して寝室の照明を操作
  • 実行前に確認ステップを挟むことも可能。安全側に倒した設計も簡単
自然文 → スキーマ通りの型付き値 → 機器操作。音声アシスタントの脊髄をJevで組み直すイメージ

⑭図解: スキーマから値まで

  • スキーマを先に定義: 「部屋はどれか」「明るさは何%か」などの質問と選択肢を決める
  • リクエスト送信: 自然文コマンド＋スキーマを一緒に渡す
  • 3つの質問を1回のAPI呼び出しで判定。room＝リビング、明るさ＝25%のような値が返る
  • プログラムに埋め込み: 画面の明るさ表示や機器制御に直接反映
自然文＋スキーマ Jevで並列判定 型付きの値 コード実行
ポイントは「先に型を決める」こと。聞きたいことをスキーマ化すれば、返り値はそのまま分岐条件になる

⑮デモ②: 記事の再評価システム

評価エンジンの実演
  • 評価軸をパラメータ化: 「実用性の重視度（%）」「根拠の要否」
  • 同じ記事でも重視度によって総合点が変わる様子を実演
  • 評価の部分を調整するだけで、高速かつ激安な評価基盤として運用できる
  • キュレーション・モデレーション・品質管理など、大量の判定が必要な業務に直結するデモ
「評価関数を作れ」という近年の開発観とぴったり合う実例。試行コストが低いので調整サイクルも速く回せる

⑯性能が足りない時は

  • 現状のモデルで性能が足りないケースもあると正直に解説
  • その場合はより多くのトークンをかけるなどして問題解決する方向
  • それでもコストが桁違いに安いので、贅沢な使い方でカバーする余地が大きい
  • プロンプト形式の利用は精度が下がり値段が上がるため、スキーマ使いが基本。設計の抜き差しが効く
万能薬ではなく「得意・不得意がある道具」。だからこそLLM・プログラムとの住み分け設計が重要になる

⑰なぜ注目すべき技術か

  • 爆速・激安・新しい仕組みの三拍子。まだ未知の部分が多く、今は「当たり前じゃないこと」ができる
  • 出力が型付きなのでプログラムとの相性が根本から良い。パース破綻のような事故が起きにくい
  • 開発者の間で「LLMの次」の候補として注目度が急上昇中
  • まさお氏の結論: 「注目しておいた方がいい技術」「皆さんも使ってみた方がいい」
同日のニュースではJevがスーパーマリオをプレイしたデモも話題に。実行型AIとしての実力も合わせて確認したい
