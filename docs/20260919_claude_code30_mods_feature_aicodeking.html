①今週の目玉: Claude CodeがAGENTS.mdを読める

v2.1.277 2026-09-18
  • Claude CodeがついにAGENTS.mdを読み込めるようになった
  • プロジェクトが既にAGENTS.mdでコーディングエージェントへの指示を運用しているなら、Claudeがそれを直接拾える
  • 動画のカバー範囲は2026年8月20日〜9月18日のアップデート一括レビュー
  • 注目すべきは実装方法: この対応は組み込みmodとして実装されている
AGENTS.md Claude Codeが直接読む 指示が反映
単なる「ファイル対応」に見えて、中身は mods という新しいカスタマイズ機構。ここが本動画の主役
02

②優先順位のルール: CLAUDE.mdとの住み分け

  • デフォルトでは、プロジェクトにClaude専用の指示ファイル（CLAUDE.md等）がない場合のみAGENTS.mdを使用
  • 既にCLAUDE.mdがあるなら、デフォルト設定ではそちらの指示が優先
  • 挙動は/configの「Project instructions」で変更可能
  • 両方のファイルを読み込むオプションもあり → 共有ガイド＋Claude専用指示の併存ができる
「共有ルールはAGENTS.md、Claude固有の話はCLAUDE.md」という運用が全国的にできるようになった
03

③AGENTS.mdに書く中身: エージェント共通の規約

  • テストの実行方法（どう動かすか）
  • 使うべきパッケージマネージャーの指定
  • 生成ファイルが入るフォルダ（触らない場所の明示）
  • 同じプロジェクトでコーディングエージェントを切り替えて使う場合、ルールを一元化できて重複管理から解放される
# AGENTS.md 記載イメージ
- テスト: npm test を実行
- パッケージマネージャー: pnpm
- src/generated/ は自動生成。編集しない
「エージェントが実際に必要とするコマンドと規約」だけを書くのがコツ。共有ファイルは絞り込むべし
04

④導入時の注意点: 読めれば安心ではない

  • ローンチ時点でBedrock・Vertex AI・Foundryではまだ利用不可
  • ファイルを読める＝全指示が完璧に守られる、ではない。実際に従っているか作業結果をチェック
  • 共有ファイルはエージェントが本当に必要な情報に集中させる。詰め込みすぎない
  • 指示が守られているか定期的に検証する運用をセットに
「読み込ませる」で終わりではなく「確認する」までが仕事。指示ファイルは薬ではなく栄養剤

第2章: Mods — ハーネスをカスタマイズする新システム

CHAPTER 02
05

⑤Modsとは: Claude Code本体を改造する仕組み

本動画の主役
  • Anthropicがサイレントに投入した最大級の新機能がmods
  • modsとはClaude Codeそのもの（ハーネス）をカスタマイズする、これからの中心的な仕組み
  • AGENTS.mdサポートは、その最初の組み込みmodという位置づけ
  • 動画主が最も注目しているアップデートと明言
地味なリリースノートに見えて、実はClaude Codeの拡張の方向性を示す重大発表。タイトルの「SILENTLY」は伊達じゃない
06

⑥「ハーネス」とは: モデルを囲むソフトウェア

  • ハーネスとはモデルの周りにあるソフトウェアのこと。LLM本体そのものではない
  • 役割その1: コンテキストの組み立て（何をモデルに見せるか）
  • 役割その2: ツールの呼び出し（道具の実行をつなぐ）
  • 役割その3: セッションの表示（ユーザーへの見せ方）
LLMモデル ハーネス Claude Code
モデルは同じでも、この「囲む部分」の設計次第で挙動も成果物も変わる。modsはここに手を入れられるようにする話
07

⑦Modの正体: function hooks付きプラグイン

  • Anthropicの定義: modとはfunction hooksを使うプラグイン
  • 早期デモ①: インターフェースの部品を変更
  • 早期デモ②: モデルが受け取る前のツール出力をフィルタリング
  • AGENTS.mdサポートは好例: どのプロジェクト指示がモデルに届くかを変更
  • 開発者はこの指示読み込み動作の独自版を構築可能になる見込み
ツール出力 modがフック 加工してモデルへ
「モデルに渡す前後をフック」できるので、見た目も文脈も自分好みに改造できる。プラグインより一段深い階層
08

⑧公開リポジトリの4つの組み込みmods

  • agents.mdローダー（今回の目玉機能の本体）
  • diffパネル（第3章で詳しく）
  • telemetry（計測・解析）
  • 組織セキュリティmod
  • 公開リポジトリで実装の中身をそのまま検査できる
「機能がどう実装されているか」をお手本として読めるのが公開の強み。自作modを作るときの教材になる
09

⑨カスタムmodsはEarly Access: まだ発展途上

  • ドキュメント確認: カスタムmodにはfunction hooksの有効化が必要
  • APIはリリース間で変更され得るとの明記（初期段階）
  • 組み込みAGENTS.md機能はすでにリリース済み。より広いカスタマイズ体系はまだ開発中
  • 専門的なコーディングワークフロー構築者には要ウォッチの領域
  • 動画主の願望: 大規模プロジェクトの各部分に適切な指示だけを組むmod（全チームの規約を毎タスクに読ませない）
「インターフェースが固まったら何が生まれるか」——ここが一番の楽しみ、というのが動画主の結論

⑩/diffライブパネル: 会話の横に差分を常時表示

v2.1.260 2026-09-03
  • フルスクリーンモードで会話の横にライブdiffパネルが常駐
  • Claudeが編集・コマンド実行するのに合わせて変更ファイルと行カウントがリアルタイム更新
  • 行を選んで次のメッセージに添付できる
  • 要件: gitリポジトリ＋110列以上のターミナル
間違った関数をいじられたら「その行」を指差して、会話を見ながら修正を指示できる。フィードバックが格段に楽に
11

⑪再設計されたProjects beta: 調整者が仕事を振る

2026-09-17
  • プロジェクトにcoordinator（調整役）が新設
  • 仕事を別々のスレッドに分解 → タスクを委任 → 結果をレビュー
  • スレッド間はプロジェクトメモリを共有
  • 各スレッドは専用ブランチ＋リポジトリコピーを持つClaude Codeクラウドセッションとして実行
coordinator スレッド分解 並列実行 レビュー
マルチエージェント調整がついに公式機能に。しかも実行環境ごと分離して安全に回す設計
12

⑫クラウドで動き続ける: ラップトップを閉じてもOK

  • 仕事はクラウド側で走るので、PCを閉じても処理が継続
  • 動画主の試験方法: API変更が要る機能＋フロントエンド更新を一緒に渡す
  • 見極めポイント: 複数パーツをきちんと調整できるか、ミスマッチを捕捉できるか
API変更 フロント更新 整合性チェック
「複数エージェントを走らせる」のは仕事の一部にすぎない。本質は受け渡し（handoffs）をどう処理するか
13

⑬Projects利用の条件とコスト面の注意

  • 当初は選ばれた Pro / Max サブスクライバーのみ（ベータ）
  • 条件: クラウドセッション利用者で、web・desktopに既存プロジェクトがないこと
  • Team・Enterpriseアクセスとローカル実行は後日提供予定
  • 並列スレッドはallowance（利用枠）を速く消費する点に注意
方向性は良い、が動画主の評価基準はひとつ:「handoffsの巧さ」。並列数より受け渡し品質で判断したい、とのこと
14

⑭バックグラウンドコンピュータ使用: PCを使いながら作業させる

8/31〜9/4の週
  • macOS 15以降のデスクトップアプリに新機能（ベータ）
  • 承認したアプリの中でClaudeが作業し、その間も自分はPCを使い続けられる
  • CLIを持たないネイティブアプリのタスクで特に有用
  • Claudeが触れるアプリは自分が承認。デスクトップアプリは起動したまま必要
  • 実PC上で動くので、作業中はスリープさせず起こしておくこと
対象は Pro / Max 向けベータ。「目の前のMacでAIが黙々と作業、人間は別作業」が現実に

⑰/skill-doctor: スキルの健康診断

9月上旬の更新
  • /skill-doctorが、各スキルのコンテキストコストと使用状況を表示
  • データを見て無効化すべきスキルを特定できる
  • 重要な背景: 利用可能スキルの一覧は呼び出されなくてもコンテキストを占有
  • 「入れているだけ」のスキルがモデルの入力を静かに圧迫していた、なんてことが可視化される
スキルはタダではない。定期的に健康診断して、使わない子はお休みさせるのがコンテキスト衛生の基本
18

⑱claude plugin eval: プラグインの効能を実測

v2.1.269 2026-09-11
  • claude plugin evalにテストケースとスコアリング基準を渡すと、プラグイン装着状態で実行
  • デフォルトでプラグインなしの比較実行も実施 → カスタマイズの貢献度が見える
  • 注意: 実モデル呼び出しなので評価もusageを消費
  • 動画主の推奨手順: 繰り返すタスクを数個選ぶ → 良い結果の定義 → 導入コストと複雑さに見合うか判定
$ claude plugin eval
  テストケース + スコアリングチェックを指定
  → プラグインあり/なしで比較実行
  → 貢献度を数字で確認
「便利そう」で終わらせない。複雑なワークフローを追加する前に、費用対効果を実測する習慣がこれで定着する
