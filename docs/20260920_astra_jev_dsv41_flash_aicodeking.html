①問題意識: 高いモデルの「日常業務」がもったいない

課題
  • 高価なコーディングモデルを使っていると、使用量の多くがありふれた作業に消える
  • 具体的にはファイルを読む・定型的なコードを書く・import修正・小さな変更
  • プロジェクトのすべての部分に最も高価なモデルは必要ない
高額モデル単体 計画とレビューだけ 実装は安価なモデルへ
「何に課金しているか」を見直すだけで、コスト構造はガラッと変わる
02

②元ネタ: Redditの「0.94ドル」構成

発端
  • Redditの投稿が発端: AstraとDeepSeek 4.1のサブエージェント8体を組み合わせた構成
  • 投稿者の弁では、ワーカー側の費用は0.94ドル。Astraは週間サブスク枠の約10%を使用
  • ただしこれは投稿者の数字であり、構成全体が0.94ドルだったわけではない。自分の実行で計測する必要がある
  • 拡張版の解説ではMCPでDeepSeekをCodexに接続し、Codexが開発を主導しワーカーをレビューする構成（リンクは動画概要欄）
「強い1体＋安い8体」の発想が発火点。今回はこれをツール内蔵の機能で再現する
03

③ツール選定: なぜBambooか

Bamboo
  • チーム構成が最初から組み込まれており、モデルを選び、インターフェイス上で仕事を追える
  • Jevはオプション追加。JevのAPIキーがなくても、Bambooでチームを走らせ、変更をレビューできる
  • 料金は月20ドル。モデルのサブスクとAPI利用料は別課金。まだアルファ版で荒い部分もある
  • 魅力はチーム管理・会話・ブラウザー・変更確認が、心地よい1つのワークスペースにまとまっていること
項目内容
料金$20/月（モデル利用は別）
成熟度アルファ版
Jev任意追加（キー不要でも運用可）
「またサブスクか」と思いつつ、開発体験の良さで選ぶ。その判断は自分で計測してから
04

④ワークスペースの見た目

作業環境
  • 多くのコーディングツールは暗く素っ気ない画面。Bambooは自然の背景写真＋半透明パネル
  • エージェントの応答を何時間も見る作業では、単調さが軽減されて快適
  • 壁紙の変更・可視度の調整・ぼかし追加が可能。景色を残しつつテキストの可読性を確保できる
長時間エージェントと付き合うなら、UIの心地よさは馬鹿にできない
05

⑤役割分担: アーキテクト / ワーカー / Jev

3つの役割
役割担当
アーキテクト全体目標の管理・構築内容の決定・課題への分解・部品の適合チェック
ワーカー明確なファイル所有権と期待成果の記述をもとに課題を実装
JevTypesafeの意思決定モデル。与えられた情報を見て的確な判断のみ行う
  • Jevに任せる判断の例: どのワーカーが課題に合うか・完了主張を裏付ける証拠があるか
  • 計画・コード記述・問題修正はあくまでコーディングモデルの仕事
  • 節約の本質は仕事の賢い分割。安いワーカーが実装し、アーキテクトは調整とレビューに集中
  • Jevの呼び出し1回ごとに費用が発生するため、使う場面は選ぶ
「強い模型は指揮官に、安い模型は現場に、判断専用AIは審判に」——役割の切り分けがすべて

第2章: セットアップ手順

CHAPTER 02
06

⑥インストールとモデル接続の前提

STEP 1
  • WebサイトのアカウントからダウンロードとライセンスでBambooをインストール・有効化（動画ではmacOS版を紹介）
  • 選んだコーディングツールをインストール済み＆サインイン済みにしておく
  • Bambooのサブスクには各ツールの有料モデルは含まれない
  • 対応接続の例: 今回はアーキテクト=Codex・ワーカー=OpenCode。ほかにClaude Code・Kimi Code・Claude Code経由のGLMなども選択可
  • 利用できるモデルは接続したハーネスとアカウント次第
まず「指揮官」と「作業員」をどのツールで揃えるか決めよう。今回の指揮官はCodex
07

⑦OpenCode に DeepSeek を接続

STEP 2
  • まずOpenCodeを起動する
  • /connect を実行し、DeepSeekを選んで、接続プロンプトにプロバイダーのキーを入力
  • /models で利用可能なモデルを確認
  • アカウントに実際に表示されるモデルを使う。Reddit投稿とまったく同じバージョンに依存しない設計
# OpenCode 内での手順
/connect        → DeepSeek を選択 → キー入力
/models         → 利用可能なモデル一覧を確認
# 自分のアカウントに表示される実在モデルを指定
モデル名は自分のアカウントで確認できたものだけ信じる。これでバージョン違いの事故を防ぐ
08

⑧Bamboo 側でワーカーモデルを選択

STEP 3
  • Bambooの設定 → エージェントを開き、OpenCodeモデルの「モデルを選択」をクリック
  • 使いたい項目を選んで保存すると、メインのモデルドロップダウンとチーム選択画面で使えるようになる
  • 「default」しか出ないときは、プロバイダー接続後にカタログを更新し、明示的にモデルを選ぶ
設定 エージェント モデルを選択 保存
ここで選んだモデルが「ワーカー」の候補になる。先に接続、あとで選択、の順番を守る
09

⑨Jev のセットアップ（オプション）

STEP 4

意思決定アシスト

  • 設定のエージェント欄でSetup Jevを開き、意思決定アシストを有効化。TypesafeのAPIキーを追加して保存
  • これだけでワーカー提案・コンテキスト検索・レビューチェックが使える。ブラウザーランタイムも追加のテキストモデルも不要

ブラウザーテスト（別スイッチ）

  • 「let your agents test their apps」のスイッチを有効化し、テキストモデルのAPIキーも追加して保存
  • ボタンでJevランタイムをインストールし、セットアップを確認。ChromeとUVパッケージマネージャー or Python 3.12以上が必要
  • ブラウザーヘルパーモデルは別々に設定可能。判定機能だけ欲しい場合はテストをオフのまま省略可
  • プライバシー: Jevチェックに使う情報はTypesafeへ送信、ブラウザー入力は設定したヘルパープロバイダー利用。レポートは端末内に保持。両機能とも初期状態は無効
追加のプロバイダー接続は利用料も別。有効にするかどうかは常に自分がコントロール

第3章: チームを組んでマインスイーパを作る

CHAPTER 03
10

⑩チーム編成と「budget coding」プロファイル

TEAM SETUP
  • プロジェクトを開いて新規タスクを作成。Bambooは最後に使ったプロジェクトを使うため、名前を確認・変更
  • メッセージ欄のTeamボタンでコンパクトなアーキテクト&ワーカー設定パネルを開く
  • アーキテクトにCodex＋計画用モデルを選択。Astraが使えるならReddit流に。信頼するモデルなら他でもOK
  • 推論の努力度（reasoning effort）は対応箇所で設定。ただし全エージェントを最高設定にするのは非推奨
  • ワーカーにはOpenCode＋追加したDeepSeekモデルを指定し、logicとinterfaceの2つのプロファイルを作成（同じモデルでも別モデルでも可。名前は役割を表すもの）
  • ワーカー数は最大3体まで同時（Redditの8体より小規模）
  • Run limits and contextで課題数・アーキテクト巡回数・ワーカー出力の要約度を制御。これはワークフロー上限で、ドルの予算ではない
  • この組み合わせを「budget coding」プロファイルとして保存すれば、次回からモデルを選び直さず切り替え可能
プロファイル保存が地味に便利。「安く回すチーム」と「全力チーム」をワンクリックで使い分けよう
11

⑪プロジェクトルールを2つ登録

RULES
  • JevアシスタントのProject Rulesから登録（タスク操作の「review」に具体ルールを追加）
  • ルール1: ゲームエンジンはブラウザーの画面（interface）を読み取ったり変更したりしない
  • ルール2: ゲームルールの変更には、影響を受ける動作への意味のあるテストを必ず含める
  • ルールの保存だけでモデルは呼ばれない。後で保存済み変更と照合する。タスク依頼にも含めて、ワーカーに事前期待を伝える
# Project Rules（イメージ）
1. エンジンは interface（画面）を読み書き禁止
2. ルール変更には影響範囲のテストを添える
→ 保存時はAPI消費なし / レビュー時に照合
「守らせたいこと」を言葉で先に置いておくのがコツ。後のレビューがルール照合だけになる
12

⑫マインスイーパを依頼するプロンプト

BUILD
  • 題材はマインスイーパ。ゲームルールと画面（interface）作業に自然に分かれるので分業向き。スクリーンショットの見た目判定ではなく、実際の動作テストで検証できる
  • アーキテクトへの依頼要件: 難易度・タイマー・フラグ・初手安全・キーボード操作・ベストタイム保存
  • 指示の要点: エンジンインターフェイスとファイル所有権を先に定義 → エンジンとテストはlogicへ、レイアウトと操作系はinterfaceへ → 独立作業は並列実行 → チェックポイントとブロッカーを求める → 最後にレビューして統合
  • Jevへの指示: 使えるときだけワーカー提案と保存済み変更チェックに選択的に使い、必要な文脈抜粋を活用。結果は助言として扱い、Jevが使えなければ通常どおり続行。ゲームは実際のテストで検証
  • 完全版プロンプト（ブラウザーチェック含む）は動画概要欄にリンク
Build: ブラウザで動くマインスイーパ
- 難易度 / タイマー / フラグ / 初手安全
- キーボード操作 / ベストタイム保存
- 先に「エンジンAPIとファイル所有権」を定義
- engine+tests → logic / layout+controls → interface
- 独立作業は並列 / checkpoint & blocker を報告
- 最後にレビューして統合
依頼文の肝は「先に境界を決めさせる」こと。雑に「全部作って」だと破綻する
13

⑬委任の様子を観察する

WATCH
  • まず見るべきはアーキテクトが実際に委任しているか。合意済みインターフェイス付きの別々の課題割り当てがあるのが理想
  • エンジン側は盤面の状態とゲーム操作を公開し、画面側はその使い方を知っている必要がある。さもないと「どちらもそれなりに動くが噛み合わないコード」が出来る
  • チームは共有チェックアウトを使い、宣言済みファイルスコープの重なりを調整。それでも賢明な境界線が重要。両ワーカーが同じページを書き換えるのは事故のもと
  • 会話右側のArchitect and Workersパネルで課題と状態を確認。ワーカーをクリックすれば応答・ツール活動・最新チェックポイントを読める。本体の会話は散らからない
  • ワーカーはアーキテクトや仲間と通信可能。画面側がエンジンの応答仕様変更を求めれば、課題を上げてアーキテクトが調整
  • チェックポイントには進捗・次の一手・ブロッカーを記録。数ラウンドに及ぶタスクで有効
課題割り当て 並列実装 checkpoint報告 レビュー＆統合
放置してよいのは「境界が決まった後」。決まる前は人間がインターフェイスの合意を見届ける

第4章: Jevの3つの使いどころと仕上げ

CHAPTER 04
14

⑭Jev活用①: Find Context（文脈検索）

用途1
  • シチュエーション: エンジンと画面の契約（contract）を議論した後、その合意内容をもう確認したい
  • JevアシスタントのFind Contextで「エンジンと画面の間で合意した契約は何？」と質問。抜粋をプレビューしてから検索を実行
  • 結果は最近のタスク会話から関連する原文を返す。履歴を書き換えないし、全ファイル・全ワーカーの記録を横断する検索でもない
  • 合意が直近の範囲外なら元のワーカー会話を開く。長期タスクの一貫性はチェックポイントと会話履歴が主役。Jevに全部覚えさせる設計にはしない
「さっきどう決めたっけ？」を即取り出せるのが便利。ただし補助輪であり主役ではない
15

⑮Jev活用②: 変更内容のレビュー

用途2
  • ワーカーが落ち着いたら保存済み変更（saved changes）を開く。見たいのは差分（diff）と実際のテスト出力であって、「全部できました」という自信満々な文章ではない
  • ワーカーまたは保存済みdiffからReview with Jevをクリック。「求められた動作を利用可能な証拠がカバーしているか、検証の抜けを指摘して」と依頼
  • Preview evidenceで評価対象を事前確認。レポートは根拠のない主張や不確実さを指摘できる
  • 例: ワーカーが「ベストタイムは保存される」と主張するのに関連するテストもブラウザー証拠も無い→要調査
  • チェック自体はテストを実行しない。次に何をするか決めるのはアーキテクトのまま
  • レビューは完了したワーカーに対して。実行中に見れば「未解決」として扱われ、終わるまで呼び続ける意味はない
  • 保存済み変更をプロジェクトルールと照合: エンジンが画面コードから分離しているか、ルール変更に意味のあるテストがあるか。ファイル単位の判定なので、指摘されたらソースdiffを開く
  • Use report in promptで結果を下書きに追加し、アーキテクトに調査させ、該当ワーカーへ的を絞った追加指示を出せる。レポートを開いただけで送信されることはない
「証拠はあるか？」を機械に問わせるのがJev審判の真骨頂。自信と根拠は別物
16

⑯Jev活用③: ブラウザーでアプリをテスト

用途3
  • アーキテクトにローカルプレビューを起動させ、Bambooのブラウザーパネル／ローカルサーバー一覧から開く（オプションのブラウザー統合を有効化しておく）
  • Test with Jevをクリックし、具体的な旅程を指定: ゲーム開始 → マスを開く → フラグ設置/解除 → 再スタート → 難易度変更 → ゲーム画面で終了 → 失敗した操作を報告
  • Jevは独立したChromeセッションを駆動するため、自分のブラウザーのタブやログインCookieは使わない
  • ビルド時のプロンプトでタイトル「Minesweeper」と難易度・New Gameの表示ラベルを求めておくと、タイトルと可視テキストが独立した最終チェックに使える
  • 操作がレポートにストリーミングされ、スクリーンショットも検査可能

結果の読み方に注意

  • Agent finished＝ブラウザーエージェントが「終了した」だけ。Checks passed＝指定した個々のアサーションが通った
  • タイトルが正しいだけでは地雷配置やタイマー論理の正しさは証明できない。エンジンテストは残し、ゲームプレイも目視で確認
  • モバイルプリセットで2回目のチェックを実行し狭いレイアウトも確認。キーボード操作は手動で、ベストタイムは再読み込み越しに検証
  • 自動化は未対応の操作で止まることがある。停滞は成功と数えず、制限として報告させるのが正しい運用
「動いた気分」と「確認できた」は違う。旅程を言語化して渡すのがテストの質を決める
17

⑰修正ループを回す

FIX LOOP
  • 例えば難易度変更後もタイマーが動き続ける場合、その正確な動作をそのままアーキテクトに返す
  • アーキテクトは的を絞った修正を割り当て、影響するテストを再実行し、同じブラウザー旅程を繰り返す
  • 新しい証拠が出たら、修正後の保存済みdiffを再度Jevでチェック
  • 目指すループ: 明確な割り当て → 実装 → 有用な証拠 → 的確な修正。Jevは要所のみ。開発の主体はアーキテクトとワーカー
  • Jevなしでも同じ流れは可能: 通常のワーカー会話・diff・テスト・ブラウザーパネルで回す。判定機能だけ有効化して画面は自分でテストする選択肢もあり、チーム機能だけを使うために他のモデルサービスは必須でない
  • 運用tip: チームメイトのメッセージやレビュー待ちでアーキテクトを呼び戻せる。一時停止・再開・停止の操作もあり。同じブロッカーが繰り返すなら、追加ラウンドにお金を使う前に状況を確認
失敗を報告 的を絞った修正 テスト再実行 Jevで再評価
「丸ごとやり直し」ではなく「ここだけ直す」。小さいループを速く回すのが安く仕上げるコツ
18

⑱コスト戦略とまとめ

ECONOMICS
  • まず実際に分離できる作業から始める。独立した2コンポーネントならチーム編成の正当化になる。1行変更に2ワーカーと複数回レビューは不要
  • 割り当ては具体的に、チェックポイントは簡潔に
  • 安いモデルが繰り返し詰まるなら、強いワーカーの方が総額では安く上がることも。最安のトークン単価＝最安の完了タスクとは限らない
  • コスト比較にはアーキテクト＋ワーカー＋再試行＋Bamboo月額＋Jev/ブラウザーヘルパー利用を込みで計上
  • 追加チェックは反復調査を省けるときだけ使い、ラン全体を計測する。モデルを足すだけでトークンや時間が節約されるわけではない
  • 投稿と同じMCPアプローチで自作してもよい。今回は1か所でチームを選び、進捗を追い、整ったUIでレビューできる点を評価
  • まとめ: 月20ドル・アルファ版だがアーキテクト&ワーカーのワークフローが内蔵で、プロファイルの再利用が容易。Jevは周辺の興味深いオプションチェック。既存モデルから始めて、役立つときだけ追加すればよい
「速く・安く・賢く」の正体は仕組みの工夫。まず手持ちのモデルで始めて、足りないぶんだけ足す
