⑦Dart Bridge: 同一プロセス通信

アーキテクチャ刷新 sockets → in-process
  • 旧バージョンではPythonと描画エンジンがソケット経由でメッセージをやり取り。2つのプログラムがメールを交換するようなものでした
  • 新方式の Dart Bridge では、PythonとFlutterエンジンが同一プロセス内で直接対話。手紙の往復と、隣の人に声をかけるくらいの差です
  • より高速で信頼性が高いため、ライブチャートストリーミング画像が実用的な速度で維持できるように
旧: Python ⇄ sockets ⇄ Flutter 新: 同一プロセス内 Dart Bridge

⑨Flutter MCPサーバーが鍵

MCPClaude / Cursor 対応
  • MCPとは、正確な最新情報をAIコーディング支援ツールに直接供給する仕組み。ClaudeやCursorなどで使えます
  • 普段AIは古い学習データからFlutterコードを推測して書くため、見た目は問題なくても実行できない古いメソッドだらけ。書いてもいないコードのデバッグに1時間を溶かします
  • Flutter MCPサーバーを接続すれば、支援ツールが現行のバージョン固有のFlutter APIを参照。推測が消え、最初から動くコードが返ってきます

  • 本物のAPIを参照しているから最初から動くコードが手に入る。「器用なデモ」と「本当に使い続ける道具」の分かれ目はここにあります

⑪Pytestでパッケージ済みアプリを検証

自動テストデスクトップ / モバイル
  • Flet 1.0では自分のアプリにPytestで本物のテストを書けます。デスクトップでもモバイルでも、パッケージ済みアプリに対して実行できます
  • テストはボタンを押し、フィールドに入力し、一連のユーザーフローを最後まで歩く動作検証。全体が崩れていないか確認できます
  • スマホではスクリーンショット比較まで対応。誰よりも先に表示の崩れを捕まえられます
  • これこそ週末プロジェクトと、人が依存していい道具との違いを分けるもの
# PytestでUIを検証: ボタン押下〜入力〜フロー完走
def test_signup_flow(page):
    page.click("送信")
    page.type("名前", "Pippa")
    assert page.total_joined == 1

⑫宣言的UIで大きなアプリ破綻防止

Declarative UI状態ベース
  • ボタンやラベルを1つずつ手で配置する代わりに、アプリの状態に基づいて画面を記述し、Fletが常に最新に保つ方式です
  • 小さいアプリでは違いはほぼ分かりません。しかし成長するアプリでは、後の混乱を本気で防ぎます
# 宣言的UI: 状態を書けば画面はFletが同期
ft.Container(content=ft.Text(
    f"メンバー数: {state.count}"))

⑬旧バージョンからの移行は注意

0.28ユーザー向け警告フル再構築
  • 旧Flet（例: 0.28）を使っている場合、安易にアップグレードして祈るのは厳禁。Flet 1.0は完全な再構築です
  • APIが変わり、名前が変わり、アプリの内部動作方式まで変更されました
  • 既存アプリは公式の移行ガイドに従って慎重に。コードの実行方式に関する特定の変更により、雑なアップグレードは動作が重く感じられる原因になります
  • 新規プロジェクトなら無縁の話。1.0で新規作成→即GOで問題ありません
