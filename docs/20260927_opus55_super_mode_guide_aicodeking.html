ガイドの全体像

①

公式ガイドの概要

  • AnthropicがClaude Opus 5.5の活用ガイドを公開。著者はAddy Osmani氏（Claude開発者ブログ）
  • テーマは「日常のコーディングで効く実践的なアドバイス」
  • 注意点が2つ: フラグで旧モデル切替とfast modeの別料金
「carefully考えて」といった指示を消すだけで良くなる、って面白いよね！
②

「完成の定義」を明確に

  • Opus 5.5は長いコーディング仕事向けに位置づけられている
  • 長い作業ほど最初のリクエストが重要。モデルは「どこまでやるべきか」を知る必要がある
  • 巨大な仕様書は不要。ただし受け入れ基準になる細部は最初に伝える
「ここまで出来たらOK」というゴールラインを、スタート時に示すのがコツだよ！
③

実例: ノートアプリの検索

  • 検索はタイトルと本文の両方を対象にする
  • 大文字小文字を無視してマッチさせる
  • ノートを編集したら結果が更新される
  • 空の検索は全ノート表示、ヒットなしは役立つメッセージを表示
挙動を箇条書きで描写するだけで、評価しやすい依頼になるんだ！
④

検証できる依頼にする

  • 依頼内容: ①挙動を実装 → ②実行中のアプリで確認 → ③できなかったチェックを報告
  • 既存ノートの保存形式の変更は事前相談を条件にする
  • 見た目の良い検索バーだけでは不合格。タイトル検索・編集・更新を自分で試して判定
エージェントが戻ってきたとき、自分で試して判定できる依頼にしよう！

thinking と effort の使い方

⑤

adaptive thinking と effort

  • Opus 5.5はadaptive thinking が常時ON
  • effort設定が1回答に込める工作量を制御。デフォルトはmedium
  • 高いeffortはトークン増・時間増。小さな編集を毎回最大にする必要はない
まずmediumで自分のタスクと比較して、難しいバグだけ引き上げるのがおすすめ！
⑥

「think carefully」は削除

  • Anthropic推奨: think carefullyのような汎用指示を保存済みプロンプトから削除
  • 蓄積した指示をレビューし、各自の目的がまだあるかを問い直す
  • 「エッジケースを確認せよ」のような具体的要件は有用。「極めて賢くあれ」はノートアプリに何も伝えない
曖昧な賢さの要求より、具体的要求。これがeffort時代の新しい礼儀だね！
⑦

説明の求め方

  • 求めるべき説明: 決定の理由・前提の記述・確認したい計算
  • 内部推論のトランスクリプトは要求しない。それなしでも十分役立つ説明が得られる
「なぜその判断をしたのか教えて」が一番効く質問かも！
⑧

途中で止まる問題への対処

  • エージェントの悩みの種: 明らかな残作業があるのに停止
  • 繰り返しの好みはCLAUDE.mdに記載。ルーティン作業は継続し、本当に必要な決定だけ尋ねるルールを書く
# CLAUDE.md 記載例（ノートアプリ）
- チェック成功後は残りの検索挙動を継続すること
- 一部がブロックされたら、 blocker を説明し
   独立した作業を進めること
- 保存形式の変更やノート削除は事前に相談
「最後まで走って、分岐点だけ聞いて」をファイルに書いておくのがポイント！

長いジョブの管理

⑨

CLAUDE.mdはガイドに過ぎない

  • 境界はプロジェクトによる。新しいコードベースの学習中は変更前の簡単な説明を好むことも
  • 実装方針が合意済みなら、できる仕事は最後までやらせる
  • CLAUDE.mdはモデルへのガイド。権限チェックは別途維持（特に破壊的コマンド）。ファイルに文を書くだけでは境界を強制できない
お願い文と権限設定は別物。安全性はツール側の設定で守ろう！
⑩

tasks.mdで進捗管理

  • 長いジョブはtasks.mdに残作業・完了チェック・ブロッカーを記録させる
  • セッションがいっぱいになるとClaude Codeは過去の会話を要約する。ファイルなら次の作業区間に具体的な情報を渡せる
  • 「全部完了」でもブラウザテストが未実施なら、質問すべき箇所が一目で分かる
会話の圧縮に負けないよう、状態はファイルに外置きするのがコツ！
⑪

ハンドオフとフォローアップ

  • 停止前に短いハンドオフ記録を依頼: 何が変わったか・何が失敗したか・どこから再開するか
  • セッションを閉じて翌日戻ってきても、その記録が役立つ
  • 作業中に要件を思い出したら具体的なフォローアップを送る（例: 検索はアクセント付き文字も処理する）。タスクのどの部分を変えるか分かるように
「あとそれも」じゃなくて「検索のこの部分をこう変えて」が正解！
⑫

サブエージェント活用

  • 独立した部分があるならサブエージェント。独自コンテキストを持ち、調査結果を本体に返す
  • 割り当ては狭く: ①ノートの読み込み方法の調査 ②既存検索テストの網羅調査
  • レポートは該当コード or 再現可能な失敗を指すべき。証拠を確認してから受け入れる
  • ボタンラベル変更にチームは不要。調整コストとトークン増に見合う規模で使う
複数サービス横断レビューは並列調査が効くよ。でも鵜呑みは禁物！

フロントエンドと視覚的理解

⑬

「AIっぽい見た目」の直し方

  • 「generic なAI感を避けて」のような曖昧な依頼は、別のデフォルトスタイルを生むだけ（Anthropicの指摘）
  • 除外したいパターンを名指しする。さらに一歩進めて使いたいものを描写
  • 例: コンパクトなサイドバー・読みやすいテキスト・常時見える検索欄。巨大なウェルカムパネルは毎回画面の半分を奪わない
「もっと高級感て」の繰り返しより、はるかに良いデザイン会話になるよ！
⑭

具体的フィードバックとスクショ

  • 結果を見て具体的に: サイドバーが広すぎればそう言う。抜粋が読みにくければ理由を説明
  • Opus 5.5はチャート・図・スクショの読み取りが向上。画像を添えて詳細を直接質問
  • 賑やかなUI: 何が注意を奪い合っているかを聞き、実際のスクショに紐づく変更を依頼。図には答えを支えるつながりを同定させる
  • 密集した画像でも読める版の提供は必要。視覚理解が向上しても小さなラベルは魔法のように読めない
スクショ1枚貼るだけで、デザイン議論の精度が段違いになる！
⑮

長文ドキュメントと成果物

  • 長いドキュメントのチェックにもClaudeを活用
  • 完成品が必要なら完成ファイルをそのまま要求: 例ダウンロード可能な比較スプレッドシート
  • 要件は具体的に: ソース列つき・欠損情報の欄を分ける。確認して共有できる形に
説明文じゃなくて「渡せるもの」で受け取る。これが仕上げの形！
⑯

コーディング結果の検証

  • 最終レポートは要注意箇所から開く。アクセス不足で実行できなかったチェックは即見える化
  • 報告書式を指示に含める: 実行したチェックと推測の区別・テスト結果・残った失敗・変更の簡単な説明
  • diffレビューはユーザー影響のある失敗に絞る: 編集後も古い結果・消えたノート・保存データの誤変更。再現に足る詳細を求める
  • 自分でも試す: 特徴的な単語のノート作成 → 検索 → 単語変更 → 再検索。古い結果が残っていればレビュー案件
「全部動きます」の自信満々より、自分の手で確認した1チェックの方が説得力がある！

注意点とまとめ

⑰

フラグと旧モデル切替

  • Opus 5.5には生物学・サイバーセキュリティ分野の追加保護がある
  • フラグされたメッセージの多くは旧モデルへの切替となり、会話はそこで続行。通知が出たらモデル名を要確認
  • チェックは過去の会話・添付ファイル・検索結果も含む。戻すと再フラグの可能性も
  • 正当な作業も誤ってフラグされ得る。通知＝リクエストの faults と決めつけない
# Claude Code での操作
/model    # Opus 5.5 を再選択
/config   # 自動切替の設定変更
/feedback # 誤フラグを報告
# Claude アプリ: 設定 → 機能
出力の調子が変わったら、まずどのモデルが答えているか確認してから考えよう！
⑱

fast mode・料金・まとめ

  • 標準API: 入力$4 / 出力$20（100万トークンあたり）。月額サブスクとは別物
  • fast modeは /fast で切替。研究プレビューで出力最大2.5倍。料金は入力$8 / 出力$40
  • サブスクでは有償の従量クレジットが必要（含まれる利用分が残っていても）
  • 使う基準: 返信待ちが仕事を妨げているときのみ。スロービルド中の高速テキストは意味がない
  • 長いチャットの遅いフォローアップ: 「現在の質問に集中し、過去の回答は確定として扱う」指示も選択的に活用
まず既存アクセスで試せるワークフロー改善から。速さにお金を払うのはその後でいいよ！
🎁

まず1つの実タスクから

  • 最も有用な最初の一歩: 1つの実タスクを選び、結果を確認しやすくすること
  • 期待する挙動を伝え、入力が要る場所を示し、終了時に証拠を求める
  • どの部分が一番の悩み？ 未完了タスク・汎用デザイン・事後チェックの時間をコメントで教えて
依頼を明確にするだけで、プランもeffort設定も変えずに問題が解決するかも！
