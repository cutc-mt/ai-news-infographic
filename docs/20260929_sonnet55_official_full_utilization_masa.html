PART 1 — なぜ今、Sonnet 5.5 なのか

①「5.5」の名を超えた進化

  • 実力は「5.6・5.7と呼びたくなる」レベル — まさお氏が太鼓判を押す仕上がり。
  • 「Sonnet」という名前だけで敬遠していた層が、使い直すべき状況に。
  • 「Opusがあるからいいや」と思っていた本人もびっくりするほど良好だったと告白。
モデル名で判断せず「実力で選ぶ」— これが今回の大前提なのだ。

②情報源は「公式」にあり

  • 公式プロンプトガイド・DevBlog・公式ツイートの内容を集約して解説。
  • まさお氏自身の実使用感も加え「効くところ」だけをピックアップ。
  • 氏の運用: サブエージェントにOpusとSonnetの両視点でフィードバック→フェイブルで統合。
噂ではなく一次情報ベース — 「公式が推奨する使い方」をそのまま学べる動画なのだ。

③総論: プロンプトは「減らす」方向へ

  • Sonnet 5時代のプロンプトは変更なしでも動くが、公式は「ここは変えろ」と明示。
  • かつての回避策・小細工は他の調整より先に削除してよい(公式見解)。
  • プロンプトやフックで補っていた自律性は、モデル側に組み込まれた。
「足すプロンプトエンジニアリング」から「削るプロンプトエンジニアリング」へ — 時代が逆転したのだ。

④CLAUDE.md を総点検せよ

  • Claude Codeはシステムプロンプトを8割削減(7月24日頃のトレンド)。
  • 削除候補の見つけ方: /doctor のプロンプトオーディットで冗長な指示を可視化。
  • 複雑な指示なしでも意図通り動く今、移行時に1回総点検が最優先タスク。
Sonnet 5 → 5.5 へ乗り換えるなら「最初にやる作業」はこれなのだ。
PART 2 — 公式プロンプトガイドの要点

⑤注意力は有限リソース

  • 矛盾する複数の指示・細かすぎる指定は注意力を分散させる。
  • 公式が繰り返す主張: 「できる限りシンプルに」してモデルを迷わせない。
  • 判断に迷ったらモデル本人に聞く —「このCLAUDE.mdで迷わない?」と複数問いでチェック。
指示は「迷路」ではなく「一直線の道」に — モデルの頭の使い方を設計するのだ。

⑥NGリストは「くぐり抜けられる」

  • 禁止・NG系を書いても回避ハックで抜け道を探されることがある。
  • 公式の推奨は判断基準を1つだけ渡す→周囲の情報から判断させる方式。
  • 細かいルールで縛るほど弱い — 方法論(ハウ)の記述は軽くしてよい。
「あれするな」の列挙より「この基準で判断しろ」の一本 — 守りはシンプルなのが正解なのだ。

⑦昔の「呪文」は逆効果に

  • Sonnet 5時代の「怠けるな」系プロンプトは、今は効きすぎてオーバーな行動を誘発。
  • 「よく考えて」等の言葉での調節は不要 — effortパラメータで置き換えるのが公式流。
  • モデルの癖を見ながら個別に調整する意識が今は重要。
増築した古い呪文が「暴走スイッチ」になっているかもしれない — 点検必須なのだ。
PART 3 — エフォート(思考量)の教科書

⑧effort階段の基本

  • Haiku以外の全モデルが effort レベルに連動 — トークン消費が変わる。
  • medium以上は挨拶ですら少し考える — 思考のON/OFF感覚を更新しよう。
  • 思考を減らしたい時は言葉ではなく effort を下げるのが公式の解答。
「頑張って」は呪文じゃなくダイヤルで調整する時代になったのだ。

⑨Sonnetの壁は medium/high の間

  • まさお氏の体感+ベンチから: medium と high の間にクオリティラインがある。
  • Sonnetならmedium〜highの切替点を最初に意識するのが得策。
  • xhighは天井を掘り続ける手段 — ある程度Sonnetでできる今は使い分けの時代。
「どの段で壁を越えるか」を知っているだけで、コストと品質の両取りができるのだ。

⑩effortは「時間とコストを買う」

  • xhighはその分トークンを消費し時間がかかる — 1タスク完了コストに直結。
  • 「mediumでできる物はmediumで、highでできる物はhighで」が公式の合言葉。
  • 速度面でも効く — effort選択はコスト×速度のトレードオフ制御そのもの。
「とりあえず最高設定」は今や浪費 — 適正段階を選ぶのが腕前なのだ。

⑪effortの効能と限界

  • 公式見解: effortは見落としを減らす — だが方針の違いは減りにくい。
  • 方針が問われる重要タスクはhigh以上をきちんと使うのが正解。
  • バランス感覚は定量評価が困難 — 評価( evals )を作ることで対応を。
「見落とし可」の軽タスクと「方針が命」のタスク — 仕分けが節約の出発点なのだ。
PART 4 — 実害パターン別・処方箋

⑫止まる・書きすぎる

  • low/medium で途中で止まるなら、まずはeffortを上げるのが公式の処方。
  • 頼んでもないテスト・文書を量産するなら、タスク範囲を絞る。
  • 対処の核心: 徹底ぶりを「広さ」から「深さ」へ — タスクの内側に向ける。
「もっと頑張れ」ではなく「範囲を狭めて深く」— 指示の方向を変えるのがコツなのだ。

⑬無言時間・推論の漏れ

  • 気になるなら「最後のまとめ報告」を消す設定が有効 — 無言対策にはdisplayUpdate系・β機能を。
  • 無言が続く時は「短い声かけ」を追求 — Opus 5.5時代と同じ作法。
  • 推論を本文に書かせると出力カテゴリ判定に失敗することも — 「理由が欲しい」と欲しい形で頼む。
沈黙の長さも「見せたい物は見せ方ごと指定する」— 細部まで設計対象なのだ。

⑭インジェクション訓練の落とし穴

  • ユーザー発言をツール結果に追記すると、プロンプトインジェクションと疑われ拒否されることがある。
  • 原因は新しいモデルのセキュリティ訓練 — 攻撃ではなく仕様への適応が必要。
  • 発言の伝え方(経路)を設計し直せば回避できるのが今回の学び。
「なのに動かない」は模型的に正しい反応だった — 情報の通り道を見直すのだ。

⑮「自信があっても検索で確かめる」

  • Sonnet 5.5の特徴: 検索すべき場面で学習知識のまま答えることがある。
  • 処方: プロンプトに「自信があっても検索で確かめる」を組み込む。
  • ツールを絞ると、モデルの素の能力で調節してくれる場合もある。
賢いモデルほど「知ってるつもり」の罠に注意 — 確認の一手を仕込むのだ。
PART 5 — 道具の設計とモデル編成

⑯言葉を足すより「道具」を設計せよ

  • 公式の結論: 言葉を足すより検証ツール等の「道具」を先に設計して渡す。
  • ツールなしより道具ありが成果を分ける — 最近のモデルに求められる要素。
  • 「まず検証ツールを作らせ、それから進める」という進行が有力に。
プロンプト職人から道具設計者へ — エージェント時代の技能シフトなのだ。

⑰モデル×effortは「グラデーション」

  • Sonnetが良いからとSonnet一辺倒は損 — 要求クオリティで選ぶ。
  • 要求ゾーンが低めならSonnet medium か Opus low — Sonnet xhighよりOpus mediumが効率的な事も。
  • Claude Code Projectsでは役割別に規定effort — 「軽く考えて」は書かず設定側で指定。
モデル×effortの掛け算で最適点を探す — 発想を「階調」に切り替えるのだ。

⑱まとめ: ルーター時代の幕開け

  • まさお氏の結論: モデルルーターを作り込み「このタスクはSonnet・この難易度はOpus」と自動振り分け。
  • カットオフが近くても新世代感・TPS(速度)・トークン効率でSonnet優位のシーンが拡大中。
  • OpenAI DevDay前の「先制ジャブ」 — 次はフェイブルでまた祭りの予感。
「削るプロンプト×effort階段×モデルルーター」— この三つ組がフル活用の鍵なのだ！
