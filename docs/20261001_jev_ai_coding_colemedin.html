② Jevの仕組み — stateと多肢選択

00:52 How Jev Works
  • 入力はstate（状況）＋多肢選択式の質問リストの2点だけ
  • 各質問に確率（信頼度）付きで並列回答——一気に全部答える
  • ClaudeやGPTのようなLLMとは全く違う仕組みの決断特化モデル
  • 回答をキーにワークフローを分岐できる——決断のAPIとして利用
state＋質問リスト 並列で確率回答 分岐へ
出力はテキストじゃなく「確率付きの判定」——ここがLLMとの決定的な違い！

③ 圧倒的な速度とコスト

00:52 How Jev Works
  • LLMでも構造化出力なら同様の決断は一応可能
  • しかしJevは意思決定でLLM比20〜200倍高速
  • コストは40〜1000倍安い（比較対象のLLMにより幅）
  • どのLLMと比較しても、決断に関してはJevが高精度・高速・低コスト
20〜200倍速い 40〜1000倍安い 決断はJevへ
20〜200倍速くて40〜1000倍安い——純粋な「決断」ならLLMの出番はもうない！

④ ユースケース1: エージェントが無謀すぎる問題

02:48 Security Hooks
  • AIコーディング支援はやりすぎる——環境変数の読み取りやフォルダ全削除も平気
  • グローバルルールやスキルで禁止してもコンテキスト肥大化すると抜け道を探す
  • 巧妙なプロンプトで回避手段を見つけて実行してしまう
  • だから必要なのは技術的なガードレール——破壊的アクションの阻止
ルールで禁止 それでも突破される ガードレールへ
ルールを書いても知的に突破してくる——だから強制力のあるフックが要るんだ！

⑤ pre-tool-useフックで防止

02:48 Security Hooks
  • Claude Code発の「フック」は今やほぼ全てのコーディングエージェントに搭載
  • エージェントのライフサイクルイベントに自動化を紐付けられる
  • 人気NO.1はpre-tool-use——ファイル読み取りやコマンド実行の直前に解析
  • 定番は.env読み取り検知——シークレットのコンテキスト露出を防ぎ、.env.exampleへの誘導も可能
ツール実行直前 解析 ブロック or 許可
ツールが動く直前に割り込む——ガードレールの設置場所はここ一択！

⑥ 従来手法のジレンマ — 高いか、ザルか

02:48 Security Hooks
  • LLMで全アクション解析は月数百〜数千ドル——ブロック自体はたまにしか起きないのに
  • 動画主の従来案は正規表現——Google認証情報の読み取りや削除をパターン一致で検知
  • しかし破壊的手口は無数: 直接読み取り、Pythonスクリプト、bashコマンド…リストが膨張
  • 取りこぼしだけでなく誤検知（偽陽性）も多発——完璧には程遠い
LLM＝高すぎ 正規表現＝ザル 第三の道へ
「.envって単語をMarkdownに書くだけ」までブロックする誤検知…ストレスだった！

⑦ JevGuardの設計

02:48 Security Hooks
  • pre-tool-useフックを正規表現版からJevGuardへ置き換え
  • 質問例: シークレット露出？ データ破壊？ 持ち出し（プロンプトインジェクション含む）？
  • さらに「タスクから逸脱していない？」——セキュリティ以外の監視にも流用
  • stateはツール名・効果・引数・作業ディレクトリで全体像を提示
state = {tool, effect, input, cwd}
questions = [secrets?, destroy?, exfil?, off_task?]
→ OpenRouter の decision エンドポイントで Jev 呼び出し
「タスク逸脱検知」まで任せられるのがニクい——model as a judge の守衛版！

⑧ 実測: JevGuardの衝撃結果

02:48 Security Hooks
  • 正規表現版: リスキーな呼び出しをあまりブロックできず誤検知も多い
  • LLM版（Haiku）: 良好だが1件1秒超・約0.1セント——日数千呼び出しで積み上がる
  • Jev: ほぼ全リスクをブロック・誤検知ほぼゼロ・0.25秒
  • 費用は1セント未満のさらに端数——LLM級の判断力が実質無料の体感
正規表現＝ザル Haiku＝1秒超 Jev＝0.25秒・端数円
0.25秒・誤検知ほぼゼロ・費用は端数——実質無料の警備員が常駐したようなもの！

⑩ プレイテストでバグを捕まえる

07:45 Gameplay Testing
  • 「ユーザーらしく遊ぶ」検証ステップがJevでついに現実的に
  • ユニットテストは決定的すぎる——LLM単体ではゲームをプレイできない

LLMがハーネス構築 Jevがプレイ バグ発見

⑪ 鉄則: JevはLLMの間に挟む

10:21 Sandwiching Jev Between LLMs
  • Jevを単独で使うことは基本的にない——4ユースケースに共通するパターン
  • Jevは決断が得意だが、stateや選択肢の設計はできない・結果への対処もできない
  • 基本形はLLM（構築）→ Jev（決断）→ LLM（対処）のサンドイッチ
  • Jevはワークフローの終点ではなく一部を高速化する部品——セキュリティ例ではブロック後、LLMが別策を考える
LLMで構築 Jevで決断 LLMで対処
「LLMで挟む」——この一行がJevを活かす全ての設計原則だ！

⑭ Jevの限界と役割分担

11:10 Browser Testing
  • JevはLLMのようにテキストを生成できない——万能ではない
  • サイトへの自由文入力などフリーフォームテキストが必要な部分はLLMのまま
  • 「何にフォーカスする」「どのボタンを押す」等の純粋な決断は可能な限りJevで
  • ブラウザ自動化ワークフローの大部分をJevドリブンにするのが今後の標準
生成はLLM 決断はJev 役割分担
「どこまでJevでいけるか」を見極めるのが腕の見せ所——決断は全部Jevに！

⑮ ユースケース4: ワークフロー分類

  • ワークフローを動的にしたい——タスク難度でモデルを使い分けトークン効率化
  • 仕事の種類に応じてスキルやステップを切り替えたい

イシュー流入 Jevが分類 適切なルートへ

⑯ Archonワークフローで実装

13:36 Workflow Classification
  • Archon＝動画主のオープンソースハーネスビルダー——大規模AIコーディングワークフローを簡単構築
  • グラフ可視化: GitHubイシューを入力しJevがモデルtierとルートを2重分類
  • ワークフロー全体はYAML 1本で定義——Jev呼び出しはPythonスクリプトに引数を渡すだけ
  • 質問は大量に並列投下可能——「仕事の種類は？」「必要なモデルtierは？」
  • tier例: 高速＝GPT-6 Terra／標準＝Sonnet 5・GPT-6 Sol／強力＝Opus 5.5・GPT-6 Astra
YAML定義 Jevが並列判定 後段が実行
テストでは難易度・種類の判定がとても優秀——YAMLで組める分類ゲートが強すぎる！

⑰ 分類の精度とコスト実測

13:36 Workflow Classification
  • イシュー分類ワークフローを12回実行 → 12回とも動画主が完全同意
  • PRレビュー用ワークフローも別に構築——全面アーキテクチャレビューか軽い修正かを分類

12/12同意 15/16正解 コストは端数
