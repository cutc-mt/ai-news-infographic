② 過剰適合（Overfitting）とは？

01:50 過剰適合とは?
  • eval の点数は上がるのに、本番では効かない現象
  • 例：OCR ツールの eval スコアが 95% → 実運用で文字読み取りがボロボロ
  • テスト用データにだけ答えを合わせ込んだ状態＝過剰適合
  • eval 改善を回すほど危険が増す——自動化するほど見過ごせない問題
eval スコア ↑ 本番精度は横ばい 「点数良好」の罠
点数が良い＝良い成果物、ではない！eval を信じる前に「本番で効くか」を疑うのが出発点。

③ train / test 分割で防ぐ

03:31 train と test に分ける
  • 問題を train（訓練用）と test（検証用）に分割
  • 両方でスコアが上がった修正だけ採用——これが今回の核心ルール
  • train だけ上がって test が停滞した修正は棄却
  • test スコアの評価は別の Claude インスタンスが担当——採点の独立性を担保
修正案 train ✓ test ✓ 初めて採用
機械学習の常識をそのままエージェント開発に持ち込んだ設計——これだけで品質騙しが消える！

⑤ 頼りになる eval の4条件

05:52 eval の4つの条件
  • ① 再現性：誰がいつ回しても同じ結果になる
  • ② 判別性：良い修正と悪い修正をきちんと区別できる
  • ③ 低コスト：何度も回しても財布が痛まない
  • ④ 改善との連動：eval スコア ↑ が本番品質 ↑ に繋がる
再現性 判別性 低コスト 連動性 信頼できる eval
まさおさん「train だけ伸びて test が伸びない事故、実際に回すとめちゃくちゃ起こります」——4条件は理屈じゃなく体験から来てる！

⑦ hillclimb の回し方

10:44 hillclimb の回し方
  • hillclimb＝Claude が改善案を自己提案 → 自己適用 → 採点を反復
  • 各試行は 成功 / 失敗 に分類されて記録される
  • train と test の両方で上がった修正だけ採用して積み上げる山登り
  • 失敗の履歴も学習材料——次の改善案のヒントになる
現状の eval 改善案の生成・適用 train/test 採点 採用 or 棄却
人間が「どの修正を入れるか」悩む時間を、ループが全部引き受けてくれる——これが自動 hillclimb の本質！

⑧ 過剰適合の原因と3つの防ぎ方

08:52 原因と3つの防ぎ方
  • 原因：eval 問題が狭すぎ／採点基準が甘い／同一モデルが採点など
  • 防止①：train / test 分割で汎化を検証
  • 防止②：独立インスタンスが採点——自己採点の甘さを排除
  • 防止③：現実的な多様な問題を eval に混ぜる
原因を知る 分割 ＋ 独立採点 ＋ 多様性 健全な改善ループ
「自分で書いた答えを自分で採点」は人間でも起きる事故——インスタンス分離は構造的な解決策！

⑩ claude-api skill の改善例

16:02 skill の改善例
  • .eval ディレクトリの YAML やスクリプトがskill の改善対象
  • skill 内の YAML 定義を hillclimb が自動で書き換え
  • スクリプト（採点ロジック）も改善ループの対象に
  • 改善 → 採点 → 採用の自己改善サイクルが skill 単位で回る
# 改善対象の例（イメージ）
.claude/skills/claude-api/
  ├─ skill-definition.yaml  # ← 自動書き換え
  └─ eval/run_eval.py       # ← 採点ロジック
skill が eval で鍛えられ、鍛えた skill が次の開発を強化する——自己増強のループが回り始める！

⑪ skill / eval / harness 関係

16:02 前後の補足解説
  • skill：Claude に手順を教える定義（YAML 等）
  • eval：skill の良さを数値で測る試験
  • harness：生成 → 採点 → 改善を回す仕組み全体
  • 3層が揃うと自己改善する開発基盤が完成
skill（手順）× eval（試験）× harness（ループ） 自己改善
単発の機能じゃなく「測って・直す」土丸ごと自動化する構図——これが今回の記事の真価！

⑰ eval 設計チェックリスト

05:52 4条件の実践版
  • 問題の多様性：現実の入力の偏りを反映しているか
  • 採点の独立性：採点者が改善者と別か
  • train / test の隔離：test が改善に漏れていないか
  • 反復コスト：何十回回しても破産しないか
多様性 ✓ 独立性 ✓ 隔離 ✓ コスト ✓ 信頼できる eval
hillclimb を回す前にこの4項目を点検——土台が甘いと自動化が爆速で失敗を量産するだけ！
