② 本命は「内部ハーネスへの介入」

01:21 Mods の本命
  • ターミナルでずっと向き合っている人にはプレビュー系も良いが、まさおさん個人的にはしっくり来なかった
  • 有力なのは純正のコマンドを自分なりにカスタムすること。例えばスラッシュゴールの中身を自作するなど
  • スラッシュコマンドで細かいことをやり、より決定論的にハーネスを組みたい場合に Claude Mods は非常に強力
  • バズっているレビュー系 Mods やテトリスなどは「本命ではない」というのが個人的な見解
エージェントの動きを設計 決定論的なハーネス それを Mods で実現
「エージェントの動きをどうするか」に注目するのが強力、というのが伝えたい根本ポイント！

③ スラッシュゴールの弱点とは

02:02 純正 /goal の仕組み
  • 純正スラッシュゴールの仕組みは、監視役の軽量モデルがゴールの条件文と実際のセッションを見て達成判断する形
  • 「ゴールしちゃダメなのにゴールしてる」のような抜け漏れを経験したことはないだろうか
  • そこで厳しめの判定やフィードバックを与えながら回す「マサゴール」を自作してみた
  • 純正の中身が気に入らないとき、Mods で自分で実装してしまうのが近道
条件文とセッションを参照 軽量モデルが判定 抜け漏れが発生
「ダメなのに達扱い」——あの経験、モヤモヤしませんでしたか？

④ 自作の「マサゴール」を紹介

02:02 マサゴール誕生
  • 「マサゴール」はまさおさんが Claude Mods で自作したスラッシュゴールの強化版
  • Codex と Sonnetがレビューを行い、合格したら通し、そうでなければフィードバックを返す実装
  • ひらめいたハーネスの設計パターンを Mods の中でそのまま実現できるのが魅力

純正 /goal 不満を洗い出す 自作マサゴールへ改造

⑤ 判定者を2つにする設計判断

03:34 なぜ2モデルか
  • 1つのモデルだけで判定していると、抜け漏れが出てしまうことがある
  • そこでSonnet（Claude 系モデル）とCodex exec（GPT 系モデル）の2つを判定者に採用
  • 両方が OK となったときだけゴールを解除し、そうでなければ次のタスクとして続きを送る
  • この2モデル判定は「調節する設計パターン」として、より良いゴール作りの参考になる
ターン終了 Sonnet と Codex exec が判定 両方 OK でゴール解除
異なる系統のモデル2つで判定すれば、見落としがグッと減ります！

⑥ マサゴールの動作デモ

04:34 デモと判定の様子
  • /masagoal コマンドで指示。「洗練されて視覚的にも優れた Todo HTML を1枚」という依頼を投入
  • ターンが終わるたびに判定が入り、判定回数がプレビューに表示される（例: 判定4回でゴール）
  • 不合格ならフィードバックが返ってくるため、親セッションがその分しっかり叩き直される
  • 実際に試すとゴール解除の精度が上がるのを体感できた
指示 作業 ターン終了で判定 不合格なら続きを送る
スラッシュゴールより厳しめ。メインの親セッションがびしばし鍛えられます！

⑧ Mods が入り込める場所いろいろ

⑨ プラグインとマーケットプレースの関係

05:48 Mods の居場所
  • Claude Code にはプラグインという大きな概念があり、その上にマーケットプレースが存在する
  • 第三者がマーケットプレースから入れて、プラグインをオンにして使う流れ
  • これまでにもSkills・Agents・Hooksという仕組みがあった
  • 従来の Hooks は外のコマンドを呼ぶ形だったが、Mods はClaude Code の中で動く部分を維持し、動きの途中に入って書き換えられる
プラグイン概念 マーケットプレースで配布 Mods が内部に干渉
「ファンクションフック（function hooks）」のように内部の関数に引っかかるのが Mods の正体です！

⑩ Mods の定義のしかた

07:26 定義方法
  • 定義用のフォルダにファイルを配置していく、お作法ベースのスタイル
  • 本体は registered.tsx のようなファイルに書いていく
  • 「こういうイベントが来た時に、こういう処理をしますよ」という形で本体を記述するのがお決まり
  • 配布はマーケットプレース経由。入れてもらって、プラグインをアクティブにして使ってもらう
// Mods の本体イメージ（registered.tsx）
on("turn_complete", async (event) => {
  // ここに判定や書き換えなどの処理を書く
  return { next: "続きを送る" };
});
「イベントが来たら何をするか」を書くだけ——シンプルです！

⑪ イベントでできること

07:26 イベントの力
  • イベントが発生したら、Claude Code 本体の動きに対してプロンプトを渡すことができる
  • イベントから入ってきた中身を書き換えて渡すことも可能
  • 渡す前の段階でMods が処理を断る（ブロックする）ことさえできる
  • 例: .env などの危険なファイルの書き込みを止める／シークレット情報を判別して隠してから渡す
イベント発生 プロンプト追加・書き換え ブロックも可能
危険な書き込みを止められる——安全弁としても使えます！

⑬ マサゴールが使うイベント

11:26 イベントの流れ
  • マサゴールが使うのは session_start・turn_start・ui_render・command_run・turn_complete など
  • turn_start から turn_complete の間を何度も繰り返すのが、いわゆるループの正体
  • 実際は LLM ジャッジのループで、process_run・model_complete も使って2モデルに判定させる
  • まさおさんが実際に使うのは Sonnet と Codex exec の2モデル（GPT 系の Astra や Sol なども判定者にできる）
turn_start 作業 turn_complete で判定 繰り返し
スラッシュゴールの中身を、自分でカスタムしたループに組み替えられます！

⑭ 判定ループのシーケンス

11:26 流れを図解
  • Claude Code のターンが終わったタイミングで、Mods にイベント通知が来る
  • マサゴールは session のメッセージから会話の記録を読みに行く
  • その記録を元に Sonnet と Codex exec が判定（LLM ジャッジ）
  • 判定結果に応じて、まだなら理由を添えて続きを送り、次のターンを開始する。この繰り返しがループ
// 判定ループの疑似コード
on("turn_complete", async () => {
  const log = await readSessionMessages();
  const ok1 = await judge("sonnet", log);
  const ok2 = await judge("codex-exec", log);
  if (ok1 && ok2) return releaseGoal();
  return submitNext(withReason(ok1, ok2));
});
「読んで、判定して、送り返す」——この一本道がすべてです！

⑯ 最近のトレンドは「外ループ」寄り

14:45 トレンド分析
  • 最近のトレンドは内部ハーネスより外側のループ（外ループ）。dots のようなエージェントが続々と登場している

⑰ 作り方と注意点

16:47 実践のポイント
  • Claude Code の中にプラグイン作成の支援が入っており、「こういう Mods が欲しい」と言えばいい感じに作ってくれる
