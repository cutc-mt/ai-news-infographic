② Pi とは何か — エージェントハーネス

テーマ: 基本の復習
  • Piはオープンソースのエージェントハーネス。会話を管理し、モデルにツールを渡し、実行して、結果を持ち帰って作業を続けさせる
  • ターミナルから、プロジェクトの調査・ファイル編集・コマンド実行、ドキュメントやデータを扱うタスクまで利用できる
  • 使いたいモデルは自分で接続する仕組み
  • 魅力はカスタマイズ性。スキルと拡張を足し、インターフェースを変え、独自のワークフローを組める。長く使う道具ほど「自分で直せる」のが効く
会話の管理 ツールの実行 結果の持ち帰り 作業の継続
「ああすれば良かったのに」を自分で変えられる——それがPiの設計思想です！

③ なぜMCPを取り入れたのか

テーマ: 方針転換の背景
  • Piは以前、ネイティブMCP対応をあえて入れないことを売りにしていた
  • チームが考えを変えた理由: ツール呼び出しをうまく組み合わせる仕組みが必要で、その基盤がクラシファイアなどにも使えると分かったから
  • 従来のMCPへの批判: 統合がツール説明文と巨大なテキスト結果をそのままコンテキストへ流し込む点にあった
  • 新しい方針は必要なときにツールを発見し、スクリプトで処理できる構造化データを取得すること。賑やかなissueトラッカーでは、まず集めて絞り込んでから読むのが現実的
すべての説明文を提示 必要なときに発見 構造化データで処理
「中間レスポンスの全フィールドをメインモデルに読ませる」のは高くつく、という話です！

④ Codemode の基本的な動き

テーマ: JavaScriptで統合する
  • Codemodeでは、エージェントが小さなJavaScriptプログラムを書いてツールを呼び、結果を組み合わせ、有用な出力だけを返す
  • 例: プロジェクトの最近の活動レポート。複数の情報源を並列で取得し、まとめて、コンパクトな報告として送り返す
  • 中間データはスクリプト内に留まり、会話に戻す量を自分で制御できるのが実用的な利点
// Codemode: エージェントが書く小さなJSの例
const [commits, issues, prs] = await Promise.all([
  tools.git.log({ days: 14 }),
  tools.issues.list({ state: "open" }),
  tools.pulls.list({ days: 14 }),
]);
return groupBy(prs, "area").summarize();
ツール呼び出しのまわりに「JSのオーケストレーション環境」を置く——これがPiの答えです！

⑤ Codemode を使うときの注意

テーマ: 権限とエラー処理
  • 呼び出し間で保持したいJSONデータには明示的なストレージヘルパーを使う。通常の変数は実行をまたいで勝手には残らない
  • JavaScriptはサンドボックスで動くが、呼び出されるツール自体の権限は別に存在する。シェルツールはファイルを変更でき、外部統合はアクションを実行できる
  • スクリプトが途中で失敗しても、完了済みのツール呼び出しは自動的に取り消されない
  • そのため、まともなエラーハンドリングをワークフローに組み込む必要がある
スクリプト実行 途中で失敗 完了分は残る エラー処理で救う
「サンドボックス＝安全」ではありません。ツールの権限は別管理です！

⑥ MCPサーバーのセットアップ

テーマ: 接続と公開方法
  • ローカルサーバーは標準入出力（stdio）、リモートサーバーはHTTPで接続。設定はユーザー単位にもプロジェクト単位にも置ける
  • MCPサーバーのツールはCodemode経由で公開するのがデフォルト。モデルの前にすべてを並べるのではなく、Codemodeから発見させる
  • モデルに即座に見せたいツールには別の公開モードを選べる。アカウントサインインが必要なサーバー向けにOAuthにも対応
  • おすすめの始め方: すでに使っている統合を1つだけ持ち込み、境界のあるタスクから試す（例: リリースの未解決issueを集める）
統合を1つ接続 小さなタスクで試す 結果を確認 複雑なワークフローへ
MCPがすでに手放せないワークフローなら、これは意味のある変化です！

⑦ スペシャリストモデル（Jevと画像生成）

テーマ: 専用モデルへの道
  • Codemodeはエージェントにクラシファイア「Jev」と画像生成モデルへのアクセスを与える
  • Jevは分類器。構造化した状態と質問を渡すと、選択肢・Yes/No・確率付きのスコアを返す（例: issueがバグか機能要望か）。確率はモデルの判断なので、頼る前にサンプルで検証を
  • 画像モデルはテキストプロンプトと参考画像を受け付ける。セッションの認証情報で呼び出し、生成画像を結果に添付できる
  • 注意点: 通常のモデルピッカーには出ない（拡張からも呼べる）／利用はセッション会計に反映（カタログ価格がないと金額なしで計上される）／生成画像は自動保存されないので保存処理を workflow に含める
Codemode Jevで分類 画像生成 結果に添付
画像をプロジェクトのアセットにしたいなら、保存ステップを忘れずに！

⑧ 仮想モデル — 自作のルーター

テーマ: カスタムモデルルーティング
  • 複数モデルを行き来する人にとって一番うれしい追加かも。拡張が「選択可能な1つのモデル」としてルーターを登録できる
  • 各リクエストの前に、そのリクエストを扱う物理モデルを選ぶ。難しい計画は強いモデル、定常的な実装は安いモデルといったポリシーが組める
  • ルーティングのロジックは会話を見て思考レベル（thinking level）まで選べる
  • Pi側は実際に応答したモデルと利用状況を可視化するので、ルーターの下で何が起きたか検査できる
拡張がルーター登録 リクエストごとに選択 実モデルと利用状況は丸見え
ただし「良いルーティング判断」の設計は自分の仕事として残ります！

⑨ ルーティングのトレードオフ

テーマ: コストと遅延の天秤
  • 物理モデルを切り替えると、プロンプトキャッシュの再利用を失うことがある
  • ルーティング判定にクラシファイアを使うと、その分レイテンシが増える
  • 単一モデルのベースラインと実際のタスクで比較すること。安いリクエストは、ジョブ全体が正しく完了して安く済んでこそ意味がある
  • ローンチのデモでは、PiがClaude Opusで計画しGPT系で実装する拡張を書き、Jevが切り替えを判断。リロード後にルーターを選ぶと実装モデルへ移行し、モデルコストとキャッシュ使用が表示された
強いモデルで計画 Jevが切り替えを判定 安いモデルで実装 セッションで検証
切り替え判断がどれだけ一貫するか、色々なタスクで試してみたいですね！

⑩ 遅延ツール読み込み（Deferred Loading）

テーマ: コンテキストの節約
  • 統合を増やすほど説明文と引数定義が増え、タスク開始前にコンテキストを消費してしまう
  • 拡張作者は直接宣言するツール・Codemode経由のツール・検索が見つけて有効化する遅延ツールを区別できるように
  • 他のツールを調整したりユーザー操作が必要なものは、直接呼び出しのみに制限することも可能
  • 小さなローカル編集に、無関係サービスの細かい手引書は不要。説明文の質は依然として重要なので、ツール名を明示したプロンプトだけでなく普通のリクエストでも発見をテストしよう
統合が増える 宣言を遅延 必要なときに検索して有効化
セットアップが大きくなるほど効く、実用的なコンテキスト管理の改善です！

⑪ キャッシュウォーミング

テーマ: プロンプトキャッシュの保温
  • 大量のコンテキストを持つAnthropic系ワークフローでは、長いツール実行がプロンプトキャッシュの寿命を追い越すことがある
  • Piは価値があると推定した場合、リフレッシュを発行して対象キャッシュを温存する。実行中はデフォルト設定が適用される
  • 実行間のアイドルウォーミングを有効にするか、ウォーミング自体を止めることも可能
  • 発動条件はモデルのキャッシュ寿命情報が必要で、回避できるキャッシュミス費用が5セント以上と推定したときのみ。リフレッシュの利用はセッション合計に含まれつつ、会話のコンテキストには入らない。/session で次の判断を確認できる
長いツール実行 キャッシュ期限が迫る 価値あればリフレッシュ /session で確認
数分ごとに戻る人と、週末まで開きっぱなしの人では最適解が違います！

⑫ 会話の途中に入るシステムメッセージ

テーマ: 履歴の正確な再現
  • ハーネスの指示やツール定義に相当するシステムメッセージが、会話の途中からでも記録できるようになった
  • 例: 拡張が作業開始後にエージェントの役割を変えたりツールを追加したりしたら、その時点での変更として記録される
  • 再開やブランチ移動の際、トランスクリプトから対応するプロンプトとツール状態を再構築できる。別々の指示の下で下された判断が混ざる長い会話で履歴が役に立つ
  • 対応モデルでは古いキャッシュプレフィックスを保持しつつ後の変更を表現でき、プロンプトキャッシュにも有利。ただしプロバイダ依存なので、自分の環境での対応状況を確認したい
作業中に指示が変わる 時点を記録 再開時に状態を再構築
「当時は何の指示だったのか」が分かる履歴は、長い会話の財産です！

⑬ ターミナルUIの刷新

テーマ: 見た目と操作感
  • 新しいデフォルトテーマ「system」は、ターミナルの前景色・背景色・ANSI色を読み取ってそのパレットでUIを組み、コントラストも調整する
  • 明暗が切り替わるターミナルでは色を再取得して追従。情報が部分的な端末にはフォールバックがあり、内蔵のライト/ダークや自作テーマも/settingsで選べる
  • フルスクリーンモードがデフォルトに。プロンプトエディタとステータス領域を固定し、会話だけをウィンドウ内でスクロールする
  • 従来のスクロールバックが良い人は regular モードに戻せる。長時間エージェントと対話するなら固定エディタ、いつもの履歴に残したいなら regularという選択肢
端末の色を読み取る パレットを構築 コントラスト自動調整 明暗にも追従
読みやすいターミナルを作ったのに、中のツールが崩れるのはもったいない——いい変更です！

⑭ 最終リリースの細かい改善

テーマ: 数字と認証まわり
  • GPT-5.6のリクエストで、デフォルトツール＋Codemode構成のプロンプトトークンが約5,300→3,300に。この構成では約40%減だが、全タスクの総コストが40%下がるわけではない
  • Codemodeのエラーに復旧のヒントが付くように。ツール名の誤りの候補や、不正な引数へのガイド
  • サインインまわり: /login経由の新しいサインイン（MCPサーバー設定も可能）、Anthropicでは別マシンのブラウザでログインするフローにも対応
  • MCP認証は発行者チェックの強化・認可サーバーメタデータの上書き・サーバー名とURLごとの認証情報・追加権限リクエストの処理を改善。バージョンとキーヒントだけを残す静かな起動オプションも追加
トークン削減 エラーヒント サインイン強化 MCP認証の改善
毎日Piを使う人に効く、地味だけどうれしい改良の数々です！

⑮ Pi Durable — 長く動く会話の基盤

テーマ: アプリ開発者向け
  • Pi Durableは、長時間動くエージェント会話でアプリを作るための実験的な基盤。コーディングエージェントとは別パッケージ
  • 1つのハーネスで複数の会話を並行実行でき、それぞれが独自のモデル・ツール・指示・作業ディレクトリを持てる
  • 会話をある時点でフォークして独立に継続可能。複数クライアントが同じハーネスに接続し、状態を追いながら作業の操舵や追問もできる
  • アプリデータを型付きJSONドキュメントとして、トランスクリプトの更新と一緒にコミットできる。例: 複数人が調査を追い、別スレッドで関連質問するサポートワークスペース
// Durable: 会話とデータを一緒にコミット
conversation.commit({
  transcript: update,
  appData: { caseId: 128, status: "investigating" },
});
製品の体験は開発者が作るとして、その下の機械はPi Durableが用意します！

⑯ 「耐久性」の中身と限界

テーマ: チェックポイントと再開
  • 耐久性の正体はチェックポイントの保存。プロセス停止後も、新しいプロセスが同じ永続ストレージを開いて未完了タスクを再開できる
  • 実行中断ツールは「再生が安全」と宣言されたものだけ自動リプレイ。それ以外は中断の情報とコミット済みの出力がエージェントに渡る（検索の再試行と、外部システムを変える操作の再試行では結果が違う）
  • 同じリクエストIDで再送の二重受理を防ぐ。ただしすべての外部操作が厳密に1回になるわけではない
  • ストレージはmemory・SQLite・JSONL（memoryは再起動で消える）／バックエンドは1プロセス専有／デフォルトSQLiteは電源断保証なし／APIは実験的／コンテキスト上限は残る（圧縮サンプルで復帰を実演）
チェックポイント保存 停止 再開して続きから 安全なものだけ自動再実行
「耐久性がある＝モデルの記憶が無限」ではない点に注意です！

⑰ Durable の活用例と始め方

テーマ: サンプルと導入手順
  • サンプル: 独自の会話・状態・メッセージを持つ常駐バックグラウンドサブエージェント（メインは稼働を維持）。会話とタスクの基本要素の上に実装される
  • 別の例: ツール呼び出しの完了中に拡張を更新し、進行中の呼び出しは元の実装のまま、以降の呼び出しは新しい実装に。ただし部品とサンプル実装なので、信頼できるサービスにするには実装作業が必要
  • 導入: pi.devのインストーラー、またはnpm（Node 22.19以降）。pi --version で確認 → プロジェクトで pi → /login で接続 → /model で選択
  • 最初のタスクのおすすめはプロジェクト構造とチェックの実行方法を説明してもらうこと。Pi/Pi DurableともMITライセンス（モデルやサービスの費用は別途）
インストール /login /model 構造の説明から着手
メイン＋クラシファイア＋画像生成＋ルーターの構成は、セッション全体のコスト要チェック！

テーマ: 評価と展望
  • このリリースのお気に入りは「メインモデルに届く作業量を自分で制御できる」こと

  • 専用プランモードやサブエージェントのワークフローは拡張やパッケージに任せる方針。道具を自分で設定するのが好きな人にはたまらない反面、切り替える前に欲しい機能があるか確認を
  • 総評: 今回のリリースでPiは「自分のコーディングエージェントを形にしたい人」にとってずっと面白い存在に。気になるのは Codemode・モデルルーティング・Pi Durable のどれ？
ツールの発見 コードでの処理 自作ルーティング 計測して改善
