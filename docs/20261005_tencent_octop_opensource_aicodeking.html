テンセントの「Octop」を自前で動かす

オープンソースAIアシスタント徹底ガイド——専門家エージェント・自分の文書・予定タスク・コーディング委任を1か所にまとめる18枚のまとめ
🎬 Tecent Octop (Opensource): Wait, Tencent just ENDED OpenAI Dots & Muse!? — AI Code King（2026年10月5日）

① テンセントの「Octop」登場

00:00 イントロ
  • Tencent Cloud のGitHub 組織が公開したのが、オープンソースのAIアシスタント「Octop」。自分のマシンで動かせる
  • 動画の題名は「OpenAIのDotsやMuseは終わったのか!?」と煽っているけれど、中身はOctopの導入から運用までの実践チュートリアル
  • 特徴は専門家エージェント・自分の文書・予定タスク・コーディング道具の接続を1か所にまとめられること
  • 文書について専門家に質問し、別の専門家に答えのレビューを頼み、コーディングの作業を別の道具に任せられる。環境を毎回作り直さずに済むのが魅力
導入 モデル接続 エキスパート作成 小さなワークフロー
題名は豪快ですが、中身は丁寧なハンズオン動画です！

② 無料だけどモデルは自己負担

00:49 料金とプライバシー
  • Octop 自体はMITライセンスの無料オープンソース。ただしモデルは自分で用意するので、クラウドAPIの利用費は発生する
  • Ollamaでのローカルモデルにも対応。ただし必要なハードウェアと結果の品質は、動かす内容しだい
  • アプリを自己ホストしてもすべての要求がローカルになるわけではない。クラウドのプロバイダに繋いだら、送った情報はマシンの外へ出る
  • 自分の文書をアップロードする前に、この点を理解しておくべきと動画は注意を促す
アプリは無料 モデルは自己調達 クラウドなら費用と流出に注意
「自己ホスト＝全部ローカル」ではない、ここが最初の関門です！

③ インストールはターミナルで

01:14 インストール
  • 概要欄のリンクからGitHubのリポジトリを開き、インストール手順までスクロールして確認
  • Mac や Linux ならシェルのインストール用コマンドを、Windows ならPowerShellのコマンドをターミナルに貼る
  • インストーラがPythonの環境を整えてくれるので、Pythonを手で用意する必要はない
  • 完了したら新しいターミナルを開いてコマンドを使えるように。Windows・Mac・Linux用のデスクトップ版もリリースのページにある
# インストール後に新しいターミナルを開くと octop コマンドが使える
octop --help
リポジトリを確認 コマンドをコピー 実行 新ターミナルで準備完了
Pythonの準備が不要なのは、導入のハードルを大きく下げます！

④ 起動とタイムゾーンの指定

01:52 起動
  • アプリを起動する普段のコマンドはoctop run。動画では既定のタイムゾーンをニューヨークに指定する書き方を使う
  • プロジェクトの既定はAsia/Shanghai（上海）。予定タスクを使うなら自分のタイムゾーンに必ず変更
  • ターミナルは動かしたまま、ポート8088のローカルアドレスをブラウザで開く
  • 初期設定でパスワードを求められたら、ターミナルに表示された臨時パスワードを使う。そこから管理者アカウントを作る流れへ
# 普段の起動コマンド
octop run
# タイムゾーンを指定して起動する書き方も用意されている
# （動画の例では America/New_York を設定）
octop run タイムゾーンを確認 ブラウザで8088番を開く
既定は上海のタイムゾーン——日本で使うなら最初に直しましょう！

⑤ ブラウザで完了する初期設定

02:12 セットアップ
  • 新規のインストールなら、設定はブラウザの中で完結する
  • 今回の解説でデータベースはSQLiteを選択
  • 管理者のユーザー名と強いパスワードを登録。パスワードは英数字を含む8文字以上が必要
  • 次の工程でモデルのプロバイダを設定して、初期設定を完了させればダッシュボードへ進める
臨時パスワードで入る SQLiteを選択 管理者を作成 ダッシュボード
難しい操作はなし——ブラウザの案内に沿って進めるだけです！

⑥ モデルを接続する

02:33 モデル接続
  • すでに使えるプロバイダを選び、APIキーを入力して、APIのアドレスを確認
  • 独自のサービスを使う場合は一致するAPIタイプを選び、ベースURLを入力。使うモデルを有効化して接続を試す
  • 接続が失敗したらキー・モデルの名前・利用枠の残りを確認。Octop を入れてもプロバイダの残高は増えない
  • Ollamaのローカルモデルも接続できる。今回の解説はまず1つのチャットモデルで基本を確認。文書の検索や作業の委任をさせるので、道具の呼び出しを確実に扱えるモデルが必要
プロバイダを選ぶ キーとURLを入力 接続試験 会話を確認
最初は1つのモデルだけ——動く部品を増やさないのがコツ！

⑦ 最初のエキスパートを作る

03:13 エキスパート作成
  • Octop は自分のエージェントを「エキスパート（Experts）」と呼ぶ。それぞれ独自の作業場所と設定を持つ
  • 片方には書く役割を、もう片方にはレビューの役割を与えられ、エキスパートごとに別のモデルも選べる
  • Experts のページで新規作成。「Release Helper」と名付けて、プロンプトのファイル（AGENTS.md）を編集。「明確なリリース要約を書く。提供された情報を使い、記載がないものはその旨を伝える」と指示
  • 雛形や性格の設定もあるが、まずは明確な仕事内容の記述だけで十分。起動してチャットで役割を一文で説明してもらい、普通の返事が来ることを確認
新規エキスパート 役割を書く 起動 一文で自己説明
「役割の説明文」の質が、そのまま返事の質になります！

⑧ 罠を仕込んだサンプル文書

04:06 サンプル文書
  • 動画で用意したのは、架空のアプリ「Taskboard」のリリースノート（見本のデータが動画に付いている）
  • 今回の更新でCSVエクスポート・タスクの絞り込み・タスク作成のキーボードショートカットが追加
  • 既知の不具合としてエクスポートの問題がある。デバイスの同期は未対応で、リリース日も未発表
  • もしAIがリリース日を作ったり、同期に対応と答えたりしたら文書の外へ出た（見当違いの作り話）と一目で分かる——確かめるための罠
事実を確認できる内容 作り話を見破れる内容 検証用の小さな文書
正解を自分が知っている文書で試す——これが確かめ方の鉄則！

⑨ ナレッジベースとローカル埋め込み

04:37 ナレッジベース
  • Knowledge Bases の設定を開いて機能を有効化し、埋め込み（embeddings）の作り方を選ぶ
  • 埋め込みとは文書の中から関連する箇所を探すための仕組みのこと
  • 今回は「Local on ONNX」を選び、英語の埋め込みモデルを一覧からダウンロード。準備ができたら設定を保存
  • オンラインの埋め込みサービスも使えるが、文書の内容がそのサービスへ送信され、別の費用が増える可能性もある。埋め込みのモデルは先ほどのチャットモデルとは別物で、埋め込みをローカルで動かしてもチャットモデルの居場所は変わらない
機能を有効化 ONNXのモデル入手 文書を登録 検索の準備完了
埋め込み＝検索用、チャット＝会話用。2つのモデルは別々です！

⑩ 引用付きの回答を確かめる

05:23 引用付きで質問
  • 「taskboard demo」という名前のナレッジベースを作り、リリースノートを登録。文書が準備完了と表示されるのを待つ
  • 「チャットに追加」で Release Helper と対話し、「ナレッジベースを検索して変更点を平易に要約して。既知の制限と出典を含め、同期の可否とリリース日を教えて」と送る
  • 正しい答えの条件：CSVエクスポート・絞り込み・ショートカットに触れて、アーカイブ済みのタスクも書き出せることを説明。同期は未対応、リリース日は未発表と答える
  • 答えの中の出典の参照を開いて、元のファイルと見比べる。抜けがあれば再検索を頼み、使った箇所を指させる。小さな文書なら全体を自分の目で確認できるので、大きなコレクションを任せる前の信頼の土台になる
質問 検索と要約 出典を開く 元ファイルと照合
社内文書やプロジェクトメモでも同じ流れが使えます！

⑪ 二人目はレビュー役

06:25 レビュー役を追加
  • 二人目のエキスパートとして「Reviewer」を追加。仕事は「草案を提供されたソースと照合し、根拠のない主張を指摘する」こと
  • モデルを設定して起動し、普通に返事が来ることを確認しておく
  • 書く人とレビューする人が同時にいる構図は便利。ただしモデルの呼び出しが増える分、単純な質問にはエキスパート1人で十分
  • 二人目の役割が必要になった時点でチームへ加える——これが動画の基本的な考え方
書く人 検す人 根拠の確認 修正された草案
書く役と検す役の分担——人の仕事と同じ形です！

⑫ エージェントチームを組む（β）

06:25 チーム作成
  • Experts のページの「My Teams」から「Release Team」を作成
  • Release Helper と Reviewer を2人のメンバーに加え、取りまとめ役（コーディネーター）用のモデルを選ぶ
  • コーディネーターは割り振りと結果の取りまとめを担当。メンバーが専門の作業を担う
  • メンバーはコーディネーターとは別に2人以上必要で、作業を頼む前に起動しておくこと。各メンバーに作業場所があるため、初回の実演ではリリースノートをメッセージへ直接貼る
メンバーを起動 チームへ依頼 割り振り 結果を取りまとめ
まだβ版の機能——その点は頭に入れておきましょう！

⑬ わざと間違えた草案で実力検査

06:59 チームの会話と検査
  • 依頼の例：「Release Helper に短いリリース告知文を書かせ、Reviewer にすべての主張を同じノートで検証させ、修正済みの告知文と修正点を返して」。各割り当てに元のノートを含める
  • チームの会話を見ながら誰が話しているか・Reviewer が何を指摘したか・最終的な答えに反映されたかを確認
  • もっと良い検査がある：「デバイスの同期に対応し、明日リリース」という意図的に間違えた草案を渡して、ノートを基に直させる
  • どの主張が間違いか自分で分かっているので、レビューが捕捉できるか確かめられる。2つのAI同士の合意を確かめるより、はるかに良いチェックだと動画は説明する
間違えた草案を渡す Reviewer が検証 誤りを指摘 修正と説明を回収
「AI同士が納得」よりも「誤りを見抜けたか」——検査はこう作ります！

⑭ コーディングはACPで外注

08:08 ACPでの委任
  • Octop はACP（Agent Client Protocol）経由で外部のコーディングエージェントに作業を委任できる。実演には OpenCode を使用
  • OpenCode はOctop と同じマシンにインストールし、コマンドが見つかるように設定（実行ファイルの完全なパス指定も可）
  • ACP のページで OpenCode のランナーを有効化し、Release Helper のACPランナーの道具をオンに。作業用のフォルダにリリースノートを置いて、ファイルを読ませて announcement.md の草案を作らせる
  • 許可の要求が出たら内容を確認してから続行。チャットが完了と言っても、実際のファイルを自分で検査する。ランナーの接続には道具側のモデルは含まれず、OpenCode 自身の設定が別に必要
ACPを有効化 道具を起動 読み書きを委任 実ファイルを検査
文書の調査からリポジトリ作業まで、1つの会話から繋げられます！

⑮ 予定タスクで自動化

09:24 予定タスク
  • Release Helper に「平日の朝9時にタスクボードのリリース確認表を見るリマインダー」を作らせる。固定の文をダッシュボードの会話へ届ける指定にする
  • 予定タスクのページで時刻・タイムゾーン・宛先を検査。「作りました」という言葉は、実際のタスクが登録されてこそ意味がある
  • 2つのモードがある：Text は固定の文を送るだけ。Agent は実行時にモデルに作業させる。リマインダーは Text で、プロジェクトメモの新しい要約には Agent
  • 「Execute Now」で試しに実行し、届いたら不要なら無効化。タスクにはOctop のプロセスが動き続けることが必要で、バックグラウンド化はoctop service start（背景のサービスにも意図したタイムゾーンを）
リマインダーを作らせる 登録内容を検査 Execute Now で試験 運用へ
決まった時刻の作業は仕組みに任せて、人は確認だけ！

⑯ チャンネル・コネクタ・ブラウザ

10:24 その他の機能
  • ダッシュボードには他にもメッセージングのチャンネル接続・コネクタ・ブラウザの道具がある
  • それぞれ独自の準備が要るので、基本のワークフローが動いてから追加するのが動画の勧め方
  • おまけのブラウザ試験：部品を入れて、Browser AI+ でOctop のリポジトリを開いて画面の撮影を頼む
  • 撮れた画面と実際の表示を報告と見比べて確かめる。長いブラウザ作業の前に試せる小さな課題として最適
基本の流れを完成 チャンネルを接続 ブラウザ試験 活用の幅を拡張
盛りだくさんですが、足元から1つずつ整えるのが近道！

⑰ 知っておきたい注意点

導入前に知るべきこと
  • AgentTeams はまだβ版。コーディネーターの返事を止めても、メンバーへ割り当て済みの作業は止まらない場合がある。作業の完了を待ち、メンバーの活動を確認してからアプリを再起動
  • エージェントが増えるとモデルの呼び出しも増え、請求も増える。単純な質問には1人のエキスパートで十分
  • 準備の手間はある：モデルの資格情報の管理・文書検索の方法の決定・予定作業のためにアプリを使える状態に保つこと
  • そして自己ホスト＝全部ローカルではない点も再確認（②の復習）。クラウドに繋いだ情報はマシンの外へ出る
β機能の癖 費用の増加 運用の手間 最初は小さく
便利さの裏にある費用と癖——ここを知っているのが大人の使い方！

⑱ 総評：まず小さく始める

10:53 総評
  • 特定の仕事向けにエキスパートを何体か設定し、プロジェクトの文書を与え、複数の役割が必要な時にまとめる——この組み合わせは興味深い
  • 調査・執筆・リポジトリを行き来する仕事では、コーディングエージェントへの接続が特に魅力的
  • 動画のすすめ方は「まず1人のエキスパート、1つのモデル、1つの小さな文書から」。役割が必要になったらレビュー役やコーディングのランナーを追加
  • アシスタントの設定を自分で制御したい人には試す価値あり。ソースは公開され、自分で動かせて、ワークフローを少しずつ育てる余地がある。総合的には「かなり良い」とのが評価
1人のエキスパート 役割を追加 チームと委任 自分のワークフローへ
小さく始めて、必要になったら拡張——それがOctopの楽しみ方！
