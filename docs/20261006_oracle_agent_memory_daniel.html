Oracle AI DatabaseとAgent Memoryで顧客を覚えるAIエージェントを構築

チャットをまたいで記憶は残るのか？——LangGraph＋Python＋Oracle AI Databaseで「セッション1で好みを登録→完全に新しい会話で記憶を取り出す」クロスセッション検証までを18枚にまとめ

① ほとんどのAIは「チャット内」でしか覚えない

0:00 オープニング
  • 多くのAIエージェントは1つのチャット内でしか会話を記憶できません
  • しかし実際のアプリでは、顧客が翌日新しい会話を始めて戻ってくるのが当たり前です
  • その際にAssistantが顧客を他人のように扱うのは問題——好みも過去の選択も最初から説明し直しに
  • 本動画の目標: Oracle AI Database＋LangGraph＋Pythonで小さなサポートAssistantを構築すること
セッション1で好みを共有 完全な新規会話 記憶を取り出せるか検証
「また来てくれたね」と言えるエージェント、作れます！

② 検証テストの設計はシンプルに

テストの全体像
  • セッション1: 顧客が自分の好み（好きなもの・避けたいもの）をAssistantに伝える
  • セッション2: まったく別の新しい会話を開始し、記憶が取り出せるかチェック
  • 同一チャット内の「覚えているふり」ではなく、DBからの真正な取得であることを証明する設計です
  • テストに使うのは一般公開のリソース。説明欄のリンク（割引情報もあるかも）も要チェック
顧客が好みを伝える DBに保存 新会話で取得 自然な提案
「オフカメラでなぜか動くデモ」ではなく、きちんと検証します！

③ エージェントを「データの近く」で動かす

0:49 アーキテクチャの考え方
  • Oracle AI DatabaseはAssistantを必要なデータの近くに置きます
  • メモリとアプリケーションコンテキストを別システム間でたびたび移動させずに済むのが大きな利点
  • 有用なエージェントに必要なのは良い応答だけではなく、会話状態の信頼できる保管場所
  • そして後から重要なユーザーの詳細を思い出せること——この2つをDBが担います
会話状態 Oracle内で一元管理 システム間移動を削減
「動くデモ」より「置き場所が正しい構成」——地味だけど効きます！

④ チェックポイントと長期記憶の2層構造

記憶の2つの部品
  • チェックポイント: 1つのアクティブな会話を追跡し、ワークフローがどこで止まったかを記憶
  • 長期記憶: ユーザーに帰属する情報。新しいチャットで戻ってきても重要な詳細を利用可能に
  • この構成ではOracle Saverがチェックポイントを、Oracle Storeが長期コンテキストを担当
  • 考え方の基本: thread_idは会話、user_idは顧客を表す——この分離がアーキテクチャの核心
thread_id（会話単位） user_id（顧客単位） 2つの記憶が協調
似たような仕組みに聞こえるけど、解く問題が違う——ここが肝！

⑤ DockerでOracle Databaseを起動

1:43 構築スタート
  • 最初の一歩はDocker。エージェントのメモリを実際のデータベース内に置くためです
  • 古いメッセージをプロンプトに戻すだけでも「保存したように見える」けど、会話終了後に残る証明にならない
  • Oracle Database Freeのイメージをpullして画面のコマンドでコンテナ起動
  • DBが準備完了を報告したら基盤完成。永続ストレージがAssistantの背後にできました
# DockerでOracle DB（Freeイメージ）を起動
docker run -d oracle/database-free
# → DATABASE IS READY TO USE が出たら土台OK
「本物のDBに置く」——これがデモと実運用の境目です！

⑥ 最初にやるは接続テスト

開発者流の順序
  • 次にPython環境を整え、モデルアクセスキーを設定してプロジェクトフォルダを準備
  • agentロジックに触る前に軽い接続テストを実行——この小さな確認が時間を大幅に節約します
  • PythonがOracleコンテナに届かない状態でLangGraphメモリをデバッグするのは無駄になる恐れ
  • 接続ファイルに必要なのはDBパスワードだけ。他の設定はローカルDBへ既に向いています
環境構築 接続テスト成功 ようやくagent.pyへ
地道な下準備こそ、後のトラブルを防ぐ最短ルート！

⑦ agent.pyの骨格——StoreとSaver

メインファイル解説
  • 例は意図的に小さく保ち、動作を追いやすくしています（完全なサポートシステムではない）
  • Oracle Store: user_idに紐づく長期記憶を管理。テスト顧客は「customer 42」
  • Oracle Saver: LangGraphワークフローのチェックポイントを管理し、thread_idに紐づく
  • まとめると——threadは会話を覚え、storeは顧客を覚える。この分離がアーキテクチャで最も重要な部分
# agent.py の役割分担（イメージ）
store  = OracleStore()  # 長期記憶（user_id）
saver  = OracleSaver()  # チェックポイント（thread_id）
似た2つの仕組み——でも役割はまるで別物なんです！

⑧ 単一ノード「model」の記憶ループ

LangGraphフローの中身
  • LangGraphフローにはmodelという1つのメインノードのみ。構成は極簡です
  • 応答の前にOracle Storeを検索し、現在のユーザーに関連する好みがないか確認
  • 記憶が見つかれば、それをモデルのコンテキストに追加してから回答を生成
  • 同時に新しいメッセージを走査し、保存する価値のある詳細がないかレビューします
メッセージ受信 Store検索 コンテキスト注入 応答＋保存判定
読んで・足して・書く——たったこれだけで記憶が回る！

⑨ 何を保存するか——デモと実運用の境界

保存ロジックの設計
  • デモでは、顧客が製品の好みやカフェイン制限に言及したらStoreへ書き込むシンプルな判定
  • 実運用ならもっと厳格なルールが必要——ユーザーは何が保存されるか知り、更新・削除する手段を持つべき
  • 1つのメッセージに現れたという理由だけで個人的な詳細を全部保存することはすべきでない、とDaniel氏
  • ただしチュートリアルではシンプルな方がテストを理解しやすい——割り切りのバランスも設計のうち
言及を検知 ルールで判定 Oracle Storeへ保存
「保存の透明性」——実製品化のときに忘れちゃいけない視点！

⑩ セッション1——好みを伝える

最初の会話
  • thread_idはsession-one、user_idはcustomer 42で会話を開始
  • 伝える内容は2つ: シトラスパンチが好きなこと、午後6時以降はカフェインを避けたいこと
  • 応答は両方の詳細を正しく反映——しかしこれだけでは長期記憶の証明にならないと警戒
  • 同一会話内にまだ情報が見えているので、単なる復唱の可能性を排除できないためです
「シトラスパンチ好き・6時以降カフェイン回避」 応答は正しい…が証明はまだ
「答えが合ってる」だけじゃだめ——証拠が要るんです！

⑪ セッション2——何もなかったかのように聞く

クロスセッション検証
  • 新ファイルsession2.pyを作成。ロジックもuser_id（customer 42）もそのまま
  • 唯一の重要な変更はthread_idをsession-twoにすること——完全に新しい会話になります
  • 1つ目のスレッドのチェックポイントは以前のメッセージを持ち込まないので情報はゼロの状態
  • 質問はたった一言——「今夜は何を注文すべき？」。シトラスパンチもカフェイン制限も一切言及しません
thread_idだけ変更 過去メッセージゼロ 「今夜何を頼む？」
ヒントを一切出さない——フェアな実験デザインです！

⑫ 結果——記憶が新しい会話に届いた

検証の結果
  • Assistantはシトラスパンチを推奨——しかも午後6時以降のカフェイン回避の希望も尊重
  • 顧客側の体感は「エージェントが自分を覚えていた」のように感じられます
  • しかし技術的に重要なのは、Oracle Storeが保存済みの好みを取得し、真新しい会話に注入したこと
  • これは1つの長いチャット内のパーソナライズではなく、本物のクロスセッション知識です
Oracle Storeから取得 新会話へ注入 的確な提案が完成
体感は「気配り」、正体は「設計」——いいとこ取り！

⑬ DBの中を直接のぞいて確認

8:08 検証を突き詰める
  • 結果を信用するだけでなく、別ターミナルからOracleコンテナに接続して直接確認します
  • LangGraph連携はチェックポイント用と長期記憶用で別々のテーブルを自動作成
  • 今回はOracle Storeが使うテーブルに注目し、SQLクエリを実行
  • するとcustomer 42のレコードがデータベースに直接現れました
-- Store用テーブルを直接確認
SELECT * FROM store_table
WHERE user_id = 'customer 42';
→ シトラスパンチ好み＋カフェイン制限が記録
「パーソナライズされた気がする」じゃなく、レコードが見える！

⑭ store JSONに全道筋が見える

証明の瞬間
  • StoreのJSONにはシトラスパンチの好みと午後6時以降カフェイン回避のルールの両方が格納
  • 全過程が可視化: セッション1で顧客が共有 Oracle Storeが保存
  • セッション2は新threadで開始したが同じuser_idを維持
  • ワークフローがレコードを取得し、まったく別の質問に答えるために使用——これが証明モーメント
// store JSON（イメージ）
{ "preference": "citrus_punch",
  "rule": "no_caffeine_after_6pm" }
保存→取得→活用のパスが全部見えました！

⑮ この検証にベクター索引は不要

実装の取捨選択
  • 今回の例ではノンベクター版のテーブルを使用——それで十分だと判断
  • 理由はシンプル: user_idが既に分かっていて、特定の好みの取得だけが必要だから
  • こんな小さなテストにベクター索引は不要な複雑さを加えるだけ、と割り切り
  • 用途に合わせてシンプルな構成と高度な検索を使い分ける判断もエンジニアリングのうち
user_id既知 キー検索で十分 複雑さを避ける設計
最新機能を詰め込むより「目的に合う道具選び」が本番！
