Cole Medin（AIエンジニアリング解説）

「Agentic Apps」——大企業はAIエージェントをこう使う
〜エージェント・ファーストからの脱却〜

個人向けの「1つのエージェントとチャット」型アプリではなく、ビジネス成果を中心に複数のAIエージェントを組み込んだアプリ（Agentic App）こそ企業に必要な形——Cole MedinがOracle AI Agent Studioを実例に、LLMを必ず決定論的なワークフローの一部として呼び出す設計、ポリシーによる細粒度の権限制御、RAGではなくテスト済みコードへのコード化、視覚的アーティファクトによる生産性向上までを18枚のカードに整理します。

① 個人エージェントの「チャット型」パターン

Coleが2026年にチャンネルで作ってきたセカンドブレイン、コーディング支援、カスタマーサポート系エージェントは、すべて1つのエージェントをユースケース周囲に構築する同じ形でした。

  • チャット入力で依頼を送り、返ってきた回答を読む——それがすべて
  • この種のエージェントはCole自身のビジネスの多くを実際に支えている
  • 個人用途では十分に機能する「ファンタスティック」な構成
「でも企業にエージェントックAIを導入しに行くと、もっと包括的なものが必要になることが多いんだ」

② 企業が本当に必要とするもの

Coleが企業にAgentic AI統合のコンサルに入るとき、求められるのは単発のチャットボットではなくよりホリスティック（全体最適）な仕組みです。

  • 1つの役割（ロール）を支える統合された体験が必要
  • 「仕事のこの部分をどう助けるか？」という問いから設計が始まる
  • 企業向けの話だが、個人アプリ開発者にも学ぶことが多いとColeは強調

③ 落とし穴: エージェント＝アプリ全体にする誘惑

ここ数年のAIブームで、エージェント開発者はエージェントそのものを丸ごと自動化・アプリにしてしまいたい誘惑に駆られがちです。

  • 本来はより決定論的なワークフローやアプリの中の1ツールであるべき
  • 「最新技術に乗っかりたいがための統合」をColeは頻繁に目にすると告白
  • ほとんどの人が本当に必要なのはエージェント過剰なアプリではない
「エージェント・ファーストではなく成果ファースト。これがOracleの公式定義で、本当に気に入っている」

④ Agentic Appとは——Oracleの公式定義

Agentic App（エージェント・アプリ）では「このAIエージェントで何を自動化するか」から考えるのではなく、ビジネス成果から考え始めます。

  • 第一の問い: 「誰の役割のどの部分を、どう助けるか?」
  • その体験を設計してからマッピング
  • その上で複数のAIエージェントをアプリに組み込み自動化を支援
  • エージェントはアプリの部品であり、アプリそのものではない
ビジネス成果 体験設計 複数エージェント配置

⑤ 成果ファーストが価値を届ける

ビジネス成果に先にフォーカスすれば、組織に実際に価値を届けられる可能性が格段に高くなります。

  • 「最新技術導入のためのエージェント統合」は価値を生まない
  • 成果起点の設計こそ最も実践的なAgentic AI統合の形
  • 個人のセカンドブレインのようなチャットアプリから、多数のエージェントが裏で働くアプリへ進化させるのが本動画の主題

⑥ ツール化＝制御と決定論の獲得

AIエージェントを大きなアプリの中の1つのツールにすると、飛躍的に制御性が上がります。

  • アプリ全体でLLMを使うワークフローを組むが、エージェントが常時すべてを駆動するわけではない
  • より決定論（デターミニズム）の高い構成を作れる
  • 確実性が要求される業務では、エージェントに間違える余地を与えられない
決定論的なワークフロー+ツールとしてのLLM——これが企業向けの信頼性設計の基本

⑦ Oracle AI Agent Studio——本動画の舞台

Coleが「見てきた中で最も良い」と評価するのがOracle AI Agent Studioです（※本動画はOracleとの提携による提供）。

  • 裏側のワークフローとセキュリティの作り込みに学びが多い
  • 始め方はコーディングエージェントと同じ: 作りたいものを自然言語で記述するだけ
  • 非技術者のビジネスユーザーでも構築できるのが特徴
  • プラットフォーム固有の話から一般的な教訓を抽出して解説

⑧ 実例: マネージャー・コーチング・アプリ

Coleが投入したプロンプトは「マネージャー・コーチング用アプリが欲しい。ディレクター級マネージャーで、チームは約12名。メンバーの育成へのエンゲージメントを一望できるビューが要る」というものでした。

  • 1つのプロンプトからエージェント・アプリ全体が生成される
  • 重要なのはアプリの主題ではなくビジネス成果（1つのビュー）の指定
  • 複数コンポーネントで構成された包括的なワークフローが実行結果
12名設定したチーム規模
1プロンプトアプリ生成の入力
1ビュー目指すビジネス成果

⑨ 全コンポーネントの裏でワークフローが走る

アプリ内でエージェントを使うすべての部分は、裏側で必ずワークフローを実行しています。

  • より決定論的なプロセスがエージェントの使い方をガイド
  • チャット体験は失われない——フォローアップ質問も自由に可能
  • 事前構成済みコンポーネントの並ぶダッシュボードでより強い構造性を獲得
  • ワークフローが包括的だったため構築には時間を要したが、結果は「素晴らしい回答」

⑩ 例: フォローアップメール部品

ダッシュボード末尾のコンポーネントは「目標未達成のメンバーにフォローアップメールを送る」機能。裏ではワークフローがドラフトを書きます。

  • ドラフトがその場でコンポーネントとしてレンダリングされる
  • 送信前にレビュー・編集してから実行可能
  • 別アプリへ行き来せずアプリ内で完結する制御
「1つのビジネス成果に必要なすべてを1つのビューで管理する——それがAgentic Appの全構想だ」

⑪ バックグラウンド・エージェントの提案

Coleお気に入りの機能が画面右上: 各コンポーネントのエージェントとは別のバックグラウンド・エージェント群が常時全体を見渡します。

  • 部下の状況や優先事項を俯瞰しネクストアクションを提案
  • 例: 「部下にメールを送っては?」——クリックして編集しそのまま実行まで完結
  • 考えるだけでなく行動（アクション）まで支援
  • 詳細は各コンポーネント、概要は提案欄と使い分けられる

⑫ 最重要ポイント: LLMは必ずワークフローの一部

「この動画から持って帰る教訓が1つだけなら」とColeが挙げるのは——Agentic AppでLLMを呼ぶときは必ずより大きなワークフローの一部として呼び、決定論を加えること。

  • 実行冒頭でコンテキストを注入
  • コードノードと条件分岐を組み合わせる
  • アプリでの表示用に回答のフォーマット変換を行う場合もある
  • 入力をそのままLLMへ渡すチャットアプリとは制御の次元が違う
コンテキスト注入 コードノード 条件分岐 LLM呼び出し 出力整形

⑬ 業界全体が「決定論的ワークフロー」へ収束

業界全体が「エージェントック・ワークフローは可能な限り決定論的に」という考えに収束しつつある、とCole。

  • LLMは柔軟で有能——問題を見て手順を導ける
  • しかし企業では保証が要る: 文脈は常に定められた通りに読み込まれ、適切なLLMが呼ばれ、整形も確実
  • ミッションクリティカルな業務では間違いの余地を残せない
  • これは最も信頼できるLLM自動化の形
Cole自身のOSSArchon（ハーネス・ビルダー）のワークフロー構築UIもOracleと似た設計——即座に使いこなせた

⑭ 構築の順序: ワークフロー→アプリ

Oracle AI Agent Studioでは、まずワークフローを構築し、その後にアプリがそれを利用します。

  • 単一ビューに持ち込みたい個別の自動化を先に洗い出す
  • 各コンポーネントがワークフローを利用する構成
  • ボタンをクリックするとダッシュボードの内容を入力としてワークフローが直接起動
自動化の設計 ワークフロー構築 アプリ部品に接続

⑮ ポリシー: エージェント権限の細粒度制御

ワークフローが可能にするのがポリシー——エージェントに与える関数単位の細粒度（グラニュラー）な権限と能力の定義です。

  • HR用途の例: HRハンドブック（PDF）を直接アップロード
  • ガイドラインがすべて関数（コード）にコード化される
  • 各関数には生成済みソースコード・検証用テストケース・厳密な入出力が付く
  • 生成・テスト済みのポリシーをワークフローに組み込んで利用

⑯ RAGではなくコード化——「たいてい正しい」は足りない

多くの人はHRハンドブックをRAGで解決しがち——アップロードして検索でチャンクを引き、その場で回答させます。しかしそれは確率的な回答です。

  • RAGは優秀で「たいてい正しい」——しかし福利厚生や休暇ポリシーに「たいてい」は不十分
  • LLM呼び出しの前にポリシーを読み込み、必要なツールだけを与えてスコープ
  • ワークフロー先頭は分類LLM呼び出し: 育児休暇の質問か、休暇ポリシーの質問か
  • テスト済みコードにコード化して100%正確な回答を保証
  • 構築中にJSON出力でワークフロー単体を直接テスト可能
「構造を持たせて、毎回100%正解できるようにする——これがRAGとの決定的な違いだ」

⑰ セキュリティ: 実行者と実行主体の統制

エージェント側の権限だけでなく、アプリを使う人側のセキュリティもワークフロー単位で管理できます。

  • 誰がそのワークフローを実行できるかをスコープ
  • 自動化の実行中にどのアイデンティティで実行されるかも制御
  • ワークフロー全体で使うLLMの選択も切替可能
  • トリガーはアプリ内クリックに限らない——受信メールを起点にした自動実行などにも拡張

⑱ ホームベースと視覚的アーティファクト

Agentic Appはホームベース——状況確認、手動トリガー、質問、すべてが1か所に。そしてエージェントには視覚的な出力を求めるべき、とColeは続けます。

  • スライド資料やPDFなどのアーティファクト生成——後で使わないまでも理解が速くなる
  • 実例: 学習リスク概要レポート（PDF）を出力——テキストの壁より格段に読みやすい
  • 1日中テキスト回答を読むのは精神的な消耗が大きい
  • だからCole自身も動画に必ず図解を添える
