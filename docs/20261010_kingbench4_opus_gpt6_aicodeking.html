〜Opus 5.5 vs GPT-6 Astra vs Sol vs Haiku 5.5 vs GLM 5.3〜

① KingBench 4 (HARD) 開催

AI Code Kingによる大型ベンチマーク第4弾。今回は「HARD」の名の通り、5モデル×6プロジェクト＝合計30ビルドという過酷な構成です。

  • 出場: Opus 5.5／GPT-6 Astra／GPT 6.1 Sol／Haiku 5.5／GLM 5.3
  • 課題: エミュレータ／Docker代替／3Dルームデザイナー／QMK VIA代替／Pokémon Red／Fitbit分析の6種
  • 各課題10点満点・6課題とも均等ウェイトで総合成績を算出
5モデル出場
6課題同一プロンプト
30ビルド総数

② モデル×コーディングエージェントの組わせ

各モデルは別々のコーディングエージェントで動かします。「モデル＋ツール」の組み合わせとして、各エージェント内で使える能力を評価する設計です。

  • GPT 6.1 Sol／GPT-6 Astra → Codexで実行
  • Opus 5.5／Haiku 5.5 → Claude Codeで実行
  • GLM 5.3 → OpenCodeで実行
  • 実施日: 4モデルは10月3日、Haikuのみ10月8日（新しいClaude Code版で実施）
同じモデルでも エージェントが違えば 使える道具も変わる

③ 共通ルールと採点方法

全モデルに同一のタスクプロンプトと納品指示を渡し、プロジェクトごとに新しいセッションで実装させます。

  • 1実行につき60分の打ち切り＋対応ツールではhigh reasoningを指定
  • 「納品された状態」で評価——足りない機能を評価者が補完しない。タイムアウト・中断も結果の一部
  • 採点軸: 要求機能／実際のワークフロー／ビジュアル品質／エラー処理／避けられた無駄な負荷
  • 小さいサンプルなので僅差で永久の優勝者を決めない注意書きも明記

④ 6つの課題ラインナップ

どれも「1セッションで納品」には大きすぎる、非常に大きなソフトウェアを要求する課題ばかりです。

  • Game Boy／Nintendo DS／3DSエミュレータをRustでスクラッチ（セーブステート対応）
  • Docker代替——Dockerイメージが使え、Dockerより効率的であること
  • 3Dルームデザイナー——家具配置・ライティング・リアルな素材
  • QMKキーボードのVIA代替——黄色テーマのコンフィギュレータ
  • Pokémon Red再現——初回ジム（ニビジム）攻略まで
  • Fitbitワークアウト分析デスクトップアプリ（Rustバックエンド）

⑤ 課題1: エミュレータは全滅

最大の難所。要求は「Rustでスクラッチした Game Boy・DS・3DSの3システム＋セーブステート＋大半のゲーム互換」。実態は3つの別システムの同時実装です。

  • DSのカートリッジからタイトル読み取りだけでは、動かすためのハードウェアシミュレーションにならない
  • 全モデルが未完成——最高スコアでも3.7/10という壊滅的結果に
  • 「Game Boy部分が優秀」でも未実装の2/3のポイントはもらえない採点方針
「誰も完全なエミュレータを納品しなかった——要求と納品物のギャップが最も大きい課題」

⑥ 課題1の結果明細

  • Opus 5.5＝3.7: Game Boy動作に加えDS診断／自作2プログラム（Arm Wrestler・Bunny Garden）が両画面で動き、DSセーブステート復元も決定的に動作
  • Sol＝2.2／Astra＝2.2: Game Boyコアは診断12種パスも、DS・3DSはヘッダ検査止まり
  • Haiku＝1.8: Mooneye診断12種中10パス。しかし境界テストでタイマー・割り込み不整合、不正状態を受け入れ次フレームでクラッシュ
  • GLM＝0.6: 実行ファイルがプロジェクト名を表示して終了。ROM選択もプレイも保存も不可

⑦ 課題2: Docker代替は誰も「効率」を証明できず

要求は「Dockerイメージを利用可能・Dockerのライブラリやコピーコードなし・Dockerより効率的」。イメージ取得・レイヤ適用・隔離実行・比較証明まで、複数の仕事が内包されます。

  • 5案とも高速性・効率性の証拠なし。Linux隔離の独立検証も全案で未達
  • 判断材料は「runコマンドの有無」ではなくイメージ処理チェックの実績
  • 有力視されたのはイメージツール部分——アーカイブのインポート／エクスポート／タグ保存などの実装
「完全置き換えでも効率優位でもない。それでもイメージエンジンとして有用な仕事はあった」

⑧ 課題2の結果明細

  • Sol＝5.0: アーカイブ境界チェック4種（リンク脱出・削除ファイル・レイヤ絡み）をパス。ただしポート公開や対話ターミナル等は未実装
  • Opus＝4.6: コンテナ系コマンドが最広範。ただしwhiteout誤処理で同レイヤ内の新ファイルを誤削除
  • Astra＝4.6: 境界チェック4種パス、build/save/load/tag対応。リソース制限・Dockerfile等は欠落
  • GLM＝3.0／Haiku＝3.0: アーカイブ展開がディレクトリ外へ書込・削除（GLM）／外部ファイルの権限書換（Haiku）という重大欠陥で足切り

⑨ 課題3: 3Dルームデザイナーは全員健闘

唯一5モデルすべてが実際に部屋を編集できるアプリを納品した課題。差がついたのは写実性・細かい操作性・保存処理・無駄な再レンダリングです。

  • Opus＝8.5: 布と木の質感差・コンタクトシャドウ・反射が最高峰。ただし保存失敗時も「ローカル保存済み」と嘘をつくバグ
  • Astra＝8.3／Haiku＝8.3（同点）: Haikuは9種のカスタム形状に加え、無操作時は描画を停止する省エネ設計が光る
  • Sol＝8.0: 操作系は優秀だが、色スウォッチをクリックするとフォームが途中で送信されるUX事故
  • GLM＝7.8: 木部アクセントが選択色を無視して白のまま。植物は幾何学形体の積み重ね

⑩ 課題4: QMKのVIA代替——接続が分水嶺

黄色テーマのコンフィギュレータで、鍵は実機キーボードとの通信。キーボードの絵を編集してローカル保存するだけでは課題の中心を果たしません。

  • Opus＝7.5: デバイス開通・直列化通信・レイヤーキーマップ読み書き・マクロ・照明・バックアップを網羅。テスト用ファームから変更キーを読み戻して検証
  • Haiku＝6.7: コアキーマップ・エンコーダ・マクロ・照明は動作。ただしアクセント記号1文字でアプリが真っ白になる描画クラッシュ
  • GLM＝4.6: 接続を実装するも、鍵位置誤り・標準キーボード定義の拒否・照明ペイロード誤りなどプロトコル詳細を連発ミス
  • Sol＝3.0／Astra＝3.0: 洗練されたローカルエディタながら接続リマップが未実装——絵に描いた餅

⑪ 課題5: Pokémon Red再現——Opusの悲劇

「HTMLでマサラタウンからニビジム攻略まで」を再現する課題。御三家入手から捕獲・道具・バトル・バッジ進行まで、一連のシーケンス全部が求められます。

  • Astra＝8.5: 通常ルートでバッジ獲得＆リロード後も保持。緑のGame Boy風パレットと戦闘スプライトで本家への類似度No.1
  • Sol＝8.2: パーセルクエスト・御三家入手・ジム攻略まで接続。ただしマップや戦闘アートの改変大きめ
  • Haiku＝6.3: ルートは機能するがフシギダネが緑の丸、ライバル戦欠落、PP切れで詰みの死角
  • Opus＝3.0: ジム勝利・育成・回復まで動くのに、スタートキーでメニューが開いて即閉じるバグでセーブ不能——獲得バッジが消える
「大量の動作コードが、たった一本の壊れた操作経路で台無しになる好例」

⑫ 課題6: Fitbit分析アプリの明暗

「Rustバックエンド＋Whoop級の機能深度」のワークアウト分析アプリ。綺麗なダッシュボードよりも欠測データ時の計算の誠実さが試されます。

  • Opus＝7.4: 睡眠負債・適応ベースライン等の分析機能が最広範。ただし深夜2時の安静時心拍サンプル1つで1日の負荷がゼロになる計算バグ
  • Astra＝7.3: 公式形式のインポート対応。ただし欠測日をゼロ扱いして測っていない上昇グラフを描画
  • Sol＝6.6／Haiku＝6.4: HaikuはSQLite＋実ファイル形式で基盤堅実。Solは1,000行で2万超のDOM要素を生成
  • GLM＝4.4: 欠測心拍を120や150と捏造し、重複IDで負荷を二重計上——欠測を「自信ありげな数値」に変換

⑮ Haiku 5.5 のコスパ衝撃

トークンとコストはAPI換算の推計（サブスク課金額ではない）。共通記録が揃う3課題（ルーム／キーボード／Fitbit）で比較すると対比の構図が見えます。

  • 3課題合計: Solは約926万トークン、Haikuは約4,118万トークン——4倍以上を消費
  • それでもHaikuのAPI推定コストはOpusより約85%低い（入出力・キャッシュ単価の違いが効く）
  • 同一3課題の平均スコア: Haiku 71.3% vs Opus 78.0%——安くてそこそこの関係
  • Haiku全6課題の総消費: 約7,819万トークン（うち入力約7,665万）／API換算約$7.40

⑯ 教訓: 機能を「最後まで」追う

著者が強調するのは、ファイル数ではなく実際の動作を追い切るテスト習慣。スコアの差はまさにここで生まれました。

  • キーを変更してデバイスのメッセージを検査する（VIA代替課題）
  • ジムを勝ってゲームをリロードする（Pokémon課題——Opusはここで沈んだ）
  • 欠測値ありのワークアウトをインポートしてグラフ表示を確認する（Fitbit課題）
  • 「動くように見える」で終わらせない——納品された状態で評価する姿勢がベンチの信頼性を作る
「それらの操作こそが、モデルが作ったファイル数よりもはるかにスコアをよく説明する」

⑰ 作者の用途別チョイス

ベンチ結果を踏まえた実際の選び方。目的別に推しモデルが分かれるのが KingBench 4 の結論です。

  • Opus 5.5: 最広範な出発点——ただし保存パスと計算は信用前に検証すべし
  • GPT-6 Astra: ブラウザゲームの本命——ジム攻略＋保存＋本家類似度を両立
  • GPT 6.1 Sol: コンテナ／イメージツールで最強結果。Pokémonも接戦
  • Haiku 5.5: コストが効く有界なアプリなら真っ先に試したい1番——でもエミュレータは非推奨＆Dashboardの数値を過信しない
  • GLM 5.3: ルームとゲーム攻略で力量はある——アーカイブ脱出と捏造データを克服すれば再評価の余地

⑱ まとめ: 勝者でも60%未満

KingBench 4 (HARD) の最大の発見は、どのモデルも巨大要求を1セッションで完遂できなかったという現実です。

  • 総合1位のOpusでも57.8%——要求とのギャップが点数に正直に反映
  • 「プロジェクトの動く一部」は有用でも残りの仕様を満たさなければ満点はない
  • Opusのセーブ不能、Sol／Astraの接続未実装——一つの欠陥が全体を決めることがある
  • それでも全30ビルドは再現可能な比較として貴重な公開データ——「Overall, it's pretty cool」
