② ユースケース: 顧客ローン乗換の提案

舞台はリテールバンク。マーケティング支援のために、高金利クレジットカードから低金利個人ローンへの乗換を見込める顧客を特定する ML モデルが必要。

  • 現状: 顧客は高金利のクレジットカード残高を抱えている
  • 提案: 新しい低金利の個人ローンへ切り替えれば利払いを削減できる
  • 目的: 乗換で節約になる顧客と、実際に承諾しそうな顧客の2段階で狙い撃ち
「私がリテールバンクのデータサイエンティストだとして——マーケティング支援の ML モデルを作る必要がある」

③ ステップ1: Gemini にデータ景観を質問

コードを書く前に、まず自然言語でデータを探索。「顧客口座・カード支出・過去のローン提案のデータはある? データ景観を可視化して」と Gemini に質問。

  • Gemini が事前構築済み Data Cloud スキルのセットで応答
  • データエステート（データ資産）全体を横断的に探索できる点が特徴
  • 探索の起点が SQL ではなく対話——raw discovery から始まる Lakehouse ワークフロー
質問 Gemini データ景観の可視化

④ Knowledge Catalog: メタデータの中央登記所

応答の裏側にあるのが Knowledge Catalog（Dataplex Metadata）。Google Cloud 内とクロスクラウドのデータセットを、豊富なメタデータ付きで登録済み。

  • Google Cloud ＋ クロスクラウドのデータセットを横断的に登録
  • リッチなメタデータ: スキーマとグロッサリー（用語集）を保持
  • 人間だけでなくGemini エージェントも同じカタログを読み書きに利用
  • ガバナンスされた単一の信頼できる情報源として機能

⑤ 開発者もカタログに登録・記述できる

カタログは静的ではない。開発者が新しいデータセットやビジネスロジックを作成・登録・記述でき、その説明も即座に人間と Gemini エージェントの両方へ開放。

  • 新規データセットの作成・登録・説明付けを簡単なオペレーションで実施
  • 登録された説明は人間とエージェントの双方が参照——暗黙知の共有化
  • ビジネスロジックも資産化され、再利用可能な部品として蓄積
「データセットとその説明を、人間と Gemini エージェントの両方が使えるようにできる」

⑥ PySpark コード生成とゼロコピー結合

「乗換で節約になる顧客を見つけて」と頼むと、Gemini が PySpark コードを生成。Lakehouse 上の顧客・カード支出データセットをクエリし、結果を Lightning Engine（BI エンジン）へゼロコピーでプッシュ。

  • 対象: Lakehouse の顧客データセットとカード支出データセット
  • 事前構築済み Data Cloud スキル経由で0コピー結合（0 copy join）を実行
  • データの複製なしに解析エンジン側で処理——ムーブメント不要のフェデレーテッド解析
プロンプト PySpark 生成 ゼロコピー結合

⑦ ブラックボックスなし: 次世代 Python ノートブック

生成物は鞘に収まらず、次世代 Python ノートブック上のライブ環境で開くことができる。「何が起きているか」が常に見える設計。

  • PySpark コードを Gemini 内で1行ずつライブ編集可能
  • ドロップダウンを切り替えると、下流のチャート群が即座に再計算
  • 「none of this is in a black box（黒箱なし）」——コード・データ・出力が常に露出

⑧ 最初の成果: 5万人・平均3,400ドル

探索と集計だけでもう十分な価値。50,000人超の顧客が乗換で節約できる見込みで、その平均額は 3,400ドル。

50,000人超乗換節約の見込み顧客
$3,400平均節約額
  • 次の問い: 節約になる顧客のうち、実際に承諾するのは誰か?
  • その答えには機械学習モデルが必要——ステップ2への導入部
「素晴らしい。でも、実際にイエスと言うのは誰かを知りたい」

⑨ ステップ2: ML モデル構築をプロンプト

「このオファーに乗り換える可能性が最も高い顧客を特定する機械学習モデルを構築して」とプロンプトするだけで、学習パイプラインの生成が始まる。

  • 分析コードと同じ対話の流れでモデリングへ移行——文脈が切れない
  • タスク: 各顧客の乗換傾向（propensity）をスコアリング
  • 教師データの調達も Gemini がカタログ経由で自動解決（次カードへ）

⑩ グラウンディング源: BigQuery の3年分の履歴

Gemini は Knowledge Catalog を通じて、BigQuery に保存された過去3年分のキャンペーン履歴を取得。これがモデルの学習と根拠のグラウンディング源になる。

  • 教師データ: 過去3年分のキャンペーン実績（誰に誰が反応したか）
  • カタログのメタデータで「どのテーブルが何を意味するか」を自動特定
  • 捏造ではなく実在の企業データに錨を下ろす＝グラウンディングの本質
Knowledge Catalog BigQuery 履歴 学習データ

⑪ XGBoost ＋ Managed Spark を自動選択

Data Cloud スキルを使って、Gemini が最適なアルゴリズム XGBoost と最適な学習サービス Managed Spark を選定。右側の画面には高品質なコードが並ぶ。

  • アルゴリズム選定: 傾向スコアリングに適したXGBoost
  • 実行基盤選定: Managed Spark——インフラ運用不要の学習環境
  • 生成コードは特徴量再構築に必要なカラムを正しく把握している
  • カタログのスキーマ情報があるからこそ実現できる列レベルの正確性

⑫ 説明可能な評価: 適合率85%

Gemini が履歴テストデータでモデルを評価すると、適合率（precision）85%。しかもどのシグナルが予測を牽引したかを説明してくれる。

85%モデルの適合率
2つ主要な牽引シグナル
  • 牽引要因1: 高金利のクレジットカード金利
  • 牽引要因2: 毎月安定した給与振込
  • 「すべてが説明可能（it's all explainable）」——精度だけでなく根拠も提示

⑬ モデルを Knowledge Catalog に公開

品質に満足したら、その場でモデルを Knowledge Catalog へ公開。ビジネスユーザーとエージェントが同じモデルを発見・利用できるようになる。

  • 公開先はデータと同じカタログ——モデルも資産として一元管理
  • ビジネスユーザーとエージェントが利用者
  • データサイエンティストの成果が現場に直接流通する経路を確保
「このモデルの品質が気に入った——このままKnowledge Catalog に公開しよう」

⑭ 視点切替: マーケティングマネージャー

ここでデモは視点を切り替える。今度はマーケティングマネージャーが、公開済みのあの ML モデルを自然言語で呼び出す。

  • 指示: 「イリノイ州でこのオファーを最も受け入れそうな顧客を特定して」
  • 続けて「メールキャンペーンとデジタルマーケティング資材を作成して」
  • Gemini はKnowledge Catalog からモデルを発見して呼び出す——技術的詳細を知る必要なし

⑮ 同じエージェントでキャンペーンを完結

仕組みの鍵は「同じ Gemini エージェント上に構築済み」という点。同じツール・スキル・メモリを使い、コンプライアンス準拠のメール文案から資材・リスト・ステージングまで一括生成。

  • コンプライアントなメール文案をドラフト
  • クリエイティブ資材（デジタル広告素材）を生成
  • ターゲットセグメントの CSV を生成
  • キャンペーン全体を Google Marketing Platform にステージング
モデル発見 文案・資材・CSV GMP ステージング

⑯ 1週間後: ライブデータのBIダッシュボード

キャンペーンを1週間運用したあと、効果測定も会話で完結。「トップ5郡別の個人ローンキャンペーンの成績を見せて」——ほんの数秒でライブデータのダッシュボードが出現。

  • 軸は上位5郡（top five counties）——地域別の浸透を即座に把握
  • 集計は事前計算ではなくライブデータへのクエリ
  • 追加要求にも柔軟: 「KPIを1つ追加して」でキャンペーン→ローン転換までの中央時間という新指標を即座にタイル化

⑰ ゼロトークンBI: 動的クエリテンプレート

郡をクリックして掘り下けても、裏では Knowledge Catalog に保存された動的クエリテンプレートが働く。LLM トークンゼロでチャートクエリを実行し、精度を損なわない。

  • ダッシュボードは対話型パラメータ制御に対応——LLM なしで操作可能
  • チャートクエリを0 LLM トークンで実行（精度の妥協なし）
  • BI ダッシュボードは鮮度とセキュリティを維持し、企業データにグラウンディング
  • ライブ結果をそのままチームへ共有できる
