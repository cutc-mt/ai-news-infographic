MCP Events で AI が自ら動き出す
Slack の投稿を AI が購読する新仕組み

> ai.subscribe(events=[slack.message_created, github.push, pagerduty.incident]) ... 待機中

Slack への投稿・GitHub への push・PagerDuty の障害——外で起きた出来事を AI が購読して、人がその場にいなくても動き出す MCP の拡張提案 SEP-3415（まだ下書き）。今すぐ使えるのは ChatGPT で、届け方は webhook のみ。動画では今の MCP 通知やふつうの webhook との違い、poll・push・webhook の 3 つの届け方、ChatGPT での活用事例、Claude Code の channels での実験、そして自分のサーバーに入れる前の注意点までを、18枚のカードに整理します。

① 今のAIは「呼ばれるまで寝ている」

現在の MCP の決まりでは、人か AI モデルが「聞いた時」だけサーバーが答える要求応答型。AI は常に無欲な聞き手です。

  • 新しいメール、GitHubへのpush、本番で起きた障害——誰も聞いていない時に起きたことには AI は気づけない
  • 変化を知るには何度も聞きに行くかつなぎっぱなしにするしかない
  • 英語圏Xでも「今のエージェントは決まった時刻か話しかけた時しか起きない」という声が相次いだ

② MCP Eventsとは何か

MCP のクライアントが、外のシステムで起きた出来事を前もって購読しておく仕組みの提案。これが今回の主役です。

  • 購読＝「この種類の出来事が起きたら知らせて」と登録しておくこと
  • 出来事の例：Slackチャンネルの新メッセージ
  • GitHubへのコード更新・PagerDutyの障害も例に挙がる
  • こうした出来事が起きると、ユーザーがその場にいなくてもAIエージェントが反応できる
まさぽん頼まなくても動く。今はChatGPTで使えます。 0:33 第1章

③ おさらい：サーバー／クライアント／ホスト

MCP とは、Claude や ChatGPT のような AI アプリを外のシステムにつなぐ共通の決まり。3つの役割を整理します。

  • MCPサーバー＝道具やデータを差し出す側
  • クライアント＝AIアプリの中でサーバーにつなぐ部品
  • ホスト＝AIアプリそのもの
  • 今の決まりでは AI は聞く側・サーバーは答える側——逆向きの「サーバーから AI を起こす」通信がなかった
サーバーが道具を出す AIアプリがそれを使う 帰りは何も来ない
CARD 04 / 18

④ 今のMCP「通知」は4種類しかない

通知とは MCP サーバーから AI アプリ側へ一方的に送る知らせ。つなぎっぱなしの通信で受け取りますが、選べるのは次の4種類だけ。

  • ツールの一覧が変わった知らせ
  • プロンプトの一覧が変わった知らせ
  • リソースの一覧／リソースの中身が変わった知らせ
エレン全部「何かが変わった」しか言えないんだね。メールが来た、みたいな外の出来事は運べない。 3:21 第2章
CARD 05 / 18

⑤ 今の通知が「足りない」3つの理由

SEP-3415 の提案自身が、現行通知の不足を3つ挙げています。

  • 中身を添える書き方がない——「サービスXで優先度P1の障害が起きた」を表現できない
  • つながっている間しか届かない——通信が切れたらその先は届かない
  • 切れたところから再開できない——切れていた間の出来事は消え、取りこぼしにも気づけない
変わったことは分かる 何が起きたかは分からない → AIが聞きに行くしかない（ポーリング）
CARD 06 / 18

⑥ MCP Events なら何が届くか

図の右側・MCP Events では、「何が起きたか」を表す名前と中身そのものが届きます。

  • 出来事の名前と中身がセットで届く
  • どこまで受け取ったかを表す続きの印（カーソル）も付く
  • 届くのは AI アプリが見張ると決めた種類の出来事だけ
  • 今の通知は Events が入っても削除されずそのまま残る（互換性維持）
// 今の通知
"resourcesChanged" // 変わった、としか言えない
// MCP Events
event: "incident.created" + 中身 + 続きの印

⑦ ただの webhook との3つの違い

「結局ただの Webhook じゃないの？」への答えを、Hookdeck の解説記事が整理しています。

  • 設定する人：Webhook は開発者が管理画面で1つずつ設定／MCP Events はAIアプリが動いている途中で自分から申し込む
  • 届く中身：見張れる種類と中身の形をイベントリストで事前に把握できる
  • 受け取る側：決まった処理をするコードではなく、考えるAI
Xの声違いは出来事がAIの文脈に決まった形で入ること。 Hookdeck「What are MCP Events」より
CARD 08 / 18

⑧ 仕組みは「並べる → 購読 → 届く」

MCP Events の流れはシンプルです。サーバーが出来事を並べ、AI が購読し、起きたら届く。

  • 真ん中のサーバーの箱に見張れる出来事の種類が一覧で並ぶ
  • AIアプリがその一覧から見張りたい種類を選んで購読
  • 外で出来事が起きると、サーバーからその知らせがAIアプリへ届く
  • 届いた出来事がきっかけで、人がいなくてもAIが動き出す
並べる 購読 届く AIが動く
CARD 09 / 18

⑨ events/list と、届く出来事の形

サーバーが一覧を出す呼び出しは events/list。道具のスキーマを書くのと同じ考え方です。

  • 種類ごとに名前・購読時の絞り込み条件（メールなら差出人）・中身の形・使える届け方を記載
  • 届く出来事は名前・刻・中身・続きの印のセット。重複を見分けるイベントIDは別欄
  • 第三者の受け側ツール evdock に届いた障害出来事もこの形。incident.created に番号と重大度が入っていた
name: "incident.created"
payload: { severity: "P1", id: "#42" }
cursor: "…どこまで受け取ったか"
CARD 10 / 18

⑩ 3つの届け方：poll / push / webhook

出来事の届け方は3つ。どれも必須ではなく、種類ごとにサーバーが使える届け方を宣言します。

  • poll＝自分で郵便受けを見に行く型。何も起きてなければ空の答えが返る
  • push＝つなぎっぱなしの電話。長く開いたままの呼び出しにサーバーが流し込む
  • webhook＝転送先の住所を渡しておく型。受け口URLに署名付きで送る
  • どれを使うかはAIアプリ内の部品が決める。AIのモデルには届いた出来事だけが見える
CARD 11 / 18

⑪ 切れても「続きの印」で再開できる

続きの印（カーソル）をサーバーに渡せば、切れた後も続きから受け取り直せます。

  • カーソルの中身はサーバーにしか分からない文字列。AIアプリは取っておいて後で渡すだけ
  • 過去分を再受け取りできるかは種類ごとに分かれる。間を飛ばした時は「飛ばした」合図が付く
  • evdock 実験：受け側を止めて再開すると購読し直しが発生し、止めていた間の出来事がまとめて届いた
14件止めていた間に溜まった出来事が一括到着
1回止める前の分も合わせてコマンドは1回だけ実行

⑫ 今すぐ使える場所は ChatGPT と dots

OpenAI の説明ページによると、現時点で対応しているのは ChatGPT の一部機能です。

  • ワークスペースのチャット（ワークチャット）。ブラウザ版と、条件付きでデスクトップアプリ
  • ChatGPT が対応する届け方は webhookだけ。poll と push（ストリーム）には未対応
  • dots＝常に動いているChatGPTのエージェント。クラウドに自分用のコンピューターとブラウザを持ち、PCを閉じていても動く
  • dots は順次提供の途中で、対象プランでもまだ出ていないことがある

⑬ ChatGPT で動くまでの流れと公式例

何を見張るかはチャットで頼むだけ。あとは ChatGPT が購読をセットアップします。

  • サーバーが出せる出来事を並べる
  • 人が ChatGPT に何を見張り、来たら何をするかを伝える
  • ChatGPT が購読し、届け先URLと署名用の秘密鍵をサーバーへ渡す
  • 該当する出来事だけ届き、チャットで受け取って言われた通りに動く
公式例Slackのバグ報告を見張る／文書の comment.created を文書IDで絞って購読し、頼まれた編集をする OpenAI「MCP Events」ガイドより

⑭ 実例と、一番伸びている使い方

MCP 部品を出している Upstash 社が自社サーバーで試した結果と、X での人気用法です。

  • Upstash：本番デプロイの終わりを見張り、失敗したら教えてと依頼
  • ステージングの失敗は購読条件に合わず送られず、本番の成功では ChatGPT は黙ったまま。本番失敗の時だけチャット投稿＋メール
  • ただし出来事の到着から知らせまで約3分——デプロイ通知には十分だが急ぎの知らせには向かない
  • X で一番伸びているのは看板にタスクを足すだけでAIが独立セッションで動く使い方。CI失敗で直す、特定の人のメールに返信する等も

⑮ Claude Code なら channels で試せる

Claude Code の MCP 説明に MCP Events の記載はまだありません。代わりに外の出来事を開いている会話に押し込む channels（研究プレビュー）があります。

  • CI/監視の知らせがまず手元の受け口サーバーに届き、開いている Claude Code の会話へ押し込まれる
  • 実際の実験：CIビルド失敗を送ると「リポジトリの状態を確認します」と動き出し、減算バグを加算に修正、テスト通過を報告
  • 必要なのは Claude AI ログインか Anthropic の API キー。Pro/Max はそのまま、Team/Enterprise は組織オーナーの許可が必要
3.5秒知らせが届いてからClaudeが動き出すまで（同一PC・1回測定）
CARD 16 / 18

⑯ channels の制限と、クラウドの routines

手元は channels、閉じている間は routines——Claude Code でも同じことが試せます。

  • 研究プレビュー中はAnthropicが許可したチャンネルのみ登録可能。自作は開発用の起動方法で試す（赤字の警告が出る）
  • チャンネルは一方通行の受け口。結果は送った側に返らず、知らせが届くのは会話を開いている間だけ
  • routines＝予定時刻・API呼び出し・GitHubの出来事（PRとissues）をきっかけに動く仕組み。手元ではなくAnthropicのクラウドで実行されるので会話を閉じていても動く
手元の会話なら channels PCを閉じている間は routines

⑰ 実はまだ「下書き」——SEP-3415の現在地

ChatGPT で動いていても、仕様としては入り口のドラフトです。

  • 提案書 SEP-3415 の状態は「ドラフト」。2026年10月5日、Anthropic の Peter Alexander 氏が起草
  • 種類は拡張（extensions track）＝本体の外に足す任意機能。非対応のサーバー/アプリは何も変えなくていい
  • AWS と Anthropic の人がまとめ役のTriggers & Events 作業部会から提案。PR はまだ開いたまま
  • 未決の問いが8つ（届いた出来事をAIにどう渡すか等）。公式SDKの実装もまだ無く、今あるのは第三者の実装のみ
  • ChatGPT のガイドと SEP で「対応してます」の宣言場所が異なる——SEP は拡張の場所へ移すよう求めており、今後変わる可能性
CARD 18 / 18

⑱ 自分のサーバーに入れる前の6か条

  • 届く中身を信じない——提案書自身が「前の指示を全部無視しろ」と書いたメールを攻撃例に挙げる。ツール結果と同じく信用しないデータ扱い。知らせ受領＝実行許可ではない
  • 中身は最小限に——メールなら差出人・件名・IDのみ。本文は受けたAIがツールで取りに行く
  • 届き方の保証はない——順番通り・ちょうど1度の保証なし。重複は出来事ごとのIDで見分けて捨て、冪等に作る
  • 購読の期限は短く——購読は鍵と同じ（WorkOS）。権限が切れても購読が残れば知らせは届き続ける
  • 堂々巡りを試す——AIの作業がまた新しい出来事を生んでループしないか確認
  • 署名を検証——evdock に偽署名の知らせを送ったら「署名が合わない」で一刀両断。本物の証拠は中身ではなく署名
まとめ届いた中身は信用せず・購読の期限を短く・堂々巡りを試してから入れよう。 19:40 第7章

知らせはきっかけ。確かな中身はツールで取りに行く——MCP Events はまだ下書きで、ChatGPT が一部を先に使い始めた段階。まずはCI失敗の知らせを手元のセッションに届けて、AIが動き出すところを見るのがおすすめです。
