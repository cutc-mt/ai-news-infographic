AICodeKing（AI Code King）

Claude Codeが自分自身を訓練するセットアップ
〜AutoResearchでバグ修正指示を自動改善する実験〜

私たちは日々Claude Codeへの指示に時間を費やしています。ならばClaude自身に指示の複数バージョンを試させ、どれが本当に良いコードを書くか判断させたらどうなるか？Karpathy氏のAutoResearchの実験ループとUdit Goenka氏のコミュニティ版プラグインを借りて、バグ修正スキルの指示ファイルだけを自動最適化する実験の全体像——評価ヘルパーの自作、評価ツール自身のテスト、bareモードでの分離試行、過剰適合の罠、48試行の現実的なコスト、勝った版の安全な採用まで——を18枚のカードに整理します。

📅 2026年10月11日公開（15分15秒） |  🎬 YouTubeで視聴

① Claudeに自分の指示を試させる

私たちは普段、Claude Codeへの指示に多くの時間を費やしています。今日の問いは「Claude自身が指示の異なるバージョンを試し、どれが優れたコードを書く助けになるか判断できたら？」というものです。

  • 日頃の指示: 「まず関連ファイルを読んで」「バグを再現して」「プロジェクトの半分も書き換えないで」「完了と言う前に必ずテストを実行して」
  • 基盤のClaudeモデルは不変——変わるのは周囲のワークフロー（指示ファイル）だけ
  • 小規模なバグ修正実験で、改善可能な指示ファイルを与え、未体験タスクでその効果を評価
同じモデル 指示だけ変更 成績の差＝指示の効果

② AutoResearch（Karpathy）とは

アンドレイ・カーパシー氏のオリジナルプロジェクトでは、コーディングエージェントに小規模なモデル学習環境を与えます。エージェントは学習コードを変更して実験を繰り返す仕組みです。

  • 学習コードを変更して実験を実行
  • 固定された評価指標を確認
  • 結果に基づいて変更を採用するか破棄するか決定 → 繰り返し
  • 元リポジトリは各実験に5分の学習予算・NVIDIA GPUで学習。起動・評価にも時間がかかる
「実験履歴によって、どのアイデアが成功し、どれが失敗したかが分かる仕組み」

③ Udit Goenka氏のコミュニティ版プラグイン

元のモデル学習環境を動かしたりGPUを購入したりする必要はありません。今回はUdit Goenka氏によるClaude Code向けコミュニティ版AutoResearchプラグインを使用します。

  • 目標・編集可能な範囲・指標・結果を検証するコマンドを指定する汎用的なループを作成可能
  • プラグインが実験の調整を行ってくれる
  • ただし「何が良い結果なのか」は自分で定義しなければならない——設定全体で最も重要な部分

④ 検証可能なゴールの設定

「Claudeのコーディング能力を向上させて」には明確なゴールラインがありません。一方「同じ制限下で、これら固定されたバグ修正タスクをより多く解決して」なら検証可能な指標になります。

  • 「コーディング能力を向上させて」＝ゴールラインなし（検証不能）
  • 「固定バグ修正タスクをより多く解決して」＝検証可能な指標
  • 指標は実際に望む結果を反映するものであるべき

⑤ バグ修正スキルの初期指示

実験対象として「バグ修正」スキルを作成。初期指示はあえて妥当な内容にします。最適化版を良く見せるための、わざとひどいベースラインは使いません。

  • 報告された動作を理解する
  • 焦点を絞った修正を行う
  • 関連するチェックを実行する
  • 変更内容を要約する
興味深い問い: このループが実際に使えるワークフローを改善できるかどうか

⑥ セットアップ手順

必要なのはClaude Code・Git・評価ヘルパー用のPython・プラグインフック用のNode.js。実験は別フォルダのクリーンなGitリポジトリで行います。

  • 実際のアプリの未コミット作業は実験から切り離す
  • /plugin marketplace add でUdit Goenka氏のautoresearchリポジトリを指定
  • /plugin install auto-research/auto-research → 参照ファイルが正しく読まれるようセッションを再起動
  • /autoresearch:planでもセットアップ可能。今回は指標と検証コマンドを明示する古典的実験ループを使用

⑦ スキルファイルの作成と基準の保全

.claude/skills/ 内にbugfixスキルフォルダを作り、名前・説明・初期指示を記載したSKILL.mdを配置します。これがオプティマイザーが修正できるファイルです。

  • スキルの識別子と呼び出し方法は固定——実験対象は指示内容のみ
  • 開始バージョンのコピーを個別に保存＋Gitコミットを記録
  • 信頼できる比較基準がなければ最終バージョンとの比較は不可能

⑧ 評価ヘルパーは自作する

プラグインをインストールしても万能なコーディングベンチマークは手に入りません。その部分は実験用に自分たちで構築します。

  • 個別のタスクフィクスチャ＋固定された評価テスト＋結果ログを備えた小さな評価ヘルパーをClaudeに作成させる
  • 毎回破損プロジェクトのクリーンコピーで試行を開始
  • ワークフロー指示の1バージョンごとに新しいClaudeセッションを立ち上げ、修正を試みて結果を採点
  • このヘルパーはAutoResearch同梱機能ではなく独自の実験用コード

⑨ 役割の分離が公平性を作る

実験の信頼性は「誰が何を変更できるか」の分離で決まります。採点ルールは誰にも触らせません。

  • 作業者: 使い捨てプロジェクトを変更できる
  • オプティマイザー: ワークフローの指示を変更できる
  • 採点ルール: 固定されたまま——この分離が重要
ループが解答キー（テスト）を書き換えたら、スコアが高くなってもほとんど意味がない

⑩ 開発タスクは小さなPythonバグ3つ

開発セットには、動作を正確に記述できる小さなPythonのバグ3つを使用。画面で確認できるほど小さいけれど、最初の成功例以外の挙動を考慮しているかを試すには十分です。

  • 順序を維持したまま重複を取り除く——セットを返せば重複は消えるが、要求された出力形式や順序に違反する可能性
  • ゼロを欠損値として誤って扱うケース
  • 呼び出し元の入力リストを不用意に変更してしまうケース
  • テストは空の入力や異なる位置にある重複値を含め、実際の契約内容を確認すべき
最終評価用に別タスクを保留 オプティマイザーの開発フィードバックには含めない

⑪ 評価ツール自身を先にテスト

Claudeを大量に実行して費用がかさむ前に、測定道具が機能しているかを確認します。これらのチェックは「評価ツールが動くか」は教えてくれますが、「ワークフローが改善されたか」までは教えてくれません。

  • 既知の不具合がある実装を与えて失敗することを確認
  • レビュー済みの正しいパッチを与えて合格することを確認
  • 採点テストの削除や禁止ファイルの修正をするパッチを拒否することを確認
  • タイムアウト・認証失敗時も、不完全な試行が何事もなかったかのように合格扱いにしない

⑫ bareモードで比較を守る＋課金注意

実行ごとに異なるメモリ・プラグイン・過去の会話を引き継ぐと、比較対象は命令ファイルだけではなくなってしまいます。比較を台無しにしかねない重要な詳細です。

  • ヘルパーは--bareフラグ付きでClaudeのprintモードを使用——スキル・プラグイン・メモリ・CLAUDE.mdの自動検出をスキップ
  • --append-system-prompt-fileでワークフロー指示を明示的に注入。スキルファイルから命令本体を抽出し、両バージョンを同じ方法で注入
  • bareモードはサブスクのログイン情報を使わない——APIキーかプロバイダー認証が必要。サブスクで手動繰り返しするなら「管理が甘い比較」と説明を
  • 「長いリストから適切なスキルを自動選択できるか」は測定していない。モデルと努力レベル・ツール・ターン数・時間制限は固定し、応答メタデータを保存

⑬ ベースラインと採点ルール

まずスコアなしのスモーク試行を元の指示で実行し、ワーカー起動とパッチ評価を確認。完全ベースラインはAutoResearchがスキルを変更する前のイテレーション0——二重にコストを払わない設計です。

  • スコア付き試行の判定: 修正コードが固定テストを通過＋許可ファイル内＋制限時間内に完了
  • メインスコア＝全試行のうち必要チェックをすべて通過した割合。失敗・タイムアウトも未解決としてカウント
  • インフラ問題時は分母を密かに減らさず試行を停止させる
  • 報告例を修正できても既存の動作を壊すパッチは解決とみなさない
  • 開発タスクごとに3回の新規試行で固定——結果を見る前に試行回数を決定

⑭ /autoresearch ループプロンプト

スモークテストが機能し評価基準が固定されたら、AutoResearchに指示を出します。一晩中無制限に実行するのではなく、ベースライン後に3つの候補リビジョンを作る構成です。

  • 目標: 既存の制限下でバグ修正の成功率を向上
  • 対象範囲: バグ修正スキルファイルのみ（スキル名は保持）
  • 指標: 開発パス率（高いほど良い）＋検証コマンドで評価ヘルパーを実行
  • イテレーション3回・候補ごとに1つだけ焦点を絞った指示変更・改善しない候補は破棄
  • 評価器に問題が発生したらルールを書き換えず実験を停止。プラグイン設定はサンドボックスや支出制限を保証しない——コントローラー独自の制限と停止条件が必要

⑮ 候補変更の読み方

提案される仮説の例: ①編集前に具体的な再現手順を要求 ②戻り値変更前に呼び出し箇所を調査 ③完了宣言前に境界ケースを1つ確認。これらは候補の例であり、事前に想定した結果ではありません。

  • 古い指示書を候補の横に開き変更点（差分）を確認
  • 「まず問題を再現せよ」あれば再現手順を、「入力を保持せよ」あればパッチとミューテーションを確認する試行記録を表示——指示変更を観察可能な行動に結びつける
  • 自信に満ちた助言をそのまま改善とみなさない
  • 検証後ループはスコアと採用否を記録。性能低下時は悪化状態に変更を重ねず以前の最適指示に戻す
  • 失敗試行もログに残す——隠すとプロセスが実際より信頼できるように見える。Git履歴と実ファイルで「改善された」要約を裏付ける

⑯ 過剰適合の罠——騙されない方法

この段階で簡単に騳される落とし穴: 3つの例に指示が極端に特化し、開発スコアだけが向上することがあります。特定の関数名に言及したり、期待される修正をこっそり埋め込んだり——次の実行では素晴らしく見えても、明日のコーディング問題には何の役にも立たないのです。

  • 3つの候補修正が出た後、最良のバージョンを固定
  • 検索から除外しておいたheld-outタスクで元の指示と最適化済み指示を比較
  • プロジェクトのコピーとClaudeセッションを再度新しいものに。各バージョンをタスクごとに3回ずつ同じ制限で実行し、順序を入れ替える
  • 最終セットでの失敗をオプティマイザーに見せない——次の試行を「未知のテスト」と呼ぶ。その失敗を使って調整した時点で、そのタスクは開発の一部になってしまう

⑰ 結果の読み方——4つのシナリオ

結果画面には開発用と保留タスク両方の成績（試行回数・完全合格数・タイムアウト・推定コスト・成功試行の所要時間）を表示。解釈は実際に起きたことに従うべきです。

  • 開発も新タスクも改善 → その指示がこのモデルとタスク群に寄与した証拠。ただし少数の小タスクで万能能力向上が証明されたわけではない
  • 開発のみ改善・保留は横ばい/悪化 → 過剰適合かノイズ。汎用的な改善は証明できていない
  • 両バージョンが全タスク解決 → ベンチマークの限界に到達。コスト・完了時間で比較するか、難易度の高い評価を設計
  • テストで測れなかった品質向上を主張しない——一晩実行しても自動で設定が改善される約束はない。ループは悪い指標も同じ熱心さで追求する

⑱ コスト・勝者の採用・結論

「3回の反復」は実際よりはるかに安く聞こえます。オプティマイザー自身の思考・準備・予行演習を除いても48回のコーディング試行になります。オープンソースでも実験は無料ではありません。

開発3タスク×3試行9回
ベースライン+候補3×評価36回
2版×保留2タスク×3回12回
合計コーディング試行48回
  • --max-budget-usd／--max-turns／外部タイムアウトを併用。金額は見積もりとして余裕を持つ。試行ワーカーを制限しても他のClaudeセッションは制限されない
  • 採用は慎重に: 練習タスク関連を差分から削除し、編集版を新候補として再チェックしてから特定ワークフローに採用。元バージョンも残し、無関係スキルや全体設定はそのまま
  • 同じ考え方はテスト作成・移行・コードレビューにも適用可能——実害ベースで測定
  • 結論: 頻繁に繰り返し確実に評価できる限定的ワークフローなら価値あり——「全体として、かなり素晴らしい」
