効率的なエージェント自動化の構築術
Claude Managed Agents 活用事例

Claude の開発ブログで公開された記事をもとに、毎朝の要約を自動でつくるエージェントの設計を解説。「どこまで読んだか」を状態ストアに残す工夫や、サブスクで支給される API クレジットの使いみちまで公式の事例で学びます。

動画主も前回取り上げた機能なので、今回の記事は続編として楽しめる内容です！
2

APIクレジットの使い道

  • Maxプランやチームプランの利用者には、APIクレジットが毎月支給されます。
  • その活用法として、いちばん良いのがManaged Agentsでの自動化だと紹介されています。
  • チャット画面の設定からAPIダッシュボードへ移動して、クレジットを登録します。
動画主いわく「API課金なので控えていたが、支給されるなら深掘りしたい」とのこと。
3

Managed Agents とは

  • エージェントの定義を書いて、クラウド上に展開して動かす仕組みです。
  • 手元のagent.md（エージェントへの指示書）が出発点になります。
  • 定期実行や自動化への組み込み、手動トリガーでの起動も自由です。
完成すると、結果を Discord や Slack に報告してくれます。
4

おさえたい4つの概念

  • エージェントの定義：agent.md に役割と手順を書きます。
  • デプロイメント：どのエージェントを、いつ、どう動かすかを決めます。
  • 環境：エージェントが操作する、実行まわりの置き場所です。
  • ボルトとメモリーストア：鍵と記憶を預かる部品です。
この4つをいい感じに組み合わせると、毎朝の要約エージェントができあがります！
5

クラウドで動かす強み

  • 自分のPCでも動きますが、チーム共有ならクラウドが断然らくです。
  • 手元のリソースが不足するときも、クラウドだと助かります。
  • 毎回まっさらな環境が用意され、そこへメモリーが差し込まれる設計です。
Slack や GitHub のトークンが必要になったら、ボルトから呼び出して使えます。
6

毎朝の要約エージェント

  • 公式のデモは平日の朝7時32分に起動するスケジュール設定です。
  • 情報源はSlackとGitHub。ここからまとめをつくります。
  • 完成した要約を、Slack のチャンネルへ投稿して報告します。
「おはようございます、今日のはじめに…」という毎朝の挨拶からレポートが始まります。
7

状態ストアの役割

  • 過去の状態をストアに保存して、どこまで読んだかを覚えておきます。
  • 投稿したかどうかも状態として見えるので、抜け・重複が減ります。
  • しおりを更新すれば、次の実行は前回の続きから読み始めます。
今回の動画でいちばんの学びポイントはここ、と動画主が強調していました。
8

「時間の穴」を防ぐ設計

  • 「直近24時間ぶんを読んで」と指定すると、起動がずれた日に穴が生じます。
  • 起動のタイミングが1〜3分ずれるだけで、取りこぼしが出る恐れがあります。
  • 相対時間ではなくしおり方式にすると、間の1日も拾えます。
Slack は1分単位で貴重なやりとりが流れるので、エージェント運用では特に意識したい部分です。
9

人はルールを書く係

  • 文章の好みやライティングルールは、人間があらかじめ書いてためておきます。
  • エージェントはその文体にそって、要約を人のトーンで仕上げます。
  • 人とAIの分担を決めておくのが、読みやすい朝レポートのコツです。
毎朝の読み手が同じでも、書き手のくせが残っていると、読み手に親しみが湧きますね。
10

実行のステップ全体

  • 起動直後にメモリーストアを読み込み、好みと状態を把握します。
  • 情報源を巡回しながら、必要なタスクを判断して進めます。
  • 検証をへて投稿し、最後に次のぶんの記憶を書き込む流れです。
読む → まとめる → 投稿する → 覚える。この一連の流れが自動で回ります。
11

CLI でクラウドへ配置

  • 手元からクラウドへ展開するには、Anthropic の CLIを準備します。
  • 事前にアカウントの認証をすませておく必要があります。
  • applyを実行すると、定義がワークスペース上にできます。
# 定義をクラウドのワークスペースへ反映
$ anta apply
→ agent.md / environment を配置
→ ストアも一緒に用意される
ストアへは直接でなく、スクリプト経由で書き込む方法もあります。
12

ボルトで安全に管理

  • APIキーなどのトークン類はボルトが預かってくれます。
  • エージェントは鍵を直接読まず、権限つきで呼び出します。
  • MCPサーバーを追加して、接続をひろげることもできます。
鍵を書き出さない設計なので、流出の心配がぐっと減ります。
13

通信を制限して固める

  • 環境の設定でネットワークの許可先を絞りこめます。
  • 公式のクイックスタートにも Slack や GitHub の連携手順があります。
  • MCP経由で外部サービスとつなぐと、扱いがさらにらくになります。
通信の窓口をせまくしておくと、安全な運用に一歩近づきます。
14

agent.md の3つの禁止

  • HTTP 200が返っただけで成功扱いしない。投稿可のフラグを確認します。
  • 足りないときに別のトークンを探させない。迷走の元になります。
  • 認証失敗をメモに残さない。ノイズとして記憶に居座ります。
残したメモは次の起動時にも読み込まれるので、誤記憶に要注意です。
15

重複投稿をふせぐ流れ

  • まず過去の投稿を履歴から検索して、あればそこで終了です。
  • なければ、先に投稿中の状態を記録してから作業に入ります。
  • 投稿がすんだらしおりを更新。失敗時は記録をのこします。
# 重複チェックの流れ
1. 履歴を検索 → あれば終了
2. "posting" を記録 → 作業開始
3. 投稿 → しおりを更新
4. 失敗 → 記録をのこす
「状態を先に書く」のがポイント。途中で止まっても再開しやすくなります。
16

権限は最小から

  • Slack 連携は読み込み専用にしておくと、暴れても書き換えません。
  • 読み取りと書き込みを分けて、必要ぶんだけ渡します。
  • 毎日動かすものほど、権限の設計が効いてくると公式も説きます。
「究極、暴れまわれない」状態にしておくのが安心のコツですね。
17

ストアの読み書きを使い分ける

  • ルール系のストアはリードオンリーに。人は書き、AIは読むだけ。
  • 状態メモはリードライトで、エージェントが自由に更新します。
  • 役割ごとに分けると、記憶がよごれにくくなります。
しっかりしていて、しかもシンプル。Managed Agents の設計思想が光る部分です。
18

まとめ: 部品を組み合わせる

  • 定義・環境・ボルト・ストアの部品を組み合わせれば、かなりのことが実現します。
  • API のオンボーディング対話に記事を渡すだけで、同じものがつくれます。
  • 動画主のニュース収集エージェントの実例コードも、概要欄から配布中です。
