第1部：Agent-Nativeとは何か
CARD 01

今回のテーマ

「エージェントに作らせた後、自分で直したくなったら?」

動画冒頭の例: AIエージェントにプレゼン資料の作成を依頼した後、見出しを変えたい・スライドを移動したい・あるセクションをより技術的にしたい——ごく普通の修正をどう扱うか。

  • 従来: 細かい変更もすべてチャットで説明し続けるしかない
  • 本音: テキストをクリックして自分で直したいときもある
  • 理想: エージェントに戻るときは今の状態（手動編集込み）を理解してほしい
  • これを実現するのがAgent-Nativeというわけ
「任せた後も自分の手で触れる。そしてエージェントはその変更ごと引き継ぐ」——この往復が本動画の検証軸。
CARD 02

Agent-Nativeとは

BuilderIOが公開したオープンソースのTypeScriptフレームワーク

インタラクティブなUIを持つエージェントアプリを構築するためのフレームワーク。GitHubで公開され、誰でもセルフホストできる。

  • 開発元: BuilderIO（オープンソースで公開中）
  • 言語: TypeScriptフレームワーク
  • 用途: チャットではなく操作できるアプリの中で動くエージェント
  • 公式サイト agent-native.com にSlides等のデモアプリとドキュメント
公式リンクagent-native.com ／ GitHub: BuilderIO/agent-native（説明欄に記載）
CARD 03

解決する問題

人間の編集とエージェントの編集が「同じアプリ」で合流する

従来のチャット型エージェントとの決定的な違いは、アプリの現在の状態をエージェントが参照できること。

  • ユーザーは画面上で直接編集（ダブルクリック修正・ドラッグ移動など）
  • エージェントは同じデータに対して操作を行う
  • 手動修正→エージェント継続→また手動…の往復ワークフローが成立
  • 「どのスライドの話か」を現在開いている画面・選択から特定できる
変更文をチャットにコピペして文脈を説明し直す——このストレスを消すのが設計思想の中心。
CARD 04

押さえておく4つの特徴

「自分のもの」を手放さない設計

動画で紹介されたAgent-Nativeの基本方針はすべてを自分の手元に置けること。

特徴内容
React製UIフロントエンドはReactで構築・カスタマイズ可能
モデル持ち込みBYOM——Providerを自分で接続（OpenRouter等）
自分のリポジトリアプリコードは自分のGitHubリポジトリで管理
ホスト選択対応するホストならどこにでもデプロイ可能
補足Slides等の公式テンプレートから始めて、コードを fork して独自アプリへ発展させる流れが標準
第2部：Slidesアプリ ハンズオン
CARD 05

クラウド版セットアップ

サイトを開いて「Create a Deck」するだけ

まずは公式サイトのSlidesアプリをそのまま利用するルート。動画ではここからデモが始まる。

  • agent-native.com → Slides → Create a Deck
  • サインイン後、役割についての任意質問にはSkip for nowも可能
  • モデル設定: usebuilder.io or 独自Provider（動画ではOpenRouterを接続）
  • サインインとモデル接続は別ステップ——生成前に必ず確認
  • デフォルトモデルが選択済みかModel Settingsで確認
要注意作曲者表示がConnect Agent / Connect Keysのままなら、接続とモデル設定を見直してからプロンプトを送る
CARD 06

ホーム画面の構成

生成・インポート・テンプレートの3つの入口

モデルが使える状態になったら、ホーム画面には3通りの始め方が用意されている。

  • 大型プロンプトボックス——内容を直接記述してデッキ生成
  • インポートメニュー: PDF / Google Slides / PPT形式に対応
  • テンプレート一覧を閲覧して雛形から開始
「生成だけが正解じゃない」——既存資料のインポートや雛形編集も第一級の入口として用意されている点が実用的。
CARD 07

テンプレートで手動編集

エージェント介入前に「普通の編集」が効く

動画ではLaunch Keynoteテンプレート（7スライド）を開いて手動編集を実演。

  • 見出しをダブルクリック→書式付きテキストエディタが開く
  • 実演: 見出し「meet Lumen」→「Agent UI」に変更——再読み込み後も保持
  • フィルムストリップのサムネをドラッグしてスライド順を入れ替え
  • テンプレートは固定レイアウト——長い文ははみ出すのでキャンバス注視
実感エージェントを出す前の「普通のプレゼン編集」が普通にできる——これがAgent-Native体験の土台
CARD 08

プロンプトでデッキ生成

構成を指定して6スライドを一気に作らせる

次はエージェントの出番。動画で投げたプロンプトの骨子はReact開発者向けAIコンテンツアシスタントの6スライド。

  • 構成指定: 課題→ワークフロー→共有アクション→人間のレビュー→実例→まとめ
  • スタイル指定: 短い見出し・暗い背景・1色のアクセント
  • 「統計を捏造しない」など事実精度の制約もプロンプトに明記
  • 生成中はエディタ上でスライドが追加されていく様子をリアルタイム視聴できる
完成後はスライドをクリックして回り、構成通りか・文字が収まっているか・説明が通じるかを先に確認——見た目が良くても説明が弱いことはある。
CARD 09

手動編集→エージェント継続

本題: 「このスライド」が通じるか

デッキのhuman reviewスライドを手動でいじり、その後エージェントに続きを頼む——動画の核心シーン。

  • 手動: 見出しを「always review before publishing」に書き換え
  • 手動: スライドをworkflow直後に移動（物語順を前倒し）
  • 指示: 「このスライドをより技術的に。今編集した見出しはそのまま」
  • 検証: 開いているスライドを編集したか／見出しを保持したか／位置が維持されたか
理由見出しをチャットに貼り直さなくても参照が通じる——これが「現在のアプリ状態を理解している」証拠
CARD 10

部分指定の指示とエクスポート

文単位のrevise with AI＋4形式への書き出し

さらに細かい調整は文を選択→revise with AI。バブルメニューの小窓に選択文が表示され、的を絞った依頼ができる。

  • 実演: 「この文を承認フローの例で20語以内で説明して」
  • large draft は任せ、細かい言い回しは自分で、特定部位だけエージェントへ差し戻し
  • 書き出し: HTML / PDF / PPTX / Google Slidesの4形式
  • エクスポート後はフォント・レイアウトの差異を必ず確認
「技術的には正しいけど自分の声じゃない文」を自分で直せるのが価値——そのために部分指定が要る。

CARD 11

ローカル起動の手順

Node＋PNPMで自分のマシンにSlidesを立てる

自分のコピーを動かすにはNode 22.22以降とPNPMが必要（動画ガイド）。

  • プロジェクト置き場でターミナルを開く
  • スターター生成（正確なコマンドは動画説明欄に掲載）
  • 生成フォルダに cd
  • PNPMが無ければ corepack enable
  • pnpm install → pnpm dev、表示されたローカルURLを開く
  • オンボードで「continue as local dev」→モデルを接続
# スライド用スターター（要旨）
npx --yes @agent-native/core@latest create-...-slides --standalone --template slides
モデル選択肢はBuilder / 独自Provider / ローカルOllamaの3系統（ドキュメント記載）
CARD 12

コストの考え方

フレームワークは無料・かかるのはモデルとインフラ

フレームワーク自体は無料＆オープンソース。ただしモデル利用と選んだインフラには費用が発生しうる。

  • OSSライセンスで無料——ソースコードは自分のリポジトリで管理
  • Builderのセットアップには無料クレジットあり（サインイン時に残量確認）
  • OpenRouter等の外部Providerは各自の従量課金
  • 最初の実験は小さいデッキ＋不要な画像生成を避けるのが動画の助言
ねらい課金より先に編集ワークフローの理解に集中するための工夫
CARD 13

アクションの設計（defineAction）

エージェントに渡す「操作」を自分で定義する

開発ガイドの核はdefineAction関数。エージェントが呼べる操作を明示的に定義できる。

構成要素役割
description操作の説明——エージェントへの使い方の伝達
schema入力の定義（型・必須項目）
run実際に編集を行うコード
  • updateSlideの入力: deckId＋slideId＋差し替え/新規コンテンツ
  • 編集前にeditor権限を検査し、保存後に接続クライアントへ通知
  • 操作は検査・改変・許可の制限すべて自分の管理下
CARD 14

UIとエージェントが同じアクションを共有

MCPとの違いはここにある

定義したアクションは画面側・エージェント側の両方から同じものを呼べるのが最大の特徴。

  • Reactからはフック経由: 読み取りuseActionQuery／変更useActionMutation
  • 同じアクションをHTTP経由・MCP経由でも公開可能
  • 例: renameDraft——UIは保存時に、エージェントは依頼時に呼ぶ。空タイトル拒否等のルールは1箇所に集約
  • Slides実装の妙: ブラウザ編集はpatchDeck、エージェントはupdateSlide——同じデッキとロック機構を共有
比較特徴
MCP単体外部ツールをエージェントへ接続するプロトコル
Agent-Native人間・UI・エージェントが同じアクションと状態を共有するアプリ基盤（MCPでもアクション公開可）
CARD 15

コンテキスト・アウェアネス

「どのスライド/原稿の話か」を界面が伝える

エージェントが現在の状況を知る仕組み。インターフェースが現在のビューと選択を供給し、view screenアクションが関連レコードを取得する。

  • プレゼンなら開いているデッキ＋選択中のスライド/要素
  • コンテンツエディタなら現在の下書き＋編集中の段落
  • 共有データベースでUIとエージェントが同じ記録を扱い、アプリ状態は選択等を表現
  • 検証法: ドラフトAを開いて手動変更→要約依頼、ドラフトBに切り替えて再依頼——応答が開いた対象に追従するか
開発指針まず有用なID数個＋現在の選択を配線し、対応コンテンツを取得できることを確かめる

CARD 16

Claude Codeでアプリ自体を改造

オープンソースの真価はここから

生成したプロジェクトをClaude CodeやCodexといったコーディングエージェントで開けば、アプリのカスタマイズ自体を任せられる。

  • まず既存構造をinspectさせ、その後自然言語で変更を記述
  • 実演: 「各プレゼンにレビューチェックリストを追加。UIでチェック・デッキと共に保存・内蔵エージェントも同じ共有アクションで読み書き。既存パターンに従え」
  • 検証: 自分で1項目チェック→内蔵エージェントに「未完了はどれ?」→同じ保存情報を参照しているかを確認
  • 改良も自然言語: チェックリストをプレビュー横に移動・コンパクト化・一覧に状況表示
動かせるアプリを土台に、コーディングエージェントが自分の働き方へ合わせて改造してくれる——OSSである意味が一段と大きくなる。
CARD 17

注意点と限界

接続しただけで魔法にはならない

動画が正直に挙げた留意点を押さえておく。

  • サンプルアプリはalphaラベル——まだ成熟段階
  • エディタにエージェントを繋いでも全ての編集が良いとは限らない
  • モデル・プロンプト・アクションの扱いは自分で評価・調整する責任
  • 質問して短い答えを読むだけならシンプルなチャットで十分な場合も
判断軸閲覧・選択・編集・レビューを複数ラウンド行う作業かどうかで価値が決まる
CARD 18

まとめ: 向いている人・始め方

「触れるエージェントアプリ」を作りたい人へ

向いている用途

  • プレゼン資料——順序・レイアウト・言い回しが問われる物
  • コンテンツカレンダーやドキュメントエディタ
  • 人間の確認を挟む複数ラウンドの作業
  • アプリを自分流に改造したい開発者

動画推奨の始め方

  • 公式サイトの既存アプリ（Slides）から開始
  • 小さいものを作り、自分で編集、エージェントに継続
  • ソースを開いて1つのワークフローだけ改造
  • 手動⇄エージェント交互時に編集保持・最新反映・復帰を確認
設計美取り組む場所が具体的——検査するアクション・更新するデータ・渡すコンテキスト。ワークフローを段階的に構築・評価できる
結論: エージェントを「チャットの箱庭」から「作業するアプリ」へ引き上げる現実的な一手——OSSなので今日から試せる。
