みんな知ってる「Claudeあるある」2連発

動画冒頭で紹介される、エージェントあるあるの代表例
あるある① バグ修正
  • バグ修正を依頼→大量のファイルを編集
  • テストも走らせて「直りました」報告
  • アプリを開くと…同じバグが残ってる
あるある② エクスポートボタン
  • 「ボタンを追加して」と頼んだだけ
  • なのに気づけば新フレームワークの保守を押し付けられる
  • 依頼と釣り合わない巨大変更に
  • 原因は「調査せずに編集」「修正がデカすぎる」「動作確認を省略」の3パターンに集約される
  • P Stack はこの3つを逆から潰す設計 — つまり先行調査・最小変更・実動作チェックを強制する
「『直った』って言ったのに直ってない問題、本当に全人類が通る道…」

P Stack の3本柱 + おまけ3機能

「小さく直して、ちゃんと確認する」文化をスキル化
1編集前に調査させる — 原因の見当がつくまでファイルを触らせない
2修正は最小限に保たせる — 依頼に対して釣り合った変更量を維持
3頼んだものが実際に動くか検証させる — 「言った」でなく「見せた」
  • さらにデザイン比較・調査の分割・別エージェントによるレビューの手段も用意
  • それぞれが独立したスキル（コマンド）になっていて、必要な場面だけで呼び出す設計
「『とにかく全部盛り』じゃなくて、引き出しを選べるのが良い感じ」

セットアップ — Claude自身に「適応」させる

リポジトリを渡して、あとはClaude Codeに任せるのが作法
SETUP
プロジェクトで Claude Code を開き、動画概要欄の P Stack リポジトリ を渡して依頼:
「このスキルを本プロジェクト用に適応して。既存の指示は保持し、利用可能なツールとモデルを使い、全部動くか確認して。追加で必要なものがあれば教えて」
  • 互換性の調整（Cursor 用の記述 → Claude Code 用への書き換え）はClaude 側に丸投げして良い、というスタイル
  • セットアップ確認が済んだら、普段使う入口は /potato-mode の1つに集約される
  • 大事な制約: プロジェクトの既存ルールを上書きさせないこと
「「導入もAIにやらせる」のが逆にAI時代らしい使い方で面白い」

/potato-mode — メインの入口はこれ1つ

タスクと「完成の定義」を渡せば、プレイブックが手順をガイド
HOW TO USE
/potato-mode に タスク と 望む完成形の明確な説明 を添えて実行。
→ スキル内のプレイブック（作業手順書）が Claude をステップごとに先導する
  • コツは「何をもって完成と言うか」を最初に書くこと。例: レビューできる状態で変更を残す
  • プレイブックはバグ修正・設計・調査などシーン別に用意されており、タスクに応じて自動で選ばれる
「"完成条件"を先に言語化するの、人間側の訓練にもなるんだよねこれ」

実例: 高速入力で検索結果が「昔に戻る」バグ

動画で実演される題材 — 素早くタイピングすると古い結果が上書き表示される
EXAMPLE PROMPT
/potato-mode 実行中のアプリで検索バグを再現し、原因を特定、最小の修正をして、同じ操作を後で検証。変更はレビュー可能な状態で残して。
  • 推測される原因: 古いリクエストの応答が遅く帰ってきて、新しい結果を上書きしている（リクエストの順序問題）
  • ただしそれは「推測」。プレイブックは Claude にリクエストを観察し、どの応答が画面を更新したか確認させる
  • 証拠が別の原因を指すなら、そちらを追いかけるのがルール — 最初の仮説に固執しない
「race condition の教科書例。人間でもハマるやつをAIに淡々と追わせるのがミソ」

バグ修正プレイブックの流れ

「修正を選ぶ前に、まず故障を再現せよ」が第一命令
1再現: 実アプリで障害を確実に起こす（リクエスト観察・更新タイミング確認）
2原因確定: 証拠が仮説を裏付けるまで追跡。反する証拠が出たら方針を切り替える
3失敗テスト: 安価に書けるなら failing test を残す（再現の固定化）
4最小修正: 原因に直接効く変更のみを加える
5再検証: 元の操作を再現 — 古いリクエストを遅延させ、新しい検索が勝つことを確認
  • パッチ受け入れ前のチェックは 「失敗を見せる → 原因を説明 → 修正後に同じ操作が動く所を見せる」の3点セット
「"テスト通りました"より"目の前で直ってる"の一万倍強い。それがデモ」

仮説が崩れたら変更を「撤回」させる

地味だけど効く — デバッグの残留物を防ぐルール
  • Claude が何か試して証拠がその理論を否定した場合、プレイブックはその理論に基づく変更を削除するよう指示
  • なぜなら: この撤回がないと、デバッグ1回で「5つのワークアラウンドが残り、どれが効いたか誰も分からない」状態になりがち
  • 常に「今の正解」だけがコミット対象になる — レビューする側も diff が読みやすくなる
「試行錯誤の跡が全部コミットされてるの、レガシーコードの生成装置なんだよね…」

/how — コードの「流れ」を追跡して説明させる

何を変えるべきか分からない前に、まず理解から
USE CASE
例: 「このフォームの検索フィルタはどうやって DB クエリまで届くの?」
→ Claude がコードをトレースしてデータの流れを説明してくれる
  • 使いどころ: 初見のプロジェクトで「どこに何があるか全く分からない」とき
  • 編集は一切発生しない 読み取り専用の調査系スキル。影響範囲の見極めに最適
「巨大レポジトリに放り込まれた初日のコレ、ほんとに助かる」

/why — 「なぜこのコードは存在するのか」を掘る

削除依頼の前に、歴史と証拠に当たらせる
  • 典型例: 一見して根拠不明なリトライ上限。「消して」と言う前に、なぜ追加されたのか /why で調査
  • アクセスできる履歴（コミットログ等）と証拠から、関数本体からは読み取れない当時の事情を拾ってくる
  • 身に覚えのない「謎の定数」ほど、実は事故対応の傷痕だったりする — 削るなら根拠を持って
「"意味不明だから消す" → 数ヶ月後に同じ事故が再発、は古典的な死にパターン」

/teach — 答えを「自分の理解」に変える

作るだけでなく学ぶ — 保守する人間のためのスキル
AFTER THE FIX
検索バグ修正のあとに: 「リクエストの順序がどう崩れたか、この変更がなぜ防げるのか説明して」
→ 分かるまで追撃の質問を続けられる
  • 使いどころ: 作りながら学ぶたいとき。自分が今後メンテするコードを相手の言葉で咀嚼
  • 理解が曖昧なまま accept せず、納得するまでフォローアップ質問して良いのが明文化されている
「AIに丸投げしても、保守は結局人間。"分かったつもり"をなくす一手」

/architect — 実装の前に設計を通す

例のエクスポートボタン、正しい順序で作る
DESIGN FIRST
/architect: 「現在フィルタされた結果をダウンロードするエクスポート機能を設計して」
→ ページ・API・エクスポートコードの繋がりを、実装前に示させる
  • 前倒しで検討すべき問い: どのフィルタが適用される? データ量は最大どれくらい? 既存クエリを再利用できない?
  • これらの答えは機能を半分書き終えた後に知りたくない — 最初に答え合わせする文化
「"あとから仕様が判明"で書き直す手間、ゼロにできるならやらない手はない」

「解を小さく保つ」原則 — 新ジョブシステムはいらない

P Stack の思想: 依頼に対して釣り合った規模の実装を
これで十分
  • シンプルなダッシュボード
  • 既存実装の再利用で賄う
  • 変更 diff がすぐ読める
要らないまで作る
  • エクスポートに新ジョブシステムを導入
  • 保守対象が無駄に増える
  • 「ボタン追加して」という依頼本体が埋もれる
  • 判断基準はシンプル: その機能が本当に必要とするか。必要ないなら作らない
「エクスポート機能を頼んだらジョブシステムが生えてくる事件、完全に冒頭のあるある②」

/arena — 同じタスクを複数エージェントで競作させる

「最初の一案それで本当にいい?」に答えるスキル
1同一タスクを複数エージェントへ送り、独立した候補をそれぞれ作成
2リードが候補を比較し、もう一つの判断を得てベースを採択
3他の試行から使えるアイデアを移植し、統合結果をチェック
  • エクスポート例: ファイル直接返却 vs バックグラウンドジョブで準備 を同じ要件で比較
  • 評価観点は 想定データ量・複雑さ・ユーザー体験の3軸
  • 適する場面: 最初の案が「それっぽい」けど、決定前に別アプローチも見たいとき
「文字通りアリーナ。AI同士を戦わせて、ジャッジ役のAIが裁く時代」

/swarm — 調査を分割して群がせる

並列で走る専門調査部隊、とりまとめはリードが担当
  • 分割例: ①バックエンドのフィルタ追跡 ②ページ側のフィルタ状態調査 ③既存テストの確認 — 各エージェントに特定の仕事を割り当て
  • 大きなレポジトリではパッケージ横断でも同じ分割が可能
  • 成果物は発見された問題点+検証できなかった箇所をまとめた1つのレポート
  • 最重要ルール: 未完了のチェックを黙って「合格」にしない — 残課題は残課題として可視化
「"たぶん大丈夫"を"検証済み"に偽装しないのは、AI チーム運用の生命線」

/interrogate — 完成物を独立レビューにかけさせる

ビルド成功＝機能が正しい、ではない。レビューと実機確認で締める
1レビュアーに確認項目を渡す: 例 「選択中フィルタを尊重するか」「失敗を適切に扱うか」
2独立した複数レビューを取得し、発見事項を評価
3リードエージェントが判定: 機能を壊す問題 / 採用すべき提案 / 文脈を欠く誤指摘
  • AIレビューは提案を「全部要件化」しがち — このスキルは判定付き verdictを返し、自動全適用しない
  • それでも人間の最終確認は必須: フィルタ適用→ダウンロード→行と列を検査。ビルド成功は中身の正しさを保証しない
  • レビュー役にはClaude Code セットアップ内の利用可能モデルを使い回す
「作った本人(同じAI)が審査すると見逃すから、"独立した目"を入れるのは理にかなってる」

運用のコツ — 全部盛りしない・終了条件・コスト管理

小さな仕事に全スキルは不要。長期戦には「終わりの定義」を
  • 些細な修正なら 再現→的確な修正→アプリ内チェックだけでもう十分。オーバー思索は不要
  • 長期タスクには満たすべき終了条件を繰り返し確認させる。例: API移行で「全呼び出し元が新版利用・旧API削除・関連テスト合格」
  • 決定ログを取り、別セッションが必要なら チェックポイントを残す — 戻ってきたときのレビュー対象が明確になる
  • コスト面: 追加エージェントとレビュー周回は利用枠/API予算を消費。まず1実装+1集中レビューから始め、比較系は重要判断に温存
「"強いほど良い"じゃなくて"適量が良い"。予算管理と同じで、地味に大事」

まとめ — 試す価値あり、判断は「パッチと検証」で

動画の結論: P Stack は試す価値がある、特にこの2つの習慣を強制してくれる
  • 効果が大きいのは バグを再現するよう促すことと、"完了"の前にアプリを確認させること — その期待をスキルに書いておけば再利用・調整できる
  • 始め方: 自分がよく分かるタスクを1つ渡して、返ってきた成果物を見比べる
  • 評価基準は 「パッチの中身」と「走らせた検証」 — 宣伝文句ではなく成果で判断するスタイル
  • リポジトリは動画概要欄にリンク。Claude Code にも好きなコーディングエージェントにも適応可能。「全体として、かなりイケてる」というのが作成者の評
