01

「オーケストレーション」とは何かWHAT IS ORCHESTRATION

1つのモデル（リード）が作業を計画して結果をチェックし、別のモデル（ワーカー）が割り当てを実行する仕組み。リードの出す計画と割り当ての質がアプリ全体を左右します。

今回の動画では、チーム間の会話を追いかけながら、実際にアプリを起動してどこで連携が功を奏し、どこで失敗したかを検証。

よもぎ企画する人と作業する人が分かれてるのがオーケストレーションなんだね。チーム開発そのものだ…！

05

比較の限界という注意書きCAVEATS

この比較には守るべき但し書きがいくつもあります。

  • 計算バジェットは均等化されていない
  • ソロ実行との比較・役割入替のテストは未実施（委任自体の効果は分離できない）
  • クォータエラーで中断されたランあり

つまり「どのペアが絶対的に優れるか」ではなく「今回のランではどうだったか」を見るベンチマークです。

リードの計画がすべてを決めるPLAN SHAPES EVERYTHING

エミュレータ課題では、Astraリードの2チームはGame Boyの実行まで計画した一方、DS・3DSはファイル検査のみを割り当て。実行パスが最初から存在しませんでした。

Game Boy対応を改善しても、DSのファイル検査はDSのゲームを動かせない。計画段階の欠落は、その後の作業では取り返せないという教科書的な失敗例です。

求められるレビューループTHE REVIEW LOOP

Opus + Solのプロジェクトでは、テスターが「椅子を選択すると画面が真っ白になる」バグを発見。リードは最初ビルダーの古いスクリーンショットの問題と疑いましたが、テスターが障害を再現。ワーカーが選択ハイライトを修正し、リードが再ビルド後のアプリを確認しました。

「疑う→再現→修正→確認」。著者がチームに求めるレビューループの理想形として紹介されている場面です。

よもぎ
よもぎリードが疑っても、テスターがちゃんと再現を見せて修正につなげたのがすごい！ assumptionを手放すの、大事だね。

次のプロジェクト前のチェックリストBEFORE LETTING WORKERS LOOSE

  • 必要機能すべてに担当者が付いているか、作業開始前に確認
  • 異論のある失敗は再現してから直す（Opus + Solのレビューループ）
  • 通常のユーザージャーニーを実際にテスト
  • 最終パッケージを確認する

より広い信頼性・コスパの主張には、さらなる再走行と完全なコスト記録が必要——と結論づけられています。Rate limitingとquotaとの戦いは、これからも続きます。
