知らないと危険 — AIエージェントから情報が漏れる理由と今すぐできる対策

情報漏洩ニュースが連日続くなか、KEITO氏がClaude CodeなどのAIエージェントを安全に使うための基礎を解説。攻撃側のAI活用実態（IPA・Gambit Security・Anthropicの3つの根拠）、情報が外に出る4つの出口、プロンプトインジェクションの仕組み、そして権限モード・Deny/Allow/Hook設定・MCPの危険性・サンドボックスまでを一気通貫で整理します。本インフォグラフィックは動画内容を再構成したものです。

CARD 07

Claude Codeにできること＝リスクの正体読む・実行する・外に出る — 人間がやれることをほぼ全部やれる

RISK MODEL
  • 読む: ファイルの中身・各種ログ・MCPやコネクター経由の情報まで読める
  • 実行する: コマンド・スクリプト・アプリの起動テストなどを実行
  • 外に出る: メール送信、Webアクセス、git push、MCPによる外部連携・送信
  • 喩えれば「超優秀だけど善悪の判断ができない新人」 — 机上の書類も鍵ファイルも全部読め、誰にでも電話でき、宛先を間違えれば情報が外に出る
  • リスクと利便性は表裏一体のトレードオフ。全部OFFならWebチャットで十分
よもぎ
よもぎ:新人に悪気はないのに事故が起きるのは、権限を渡す側が「どこまで任せるか」を決めていないから。Claude Codeでも同じです。
CARD 08

情報が外に出る4つの出口特にB（外部送信）とC（会話ログ）が要注意

ESCAPE ROUTES
出口内容できる対策
A. モデル本体
通常動作		読んだファイルやコマンド結果が会話としてAnthropicのサーバーへ送信される。GmailがGoogleのサーバーに届くのと同じで止められない「何を読ませるか」を選ぶことまで
B. 外部サイト・サービス
要注意		curl等の送信コマンド、Webアクセス、git push、外部連携MCP。悪意ある指示が仕込まれていれば危険な情報送信も起こり得る送信前の確認（Ask）と通信先の制限（CARD 13・16）
C. 会話ログ
要注意		PC内に暗号化されない平文で保存。規定で30日残り、バックアップやクラウド同期にも残る。悪意あるコードがここから情報を抜く可能性も保持期間の短縮（CARD 14）
D. フィードバック送信
低頻度		フィードバック機能やアンケートで送った会話はコードごと5年保持される。使う場面は少ない使わないなら機能をOFFに（CARD 14）
よもぎ
よもぎ:Aは「仕組み上どうしようもない」、Dは「あまり使わない」。狙うべきはBとCの窓をいかに狭めるか、です。

CARD 10

現実に多いのは派手な攻撃より4つの事故パターン「設定より先に崩れるのは人間の確認習慣」

PITFALLS
  • .envをそのまま読まれる: パスワードやAPIキーをまとめたファイルが作業フォルダ内にあると確認なしで読まれ、鍵の値が会話にもログにも残る

  • 読まずに押す1回: 確認が多すぎると中身を見ずに承認する癖がつく。設定より先に崩れるのはここ
  • 知らないリポジトリの設定が勝手に動く: 設定ファイルが同梱されたリポジトリを信頼した瞬間に動き始める
よもぎ
よもぎ:ハッカーの超高度な攻撃より「いつもの流れでOKを押しちゃった」の方が圧倒的に多い、というのは身に覚えがありすぎます…。
CARD 11

対策の方向性はたった4つこの動画で話される全設定はどれかに当てはまる

STRATEGY
読ませない秘密ファイルを置かない＋読み取り禁止ルール＋隔離
→
送らせない送信前の確認＋通信先の制限
→

よもぎ:個別の設定を暗記する必要はありません。「読ませない・送らせない・残さない・確認する」の4語だけ覚えて帰ってください。
CARD 12

すべての土台: 権限モード4種どこまで確認なしで進めるかを決める最初の選択

PERMISSION MODE
  • bypassPermissions（全開モード）: ほぼ何も聞いてこない。利便性最大・リスク100%。隔離された環境以外では非推奨
  • 自動判定（autoモード）: 別のAIモデルが分類機として危険な操作を止める。現在の基本となるモード（なければClaude Codeをアップデート）
  • 編集だけ自動（acceptEdits）: 作業範囲内のファイル編集は自動、コマンドと通信は確認。差分を見ながらの開発に向く
  • 全て確認: 最も安全だが毎回承認が必要で利便性は大幅低下
  • CLIではShift+Tabで切替。プランモードは何も実行しないため最も安全（通常のチャットAIに近い）
よもぎ
よもぎ:著者も「大丈夫だろう」と判断した作業では全開モードを使うことはある、と正直に話しています。ポイントは危険を知った上で使うかどうかです。
CARD 13

設定の4用語: Deny / Ask / Allow / Hookすべて settings.json に書く。Denyは全モードで最強

SETTINGS
用語意味ポイント
Deny（禁止）一致したら必ず拒否どのモードより強く、全モードで有効。bypassPermissions全開モードでも絶対に通さない。Allowで例外は作れない
Ask（確認）一致したら必ず確認を出すAPIキー利用や送信手前など「絶対確認したい操作」に。全開モードでもここは止まる
Allow（許可）一致したら確認なしで通過ドキュメント読み取りや軽微な編集を登録すれば作業がスムーズに
Hook（検問）ツール実行直前に自作スクリプトで判定外部送信を一旦止める等に利用。止める側にだけ強く、Hookで許可してもDeny/Askは覆せない

判定順は Hook → Deny / Allow → モード規定。/permissions を実行すると有効なルール一覧（Allow・Ask・Deny等）を画面で確認でき、設定変更後の動作確認に使える。AIは賢いのですり抜け手段を考え得るため、Claude Codeの設定だけでなく端末側でのブロックも検討したい。

よもぎ
よもぎ:覚えるのは2つ。「DenyはAllowより強く全モードで効く」「禁止と確認のリストに書いておけば、モードを何にしても守られる」。
CARD 14

今すぐやる5つの基礎設定完璧ではないが、基礎の基礎として理解したいラインアップ

QUICK WINS
  • ① プロジェクトのルートで起動: ホームディレクトリ起動はPC全体を見渡せる状態＝リスク。CLIはcdで移動してから起動
  • ② 秘密ファイルをプロジェクトに置かない: .envにAPIキーを置いて読ませる運用は便利だが危険。1Password等のパスワードマネージャー経由で都度読み込ませると安全（利便性は低下）
  • ③ 権限の狭い鍵だけ使う: テストモード鍵・対象リポジトリを絞ったトークン・期限1週間のAPIキー。週1でローテーションし、上限金額（例: 100ドル）を設定しておけば漏れても被害を最小化
  • ④ ReadのDenyルール: ~/.claude/settings.json（ユーザー設定）の禁止リストに .env / .claude / secrets / .ssh / .gcloud 等を列挙。書いたら/permissionsで反映確認
  • ⑤ 送信と記録を最小化: 会話ログの保持を規定30日→7日に短縮。/feedback・/bug・/shareをOFF（設定値は文字列の「1」でオフ）
よもぎ
よもぎ:著者イチオシは③の運用系。利便性をほぼ下げずにリスクだけ減らせる「すぐやれる」対策です。著者自身、週1でキーを削除・作り直しているとか。
CARD 15

MCP連携の危険性: 出口が増える仕組み信頼できる提供元のものだけ接続する

MCP RISK
  • MCPはNotion・Slack・データベース等をClaudeから直接触れるようにする連携機能。できることが広がる分、情報の出口も増える
  • MCPに渡した内容はそのサーバーに届く。サーバーからの応答にClaudeへの指示が混ざることも＝プロンプトインジェクションの入り口
  • 「○○を1000個集めました」系のバズった怪しいMCPは自作が容易。非エンジニアでも悪意あるコードを仕込める
  • リポジトリ同梱の .mcp.json に書かれたコマンドは手元のPCで動くプログラム。知らないパッケージ名は承認しない（「使わない」を選んでもClaude Codeは普通に動く）
  • 公式マーケットプレース掲載のMCPや大手（Google・Figma・X等）のものは基本的に安心。/mcp で接続一覧を定期的に棚卸し
よもぎ
よもぎ:MCPサーバーが増えるほど出口が増える、と考えると「やみくもに繋がない」のが自然な結論です。確認画面が英語で分かりにくいなら、日本語化するMOD・プラグイン導入から始めるのも手。
CARD 16

サンドボックス: 文字列の限界をOSで突破「口で見ないで」ではなく物理的に手が届かなくする

SANDBOX
  • Deny/Askはコマンドの文字列照合なので、フルパス表記やsh -cで囲むと一致せずすり抜け得る
  • サンドボックスはOSレベルで囲む仕組み。bashとその子プロセスの読み書き場所と通信先を限定し、許可外はOS側で失敗させる
  • 喩えれば「新人の机をガラスの小部屋で囲む」イメージ。有効化は /sandbox だけでOK、通信先も許可ドメインだけに絞れる
  • Linux / WSLは専用ソフトが必要、Windowsはそのまま使えずWSL2内での利用が必要
  • 注意: Read・EditなどのファイルツールとMCPはサンドボックスの外側。それらはDenyルールで別途守る
  • 最も安全なのは秘密情報が存在しない場所で動かすこと。ブラウザ版Claude Codeや開発コンテナ・VM（Parallels等の別マシン丸ごと用意）も選択肢
よもぎ
よもぎ:「見る場所がGoogle Driveだけ」など業務が決まっているなら、通信先をそのドメインだけに絞ると暴走・流出の両方を抑えられます。
CARD 17

一段上の対策と、人間側の運用習慣顧客データや本番環境を扱うならここから

ADVANCED
  • 送信コマンドにAskルール: curl・wget・git push・パスワードマネージャーコマンドの前に確認を挟む。ただし文字列照合の限界（フルパス・sh -cで回避され得る）は知っておく
  • 作業範囲外を読む時はAsk: 安全なプロジェクトフォルダ内なら全開モードで自動運転し、外に出ようとした時だけ止まる、という使い方ができる
  • 確認画面をちゃんと読む: 許可を求める内容が少しずつ分かるようになる。不安な単語はその場で検索
  • 月1で /permissions の棚卸し: 気づけば「常に許可」が増えている事故を防ぐ。削除系は常にAskに
  • 診断を活用: /doctor で無効な設定や環境変数の不足を確認。「私の環境のセキュリティリスクは？」とClaude自身に聞くのも有効
  • 知らないリポジトリは吟味: Xでバズっているだけの第三者ツールを鵜呑みにしない。Web版ClaudeにGitHubの中身を確認させてから導入する
よもぎ
よもぎ:設定は一度すれば終わりではありません。「月1の棚卸し」と「確認を流さない癖」 — 地味な人間側の習慣が最後の砦です。
CARD 18

まとめ: セキュリティと利便性は自分で選ぶものチェックリストと「リスク×利便性シミュレーター」

CHECKLIST
  • 攻撃側はAIでコスト1/10。日本は今、集中的に狙われている（IPA・Gambit Security・Anthropicの3根拠）
  • Claude Codeの能力（読む・実行・外に出る）＝そのまま情報流出の出口。出口はA〜Dの4つ、特に外部送信と会話ログを絞る
  • 基本はautoモード＋settings.jsonのDeny/Ask。Denyは全モードで最強、Hookは止める側だけに有効
  • 5つの基礎設定（起動場所・秘密を置かない・狭い鍵とローテーション・Read Deny・送信と記録の最小化）を今日から
  • MCPは信頼できる提供元のみ。サンドボックスでOSレベルの防御を追加
  • 月1のルール棚卸しと確認習慣が、設定よりも先に崩れないための生命線
  • 動画の概要欄の公式LINEに「リスクと利便性シミュレーター」と送ると、設定ごとの残リスクと利便性を数値・グラフ化したシミュレーターが配布される
