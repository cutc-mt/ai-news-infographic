第1章　Modとは何か
1
コーヒーを淹れている間に何が起きた?

Claude Codeなら、コーヒーを淹れている間に機能を丸ごと構築することもできます。でも戻ってきたとき、困るのは「何が変更されたのか」「2つのエージェントが同じファイルを編集していないか」「なぜコンテキスト料金がまた高くなったのか」を確認しないといけないこと。

放置してる間に何が起きたか把握するのが、実はいちばん大変なんだよね。
2
Mod = Claude Code内で動く拡張機能

Modとは、Claude Codeの中で動作する拡張機能のこと。イベントに反応したり、インターフェースの一部を変更したり、ツール実行前に介入したりできます。プラグイン経由でインストールされますが、スキルだけを含むプラグインが自動的にModになるわけではありません。

  • ファイルエクスプローラー、編集の再生、危険コマンドへの警告など
  • 並列エージェントや繰り返しの修正を管理するツール
  • 一見節約に見えるキャッシュModは仕組みに注意点あり
3
セットアップと安全確認

ターミナルでclaude --versionを実行。今回の解説にはバージョン2.1.287以降が必要です。ネイティブインストール版ならclaude updateで更新。このバージョンではModはデフォルトで有効なので、古い実験的な環境変数は不要です。

ここ大事 Modはあなたの権限でコードを実行する。インストール前に発行元とリポジトリを必ず確認。インストール後はセッションを再起動し、/pluginで読み込みを確認する。
環境のメモ 複数のModがサイドパネルを奪い合うため、ターミナルのウィンドウは広げておく。デモは小さなタスク管理プロジェクトで実施。
第2章　Filetree − 会話の横にファイルツリー
4
エディタとの切り替えから解放される

ターミナルでClaude Codeを使っていると、ファイルを探したりClaudeがどこで作業しているか確認したりするために、エディタとの切り替えに意外と時間を取られます。Filetree（DataGoblin氏のリポジトリ）を使えば、会話のすぐ横にプロジェクトブラウザを表示できます。

marketplaceに追加 plugin install --scope user
--scope userが便利 付きでインストールすれば、他のプロジェクトでも同じプラグインが使えるようになる。
5
使い方: /filetree と変更マーク

フルスクリーンモードにしてから/filetreeと入力。表示にはフルスクリーンと110カラム以上のターミナル幅が必要。パネルが出ない場合はウィンドウを広げましょう。/filetree ./srcのようにソースフォルダを絞ることも可能です。

  • Claudeが読んでいるファイルとツリーの動きを対応付けて眺められる
  • 特定のファイルを選んで次のプロンプトのコンテキストに含められる
  • Filetreeの変更マークとターミナルのgit diffを見比べると変更を把握しやすい
コストの落とし穴 ツリーを表示するだけではモデルへのリクエストは発生しない。ただしプロンプトにファイルの中身を多く足せば、その分トークン消費は増える。「見た目のパネル」と「送るコンテキスト」は別物。
エディタの全機能を置き換えるものじゃないけど、ターミナルに留まりたい人にはかなり便利だよ。
第3章　Replay Theater − 編集をステップ再生
6
直前の編集セッションを順番に再生

「Claudeがどう変更したか」を会話ログから推測するのは大変。Replay Theater（Anthropicのplaygroundリポジトリ収録）は、直前の編集セッションでのファイル変更リクエストをステップごとに確認できます。

  • playgroundリポジトリをクローンし、modsフォルダをローカルのマーケットプレイスとして登録
  • /replay入力後、next / previous（n / pキー）でステップ移動
  • デモ: add_task関数をcreate_taskにリネーム（実装・CLI・テストを動作を変えずに更新）
長いトランスクリプトを行き来するより、ずっと分かりやすいんだ。
7
注意: リプレイ＝適用証明ではない

Replay Theaterが記録するのは「編集リクエスト」。失敗や拒否された編集も表示されるため、リプレイだけで変更がファイルに適用された証明にはなりません。

検証の手順 パネルを閉じて git diff → npm test。リネームが全ファイルで行われ、既存のテストが通ることを自分で確認する。
セッションビューである点に注意 永続的な履歴や「取り消し」ボタンではない。新しい編集が行われると前のリプレイは置き換えられ、再起動で失われる。大規模変更はパネルで切り詰められることも。Mod自体はモデルを呼ばないので追加料金なし（コーディングは通常の利用枠）。
第4章　Blast Radius − 危険コマンドの爆風半径
8
rm -rf を実行前に保留する

Claudeが最善策としてフォルダ削除やリセットを選ぶことはあります。理にかなっている場合でも、「そのコマンドが何に影響するか」は見ておきたい。Blast Radiusは特定の危険なbashコマンドを監視し、実行を保留して、実行・キャンセル付きのレポートを表示します。

rm -rf build を依頼 Modが保留 影響レポート 実行 / キャンセル
デモの検証結果 キャンセル→別ターミナルで確認するとファイル3つが残存。再実行して「続行」ならダミーのbuildフォルダだけ削除。ボタンのアニメーションだけで判断せず、実行後にファイルシステムを確認する。
9
限界: 完全な保護ではない

仕組みは「特定のbashパターンを認識する」もの。スクリプト、エイリアス、別ツール、複雑なコマンドは対象外になる可能性があります。複数の操作を1行にまとめると、レポートがその全体を測るとは限りません。

解説者のおすすめ 取り返しのつかないミスを防ぐ「もう一つの手段」として活用する。注意を怠る理由にしない。通常の権限は維持し、実際のコマンドは自分で読む。
広いターミナルではサイドペイン、狭い場合はプロンプト上にレポートが出るよ。他のModとスペースを奪い合ったら単独表示させよう。
第5章　Collision Guard − 編集の衝突防止
10
2つのセッションが同じファイルを編集…!

同じプロジェクトで2つのClaudeセッションが動き、両方が同じファイルを編集しようとしたら? Collision Guard（Nate Hurk氏のリポジトリ）は、2つ目のセッションが競合する編集を行う前に決定を仰いでくれます。

  • 両方のセッションでModが読み込まれている必要がある（参加していないセッションは追跡情報を共有できない）
  • セッション1でラベルを「starter」に変更→開いたままセッション2で同じラベルを「pro」に変更しようとする
  • 2回目の編集で競合判断が表示される。cancel→設定ファイルは1つ目の値のまま
  • /guardで状態確認。デフォルトでは過去30分の他チャットの編集を探す
11
worktree提案と監視の限界

Git追跡ファイルの場合、対話形式で作業ツリー（worktree）のルートを提案することも。2つ目のタスクを分離されたチェックアウトで続けられます。ただし既存の変更を魔法のように移行するわけではなく、保留中の編集は拒否されます。

監視範囲の限界 同一マシン上のClaude編集ツールを追跡するもの。bash経由のフォーマッタ、普通のエディタからの編集、他マシンからの斜め上の編集は対象外の可能性。
重複編集をうっかり承認する前に可視化してくれるのが価値。独立タスクには今も別worktreeがおすすめだって。
第6章　Agent Flow − 並列エージェントの見える化
12
どのエージェントが何をしてるか見える

Claudeがタスクを委任したとき、どのエージェントが実行中で、どのツールを使い、何が承認待ちなのか知りたい。親の会話が静かに見えても、裏では多くが進行している可能性があります。Agent Flowの/flowでパネルを切り替え、/flow textならテキスト版も使えます。

  • 各エージェントの行・状態・現在のツール・経過時間を表示
  • 行を展開して詳細確認し、完了した要約とメイン会話の結果を比較
  • デモ: 入力バリデーション検査／テスト不足のレビュー／CLIのエラーハンドリング確認の3エージェントを並列起動
13
向く人・向かない人

このパネルはエージェントを自動作成するわけではなく、コードの実行が速くなるわけでもありません。パネル描画だけのためのモデルリクエストはなく、監視対象のエージェントがいつも通り利用枠を消費します。

向いている人まず他のModを
まとまった作業を頻繁に委任する人。委任先の状況を把握したい場面一度に短い会話が多い人はFiletreeやReplay Theaterの方が先に価値が出る
コスト感の注意 小さなプロジェクトで3エージェントはあくまで表示機能のデモ。実際の作業では「独立したレビューの価値があるときだけ」タスクを分割する。
第7章　Reflect − 繰り返しの指示を保存
14
「remember:」で好みをルール化

パッケージマネージャーの指定、テストの書き方、コードの配置場所——同じ好みをClaudeに何度も伝えるのは面倒。Reflect（Bayram Annacoca氏のリポジトリ）は、再利用可能な修正案を保存可能な指示として提案します。

  • 注意: リポジトリには2つの実装がある。古いClaude ReflectプラグインではなくMod版の「Reflect Mod」を
  • 明示的な「remember:」接頭辞なら検出モデルを通さず直接レビューUIへ
  • Haikuを使った自動検出も可能（その分モデル利用量が発生）
  • /reflectqで保留中の候補確認、/reflectpauseでトグル切り替え
「新しいテストにはNode組み込みのテストランナーを使え」みたいな指示を保存しておくイメージだよ。
15
スコープ選びと保存後の検証

保存時はスコープが重要。小さなNodeプロジェクト向けのルールが、全リポジトリに効くグローバル設定になってはいけません。リポジトリスコープを選び、提案テキストを確認・編集してから保存します。

検証の手順 保存後にプロジェクトのCLAUDE.mdファイルとgit差分を確認する——承認された指示が意図した文言で意図した場所に書き込まれたか。2つ目の候補を「スキップ」して、ルールが追加されていないことも確認。
過信は禁物 これはClaudeの再学習ではない。ルールを書いても完璧に従うとは限らない。指示ファイル管理の道具と考え、ルールは簡潔に保ちプロジェクトの変化に合わせて見直す。
第8章　Cache Tax − キャッシュ維持の実コスト
16
「冷えた」会話のウォームアップ

Claudeがキャッシュ済みの会話プレフィックスを再利用する場合、そのプレフィックスを再書き込みするより安くなることがあります。Cache Tax（Karan Benzel氏のマーケットプレイス）は、使っていない会話に戻る際のコストを予測し、既存プレフィックス維持のため小さなリクエストを打つことがあります。

  • /cachetaxで情報表示、/cachetax guard warnでガードを警告に変更
  • /keepwarm 90mで90分間有効。/keepwarm単体はデフォルト6時間なので明示指定が安全
  • デモ: /keepwarm 1h every 1mでpingの様子と使用状況を確認→/keepwarm offで必ず解除
17
節約話はここまでよく読んで

標準の50分間隔pingは「会話キャッシュが1時間」という前提。サブスクリプションの利用枠は長期ですが、APIキーやクラウドプロバイダー経由のデフォルトは約5分で、期限切れ後のpingでは維持できません。有効化前にプロバイダーの公式キャッシュ設定を確認しましょう。

過大評価に注意 ウォームアップのリクエスト自体にもトークンがかかる（入出力込み）。維持料金を払っても二度と戻らなければ節約にならない。短いデモ間隔の成功は「1時間放置した会話の節約」の証明ではない。Mod付属の56個の自動テストは全合格したが、モック検証であり実運用の節約を保証しない。サブスクのドル換算はAPI相当の見積もり。
「再開するつもりの長い会話」だけ検討して、短いセッションや完了プロジェクトのウォームアップ維持はしない、が解説者のスタンスだって。
第9章　どれから始める?
18
困っている問題から1つずつ

7つすべてを同時に実行する必要はありません。実際に抱えている問題から始め、そのModをインストールし、小さなプロジェクトで動作を確認する。期待した効果がなければ/pluginのインストール済みセクションから無効化できます。

こういう人まずこれ
ターミナルを離れずプロジェクトを操作したいFiletree
小さな変更をていねいに確認したいReplay Theater
リスクのあるコマンド前にチェックポイントが欲しいBlast Radius
並行作業の編集重複とエージェントの見える化Collision Guard / Agent Flow
繰り返しの修正をプロジェクト指示として精査したいReflect
キャッシュ維持のコストを慎重に評価したいCache Tax（実使用量と照らして）
#ClaudeCode #Mod #拡張機能 #エージェント開発
Modは結果を自分で検証できるコントロール。「実際のコーディングに有益な方向性だ」というのが解説者の評価だよ。

「何が変更されたか、自分で確認できるようにする」——それがModの本来の役目、おわかりいただけただろうか。
