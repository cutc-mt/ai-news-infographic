SECURITY ALERT / PHP (PHP2Shell)

PHP重大脆弱性「修正版までに何をする？」——
棚おろし・暫定策・パッチ適用・侵害チェックを全部整理【あきらパパ】

2026年10月21日、国家サイバー統括室がPHPの重大な脆弱性について注意喚起を発表。「公開しているウェブサイトでPHPを使っているか確認し、日本時間の夜13時に公開される修正パッチをすぐ当てられるよう準備せよ」という内容だ。動画では結論から「本命はパッチ、それまでの対策は時間稼ぎ」と断じ、パッチ適用後も侵害チェックで足跡を調べるまでが作業だとする、4つの時間軸による完全な道筋を示す。

チャンネル: あきらパパ 対象: PHP / CERT EU / Cloudflare / PHP-FPM 構成: ①現状把握 ②棚おろし ③暫定策 ④適用と侵害チェック
よもぎ
「夜の城」に例えて最後まで話す回です。城の門（公開サーバー）だけでなくすべての門を数えること、そして城主（開発者）の責任はパッチを当てて終わりではなく泥棒の足跡調査まで。CARD 01〜05で現状、06〜09で棚おろし、10〜13で暫定策、14〜18で適用と事後チェックを見ていきましょう。
CARD 01

全体像サマリ: 本命はパッチ、暫定策は時間稼ぎ作業は「4つの時間」に分けて整理する

OVERVIEW

国家サイバー統括室が10月21日に注意喚起を出したのは、PHPにCVSS 9.2（10点満点）の重大脆弱性2件が見つかったため。修正版は日本時間での公開予定を待つが、攻撃は修正版より先に始まっている。動画の結論は明快で、①今すぐ棚おろし（PHPが動いている場所を全部洗い出す）→②修正版までは暫定策（時間稼ぎ）→③修正版が出たらすぐ適用→④その後に侵害チェック、の4段階。例え話は「夜の城」。PHPは城、その城に重大な穴が見つかり、新しい壁材は23時に届く。それまでは柵と堀（暫定策）でしのぐ、という絵で最後まで話が進む。

① 今すぐ棚おろし——全ての「門」を数える
→
② 修正版まで暫定策——セッション進捗オフ・WAF・堀
→
③ 修正版公開後即適用——4ステップ手順
→
④ 適用後侵害チェック——足跡を調べて初めて終わり
よもぎ
よもぎ:「パッチを当てたら終わりではありません」——この一言が全体の骨格です。勝負は修正版が出てからどれだけ早く当てられるか。
CARD 02

公式発表の確定事項: 脆弱性2件、CVSSはどちらも9.2修正版は日本時間での公開予定、影響バージョンはその時に判明

OFFICIAL
  • PHP公式サイトが10月に事前の予告（プレアナウンス）を公開——重大な脆弱性が2件
  • 深刻さを示す CVSSは2件とも9.2（10点満点）という極めて高いスコア
  • 修正版は日本時間の夜13時の公開予定。影響するバージョンと修正済みバージョンはその時に発表される
  • 詳しい中身が漏れたり悪用が見つかったりしたら前倒し公開もあり得ると明記
よもぎ
よもぎ:公式はまだ中身を公開していません。だから動画では「PHP公式の発表」と「報道・セキュリティ会社の情報」を明確に分けて扱います。この切り分けが今回の重要ポイント。
CARD 03

報道・セキュリティ会社情報: PHP2Shell、リモートコード実行の恐れEUのCERTは「ログインなしでサーバー上でプログラムを動かされる可能性」

PHP2SHELL
  • 報道機関やセキュリティ会社の情報として、この脆弱性は「PHP2Shell」と呼ばれている
  • ヨーロッパの緊急事態対応機関 CERT EU は「ログインなしで、外部からサーバー上でプログラムを動かされる恐れがある」と指摘——いわゆる認証前リモートコード実行の怖さ
  • 本来は10月22日に公開される予定だった情報が、その前にネットに出回ってしまった
  • つまり攻撃者は詳細を把握した状態で修正版を待っている可能性がある
よもぎ
よもぎ:情報漏れによって防御側と攻撃側の持ち時間が同じになってしまいました。だから「待つ理由はない」のです。
CARD 04

攻撃はもう始まっている: Cloudflareが21日午後に観測修正版の公開を待たず、悪用が先行

IN THE WILD
  • Cloudflareは日本時間21日午後4時43分頃から攻撃が出始めたことを観測
  • 修正版が公開されるより前に攻撃が始まっているということ
  • 修正版として報じられているのは8.2から8.5までの4つの系列の新しい版
  • 8.1より前はサポートが終了しているため、公式の修正版は出ない見込み
よもぎ
よもぎ:「パッチが出てから考えよう」は通用しません。城に壁材が届く前から、泥棒はもう塀の外にいる状態です。
CARD 05

自分事かどうか: サーバーサイド言語の約7割がPHP「関係ない」と言い切れる人は少ない

SCOPE
  • サーバー側の言語が分かるウェブサイトのうち、およそ7割がPHPと言われている
  • WordPress などの CMS や受託開発のレガシー環境を含めれば対象は非常に広い
  • 公式に確定している情報はまだわずか——でも「待つ理由はない」
  • 個人サイト・社内システム・゙テナのどこかに PHP が潜んでいないか、まずは確認から
よもぎ
よもぎ:7割という数字が意味するのは、攻撃者が「数撃てば当たる」スキャンを回せば広く命中するということ。標的型でなくても被害に遭います。
CARD 06

例え話: 夜の城と、全部の門を数える作業PHPは城、修正版は23時に届く新しい壁材

METAPHOR

動画を貫く例えはこうだ。夜の城（PHP）の塀に重大な穴が見つかった。新しい壁材（修正版）は23時に届く。それまでは柵と堀（暫定策）でしのぐ。そして重要なのは、数えるべきは表の門（公開Webサーバー）だけではないこと。裏門、勝手口、すべての門——つまり PHP が動いている場所を全部洗い出すのが最初の作業になる。この「城」の絵を頭に置くと、以降の暫定策（堀を掘る・勝手口を閉める）と侵害チェック（城内の足跡を調べる）の位置づけがすべてつながる。

よもぎ
よもぎ:セキュリティ対応を抽象論ではなく「自分の城を守る物理的な作業」として捉え直すと、作業の順番が自然に決まります。
CARD 07

第2章・今すぐやること: 棚おろし（インベントリ）公開Webサーバー以外も、コンテナ・CI環境・開発PCまで全部

INVENTORY
  • 対象は公開しているWebサーバーだけではない——コンテナ（CI環境含む）、開発用パソコンまで、PHPが入っている場所を全部洗い出す
  • 白を言えば「表の門だけじゃなく全ての門を数える」作業
  • 洗い出し結果はリスト化し、それぞれの現在前（稼働中バージョン）を記録する
  • このリストがあるからこそ、修正版公開後に即座に全てに適用できる
よもぎ
よもぎ:パッチ適用の速度は棚おろしの精度で決まります。見落とした門が、まさに破られる門になる。
CARD 08

落とし穴: ターミナルのバージョンとWebサーバーのPHPは別物確認は必ず「Web経由」で行う

PITFALL
  • ターミナルで php -v 的に確認したバージョンと、Webサーバーが実際に使っているPHPは設定が別になっていることがある
  • なので確認はWeb経由で行うのが正解
  • レンタルサーバーやマネージドサービスなら、事業者に適用の予定を確認する
  • ここで「実際に動いている版の本当の番号」を掴むのが目的——表示上の数字を鵜呑みにしない
よもぎ
よもぎ:よくある事故パターンです。「CLIは新しかったけど Web の PHP-FPM は古いまま」——攻撃者は Web の口から入るので、そこを確認しないと意味がありません。
CARD 09

8.1以前を使っているなら: ここが一番の山場公式の修正版は届かない——系列アップの計画を今すぐ

EOL BRANCH
  • 8.1より前の版はサポートが終了しており、公式の修正版は出ない見込み
  • 使っているなら、8.2以降への系列ごとのアップグレード計画を今すぐ立てるのが最優先
  • ただし Linux のディストリビューションによっては、古い版にも修正を当てて配布（バックポート）することがある
  • 今後、ディストリビューション側のお知らせも併せて確認すること
よもぎ
よもぎ:EOL 版を抱えたまま今回を乗り切る選択肢は実質「隔離」か「系列アップ」の二択です。見送りは選択肢に入りません。
CARD 10

第3章・暫定策①: セッションのアップロード進捗をオフにPHP-FPMならプールごとの設定に固定して上書きを防ぐ

MITIGATION 1
  • よく紹介される暫定策は、PHPの設定でセッションのアップロード進捗（session.upload_progress）という機能をオフにすること
  • PHP-FPM ならプールごとの設定として固定すると、後から他のファイルで上書きされない
  • 設定したら再起動。一時的な確認ページを Web 経由で開き、オフになっているのを確認
  • 確認が済んだらそのページはすぐ消す——情報を与えるページを残しておかない
よもぎ
よもぎ:設定→再起動→Web経由で確認→確認ページ削除、までが1セットです。確認ページの放置は別のリスクになります。
CARD 11

正直な話: 設定では守れない、唯一の対策はパッチPHPコア開発者の見解——ファイルアップロード停止設定も効かない

HARD TRUTH
  • PHP の中心的な開発者は「設定では守れない。唯一の対策はパッチ」と明言している
  • ファイルのアップロードを止める設定も効かないとされている
  • 理由はリクエストの中身は、その設定が効くより前に読み込まれてしまうから
  • つまり暫定策はあくまで「パッチ適用までの時間稼ぎ」の代わりにはならない」——本命を忘れない
よもぎ
よもぎ:ここで動画が正直に見解を分けるのは信頼できるポイント。「設定したから大丈夫」という安心が一番危険です。
CARD 12

暫定策②: 城の外の堀——WAF（Cloudflare）を効かせるただしオリジンIPが知られていたら裏の勝手口から入られる

MITIGATION 2
  • Cloudflare は無料プランも含めて緩和のルールを用意している
  • ただしサーバーの本当の住所（オリジンのIPアドレス）が知られていたら、WAFを通らず裏の勝手口から直接入られてしまう
  • なので 80番・443番ポートは Cloudflare のIPアドレスからだけ受け付けるように設定
  • 「石垣（WAF）は勝手口を塞いで初めて効く」——このセットで初めて意味がある
よもぎ
よもぎ:WAFを入れた気になっていても、オリジン直撃（IP指定アクセス）を許していたら素通りされます。ポートの受付元制限までが堀です。
CARD 13

さらに攻めたい場合: マルチパートPOSTを止める・最後は切り離し止めたら必ずフォームの動作確認を

MITIGATION 3
  • アップロードを使わない経路では、マルチパートのPOSTリクエスト自体を止めるという手もある
  • ただしフォームが動かなくなることがあるので、止めたら必ず動作を確認する
  • どうしても守れないなら、修正版が出るまでインターネットから切り離すのも選択肢
  • 判定: 暫定策は時間稼ぎ。石垣は勝手口を塞いで初めて効く
よもぎ
よもぎ:「動かないサイト」も被害ですが、「踏み台にされるサーバー」はより重い被害。切る勇気も含めて判断しましょう。
CARD 14

第4章・修正版が出たら: 入手元をこの順で確認「無い」場合は待つだけではなく次の手を打つ

PATCH SOURCES

修正版が公開されたら、更新パッケージが出ているかを①PHPの公式 → ②OSのパッケージ → ③Dockerのイメージ → ④レンタルサーバー等の事業者の順に確認する。外部のリポジトリーでは当日の更新がないという報告もある。自分の使っている入手元に出ていないなら、ただ待つのではなく、他の入手先を探すか、暫定策を継続する判断が必要になる。

確認順入手元ポイント
1PHP 公式影響バージョン・修正版の正確な番号を最初にここで確認
2OS パッケージディストリのバックポート配布にも注目（CARD 09）
3Docker イメージベースイメージの更新が出るまで古いままになりがち——タグ確認
4ホスティング事業者レンタルサーバー・マネージドは適用予定を事業者に確認
よもぎ
よもぎ:「自分の入手元に今日は無かった」で止まらない。暫定策を継続する判断までがセットです。
CARD 15

パッチ適用の手順は4ステップ当てて終わりではない——再起動・確認・動作試験まで

APPLY 4 STEPS
① 適用する修正版を各環境へ当てる
② 再起動するPHP-FPM / Webサーバーを確実に再起動
③ バージョン確認Web経由で新しい版の番号を確かめる
④ 動作試験ログイン・問い合わせフォーム等の大事な画面が動くか試す
  • ③は CARD 08 と同じ教訓——実際に動いている版をWeb経由で確認
  • ④は「当てたけど実は壊れていた」を防ぐ最後の砦
よもぎ
よもぎ:④の動作試験は、パッチ後のアクセスログ確認（次カード）と同時に進めると効率的です。
CARD 16

第5章・当てた後に確かめること: 侵害チェック（足跡調査）修正版より先に攻撃が始まっていた——当てたら終わりではない

COMPROMISE CHECK
  • 新しい版に変えた後、夜の間に誰かが入っていないか足跡を調べる
  • アクセスログ: アップロードがあるはずのない場所へのマルチパートPOST、特に「PHPセッション・アップロード進捗」の文字を含むもの
  • 最近追加・変更された .php ファイル（見覚えのないWebシェルの痕跡）
  • 見覚えのない管理ユーザー、クーロンの予定外の通信も確認
よもぎ
よもぎ:ここが一番忘れやすい。攻撃はパッチ公開前から始まっていたので、「当てた版に変えても、すでに入られていたら意味がない」のです。
CARD 17

まとめ: 結論の4行最初の結論に戻る

SUMMARY
  • 本命はパッチ——暫定策の設定は「守れない」と開発者自身が言っている
  • 暫定策は時間稼ぎ——その時間で準備を整える
  • 石垣（WAF）は勝手口（オリジンIP直撃）を塞いで初めて効く
  • 当てた後に足跡を調べる——パッチ適用で終わりではない
  • 勝負は修正版が出てからどれだけ早く当てられるか——だから今のうちに門を数えて手順を決めておく
よもぎ
よもぎ:4行に圧縮すると、「数える → しのぐ → 当てる → 調べる」。夜の城の物語そのものです。
