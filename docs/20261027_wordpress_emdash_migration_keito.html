OVERVIEW

EmDashとは何かCloudflareが出した「WordPressの次」を掲げる新CMS

EmDashは、世界規模のネットワークでセキュリティと高速配信を提供する上場企業Cloudflareが開発したコンテンツ管理システムです。管理画面から記事を書く流れはWordPressとよく似て作られており、Cloudflare自身が「WordPressの次のサービス」「WordPressの後継」と紹介しています。2026年9月28日に正式版がリリースされた比較的新しいツールで、MITライセンス・無料・商用利用OK。WordPressと同じ感覚で業務利用・受託構築に使えます。最大の特徴はMCPを標準内蔵している点で、AIから直接・安全にコンテンツを更新できる「AIネイティブなCMS」として今かなり注目を集めています。

CURRENT STATE

現状確認：WordPressサイトの構成PHP＋MySQL＋テーマの3層構造

動画ではサンプルとして「ktlif.net」という架空会社サイト（株式会社春道運由）を準備しました。WordPressはPHP基盤のCMSで、日本の中小企業サイトの多くで使われています。コンテンツはMySQLデータベースで管理され、ブログ・お知らせ・メディア画像はすべてデータベース上にあります。PHPがなければWordPressは100%動かず、データベースの内容をWordPressが引っ張ってきて表示する仕組みです。サイトは「ニュース投稿」「ブログ投稿」「ほぼ更新しない固定ページ（会社情報・お問い合わせ）」で構成されています。

MIGRATION MAP

移行の全体像：何がどこへ動くかレンタルサーバーからCloudflareへ一括集約

移行後もURLは全く同じで見た目もほぼ変わりません。変わるのは裏側です。

  • CMS：WordPress → EmDash（PHP不使用）
  • サーバー：Xサーバーなどのレンタルサーバー → Cloudflare Workers
  • データベース：MySQL → Cloudflare D1
  • 画像・メディア：wp-content/uploads → Cloudflare R2
  • ログイン：ID／パスワード → パスキーのみ
  • 更新管理：本体＋テーマ＋プラグイン＋PHP → EmDash本体だけ
よもぎ
よもぎ:PHPの直近脆弱性と無縁になり、更新対象が1つに減るのが最大の構造変化ですね。

作業の進め方は①既存WordPressサイトを棚卸ししてバックアップ（失敗に備えて必須）→②EmDashの新サイトを先に構築→③コンテンツを取込んでデザインを作り直し→④URLを引き継ぐドメイン切替→⑤切替後の確認作業、の5段階。きちんとやると3日程度、詰めれば1日でも可能です。自力が難しければ移行サービスに任せる（動画では10万円弱での受付を想定。ボリューム次第で見積もり）選択肢もあります。

REASON 1

理由①：PHP脆弱性問題が「最後の後押し」に決定打ではなく、積もり積もった結論

記憶に新しいPHPの脆弱性問題が、WordPress離れを一気に加速させました。ただし解説者曰く、今回の問題は「最後の1割を後押しした火種」に過ぎず、多くの人は以前から「いつかWordPressをやめないとな」と悩んでいたとのこと。解説者自身、問題が発覚したその日に自分の全サイト（コーポレートサイト含む3サイト以上）をEmDashへ移管してしまったほどです。慌てて対応中のサイトも、まずWordPressを正常な状態に戻してから移行を検討すれば十分です。

よもぎ
よもぎ:「脆弱性が理由」ではなく「時代遅れ感が理由、脆弱性が引き金」——順序が大事です。
REASON 2

理由②：更新管理の4系統が辛い本体・テーマ・プラグイン・PHPのバージョン地獄

WordPressは本体・テーマ・プラグイン・PHPの4系統のバージョンを更新し続け、一致させ続ける必要があります。しかもプラグインは多数入っているのが普通で、どこかの歯車がずれると画面が真っ白になることも。この管理コストが大きく、運用保守業務として外部に払っている会社も少なくありません。EmDashなら更新はEmDash本体だけで済みます。AIでの運用管理に切り替えればこの保守はほぼ不要になり、セキュリティ系の保守だけは残すのが推奨構成です。

よもぎ
よもぎ:「更新業務はAI内製化、セキュリティは専門家」——保守費の使い道を再設計する発想ですね。
REASON 3

理由③：WordPressはAI時代に合わないAI連携プラグインは使いづらく不安定

WordPressにもAI連携用プラグインがあり一応AI更新は可能ですが、相当使いづらく安定しないのが実情です。セットアップも難しく、会社の一般社員に「AIで更新して」とは言えたものではありません。対してEmDashのAI更新は素人でも簡単に、しかも安全にできます。権限の振り分けも余裕で、AIネイティブなCMSとして設計されている点が最大の優位性です。動画編集の内製化と同じ流れが、Webサイト運用にも来ています。

よもぎ
よもぎ:「AIで更新できる」ではなく「AIで更新する前提で作られている」——この差が大きい。
AI DEMO

実演：Claudeからニュースを投稿するMCPコネクター経由で本番サイトが更新される

解説者のコーポレートサイトでデモが行われました。Claude Desktopに「リアライズホームページ」コネクターを設定し、コンテンツの読み取りは全許可、書き込み・削除系ツールは承認が必要にした上で、「大阪でAI勉強会やります」という告知記事を依頼。MCPがEmDashのコンテンツ一覧を探索してニュースのカスタム投稿を発見し、画像（SVGイメージ）の生成からアップロード、本文の投稿まで自動で実行しました。カテゴリーやOGP画像・SEOタイトルは人が手直しするか、AIに指示すれば設定可能。公開すると本番サイトに即反映されます。

よもぎ
よもぎ:書き込みは承認制・下書き止めも可能。人間のチェックを通して公開できるのが安心ポイントです。
COST DESIGN

保守運用費を「更新」と「守り」に2分割する更新は自社AI、セキュリティは専門家へ

WordPressでサイトを運用している会社の多くは、コンテンツ更新や日々の運用・バックアップに対して保守費用を払っています。この「更新系」はAIで内製化してほぼ不要にできます。一方でセキュリティ系の保守は絶対に残すべきです。具体的には、常時動く監視ボットによる不審アクセスの通知体制、問題発生時にすぐ切替えられる代替ページの同時運用など、「何かあった時」に集中した保守契約にお金をかける設計が推奨されます。ややこしいWordPressの運用から離れて、セキュリティに集中する時代です。

よもぎ
よもぎ:削るべきは手間、残すべきは守り。保守費の内訳を見直すだけで効果が出る話ですね。
WHY CLOUDFLARE

なぜCloudflare×EmDashなのか：PHPではない技術スタックTypeScript／JavaScript＋Astroで構築

Cloudflare上のEmDashはPHPを使わず、基本的にTypeScriptとJavaScriptで動作します。画面の枠組みにはAstroを使用し、ビルドとデプロイ時にはNode.jsが使われます。WordPressの代替として「PHPではないもの」を選ぶ流れは今後さらに強まるとのこと。また、単にCloudflare Workersで静的サイトを公開する方法もあるのですが、それだと更新作業が大変でAIネイティブ運用にも対応できないため、CMSとして管理画面を持つEmDashを選ぶのが理屈です。

よもぎ
よもぎ:静的ホスティングだけだと「更新」で詰まる。CMS層があることがAI運用の前提なんです。
SECURITY

Cloudflareのセキュリティは「世界が止まる」規模今回のPHP脆弱性攻撃も事前に大量ブロック

Cloudflareは世界中に分散した大規模ネットワークでWebサイトのセキュリティ強化と高速表示を同時に提供するプラットフォームで、ほとんどのWebサイト・アプリが何らかの形で利用していると言っても過言ではありません。今回のPHP脆弱性を突く攻撃もCloudflare側が事前に察知し、数十万件規模の不正アクセスをブロックしていました（Xで話題に）。仮にCloudflareが落ちれば世界中の大規模サイトが一斉に見えなくなるレベルなので、ハッキングされることは想定外と考えて良いとの判断です。それでも不安なら、サブの小さなサーバーでコピーサイトを並行更新する運用も提案されています。

よもぎ
よもぎ:「Cloudflareが落ちたらインターネット終わり」——冗談に聞こえるほどのスケールが安心感の根拠です。
PASSKEY

ログインはパスキーのみ——ID／パスワード概念なし指紋認証・Face IDで管理画面へ

EmDashの管理画面ログインはパスキー方式です。IDとパスワードという概念がそもそも存在しないため、「漏れるものがない」のが大きな強みです。情報漏洩事故の多くはID／パスワードの漏えいが原因なので、指紋認証やFace IDでログインする形にすれば漏洩の余地自体を削減できます。動画の実演でも、ログイン画面で指紋認証を使いスムーズにサインインしていました。

よもぎ
よもぎ:WordPressの管理画面ログイン攻撃に悩まされてきた人には嬉しい仕様変更ですね。
MCP NATIVE

MCP内蔵：AIは「用意した枠」しか触れない人間と同じ操作をAIがする、だから安全

EmDashのAI更新は、AIがサイト全体をガチャガチャと書き換える考え方ではありません。WordPressでいうカスタム投稿の枠（ニュース・ブログなど）だけを、人間と同じように書き込んで公開する方式です。AIが触れる範囲を用意した投稿枠に限定でき、下書きで止めることも可能。AI投稿後も普段どおり管理画面で人間が修正できます。WordPressでもAI連携プラグインで一応同じことはできますが、プラグイン作者がバージョン整合を追い続ける必要があり、接続確認が何度も必要になる不安定さがありました。EmDashはMCPという標準規格で最初から作られているので、一度Claudeのコネクターに登録すれば基本そのままです。

よもぎ
よもぎ:「AIに門を開けっ放し」ではなく「AI用の窓口を用意する」——安全設計の肝はここです。
MIGRATION TOOL

公式移行ツール：プラグイン1つでデータ引越し移るもの・移らないものを整理

EmDashは公式の移行ツールを用意しています。手順は、WordPress側にEmDash Exporterプラグインを入れて移行キーを出力→EmDash側の「WordPressからインポート」にキーを貼って接続、これだけです。過去のニュース投稿・ブログ記事・カテゴリー・SEO設定が一括で移行されました（メディアもインポート可能）。移らないものには注意が必要です。

  • 移る：記事データ・カテゴリー・タグ・SEO設定など
  • 作り直し：テーマデザイン（AIが復元）、フォーム機能、プラグイン相当機能
  • 移らない：ショートコード（WordPress固有）、ページビルダーのレイアウト

画像はインポーターで取り込めない場合は、サーバーに残ったファイルをClaude Codeに渡して各ページの対応位置に貼り付けさせる運用で対応できます。人間の作業は最後の確認が中心です。

よもぎ
よもぎ:「画像はAIに、確認は人間に」——役割分担がはっきりした移行フローです。
HANDS-ON 1

実演①：CloudflareにEmDashを構築無料プランの範囲で始められる

実作業はまずCloudflareへのドメイン登録から。続いてWorkersを新規作成しますが、ここはClaude Code＋Cloudflare Wranglerに「EmDashの基本パッケージを新しいワーカーで構築して」と指示して実行しました。ログインはパスキー（指紋認証）で完了。この時点ではまだデフォルト状態のテンプレートです。Workersの無料プランでも十分動き、動画では1日あたり10万リクエスト程度の無料枠（D1は5GB・R2は10GB）を紹介しています。足りなくなったら有料課金に切り替える考え方でOKです。

HANDS-ON 2

実演②：データ移行とデザイン再構築テーマをAIに再現させ、人間ファーストな管理画面へ

EmDash管理画面のインポートから「WordPressから移行」を選び、EmDash Exporterプラグインで出力したキーを貼って接続。コンテンツタイプとフィールドが自動作成され、ニュース・ブログ・固定ページが取り込まれ、画像も反映されました。続けてデザイン移行では、FTPでWordPressサーバーから使用中テーマのフォルダをダウンロードし、Claude Codeに渡して「このテーマ通りにデザインを再構築して」と指示。あわせて「固定ページは今後更新しないので静的に」「カスタム投稿の中身はHTMLより普通の段落で更新できる人間ファーストな設計に」「表記はローマ字ではなく全部日本語（カタカナ）に」と条件を付けると、管理画面が丸ごと日本語表示の使いやすいCMSに生まれ変わりました。

よもぎ
よもぎ:「HTMLを書かせる」ではなく「段落で更新できる設計にさせる」——AIへの指示の質が成果を分けます。
HANDS-ON 3

実演③：ドメイン・DNS切り替えネームサーバー変更→ドメイン移管→ Workersへ接続

最後の難関がドメイン周りです。①Xサーバー側でネームサーバーをCloudflareに変更（反映に約1時間、Wappalyzerで確認するとWebサーバーの表示がエンジンXからCloudflare＋Astroに変化）。②Xサーバーでドメインを管理している場合、レジストラロック解除のために一度ドメイン解約申請を行い、発行された認証コードをCloudflare側のドメイン転送に入力して移管を完結。③Workersのカスタムドメイン設定も「このドメインを直下に置いて」とClaude Codeに依頼し、元のURLのままEmDashサイトが表示される状態と管理画面（ドメイン直下のパス）を整えました。WordPress側の移行プラグインは用済みなので削除します。

よもぎ
よもぎ:解約手続きが絡む部分だけ慎重に。URLを保ったまま全部Cloudflareに集約できました。
HANDS-ON 4

実演④：MCP接続してAI更新を可能にするAPIトークン→/mcp URL→Claudeコネクター追加

移管が終わったら、EmDashの設定からAPIトークンを作成します。権限はコンテンツ・メディアの読み書きなどを付与し、管理者権限のフルアクセスだけはチェックしないのが安全側の設定。期限は無期限でも、不安なら30日区切りにすれば被害が短期間で止まります。続いてClaude Codeに「このトークンでMCP接続できるよう、カスタムコネクター用のURLを発行して」と依頼すると/mcpのURLが発行されます。あとはClaude Desktopの「カスタマイズ→コネクター→追加」にURLを貼り、EmDash側でログインしてツールを承認するだけ。ChatGPTやGeminiでも同様に接続できます。実演ではスマホのClaudeアプリから「サンプルブログ記事を作成して公開して」と送り、MCP経由で本番ブログが即公開される様子も確認されました。

よもぎ
よもぎ:構築はClaude Code、日々の更新はスマホのClaudeから。外でもどこでも更新できる状態が完成です。
SAFETY & VERDICT

「AIが壊せない」設計と総評実験：トップ画像の差し替えを依頼するとどうなるか

動画では興味深い実験が行われました。スマホのClaudeに「トップページのメインビジュアル画像を別の画像に差し替えて」と依頼すると、AIは「対象の設定箇所が見つからず、差し替えは行っていません」と回答。これがEmDashの設計どおりの挙動です。MCPでAIが更新できるのは用意された投稿枠（ブログ・ニュースなど）だけで、静的にコーディングされた部分には手を出せないため、AIがサイトを勝手に改変する事故が構造的に起きません。細かい静的部分を変えたい場合は、Claude Code＋WranglerでCloudflare側を直接操作できる人が担当する運用が推奨されています（一般社員向け更新はスマホAI、静的部分は専門担当という棲み分け）。

総評として、この動画1本で「移行の理由→ツールの特徴→本番実演→AI運用」まで一気通貫で学べる構成です。自分で挑戦する人は動画を頼りに1つずつ進め、公式LINEで移行マニュアルも無料配布されています。難しければWordPressからの移行・EmDashでの新規構築（デザイン・セキュリティ保守・エージェントスキルや画像生成の統一感づくりまで含む）を依頼することも可能です。
