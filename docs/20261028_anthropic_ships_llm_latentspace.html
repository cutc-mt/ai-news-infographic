TWO LOOPS

成長を駆動する2つのループ改善ループ×投資ループ＝「終わりなき無限ループ」

ホストによるS-1の整理では、Claude・Boris・Darioが「ループを愛する」ように、Anthropicには2つのフィードバックループが回っているとされます。

1改善ループClaude → より良いモデル → 用途拡大 → フィードバック増 → さらに良いClaude
2投資ループ収益 → 成長 → 投資増 → 能力向上 → さらに良いClaude
∞無限ループ2つのループが噛み合い、効率向上が永久に続く（S-1の主張）
PLATFORM

Claude Platform — モデルラボからハイパースケーラーへ「Claudeの拡散」の3本柱の1つ、包括的エージェント開発環境

S-1で語られる「Claudeの拡散」の中心が包括的なエージェント開発環境（Claude Platform）です。顧客はClaudeの能力を自社製品に組み込むためのプリミティブに直接アクセスできます。

  • 年間10万ドル以上の収益がある顧客の50%超がClaude Platformを利用
  • Claude CodeやClaude Co-workも同一のプリミティブの上に構築
  • 「ant fooding（自社プラットフォームで自社を開発）」が議論の鍵に
  • IPO叙事は「チャットボット → コパイロット → バーチャルコラボレーター（エージェント）」への進化
OPUS 5.5

Opus 5.5 — 「今世界で最も良いモデル」文章の癖を掃除し、価格を大幅に下げた次世代フラッグシップ

収録はOpus 5.5公開翌日。「高品味テスターたちの間で圧倒的な評価」と紹介されます。

  • Opus 5で指摘された文章の回りくどさを大幅にクリーンアップ（社内検証でも実感）
  • 「1ドルあたりの知能」重視 — 大幅な価格引き下げを実施
  • 後続のFable 5.5も2週間以内の出荷が噂される（IPO前という観測。内部情報ではないと明言）
  • 「古い上司から『Opus 5.5が障害対応で助けてくれた』と連絡が来た」など反響は上々
DISTILLATION

推論の盗み（ディスティレーション）対策「Stealing Reasoning Traces」論文と、思考ブロック保全の綱渡り

責任ある開示で知らされた、思考トークンからモデルを蒸留する手法への対応が語られます。Anthropicが防ぎたいのは商業的損失ではなく安全性の劣化 — 蒸留モデルにはセーフガード分類器が無いためです。

  • 思考ブロックのターン間保全を必須化、複数アカウント悪用対策も追加
  • prefix lock thinking・思考トークンの再生利用制限などの具体的変更
  • 壊れるはずだった圧縮（compaction）戦略向けに新API機能を提供して移行を支援
  • オープンソースのハーネス保守者や大口顧客と個別に協働し「ヨルヨロ締め付け」を回避
  • 効果測定でも蒸留は大幅に困難になったと確認

SCALE

1年で激変したスケール課題Pythonモノリス＋単一リージョンから、3クラウド・CPU不足の時代へ

Angelaさんが入社した1年強前、Messages APIはPythonのモノリスで単一GCPリージョンで動いていたとのこと。現在では量が桁違いになり、課題は「スケールと安全」の2つに集約されます。

  • 最大の制約はアクセラレータではなくCPU — VM・サンドボックス・CI・研究環境すべてで不足
  • エージェント時代はコード量・CI実行回数が激増しCPU需要が爆発
  • かつては予算さえあればon-demandで CPU を拡張できたが、今は事前のキャパシティ計画が必要
  • 3つのクラウドすべてで稼働しており、計算資源の割り当ては社内のゼロサムゲーム
RUST

Messages API全量をRustへ一気に移植Rust経験者ゼロのチームが、Claudeにコードを書かせて達成

CPUの壁を見越して選ばれたのはAPI全体のRustへの移植。「部屋にRust開発者が1人もいない。誰も気にしない」と始めた Crazy な決断です。

1人間が設計分散システム設計は人間が主導。重要なのは計画と検証
2Claudeが実装API全体のフォークをRustで構築
3シャドウトラフィックPython版とRust版の出力を突き合わせ検証し、フィーチャーフラグで徐々に切替
40〜50%
CPU削減（長時間ワークロードではさらに大）
10〜20%
最初のトークンまでのレイテンシ改善

新機能追加の誘惑を排した「ピュアなポート」として実行し、前週に完全ロールアウト完了。従来なら数年かかる分段階移行を一撃で行った形です。

LAUNCH

モデルローンチの内側安全性検証 → 内部ant fooding → アーリーアクセス顧客 → 公開

安全性を除くと「かなり機械化されてきた」というローンチ工程。API顧客はClaudeを別のハーネスで動かすため、汎用性の検証として特に有用です。

  • 複数のモデル候補をカットし、内部のant foodingで早期シグナルを収集
  • Cognition などの主要API顧客にアーリーアクセス提供 — eval結果と「バイブス」両方のフィードバックを収集
  • 「最も有用なフィードバックはネガティブなもの。良い指摘は検証にすぎない」
  • 実際に「怠けすぎ」検出 → 焼き直して再学習した事例も
  • フィードバックの実態はいまだ企業間のSlackチャンネル中心で、非構造的なまま
PERSONA

「怠け」と「先回り」の調整難全員が違う好みを抱える、パーソナライゼーションの未解決問題

「タスクを完遂してくれ、怠けるな」という人と「まだ計画段階なのにコードを書きすぎる」という人が必ずいる — 全員の望む地点を1つに当てるのは文字通り不可能と率直に認めます。

  • 当面はパラメータ（effort・budget等）とセグメント別デフォルトで調整
  • 無料 / Pro / Claude Code / Co-work / Enterprise / API など層ごとにデフォルト設定を変える「やさしいデフォルト」方針
  • ユーザーがClaudeのカスタマイズを失う懸念は避けたい
  • 将来的には「Claude自身が個別化信号を取り込める」仕組みが必要 — 今は判断で乗り切る
  • 最新の設定変更：Claude Code のデフォルト reasoning effort が medium に
SAFETY 3D

安全策の3つの次元と信任グラントアーキテクチャ・オンライン・オフラインの三層防御

「フロンティアのペースを守りながら11日後に新モデルを出す」矛盾への答えは、3次元の安全確認を通過したから。Opus 5.5はすべての次元で優れていたため出荷された、という整理です。

  • ①アーキテクチャ/インフラセキュリティ（brain/hands分離・資格情報保護）
  • ②オンラインsafeguards（トークン流に常駐する分類器）
  • ③オフラインsafeguards（保存データへの分類・レビュー）
  • モデルごとにデータ保持ポリシーを決定 — Opus 5.5には保持要件なし、Fableにはあり
  • cyber検証プログラムに加え新たにライフサイエンス検証プログラム — 用途申請制でデュアルユースの正当な研究を解放
  • trust grants（信任付与）がAPIのホットパスを貫通し、許可された人だけが許可された使い方をできる仕組みを構築
  • Fable級の事件に備え全員を一括ロールバックする単一ボタンも実装済み
ROADMAP

確率的ロードマップ — ヘッジのポートフォリオFable事件が変えた、「想定外」に備えるプロダクト開発

従来型の順序立てたプロダクト計画は、政府によるFable活用のような誰も予想しなかった事象で崩壊。以来、チームの計画手法は深く確率的になったと語られます。

  • 「最もクレイジーな可能性集合を想像しても、確実性はほぼゼロ」→ ヘッジを含む賭けのポートフォリオを組む
  • 実際に「使うかもしれない仕組み」を先に作ると、ほとんどの場合あとで本当に使う
  • アクセス検証プログラムを意図的にジェネリックなプリミティブで構築した結果、モデルアクセス管理・信頼アクセス・デプロイ管理に波及して「複利」を生んだ

CMA

Claude Managed Agents — ハーネス構築からの解放Messages APIの上に用意された、エージェントの高階抽象化

Messages APIが「生のトークンアクセス」なのに対し、CMAはエージェントを定義してセッションを開始するスイート型API。ハーネスやインフラの構築をスキップできる、箱から出してすぐ動く統合です。

  • 毎回のローンチで新パラメータ・破壊的変更の対応をAnthropic側が吸収し、ベストな設定を箱から提供
  • Claude Code / Claude Tag とサンドボックス艦隊などの基盤インフラを共有（ハーネス層は製品ごとに別）
  • 登場以降、各社がこぞって模倣 — 「模倣は最も誠実な賛辞」
  • メモリ・Dreaming・スキルは継続更新中。ただしチームのエネルギーは安全側にシフトしつつある
BRAIN / HANDS

Brain/Hands分離と secure by defaultサンドボックス脱走問題への設計上の回答

「エージェントがサンドボックスを脱走する」事故の多くは訓練環境の話で、本番ワークロードでは構造的に起きにくいと整理します。CMAの初期設計PMは「この構造の最重要属性はセキュリティだ」と言い続け、いま報われたとのこと。

  • Brain（ハーネス）は耐久的なサーバー、Hands（実行）はサンドボックス — 初期トークンが速く、サンドボックスが死んでもエージェントは死なない
  • 資格情報は独立したvaultに保管し、エージェントにはプレースホルダーのみ開示。egress時にプロキシが正しい資格情報を注入
  • ドメイン許可リスト / ネットワーク遮断で、生成された信頼できないコードの外向き通信を制限
  • 「brainとhands」「資格情報注入」「egress制御」— 9ヶ月前には誰も使っていなかった新しい語彙
結論
要点:サンドボックス事故の多くは「許可リストを設定していない」運用の問題。訓練時のインシデントと本番の防御を混同しないことが第一歩です。
DREAMING

Dreamingとマルチエージェント戦略の公開「CMAの上にCMA」— 自己増殖するマルチエージェントの設計

記憶の自動形成機能Dreamingの正体は、CMAの上に構築されたマルチエージェントシステム。別のマネージドエージェントを起動して前のエージェントを検査し、メモリを書き込みます。「マネージドエージェントの無限ダウン」です。

  • best-of-N・検証エージェント・ゴール追求などのヒルクライム戦略を同じ土台で構築可能
  • 近日中に基盤プリミティブを公開し、ユーザーが独自のマルチエージェント戦略を構築できるテンプレートも提供予定
  • ハーネスは意図的にシンプルに — 非差別化部分は雛形化し、ベストプラクティスはマージして還元
EVALS

評価（eval）は「多いほど良い、シンプルに始める」最大の失敗は投資不足 — エンジニアリングを研究として扱う

evalについての質問への答えは明快です。

  • 「必要なのは多くではなく少なく」ではない — むしろ多く必要。完璧な少数のevalセットは存在しない
  • メニューを見てあれこれ試す前に、まずシンプルなevalを1つ作るだけで意味がある
  • エージェントにもevalスイートの進化を手伝わせられる
  • ホスト側の補強: 「エンジニアリングを研究として扱う」とeval・ラベリング・試験のスケールが自然に増える。「時にevalが間違っていて、時に環境が間違っていて、時にモデルが間違っている」
  • 「プロンプトでevalを作れる」ことを知らない人が多い — Claudeはeval作成が得意

今後CMAにeval作成を支援する製品機能が追加される予定です。

CULTURE

スロップ対策・DevRel・結論「人間が品質に責任を持つ」— 文化と採用の現在地

スロップ（AI生成の粗製乱造）との戦い: Claudeの利用は当然だが、読まずに出すのは消費者への不当な負荷。品質責任は人間が負う。本当にスロップなら送り返してよい。一方で「Mダッシュ1つでAI文書だと警戒する」claudism過敏は不生産的、というバランス感覚。コード側は計画と設計を人間が担保し、実装はClaude、検証で高水準を維持。「2週間で13項目のリファクタリング目標のうち12を3日で達成」した事例も紹介。

DevRel: Addy Osmaniさんらがジョイン。プラットフォームとClaude Codeに2つのDevRelチームを新設。「レゴのマスタービルダー」のように作って見せる役割や、フロントオフィス（製品責任者が語る）/バックオフィス（支援チーム）の分業という未来像も。「Lanceが書いたClaude APIスキルこそ最高にレバレッジの効くDevRel」

結びのアドバイス: Opus 5.5は費用対効果が高いため、以前はコストで諦めたマルチエージェント実験に再挑戦を。設計原則は「1人のリード＋並列化可能なタスク＋共有状態＋サブエージェント同士は非同期でブロックしない」。役割を自分で割り当てずエージェントが自ら役割を決める構成こそ新しいフロンティア。
