THE ARTICLE

問題提起: 私たちは「間違った作り方」をしてきた2026年10月22日公開のAnthropic公式記事

Anthropicの記事「When to fold sub-agents into your main agent loop」（Diane Sarkis 著）は、冒頭でこう告げます —— 多くの人はエージェントの作り方を間違えている。主張はシンプルですが、今多くの人がやっていることの逆をいいます。

  • 望むのは1つのメインエージェントループ — スキルとツールを「必要になったときだけ」読み込む
  • サブエージェントは全面的に廃止ではなく、畳み込む（fold）べきというバランス感
  • 理屈ではなくAnthropic自身のClaude Code開発での実測に裏打ちされている点が説得力の源
CONWAY'S LAW

組織図をエージェントにコピーする病「Conway's Law（コンウェイの法則）が働いている」

記事が名指しするのは、会社の組織チャートをそのままエージェント設計に写すパターン。請求チームには請求サブエージェント、サポートチームにはサポートサブエージェント、その上にオーケストレーターが座って作業を振る構成です。

組織図 → 請求サブエージェント ＋ サポートサブエージェント ＋ 上位オーケストレーター → 図面では整然、実際は品質低下＋コスト増＋レイテンシ増

これは「システムはそれを作ったチームの形に似る」という古い格言Conway's Lawそのもの。図上は整理されて見えても、動かすと問題が多いと記事は指摘します。

PROGRESSIVE DISCLOSURE

答えは「段階的開示」— 1つのメインループ必要なときだけ、スキルとツールを読み込む

記事が代わりに推すのは、1つのメインエージェントループ。キーコンセプトはProgressive Disclosure（段階的開示）です。

1短い説明で開始エージェントは最初、スキル・ツールの短い概要だけを持つ
2必要な瞬間に取得実際に使う直前にだけ、フルのスキル／ツール定義を引き込む
✓1エージェントで広範囲毎回すべてのルールを抱え込まずに多くの作業をこなせる
実証
Claude Codeでの実績:Anthropicはこの方式で、高度なモデル向けのClaude Codeシステムプロンプトを80%超削減しました。
STILL USEFUL

それでもサブエージェントが正解の3場面「サブエージェントは常に悪い」とは言っていない

公平に、と動画が強調するのは、記事がサブエージェント全面否定ではないこと。このバランスこそ記事の価値だと評価します。

  • 検証（Verification） — 作っていない仕事を新鮮なエージェントがチェック。作り手が見逃す（言い訳してしまう）ミスを捕まえる
  • 並列作業（Parallel Work） — お互いに依存しない独立したピースを同時に走らせる
  • モジュール権限（Modular Permissioning） — 狭い作業には狭いアクセスだけ与える。巨大エージェントに全鍵を渡さない
FAILURE MODES

分割しすぎの4つの失敗モード「全部、私も見てきた」と動画より

  • Sub-agent Sprawl（サブエージェント乱立） — 各チームが重複するサブエージェントを出荷し、誰も全体を所有しない
  • Frankenprompt（フランケンプロンプト） — 各チームがシステムプロンプトに一文ずつ足し、ルール同士が衝突し始める
  • Telephone Game（伝言ゲーム） — エージェント間の引き継ぎごとに詳細が失われ、最後尾は最初の情報の「色あせたコピー」で作業する
  • ネストされたレイテンシ — 各サブエージェントは完全な1エージェント実行。深いチェーンはその分だけ遅くなる

MAIN LOOP TEST

何をメインループに残すか — きれいな3基準記事の判断テストそのまま

仕事をメインループに残すべきか。記事のテストは明快です。次のいずれかに当てはまるなら分割しない。

  • 各ステップが直前のステップの上に積み上がる（Chain on prior steps）
  • ステップ間で同じデータを共有する（Share data）
  • 2つの処理をほぼ必ず一緒に呼ぶ（Always called together）
視点
なぜ？常に一緒に動く2つを分割すると、得るものなく途中に引き継ぎ（handoff）が1つ増えるだけ。
RIGHT CONTAINER

正しい容器を選ぶ: Skill / Tool / Lookupこの3分割でほとんどの散らかった設計が片付く

判断 → Skill

  • 専門家が事例を扱うようなドメイン判断はスキルに

動作 → Tool

  • システムへのアクション・ライブデータ・厳しい上限値はツールに

たまの事実 → Lookup

  • ときどき必要なだけの事実はプロンプトに置かない。知識ベース検索へ

それ以外 → 何もしない

  • プロンプトは「毎回必要なもの」だけの場所にする
FOLD BACK

Router / Planner / 特化エージェントを「畳む」モデル自身がルーティングと計画をこなす時代

記事は、昨年多くの人が作った独立したルーター・プランナー・狭い特化エージェントをメインループに畳み戻せる とします。現在のメインモデルは通常の推論の一部としてルーティング・計画・分類の多くをこなせるようになったからです。

分類器 ＋ パイプライン ＋ 個別ブランチ ＋ 上位オーケストレーター → 明快な1つのプロンプト ＋ データを扱う4〜5個の薄いツール ＋ 確かなガードレール

同じ仕事を、はるかに少ない動く部品で。これが「フォールドバック」の実例です。

WARNING

警告: 1ループ＝全部詰め込む、ではないツール定義はおよそ30〜50個が上限

1つのループに統合するということは、1つのループに何もかも投げ込むことではありません。記事は明確な上限を示します。

30〜50個
この辺りを超えるとツール選択（Tool Choice）の精度が劣化し始める
  • 正解は 1ループ ＋ ユーザーがやりたいこと別にグループ化された少数の良く名付けられたツール群
  • 残りは必要なときだけ開示（Progressive Disclosure）で引き出す
MIGRATION

壊さずに移行する手順一度に1つのサブエージェントを畳む

1最頻出 or 最密結合のペアから一番よく使う、あるいは最も強く結合したサブエージェントから着手
2プロンプト→Skill、API呼び出し→Toolサブエージェントのpromptをskillに、API呼び出しをtoolに変換
3測定してから次へ結果を計測するまで次のサブエージェントには触らない

動いているシステムを一気に再構築するのではなく、1つずつ、測りながら。これが記事の移行戦略の骨格です。

EVALUATION

評価は小さく始めて、複数回走らせる「10個のゴールデン例」で足りる — でも1回だけではダメ

測定は小さく始められます。記事によればたった10個のゴールデン例（良い結果の形が分かっている実タスク群）で評価を開始できます。

  • 旧構成と畳み込み後の構成を同じ例で実行して比較
  • 各評価は必ず複数回実行する — 記事では、フォールドがサイレントにフローを壊し、2回中1回にしか現れなかったサポートチェーンの事例を紹介
警告
1回だけだと？運で通過すれば、コイン投げを shipping したのと同じ。毎評価2回以上が原則。
CHECKLIST

それでも残すべきか？ サブエージェント保持の3条件保存しておく価値のあるチェックリスト

  • ① コンテキスト害が測定できる — そのサブエージェントのコンテキストがメインエージェントを悪化させると計測できる
  • ② 並列で捨てられる文脈 — 仕事が新しいコンテキストで並列に走り、終わったら捨てられる
  • ③ 単一エージェントが苦闘する — ツール選択や衝突する指示で単一エージェントが継続的に失敗する
大原則: 問題タイプではなくコンテキストで分割せよ → 分離エージェントには「システムの他の部分をほぼ必要としない仕事」を与え、「独立リサーチ」や「完成品のブラックボックス検査」のような1つのコンパクトな結果を返させる
PANDACODE — TEAM MODE

実践編: PandaCodeのチームモードの仕組み同じタスクに「1チャット」と「チーム」の両方を用意するアプリ

Architect（建築家）

  • メインチャットにいる設計・指揮エージェント
  • 仕事を計画し、assignment に分割
  • 複数ワーカーを1バッチで並列派遣
  • 戻ってきた成果物をレビュー

Worker（作業員）

  • それぞれ新しい（fresh）コンテキストで実行
  • メインチャットのコピーではなく全会話は見えない
  • 境界のある割り当てだけを受け取り、遂行して報告
注記
正直な註:PandaCodeの公式ドキュメントに「fold」という言葉は出てきません。あくまで動画作者が記事の原則を PandaCode の機能に対応づけた自分の解釈です。
WORKERS IN DETAIL

ワーカーの柔軟な使い方ハーネス混在・ファイルスコープ・依存チェーン・フォローアップ

  • ハーネス・モデル混在: 各ワーカーは異なる harness とモデル＋努力度設定で実行可（Claude Code, Codex, Kimi, Open Code, GLM, Muse など）
  • チームプロファイル保存: 「強いarchitect＋安いワーカー数人」等のお気に入り構成を1クリックで再利用
  • Read-only / Writing ワーカー: 読み取り専用は並列でコード調査・レビュー。書き込み系は着手前に狭いファイルスコープを宣言（data / UI / tests を分担）
  • スコープは助言であって壁ではない: サンドボックスではなく強い規約。書き込みスコープが重なれば同時ではなく順次実行
  • 依存チェーン: レビューワーカーは担当ライターの完了後にのみ開始、など順序付け可
  • フォローアップ: 「惜しいが違う」結果には同じワーカーの文脈へ修正を送信 — ゼロから再開せず学習を保持（handoff の回避）
MAIN LOOP = SIMPLE

ではメインループはどこに？答えは「Simpleオプション」— fold back の実装

PandaCodeの画面でいうメインループは、Simple（単一エージェント）選択そのもの。通常チャットで1エージェントを使うか、architect に委譲させず直接答えて編集させるモードです。

  • ワーカーなし・handoff なし・フルコンテキストが1か所に集約
  • タスク開始時の選択が、まさに記事の言う「fold back への移行」に対応（動画の解釈）
  • 書き直しではなく「タスクの始め方」の変更で済むのが実用上の強み
WHEN TEAM WINS

チームモードが本気で勝つ5場面動画作者が実際に使い分けるケース

  • 並列リサーチ: 複数の read-only ワーカーがコードベースの別部分を同時調査し、短い報告を返す — メインチャットは汚れないまま
  • 大きめの機能開発: data側 / インターフェース側 / テストを別ワーカーが構築し、別のレビューワーカーが新しい目で検査（記事の「検証」ケースそのもの）
  • モデル比較: 同じプロンプトを複数モデルで走らせ、結果を並べて比較
  • 一括編集: 安いワーカーモデルがbulk編集、強いモデルは計画とレビューのみ
  • 長時間タスク: 1コンテキストウィンドウを満たす仕事 — 各ワーカーは自分のスライスだけを運び、architect が糸を握る
WHEN ONE CHAT WINS

1チャットが勝つ場面と、チームの正直なコスト「無料の高速化」として売るつもりはない」と動画より

シングルチャットでOK

  • 1ファイルのタイポや小さなconfig修正（チームは純粋なオーバーヘッド）
  • 一歩ずつ見ながらの対話的な調整
  • 失敗テスト1つのデバッグ（試行が前の試行に積もる）
  • 文脈内コードへの即席の質問
  • 同じファイルへ連続する編集

チームモードの代償

  • ワーカー1人＝モデル実行1回。トークン消費が速い（強いモデルを全席に置けばなおさら）
  • 報告は境界ある要約 — handoff のたびに詳細が失われる（記事の伝言ゲーム）
  • 全ワーカーが同じcheckoutを共有 → 狭いファイルスコープが必須

並列時間と新しい目を買い、トークンと少しの詳細で払う。トレードを知ってから選ぶのが動画の態度です。

TAKEAWAY

記事を1行に boil down すると「雰囲気で再構築するな。どちらの方向でも」

測る

1つずつ

動画作者の運用ルールも記事の助言と一致します: デフォルトは1チャット。チームは「名指しできる理由」（並列リサーチ・きれいな分割・独立検査・1コンテキストに長い仕事）で獲得するもの。理由が言えなければメインループに留まる — たいていの日、それが最速で最安の答えだと結論づけます。
