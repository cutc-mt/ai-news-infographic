  • 研究者でも提供元でもない第三者による再現は、調べた範囲では見つからなかった
  • 実際の被害報告も見つかっていない——ただし「被害がない」と言い切れるわけでもない

BASICS

前提:Tailscaleを「大きな共同住宅」に例えると動画の比喩をそのまま図式化

  • 廊下 = テイルネット——離れたPCやサーバーをつなぐ専用の通路
  • 部屋 = 端末——それぞれの機械
  • 入居ルールの掲示板 = ポリシー（ACL）——誰がどこへ入れるかの許可一覧
  • マスターキーを持つ管理人 = 常駐プログラム（tailscaled）——最強権限のrootで動いている
  • 受付窓口 = Unixソケット——部屋の中でプログラム同士が話す窓口

指摘の多くは「管理人（root権限）が窓口の管理を甘くやっていた」話として読めます。

CONDITION

「外の誰でも入れる」話ではない攻撃成立の前提条件

SSH関連の問題を悪用するには、すでに許可された端末に足場（SSH接続の権利）を持っている必要があります。インターネット側の誰もがいきなり突ける話ではありません。

  • 条件：ポリシーでSSH接続が許可されていること＋接続できる立場にあること
  • 「ワーム」と呼べるかは研究者と提供元で見方が分かれるところ
  • 表現の怖さと、自分の使い方での実際の exposure は別個に評価する

だからこそ「どの機能を・誰が・どこで使っているか」の見極めが重要です。

SSH ①

SSHの転送がroot権限で行われる一般ユーザーの接続なのに管理人が代理

転送（ポートフォワーディング）とは、接続を通して窓口まで話を取り次いでもらう機能。ところが一般ユーザーとして入った接続なのに、その取り次ぎを管理人がroot権限でやってしまうという問題です。

  • 判定：研究者の再現＋公式告知14番が認める → 修正は1.104.4に収録
  • 届いてしまう例として公式はDockerの窓口やTailscale自身の管理用窓口を挙げる
  • 更新できない間は転送だけを止める設定を入れて常駐プログラムを再起動（SSH自体は止めずに済む）

補助案（動画の推論）：転送が必要な機械と不要な機械を分けておく。

SSH ②

逆向きの転送で「本物の窓口」がすり替わるrootの受付を外して別の受付に

リバースフォワーディング（相手側に受付を作る機能）が管理人の権限のまま作られるため、rootが持つ本物の受付窓口を外して、別の受付に置き換えられてしまうという問題です。

  • 判定：研究者の再現＋公式告知14番 → 修正は1.104.4
  • 怖いのは、置き換えられた受付に本物だと思ったプログラムが話しかけると、やり取りが別の相手に渡ること
  • 対策は①と同じ：更新＋転送を止める設定

補助案：更新後、Dockerのような大事な窓口を使うサービスがきちんと動くかも確認を（推論）。

SSH ③

確認と使用の「隙間」で行き先が入れ替わるTime-of-Check と Time-of-Use のずれ

管理人は「この行き先なら安全」と確かめてから扉を開けます。その確認した時と使う時のわずかな隙間に行き先が入れ替わってしまうという指摘です。

  • 公式の告知も、この件を含めて複数の弱点が重なり、許可の一覧が守りとして機能しなくなっていたと説明
  • 研究者は新しい端末を登録できる鍵（auth key）まで届いたと主張——ここは研究者の主張の札
  • 修正では、取り次ぎ自体を接続した本人の権限で行うように変更 → 対策は更新

補助案：端末登録に使う鍵を使い切り・期限の短いものにして、漏れた時の被害を小さく（推論）。

SSH ④

許可されたSSH接続でメモリが増え続ける盗まれる話ではなく「使えなくなる」話

報告5番目の項目。許可されたSSH接続の中でやり取りを続けると、常駐プログラムのメモリが増え続けて強制終了してしまいます。

  • 判定：公式告知15番が認める → 修正は1.104.4に収録
  • 常駐プログラムが止まるとその端末のテイルネット通信が全て途絶える（DoS）
  • 条件は「ポリシーで許されたSSH接続があること」。研究者はメモリ上限と自動再起動も推奨

注意：転送を止める設定はこの件には効かない（推論）。遠くの機械には別の入り方も用意しておくと安心です。

第1部判定:SSHの4件はすべて公式が認め、1.104.4で修正ただし「治るのは更新した端末だけ」

②逆転送窓口のすり替え

③隙間確認と使用のずれ
許可一覧が機能しなくなる／修正済み
④メモリ肥大化と強制終了
通信途絶のDoS／修正済み
更新まで転送停止＋許可を絞る

SSH系4件はすべて「公式の確認」＋「修正の記録」あり。全端末を1.104.4以降へ。更新までの間は転送を止める設定とSSHの許可を絞ることが公式の対策です。
PART 2 VERDICT

第2部判定:中継と自前サーバーの2件は「使っている人だけの話」未公開機能の解釈が分かれ、Headscaleは修正待ち

報告4番目次世代App Connector
決められていない行き先にも応答——研究者「公開コードに試験中機能として存在」／公式「開発中で未公開・安定版は無影響」。修正案は公開済みだが確認時点で取り込み前。安定版利用者は対応不要
Headscale自前管理サーバー
ログイン前通信でメモリを使い果たせる（研究者報告）。悪意ある中継所（DERP）につながると端末側もメモリ枯渇——こちらは1.104.4関連の修正記録を確認済み。Headscale側は最新0.29.6時点でもまだ修正待ち

公式・研究者ともにメモリ上限と外部公開の範囲を絞ることを推奨。補助案：試験中の機能を本番端末で有効にしない／更新情報を見張る担当を決めておく（いずれも推論）。Headscale運用者は公開範囲を絞って修正版を待ちましょう。

SERVE ①

Serve:管理用ソケットへの転送を止められていなかった影響は「端末の乗っ取り」につながる

Serveは部屋の中のサービスをテイルネットの住人に開く扉、Funnelはそれをインターネットという表通りまで開く扉です。報告7番目は、Serveで通信を部屋の中の受付窓口へ転送する設定をした時、その先がTailscale自身の管理用窓口でも止める仕組みがなかったという問題。

  • 判定：公式告知16番が認める。影響は端末の乗っ取りにつながると明記
  • 条件：その端末でServeの設定をかける人がいること
  • 修正版では管理用窓口への転送を断るように。対策はUnixソケット転送を使う人の更新

補助案：Serveの設定をかけられる人を必要な人だけに絞る（推論）。

SERVE ②

Serve:安全確認が「設定を読み込んだ時」だけだった後からの差し替えが効いてしまう

転送先は安全だと最初に確かめても、後から行き先を差し替えられると確認が効かないという8番目の問題。

  • 判定：公式告知16番が2つ目の弱点として認める
  • 条件：転送先の場所を他のユーザーが書き換えられること
  • 研究者は影響は限られると評価
  • 修正版では繋ぐたびに確かめるように変更 → 対策は更新

補助案：Serveの転送先にする窓口やフォルダーを他のユーザーが書き込めない場所に置く（推論）。

FUNNEL ③

Funnel:許可の確認が端末内のコマンド側だけ「設計通り」とされる未修正の項目

表通りに扉を開けて良いかの確認が端末の中のコマンドの側だけで行われている——研究者はこれを守りとして弱い作りだと指摘（報告9番目）。

  • 公式は「設計通り」と説明：確認を外すには元々端末の管理者権限が必要で、管理者なら他のこともできてしまう、という考え方
  • 研究者の状況表では未修正のまま・見方が分かれる項目。公式の対策は特になし

補助案：Funnelを使う端末では管理者権限を持つ人を絞り、表通りに開いている扉を時々確認する（推論）。

NOTE ④

設定の注意:Serveを「外側の網」にも開く設定重大度なし——研究者も公式も見方が一致

10番目の項目は、研究者自身が「設定の注意」と分類したもので重大度はついていません。Serveをテイルネットの外側のネットワーク（LAN等）にも開く設定があり、それを入れるとその通りに外へ開きます。

  • 公式も「自分で入れる設定で設計通り」と説明——ここは見方が一致
  • 研究者はこの設定を入れないようにと注意喚起

補助案：サービスの環境設定にこの名前の設定がないか、名前だけでも点検しておきましょう。

SERVE ⑤

暗号化Serveで権限情報が「混線」する同じ相手の中での取り違い——なりすましではない

報告11番目。Serveを暗号化して使い、1台に権限の違う公開先を2つ以上置いている時、同時に流れる通信の間でアプリごとの権限の情報が別の公開先の分と混ざることがありました。

  • 判定：公式告知17番が認め、修正は10月25日に取り込み→1.104.4に収録
  • 注意：同じ相手の中での取り違いで、他の人に「なりすます」話ではない
  • 影響を受けるのはその情報で許可を決めているアプリだけ

対策は暗号化Serveを使っている人の更新。補助案：権限の違うアプリを別の端末・別の公開先に分ける（推論）。
