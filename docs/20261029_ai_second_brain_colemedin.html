Cole Medin氏は「第二の脳（AIセカンドブレイン）」を使ってビジネス全体を運営しています。この動画は、まだ構築していない人のための基礎解説であり、すでに持っている人への監査（オーディット）ガイドでもあります。フレームワークの元ネットは同じAI教育者・Nate Herk氏の「4つのC」。構築ツール（Claude Code / Codex / OpenClaw等）を問わず適用できる設計論を、実際の運用スタックとともに解説します。

まず結論——セカンドブレインの目的は「自分のビジネスを即座に把握している、自分自身の延長」になること。最大の失敗原因は複雑にしすぎること。必要なコンポーネントは「4つのC」だけ。これさえ正しく作れば、どの基盤モデル・どのツールで構築していても成功への道筋が立つ——というのがコールの主張です。
OVERVIEW

全体像:この動画が教えること基礎構築ガイド × 既存システムの監査ガイドの二役

コールのセカンドブレインは、AIニュースの調査、コンテンツ制作の準備、図解・プレゼン資料の作成、企業向け自律システムの改善まで、ビジネスのあらゆる場面を支えています。構築・運用でセカンドブレインを複雑にしすぎる人を多く見てきたといい、その回避策として「必要なコンポーネントは4つだけ」と整理したのがこの動画です。

WHY NOW

なぜ「今」セカンドブレインを作るべきか投資対効果（ROI）が凄まじい時代になった

かつては構築に長い時間がかかったセカンドブレインも、コーディングエージェントの進化によって驚くほど簡単に build & 改善できるようになりました。

  • 構築コストは激減: コールのシステムは裏でClaude Codeが動き、動画編集・図解・PowerPoint作成を有料サービスなしでPC上のコマンド実行だけでこなす
  • 改善も自分でできる: 基盤さえ作れば「セカンドブレインを使ってセカンドブレイン自体を改善」できるので、改善サイクルがさらに速い
  • 成果の実測: 構築当初は週10時間の節約だったが、今は週30時間以上（計測用の体系的システムも運用中）
LLMの力そのものがシンプルさを維持できる理由。膨大なツールを積み重ねる必要はない。
4C FRAMEWORK

「4つのC」——成功の核となるフレームワークNate Herk氏考案の設計指針

コールが数週間前のNate Herk氏のバーチャルカンファレンスで同テーマのプレゼンをした縁で採用した、セカンドブレインに必要なものを理解するための堅実な指針です。

① Context（文脈） ② Connections（接続） ③ Capabilities（能力） ④ Cadence（リズム）
  • 4つのCを正しく実践できれば「成功は約束されたようなもの」
  • 重要なのはモデルではない:コールはCodexで構築し、テストでKimi（K3.1）へ全面移行しても問題なく稼働——性能を左右するのはコンテキスト
  • どの基盤モデル・構築手段（Claude Code / Grokボット / Hermes / OpenClaw等）でも適用可能
STACK 1/2

コールの実際の技術スタック:エージェントと記憶「スライド1枚に収まる」シンプル構成

  • エージェント: Claude Code（一時期はCodexで全面運用。ツール・LLMの切り替えは簡単だが頻繁には行わない）。モデルはHaiku／Sonnet／Opusを使い分け
  • 記憶（知識の保管庫）: Obsidian。知識ベース全体をPC上のMarkdownドキュメントとして扱い、デバイス間で同期。Notion等でも可
  • ナレッジベース: Karpathy氏のLLM Wikiのような形式で構築
  • 図解: ObsidianのExcalidrawプラグインを直接使用。図解もMarkdownとして保存され、エージェントが効率的に検索できる
記憶がMarkdown一式なので、エージェントがビジネスの核心的記憶も過去の会話もすべて効率よく検索できる。
STACK 2/2

デプロイ先と外部モデルクラウドVPS運用とOpenRouter活用

  • デプロイ: クラウド上のシンプルなVPS（DigitalOcean、月額約20ドル）。メモリボルトをローカルデバイスと同期。安価ならHostingerも推奨——何を使っても大きな違いはない
  • 目的: PCがオフでもスマホからリモートアクセス・チームとのコミュニケーション管理（Slack）を続けるため
  • 画像・その他モデル: OpenRouter経由で各種モデルのベンチマーク取得やサムネイル画像生成を実施
MEMO
初心者への注意: クラウドホスティングは必須ではないよ。ローカルで構築し始めたばかりなら、VPSのことは気にしなくてOK。「とにかくシンプルに保つ」が鉄則なんだ。
COMPONENT 1/4

① Context（文脈）——セカンドブレインの最重要パート「ビジネスを即座に把握している」と感じられること

コールの断言:コンテキストこそセカンドブレインで最も重要な部分。深く掘り下げなくても、今取り組んでいることや主要な目標を即座に理解できる状態を作るのが目標です。コンテキストがなければ、どれだけ賢くても「ただのチャットボット」です。

層1中核のMarkdownドキュメント
全セッションで必ず読み込ませる。ビジネスを完全把握させている最大の要因
層2ビジネス全体のナレッジベース
Karpathy氏のLLM Wiki形式で管理。必要に応じて検索させる知識の層
監査の一言新しいセッションを開いて「私のビジネスは何をしていて、誰が働いている?」と尋ねる。チームメイトのように答えられ、メモリーシステムを深く検索させなくて済むなら合格。
改善ループうまく把握してくれないと感じたら、その状況をそのまま伝えて「どうすれば改善できる?」と一緒に考える。セカンドブレイン自身を使ってセカンドブレインを改善する。
CONTEXT FILES

中核の3ファイル:soul / user / memoryあらゆるセッションの起点になる文書群

  • soul.md —— セカンドブレインの振る舞い・どう動いてほしいかを定義
  • user.md —— 自分と自分のビジネスを把握させる。核となる事柄をすべて記録
  • memory.md —— 知識ベースから重要と判断して抽出した記憶。ビジネスの主要な目的など、検索させずとも即座に知っておいてほしい事柄

これらは知識ベースの構造も定義しているため、これに基づいて効率的な検索も可能になります。

読み込みはClaude Codeの「フック」で自動化。会話を開始すると、CLAUDE.md的なグローバルルールとともにsoul.md・user.md・memory.mdが自動で読み込まれる。
CONTEXT KB

ナレッジベースの日次ログ運用会話をすべて資産に変える仕組み

  • セカンドブレインとの会話はすべて要約され、知識ベースの日次ログとして取り込まれる
  • 動画制作・協力企業・チームメンバー・オープンソースプロジェクトまで、ビジネスのあらゆる要素についてMarkdownドキュメントを作成
  • それらすべてが時間の経過とともに保存・維持され、日々のあらゆる作業の源泉になる
TEST
コンテキストの検証項目: ビジネスの核心について尋ねたとき、深い検索に頼らず正しい回答が返ってくるか。これができていなければ、コンテキストの渡し方を改善するサイン。
COMPONENT 2/4

② Connections（接続）——実際の作業場所で機能させる情報を引き出せるだけではなく、仕事をさせる

コンテキストだけでは「非常に賢いチャットボット」のまま。タスク管理との連携、メール返信の作成、Googleドライブへのファイルアップロードができて初めて、潜在能力を発揮します。

  • MCPサーバーがないツールは、独自のシンプルなCLIツールを自作——その構築もセカンドブレイン自身にやらせるので、専用コーディングエージェントは不要
CONNECTIONS CTRL

統合を「ラッパー」で包んで権限を細かく制御ツールごとにセカンドブレインが使える操作を決める

コールは各プラットフォーム接続に使うAPI・MCPサーバーすべてを包む小さなラッパーを作成。統合ごとに使用できるツールを正確に決定できるようにしています。

  • 例:メールのドラフト作成は任せるが、送信はさせない（送信前に自分で確認したい）
  • MCPサーバーを丸ごと取り込んでGmailの全機能を与えるのではなく、自分で細かく制御
  • 副次効果:スクリプトの決定論的な挙動がより確実になり、カスタマイズ性が非常に高くなる
TEST
接続の検証（月曜の朝テスト）: 「キャッチアップして」と依頼し、優先事項・返信が必要なメール・注意を向けるべき人々を素早く見つけ出せるかを確認。遅ければ不合格＝改善の余地あり。
COMPONENT 3/4

③ Capabilities（能力）——仕事のやり方をスキルとして定着させる毎回ゼロから考えさせる無駄をなくす

コンテキストと接続があっても、「私たちがどう仕事をしているか」を理解していなければ務まりません。そこでワークフローやスキルをセカンドブレインに定義し、委任できるようにします。

  • 動画編集や図解作成のたびに手順を毎回考えさせたくない——一度やり方を確立したらスキルとして定着
  • スキルを改善し時間が経つほど、セカンドブレインはより頼りになる
  • 「時間をかけて改善し節約時間を増やす」とは、主にスキルの追加・調整のこと。多くはMarkdown文書への指示出しなので、見直しも超簡単
セカンドブレインの大部分は実際にMarkdown文書で構成されている——だから時間をかけて変化させ続けるのがシンプル。
SKILL RULE

「3回ルール」とスキルのコレクション同じ説明を3回したらスキル化のサイン

コールの経験則:どんなに小さなプロセスでも3回以上説明していることに気づいたら、間違いなくスキルに変えるべき。

Before「このプロセスをやって、あれとこれとそれをして、この出力形式で出して」…を毎回説明
After/editvideo（動画編集）や/creatediagram（図解作成）と入力し、対象の動画や可視化したい内容といった追加文脈だけ渡す
  • 現在のコレクション:動画編集、図解作成、プレゼン資料作成、Webリサーチ、最新AIニュースのフィルタリング、コンテンツ台本、受信トレイ管理、人脈（つながり）の活用支援…
  • Context・Connections・Capabilitiesは相互に関連:コンテキストが接続を使うタイミングを理解し、スキルが接続を引き寄せる
EVALUATION SUITE

最重要テクニック:変更後の「評価スイート」で回帰を防ぐ動画内で最も重要とされる部分

大きな変更（業務の委任方法や使用LLMの変更）のたびに、セカンドブレインに任せている全タスクのリスト——動画編集、図解作成、台本作成の補助、毎日のニュース要約など——を評価スイートとして一括実行し、正常動作または改善を確認します。

例LLMをOpus 5→5.5に変更
変更のたびに、以前録画した3分程度の基本動画を動画編集スキルで編集させてみる
目的本番中の事故を防ぐ
システム変更のせいで実作業中に問題に直面したくない。成功に向けて毎回準備を整える
効果壊していないかを常時確認
「変更を加えたらシステムを壊したり悪化させていないか」を確かめる標準手段
用途が何であれ、この仕組みの導入を強く推奨——セカンドブレインの長期運用における保険。
COMPONENT 4/4

④ Cadence（リズム）——指示なしで自発的に働かせる信頼が育ってから自動化する、最後のC

セカンドブレインを進化させても、大半の作業は直接やり取りしての委任です。しかし信頼して任せられることが増えるにつれ、一部を自動化したくなる——それがCadenceです。

30分毎
ハートビート自動実行
VPS
クラウド上で常時稼働
30〜60分/日
メール返信ドラフトで節約
  • コールの実装は「ハートビート（Heartbeat）」と呼ぶ30分毎の自律実行。VPS上で動き、AsanaやGmailを確認して手を離せるタスクを自律的に発見
  • 最大の活用例:大量の受信メールへの返信ドラフトを自動作成
  • 順序が重要:能力を構築→一対一で使い込む→信頼できた時点で自動化。信頼できるようになって初めてCadenceが成立する
TEST
Cadenceの検証: 手動でうまく動くワークフローを1つだけスケジュール実行してみる。ただ黙々とやらせるのではなく、何をしたか・何に注意が必要かの要約を報告させること。コールのハートビートは30分おきにSlackへ簡潔に通知する。
ROADMAP

今日から始める構築ロードマップすべて一度に作る必要はない——積み重ねが効く

STEP 1Contextから着手
soul.md・user.mdといった中核ファイルを作り、そこからKarpathy氏のLLM Wikiのようなナレッジベースへ育てる
STEP 2Connectionsは最小で
最初に連携したいツール用のMCPサーバーをいくつか入れるだけで十分
STEP 3スキルを1〜2個
最も反復的な自動化したいタスクから。/editvideo のような形で定着させる
STEP 4Cadenceは最後
信頼性が高まってからハートビートを構築。まずはメール返信案の自動作成でもOK
  • まずは週に数時間節約できることから始めれば、自然と積み重なっていく
  • 改善はセカンドブレイン自身と一緒に——優先事項と任せたいタスクを一番把握しているのはセカンドブレイン自身
  • コールと同じシステムをそのまま構築したい人向けに、GitHubリポジトリを無料公開中（説明欄にリンク）。真似る必要はなく、インスピレーションを得るだけでもOK
重要なのは強固な基盤を築くこと、そして進化させる過程で定期的に見直すこと。新規にも既存にも、この「4つのC」は役立つ。
AUDIT CHECKLIST

既存セカンドブレインの「監査」チェックリスト4つのCそれぞれに対応する検証をまとめ

すでにセカンドブレインを持っている人は、以下4つの検証を定期的に回して、最大限に機能しているかを見直してください。

① Context:「私のビジネスは何・誰が働いている?」に深い検索なしでチームメイトのように答えられるか
② Connections:月曜の朝に「キャッチアップ」と依頼し、優先事項・要返信メール・要注意人物を素早く取り出せるか
③ Capabilities:毎週の仕事への短いリクエストで、確認のやり直しやプロセス再構築なしに成果物が出るか
④ Cadence:スケジュール実行したワークフローが、要求せずとも結果の要約を報告してくるか
不合格だったら?——その旨をセカンドブレインに伝えて、一緒に解決策を練ればいい。ありきたりに聞こえるが、本当にこれだけでうまくいく。
SPONSOR

スポンサー:Arcade——AIエージェント向けMCPランタイム本当の課題は「権限管理」

  • エージェントと実行システムの中間に位置し、各ユーザーが自分のアカウントでサインイン——エージェントはユーザー本人として行動し権限範囲を超えない
  • 認証情報はモデルに渡らず、ポリシーはモデル外で強制されるためプロンプトで回避されることもない
  • 8,000以上のツールを保有。全部を読み込むと最初のメッセージ前に175万トークン消費——そこで登場したツール推奨機能が、タスクに必要なツールだけを動的に提供
  • コールはClaude CodeのセッションからMCPサーバー経由で接続。無料で開始できクレジットカード不要
WATCH OUT

失敗パターンと注意点コールが見てきた「やりがちなミス」

  • 複雑にしすぎる——これが最大の失敗原因。コールの進化したシステムですら、今も「わずかなツール＋1つのMarkdownフォルダ」で構成
  • ツール・LLMの頻繁な切り替え——切り替え自体は簡単だが、頻繁に行うべきではない
  • モデル選びにこだわる——Codex→Kimi（K3.1）移行でも完璧に機能。重要なのはモデルではなくコンテキスト
  • 最初から高度な自律化を狙う——エージェントの自律性は最初から高める必要はない
