Claude Codeにタスクを渡して作業が始まった後、「そういえば伝え忘れた」を話しかけて追加したい——この体験を、音声対話をコーディングエージェントに接続するOSS「Qwen Audio Agent」で実現します。動画では小さなアプリを音声だけで構築し、その間ずっと会話を続けられるかを検証。さらに割り込み・要件変更・バグ報告・タスク停止という、より厳しいシーンにも挑戦します。

結論:音声が快適でも、変更が正しいかどうかは別問題。声で指示し、テキストと差分で確認する——この分担がちゃんと回るかが評価の軸になります。
WHAT IS

Qwen Audio Agent とは音声会話をPC上で動くエージェントにつなぐOSS

音声での会話を、パソコン上で実際に作業を行うエージェントへ接続するオープンソースのアプリケーションです。提供されるインターフェースは3種類あります。

  • ブラウザインターフェース — 今回の検証で使用。文字起こしとバックグラウンドタスクを画面で確認しながら話せる
  • ターミナルインターフェース — CUIで完結したい人向け
  • デスクトップアプリ — 浮き出る音声オーブ（orb）付き
動画の狙い:ブラウザUIなら会話の様子とタスクの状態を同時に見られるので、「何が起きているか」を理解しやすい、という理由で選ばれています。
ARCHITECTURE

2つのモデル接続とローカルゲートウェイ声の担当とコードの担当は別

🎤 音声フロントエンド会話の処理を担当。短い一般質問にはここだけで答えられる
🛠 Claude Codeプロジェクト内での実際の構築作業を担当

この2つをローカルゲートウェイが仲介し、タスクの結果を会話へ持ち帰ります。フロントエンドはバックエンドの作業中も話し続けられるのがポイント。「アプリを構築して」のような依頼はゲートウェイ経由でClaude Codeに渡り、雑談や軽い質問は音声モデルがそのまま答える——という切り分けです。

なおClaudeとの接続にはACP（Agent Client Protocol）のアダプタを使い、この統合は自分で書かず済みます（プロジェクトがインストールコマンドを用意）。

注意:Qwen Audio Agent経由で新しいエージェントのワークフローが開くだけで、別ターミナルで既に開いているClaudeのセッションを勝手に乗っ取ったりはしません。
SETUP 1

インストール（コマンドライン版）Node 24系 + npm 10以上を確認

まず対応バージョンのNode.jsを用意します。動画では24系（24.15以降）でnpm 10以上を使用。デスクトップインストーラーは独自のランタイムを同梱しますが、今回はCLIインストール＋ブラウザクライアントで進めます。

node --version # 24.15以上を確認 npm --version # npm 10以上 npm install -g qwen-audio-agent@2.0.1
SETUP 2

音声側の設定（DashScope）APIキーとリアルタイム音声モデル

インストール後、設定コマンドを実行すると編集すべき設定ファイルの場所が表示されます。既定ではホームディレクトリ配下の ~/.config/ 内にある config.env です。

  • 音声接続にはDashScopeを使用。プロバイダのコンソールでAPIキーを作成し、該当フィールドに設定（キーを画面に映さないこと）
  • リアルタイムプロバイダをDashScopeに設定し、音声モデルはqwen-audio-3.0-realtime-plusを指定
ポイント:本体はOSSでも、クラウド音声接続にはAPIアカウントが必要。Claudeの利用料も別途かかります。費用の話は最後のカードで改めて整理します。
SETUP 3

Claude Code 側の準備単体で動くことを先に確認

1ClaudeコンポーネントのインストールClaude用のセットアップコマンドで不足部分とACPアダプタを導入。既存のClaude Codeがあれば再利用される
2Claude単体でサインインターミナルでClaudeを開き、普段の方法でログインまたはAPIアクセスを設定
3小さなリクエストを試す音声UI経由で全部デバッグする前に、単体で動作確認を済ませる
4バックエンド指定でセットアップ実行統合コンポーネントの検査。ただしこれはアカウントの割り当て（クォータ）があることの証明ではない
SETUP 4

ワークスペースの罠ターミナルを開いた場所 ≠ エージェントの作業場所

プロジェクト用に専用フォルダ（動画では voice-code-demo）を作り、ワークスペース設定にその絶対パスを指定します。

ここ重要:フォルダ内でターミナルを開いても、それがエージェントのワークスペースになるとは限りません。アプリには既定のワークスペースがあり、さらにClaude用の設定が一般設定を上書きできます。実際に設定されたパスを必ず確認しましょう。
SETUP 5

起動と初回チェックゲートウェイとブラウザUIは別ターミナルで

1ゲートウェイを起動ターミナルを1つ占有。開いたまま維持
2Web UIを起動別ターミナルで実行。既定のローカルアドレスはポート3101
3マイク許可と接続確認マイクアクセスを許可し、ゲートウェイと音声接続が「接続済み」になっているか確認
体験談:最初のテストはヘッドフォン推奨。スピーカーだとマイクがアシスタント自身の声を拾い続けてしまいます。
CHECK

まず最小の動作確認文字起こしの品質が後続の精度を決める

「英語で話して。短く答えて、聞こえていると伝えて」と声をかけ、返答と文字起こしの両方を確認します。画面上の文字が間違っていると、コーディングエージェントが誤った依頼を受け取る恐れがあります。

✅ 文字はあるのに音が聞こえないバックエンド設定を変える前に、出力デバイスとブラウザの音声を確認
✅ Claudeへの接続確認設定されたプロジェクトフォルダを調査させ、絶対パスとファイル一覧を変更なしで報告させる。実タスクが発生し、パスの食い違いを早期に発見できる
DEMO

お題：Issueトラッカー「VoiceDesk」を音声で構築あえて検証しやすい小ささに抑える

メインのデモでは、素のHTML・CSS・JavaScriptだけで作る小型のIssueトラッカーを音声指示で構築します。要件は——

  • Issueの一覧、追加フォーム、完了状態、フィルタを備える
  • データはローカルストレージに保存し、ページ再読み込み後も残る
  • 基本バリデーション付き。変更はすべてこのプロジェクト内に収める
なぜ小さくする?巨大アプリだと音声での修正が正しい場所に届いたか判断不能になるから。 点検しやすい規模が検証には最適です。
KEY FEATURE

ビルド中に会話が続くこれがこの仕組みの核心

構築タスクの実行中に、まったく別の質問を投げます。
「このアプリのローカルストレージの役割と、再読み込みでIssueが消えるかどうかを説明して。構築は続けたままで」

音声アシスタントがその質問に答えながら、Claudeのビルドが止まらず進行すれば成功です。タスクビューを会話の横に表示して両方の状態を目で確認します。

誤解しがち:これでClaudeが急に速くコードを書くようにはなりません。待ち時間を要件の整理や軽い質問に使えるようになる、という話です。
CONTROL

割り込みと要件変更：作業中の声の届け方声を止める ≠ タスクを止める

割り込み:説明の読み上げ中に「もっと短く。一文で説明して、構築は続行して」と割り込みます。古い音声がどれだけ速く止まるか（等速再生のまま確認し応答時間を見る）、新しい文が正しく認識され実際に短く答えるかを確認。

重要な区別:読み上げへの割り込みは、バックエンドが受け付け済みのタスクを自動でキャンセルしない。「説明を止めてほしいだけど、依頼した作業は続けて」ができるのはこのためです。

要件変更:ビルド実行中に同じVoiceDeskプロジェクトへ「最終デザインをライトテーマに変更し、New IssueボタンをCreate Issueにリネーム。他の要件は維持し、この指示がキューなのか適用中なのか教えて」と依頼します。追加指示は受け付けられる。問題はClaudeがいつ受け取り、いつファイルへ届くかです。現行の作業ターンを即座に変えるのではなく、後続作業として処理されることがあります。

検証のこつ:口頭での受領確認＝アプリ更新の証明ではありません。元の構築が先に終わって構わないので、両方完了後に最終アプリを調査します。
VERIFY

成果物は必ず自分で確認完了報告の声はスタート地点

ローカル起動手順はテキストで出力させ（長いコマンドを読み上げで聞くのは不向き）、アプリを開いて確認します。

1要件どおりか見た目を確認ライトテーマ、Create Issueボタン、Issue管理の動作
2実操作で試す「モバイルメニューを修正」等のIssueを追加→1つ完了にする→完了フィルタのオンオフ
3再読み込みで永続化を確認保存したIssueが残っているか
差し戻し例:ボタンがまだNew Issueのままなら「見えているラベルだけCreate Issueに変えて、動作はそのまま」と絞った修正を依頼。問題を見ながら声で説明できるのが音声の強みです。
DEBUG

バグ報告の実演：空白だけのタイトル観測可能な条件で依頼する

Create Issueを開き、タイトル欄に空白のみ入力して送信。拒否されれば検証合格、空白のIssueができたらうってつけのバグ報告になります。報告の内容は——

  • VoiceDeskのタイトル検証を確認。空白のみのタイトルは拒否必須
  • 現行コードがどう扱っているか説明し、回帰チェック（リグレッションテスト）を追加、失敗すれば修正
  • 通常のタイトルと既存の保存済みIssueは保持
役割分担:「元テキストの長さチェックでも空白混じりは通るのでは?」と音声で考えを聞き、Claudeが実装を調査する。一般論の説明は、このアプリの実際の動作の証明にはなりません。コードとテスト結果が必要です。
STOP

タスクの止め方キャンセル申請とキャンセル完了は別イベント

最後の検証はバックエンドの停止。読み取り専用のタスク（VoiceDeskのアクセシビリティレビューを、編集・追加インストールなしで準備）を実行し、動き出したら「アクセシビリティレビューをキャンセルして」と依頼します。複数タスクが動く場合はカードで特定します。

⚠ レビューが先に終わった場合キャンセルが動いているタスクを止めた実証にはならない
⚠ キャンセルは巻き戻さない既に行われた編集は残る。だからこそ読み取り専用で試し、編集タスク停止後は差分を確認
混同注意:マイクのミュートや会話を閉じるのはまた別の操作で、バックグラウンドの作業は続行し得る。「作業を止める」が意図ならタスクのキャンセル操作を使います。
COST

費用の仕組み：利用は2系統オープンソース ≠ 無料

🎤 音声フロントエンドDashScopeが会話を処理。モデルと地域の現在の価格を確認
🛠 Claude Code設定したアカウントまたはAPIでコーディング作業が課金。追加の後続タスクもバックエンド利用を増やす
  • コスト比較には同じセッションの両側を記録すると比較しやすい
  • 長い説明が不要なら読み上げを短く依頼し、詳細はテキスト・要点だけ音声にすると効く
  • 音声のローカルフロントエンドという選択肢もあるが、モデルとハードウェアの用意が必要。なお音声をローカルにしてもクラウドのClaudeがローカルになるわけではない
TROUBLESHOOT

故障時は「壊れた部分」から調べる設定変更後はゲートウェイを再起動

1文字起こしが出ないマイク入力か音声接続側の問題を疑う
2会話は普通なのにコーディングタスクが失敗バックエンドのインストール・認証・モデルアクセス・クォータ側を疑う
3設定を変えたら再起動ファイルを編集しても実行中の接続は変わらない。停止して再実行
4まず1プロジェクト・1タスクで安定してから他のクライアントやエージェントへ拡張。修正がどのタスクへのものか分かりやすくなる
VERDICT

評価のまとめ：声とキーボードの使い分け判断基準はたった4つの問い

✅ 声が向く場面機能について話し合う／作業中に質問する／アプリを見ながらバグを描写する
⌨ キーボードが向く場面正確なパス・コード・エラー文。レビュー時はアプリと差分を目前に

最終判断はこの4問に集約されます——①話した依頼を理解したか ②バックエンド作業中も会話が続いたか ③追加指示はプロジェクトに届いたか ④完成したアプリは検査を通ったか。音声の快適さと、変更の正しさは別の軸で評価する必要があります。

動画の一言:全体としてはかなり良い（pretty cool）。日常の開発組み入れを考えるなら、まずこのワークフロー一式を自分で試してから判断するのがおすすめです。
