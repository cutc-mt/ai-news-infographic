なぜAIエージェントはSupabaseを選ぶのか —— $0から評価額$10Bへの6年間と「エージェントがユーザーになる時代」

OSSのPostgresプラットフォームとして急成長するSupabaseの共同創業者、Paul Copplestone（CEO）とAnt Wilson（CTO）が、swyxのインタビュー番組Latent Spaceに初の共同出演。コロナ禍にFirebase代替として始まったサービスが、AIが作るアプリケーションの推奨バックエンドになるまでの軌跡を、技術・マーケティング・組織の側面から語り尽くします。本エピソード（1時間16分）の内容を18枚のカードに整理しました。

THEME

エージェントがユーザーになる「なぜAIはSupabaseを選ぶのか」

LLMベースのコーディングエージェントがアプリを生成する時代、そのバックエンド選定もエージェントが行うようになりました。エピソードの中心テーマは「エージェントがなぜSupabaseを好むのか」「ユーザーがエージェントに変わるとき、開発体験・ドキュメント・API設計はどう変わるべきか」です。

  • 自然言語で操作できる宣言的で一貫性のあるインターフェースが好まれる
  • ドキュメントやSDKがそのままエージェントの「教材」になる
  • SupabaseはAI構築アプリの推奨バックエンドという地位を確立
COMPUTE

データベースの隣にコンピュートを long-running compute の思想

Supabaseが進める「Compute beside the database」構想。エージェントが作るアプリは長時間動く処理（long-running compute）を必要とするケースが多く、DBの隣にコンピュートを置くことでレイテンシとデータ転送を削減します。

従来別コンテナで実行アプリサーバーとDBが離れた構成
これからDB横で実行Supabase Compute／ビルドからコードへ

「コードからビルドする（Build from code）」体験と合わせ、AIが生成したコードをそのまま近場で動かす流れが説明されます。

SCHEMA

宣言的スキーマ（Declarative Schemas）pg-delta とエージェント時代のマイグレーション

Supabaseの「Declarative Schemas 2.0（pg-delta）」も話題に。望む状態を宣言すれば差分（delta）が自動生成される宣言的なスキーマ管理は、人間だけでなくエージェントにとっても扱いやすいインターフェースです。

  • 「こうありたい」を書けばマイグレーションが導かれる
  • 手書きSQLの競合・衝突を減らす
  • エージェントによるDB変更をレビュー可能な形に落とし込める
ENGINE

OrioleDB と MultigresPostgres自体を進化させる2つの賭け

Supabaseの技術的な柱の一つがPostgresストレージエンジンの進化です。OrioleDBは新しいストレージエンジン、MultigresはPostgresのマルチプロセス／スケールアウト化を目指す野心的なプロジェクト。

  • スケールアップの限界を、ストレージレイヤーから突破する
  • OrioleDB由来のアイデアをOSS Postgresに還元
  • 「Postgresの信頼性を保ったまま限界を引き上げる」方向性
SCALE

スケールアップ・スケールアウトとTurso獲得SQLiteベースの分散DBを傘下に

縦方向（スケールアップ）と横方向（スケールアウト）の両面から議論が展開。注目はTursoの買収で、SQLite/libSQLベースの分散データベース技術がSupabaseのポートフォリオに加わりました。

LAUNCH

Supabase Select の発表Build anything / Operate with confidence / Scale without limits

エピソードの公開と同時に出た「Supabase Select」は3本柱で構成されます。

1Build anythingコードからのビルドとSupabase Compute
2Operate with confidence自分のエージェントで運用する
3Scale without limitsMultigresとOrioleDBで無限にスケール

まさにこのエピソードは、Select発表を共同創業者自身が語る公式トークと言えます。

POSTMORTEM

ローンチと移行 — 失敗を振り返るAlpha launch postmortem の文化

成長の一側面として語られるのがローンチ時の障害と移行の失敗談。Supabaseは「alpha launch postmortem（検証）」を公開する文化を持ち、何が起き、どう直したかを率直に共有します。

  • 障害の振り返りをブログとして公開する透明性
  • 大規模移行（migration）を安全にする仕組みづくりの動機
  • 信頼は宣言ではなく失敗の見せ方で築く、という開発者向け姿勢
VECTOR

ベクター、成長、AIレコメンドpgvectorで組むAI時代のデータ層

「Vectors, growth, and AI recommendations」の章では、Postgres上でベクトル検索（pgvector）を完結させる価値が議論されます。RAGやレコメンドエンジンを専用DBに分離せず、Postgres一つで賄えるシンプルさが成長を支えています。

  • 埋め込み（ベクトル）と通常データを同じDBで管理
  • AIレコメンドの実例と成長データの話
  • 「DBを増やさない」運用のシンプルさがエージェントにも好まれる
MARKETING

開発者マーケティングとミームLOLファーストで広まったブランド

Supabaseの成長を語る上で外せないのが開発者コミュニティ向けマーケティング。ミーム（開発者ネタ画像）を積極的に使うSNS運用は、巨大企業には真似できない速度と親しみやすさで認知を拡大しました。

ミーム
開発者の共感を得る投稿文化
コミュニティ
コミュニティ主導のディストリビューション

広告ではなく「開発者が共有したくなるもの」を作る——それが community-led distribution の核心です。

SALES

プロダクト主導営業とエンタープライズ成長Product-led sales への進化

個人開発者が無料で始め、気づいたら会社全体が使っている——その導入経路をビジネスに変えるProduct-led sales（PLS）についても言及されます。

  • セルフサーブの利用データから営業機会を見つける
  • ボトムアップでの採用がエンタープライズ契約に発展
  • オープンソース + クラウド課金のモデルと親和性が高い
MIGRATION

ライブマイグレーションとアナリティクス止めない移行・追える運用

「Live migrations and analytics」の章では、サービスを止めずに他DBからSupabaseへ移行するライブマイグレーションと、運用データを見るためのアナリティクス機能が話題に。移行コストの壁を下げることが、成長の加速装置になっています。

MEMO
読み解き:エージェント時代は「新規作成」だけでなく既存システムの持ち込みも自動化される——移行体験の良さがそのまま選定理由になります。
LOCAL DEV

エージェント前提のローカル開発Agent-ready local development

「Agent-ready local development」では、ローカル環境とクラウドの一貫性が議論されます。CLIで立ち上げたローカルPostgresと本番環境の差を最小化することで、エージェントがローカルで試した操作をそのまま本番へ持っていけます。

  • ローカル＝本番の再現性がエージェントの精度を上げる
  • 宣言的スキーマとの組み合わせで差分管理が容易
  • 開発体験（DX）そのものがエージェント体験（AX）に
REMOTE

6年で$0から評価額$10Bへ。資金面ではSeries Fラウンドが公表されており、完全リモート組織・OSSコアというあり方を維持したまま成長を続けています。

WORKFLOW

コミュニティと会社のワークフローCommunity and company workflows

エピソード末尾では、コミュニティとの向き合い方と社内の仕事の進め方が語られます。OSSへの貢献者・evangelist・ユーザー参加型の開発、リモート組織ならではの非同期ワークフローなど、「Supabaseらしさ」の組織面が見どころです。

  • 世界中に散るメンバーを束ねる非同期文化
