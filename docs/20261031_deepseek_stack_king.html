DeepSeek Stack — DS 4.1 Flash を Opus 並みの仕事ぶりにする29スキル pack 全解説

出典: YouTube「AI Code King」 / 2026年10月31日公開

DeepSeek v4.1 Flash は日常コーディングの主力だが、素の状態では Opus 5.5 の約60%の質。悪いのはモデルの賢さではなく「習慣」であり、テキストファイルで直せる。29個の MIT ライセンス・スキル群「DeepSeek Stack」でその差を埋める方法を整理する。

1

問題意識 — 80% は無料では来ない

DeepSeek v4.1 Flash は著者の日常業務で Opus 5.5 の約80%をこなす。しかし導入当初は60%程度だった。原因は「計画なしにコードへ突入」「テストを走らせず fixed と宣言」「同じ壊れた案を4連続で微修正」など習慣の問題だった。

2

解決原理 — テキストファイルで直せる

モデルを賢くはできないが、計画させる・作業を確認させる・詰まったら止めることは指示で可能。これで差の大部分が埋まる。流行のスキルパックから安価なモデルに効く考え方を抜粋し、特定ツール依存を排除して短く書き直したのが本パック。

3

価格 — 桁違いのコスト差

Opus 5.5 は入力 $4/百万トークン・出力 $20。対して v4.1 Flash はオフピークで入力 $0.15・出力 $0.60、キャッシュ入力は約0.3セント。ピーク時で2倍でも入力13倍以上・出力16倍以上安い。「トークンを節約する」から「トークンを品質に使う」発想へ転換できる。

4

導入 — 1コマンド

プロジェクトフォルダで npx skills add .../ds-stack を実行。使用エージェント(Claude Code / Codex / Klein / OpenCode 等)を選ぶだけ。全プロジェクトに入れるなら -g フラグ、個別スキルなら --skill ds-verify-loop のように指定。スキルはすべてds 接頭辞で衝突しない。

5

実行環境 — Pandaode + DSH

デスクトップアプリ Pandaode は複数コーディングエージェントを1ウィンドウで実行でき、DeepSeek 純正ハーネス DSH に直接対応。npm install -g でDSHを入れ、設定に API キーを貼るだけ。モデルは v4.1 Flash を選び、thinking effort を max に。ここを省くとスコアが約30ポイント低下する。

6

Klein Pass — 月 $9.99 のレビュー要員

Klein Pass には DeepSeek v4.1 Flash / Kimi K3.1 Pro / GLM 5.3 / MiniMax M3.1 Flash / Qwen 3.8 Max 等のオープンモデルが寛大な上限付きで含まれる。DeepSeek を主担当に、レビューだけ別モデルの Klein ワーカーへ投げる構成が強力。

7

Core: ds-mode — 常時オンの作法

1つだけ入れるならこれ。行動前にタスクを一行で言い換え、編集前にコードを読み、最小の変更を行い、変更ごとに実際のコマンドを実行し、出力を同じメッセージに貼るまで「完了」と言わない。同じ修正が2回失敗したら3回目を試さず停止するルール付き。

8

Core: ds-principles / ds-help

ds-principles は「根本原因を直せ」「足す前に削れ」「境界で検証し」「内部ではなくユーザーに見えるものをテストせよ」など21の工学ルール集。頻繁に直接呼ぶものではなく他スキルから参照される。ds-help は課題を記述すると適切なスキルを選んで理由まで教えてくれる案内役。

9

Loop: ds-plan-loop — 計画を新鮮な目で

複数ファイルに触るタスク用。番号付き計画を書き、各ステップに「成功証拠」のチェックを定義。その後別パスで自分の計画をレビューし、抜け・危険な前提・より単純な方法を修正してから実装に入る。設定ページ追加の例では「初回読み込み前の処理忘れ」をレビューが捕捉。

10

Loop: ds-verify-loop — 「直った」の嘘を止める

編集→実チェック実行→実エラーを読む→根本原因→修正→再実行を最大5周で停止し報告。最終の成功出力の貼付が必須で、テストを弱めたり飛ばしたりして通すことを禁止。著者が最も使うスキルで、fake confidence の大半を防ぐ。

11

Loop: ds-unstick / ds-context-reset

ds-unstick は同じエラーが2回再発したら編集を止め、失敗した修正群の共通前提を書き出して直接検証。前提が正しければ3つの別アプローチを提示して新規状態から再開。ds-context-reset は progress.md(目的・完了済みと証拠・次の作業・重要事実)を更新し、文脈が長くなったらその1ファイルだけ読む新品セッションへ移行。

12

Loop: ds-ledger / ds-review-loop / ds-jury

ds-ledger は監視しない長時間実行向けに、意思決定ごとに「何を・なぜ・証拠」を1行記録し各ステップ前に読み直してゴールからの逸脱を防止。ds-review-loop は別文脈のレビュアーと最大4往復。ds-jury は2〜3モデルのレビューを一致するまでループ(ここで Klein Pass の別モデルが活きる)。

13

Loop: ds-best-of-n / ds-swarm

ds-best-of-n は同一タスクを3〜5並列で実行し最強を土台に他の良さを移植。Opus で5試行は痛いが、DeepSeek なら5試行しても Opus 1回より安い。ds-swarm は API 全ルート監査など広い作業を並列ワーカーに分割し、証拠付きの1つのレポートに統合。

14

Build: sharpen / blueprint / tdd / blast-radius

ds-sharpen は曖昧なタスクを「より深く」再定義し計画の弱点を事前攻撃。ds-blueprint は型・関数シグネチャ・モジュール構成を先に設計して合意後に実装。ds-tdd は正しい理由で失敗するテストを先に書く。ds-blast-radius は差分の外(他の呼び出し元・設定・保存データ)への影響を実コードで証明。

15

Design: ds-design — 禁止デフォルト制

コード前に目的・聴衆・トーン・「残すべき1点」を書くデザイン方針を作り、「どの類似依頼でも同じ計画になるなら変える」と自問。紫→青グラデ、Inter 表示フォント、絵文字アイコン、中央ヒーロー+同一3カードを禁止デフォルトとして排除。デスクトップ/モバイル両サイズのスクリーンショットで確認・修正する。

16

Design: ds-design-audit — 既存 UI の採点

両サイズのスクリーンショットを取り、階層・タイポグラフィ・色・間隔・状態・アクセシビリティ・コピーを証拠付きでスコア化。上位3〜5個の問題を修正し、再撮影して比較。コーヒー焙煎業者のランディング例では、テンプレから脱した紙テクスチャ+セリフ体+焙煎状態軸のレイアウトを出力。

17

Ship: PR の自動化 — 誰も見ていなくても

ds-pr は変更ファイル羅列ではなく問題から始まる短いPR。ds-watch-pr は CI とレビューボットを監視し、本物の指摘を直してマージ準備完了まで追従。ds-ship はレビュー→PR→監視→オールグリーンでのマージまで無人完結(管理者バイパス禁止、不可逆操作前は必ず確認)。他に ds-ready(最終マージは人間)/ ds-adopt / ds-revive / ds-comments。

18

Understand と結論 — 正直な限界

ds-explain / ds-catchup / ds-lessons / ds-onslop で理解と振り返りを自動化(繰り返す失敗をリントやテスト化、AI くさい文を除去)。ただし広大なコードの深いデバッグや創造力勝負では今なお Opus が勝つ。80%は著者の体感でありベンチではない。コードは DeepSeek サーバーへ行く点、大型ジョブは半額のオフピークに実行する点にも注意。
