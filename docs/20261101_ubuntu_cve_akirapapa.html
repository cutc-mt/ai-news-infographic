04

そもそもUbuntuとは?「ホテル」に例えると分かりやすい

UbuntuはLinuxをすぐ使える形にまとめて配っているOSです。動画では1つのホテルに例えて解説されます。

  • 客室 = ブラウザーやサーバーのアプリ
  • 建物の土台とフロントの仕組み = カーネル(OSのいちばん中心)
  • カーネルはメモリーやファイルの管理+インターネットからの接続の受付を担当
🌿
よもぎ
今回の脆弱性は、まさにこの「フロント(接続受付)」で見つかったんです。
05

Ubuntuを作っているのはCanonical社

  • マーク・シャトルワースさんがDebianの開発者たちと立ち上げた会社
  • 「Ubuntu」は他者への思いやりを意味するアフリカの古い言葉
  • 最初の版は2004年10月。以降、半年に1度決まった時期に新しい版をリリース
🌿
よもぎ
名前の意味が「思いやり」ってステキですね。配布の仕組みも含めて、今回は「配っている会社ごとに修正の届くタイミングが違う」ことがポイントになります。
06

バージョン番号のルールは「都市と月」

  • 24.04 = 2024年4月版、26.04 = 2026年4月版(最新のLTS)
  • 長期サポート版 LTS は2年に1度・4月リリース
  • 標準5年+延長サポートで最長15年サポートが続く
🌿
よもぎ
この番号の読み方、この後の「影響あり/なし」の表を読むのに必須ですよ!
07

接続はTCPの「3回のやり取り」で始まる

インターネットで接続を始める時、TCPという約束事で3回やり取り(3ウェイハンドシェイク)します。ホテルに例えると…

  1. お客さんがベルを鳴らして「入っていいですか?」
  2. フロントが「どうぞ」と札を返す
  3. お客さんが「分かりました」と答えて接続成立

この間、フロントは「受付表」を作って待っています。

🌿
よもぎ
受付表には、お客さんから届いた細かい注文のメモがついていることがあります。これが「IPオプション」と呼ばれる情報です。
08

問題の発端:受付表のメモは「コピーせず」客室へ渡っていた

接続が成立するとお客さんは客室へ。この時、受付表のメモ(IPオプション)はコピーせずにそのまま客室へ渡されていました。ここが今回の出発点です。

同じ頃、もう1人のフロント係が、同じお客さんから再度鳴ったベルへの返事を書こうとして同じメモを読みに来ることがあります。

🌿
よもぎ
その間に客室が片付けられると、メモはすぐにシュレッダーへ…そしてもう1人の係は「捨てられた後の紙」を読んでしまう。これが脆弱性の正体です。
09

正体は「解放後使用(Use-After-Free)」

解放後使用(UAF)とは、片付けたはずのメモリを別の処理が使ってしまう不具合。パソコンの中では2つのCPUが同時に動く時に起きます。

  • IPv6の接続はメモをコピーして渡しているため、最初の問題の影響を受けない
  • 受付表を別の受付へ移し替える機能にも似た問題があったが、同じ方法で修正済み
🌿
よもぎ
「2人が同じ瞬間に同じメモを触った時だけ起きる」タイミング依存の問題、というのが後の危険度評価にも効いてきます。
10

直し方はシンプル「読む人がいなくなるのを待ってから捨てる」

メモを捨てる時、すぐシュレッダーにかけず回収箱へ入れる。読んでいる人が誰もいなくなるのを待ってから捨てる——カーネルの他の場所では元々この捨て方をしていました。

この2箇所だけすぐ捨てていたのが問題。修正はその2箇所を他と揃えるものです。

🌿
よもぎ
判定① 今回の正体は「接続の受付で捨てたメモを別の処理が読んでしまう不具合」。直し方は「読む人がいなくなってから捨てる」です。

どれくらい危ない? 点数は「出すところによって違う」

評価元スコア/見解
Ubuntu公式ページ(基本値)9.8
同じページの診断(新しい計算方法)8.3
SUSE8.1(攻撃は難しい)
Red Hat最も急ぐ「緊急(Critical)」扱い

同じ脆弱性でも、見る角度で数字が変わります。

🌿
よもぎ
共通しているのは「インターネット越しに、ログインも操作もなしに届くかもしれない」という点。だから外に公開しているサーバーほど関係があります。
12

悪用の報告は現時点でなし(セキュリティ会社の情報)

  • 公開された攻撃コードは見つかっていない
  • 実際に悪用されたという報告もない
  • ただし「まだない」は「これからもない」ではない

安心しきらず、慌てすぎず。点数ではなく「自分に当てはまるか」「修正が届いたか」で判断しましょう。

🌿
よもぎ
判定② 点数は割れているが、インターネット越しに届くかもしれない優先度の問題。公開サーバーほど早めに確かめる価値あり、です。

Ubuntuの今の状況:公式ページの表(10月30日時点)

バージョン状況補足
22.04 〜 26.10影響あり・修正作業中修正版リリース待ち(表中の番号は修正準備中の版)
20.04 / 18.04 / 16.04影響あり標準サポート終了。修正受け取りには Ubuntu Pro(ESM) が必要
14.04(標準カーネル)影響なし標準サポート外のため該当せず
AWS / Azure / Google Cloud 向けカーネル同様に並ぶクラウドのサーバーも同じく対象

Ubuntu Pro は個人なら5台まで無料。古い版を使い続けている人は、Proを有効化するか新しいLTSへ移るかの判断タイミング。同じLinuxカーネルを使うDebianはすでに修正版をリリース済み——配っている会社ごとに届くタイミングが違います。

🌿
よもぎ
判定③ 「治りました」の表示が出るまで、公式ページ(ubuntu.com/security/CVE-2026-98432)を直接確認しましょう!
14

手順① 自分のUbuntuの版とカーネルを知る

まず現状把握です。

lsb_release -a でUbuntuの版、uname -r で今動いているカーネルの番号を確認。

uname の番号は必ずメモしてください。

最後に「この番号が変わったかどうか」で本当に治ったかを確かめます。

🌿
よもぎ
完了判定の基準になる大事な数字です。動画内でちゃんと実演されていますよ。
15

手順② 脆弱性の状況を確認 → 手順③ 更新

  • Ubuntu Proの道具が入っていれば、CVE番号を指定して実行。まだ修正がなければ「まだ直せない」と表示される
  • 修正版が出たら sudo apt update → sudo apt upgrade
  • 部品を1つずつ選ばずまとめて更新するのが公式のおすすめ
🌿
よもぎ
更新が終わったら、/var/run/reboot-required というファイルがあれば「再起動が必要」の印です。
16

手順④ 再起動して uname -r で確認——ここが一番大事

新しいカーネルが入っても、再起動するまで古いカーネルが動き続けます。フロント係の手順書を差し替えても、交代するまでは古い手順のまま、というのと同じです。

再起動後にもう1度 uname -r。最初にメモした番号が新しい番号に変わっていれば初めて完了です。「入った」と「動いている」は別物。

🌿
よもぎ
自動更新で新しいカーネルが「入ってるだけ」の状態はよくある落とし穴。必ず再起動までやり切ります!
17

コンテナと回避策の注意点

  • Dockerなどのコンテナは同じ建物の別の部屋。土台のカーネルはホストと共有 → コンテナの中を更新してもカーネルは治らない。直すのはホスト側
  • ネットで「ある設定を0にすれば防げる」という話も見かけるが、説明でも差し替えの道を減らすだけで普通の道は残るとされている
  • 根本の対策はカーネルの更新と再起動だけ。設定でごまかさず修正版を入れる
🌿
よもぎ
判定④ 手順は4つ:①版とカーネルを知る ②状況を確かめる ③修正が出たら更新して再起動 ④uname -rで新カーネルを確認。
18 結論

「Ubuntuを使っている自分は、今何をすればいいのか?」— あきらパパさんの答え

今のUbuntuの版とカーネル番号(uname -r)を控えて、修正版のリリースを待つ

修正版が届いたら apt update / apt upgrade でまとめて更新

再起動まで実行する(再起動しないと古いカーネルのまま)

uname -r の番号が変わったことを自分の目で確かめる —「更新した」で終わらせない
