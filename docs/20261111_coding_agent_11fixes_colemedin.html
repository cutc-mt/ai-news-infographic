私たちは「ハーネスのエンジニア」

ENGINEERS OF THE HARNESS

AIコーディング時代の開発者の仕事は、エージェントを自分のコードベースで成功させる「ハーネス（AIレイヤー）」の設計に移った。11の悩みはどれも、skills・rules・hooksを自分専用に調整すれば、手軽な修正で9割方まで解決できる。複雑な大掛かりな解決の前に、まず効果抜群のシンプルな修正を実装しよう。

AIレイヤー調整 / 小さな修正×大きな効果

02

解決はいつも同じ3ステップ

THE RECIPE: DESCRIBE → SUGGEST → ADJUST

①エージェントに問題を言葉で説明する（「完了って言うけど隙間があるんだよね」）②解決案を提案する（もしくはエージェントに聞く）③skills・rules・hooksのどこに実装するか一緒に決めて、変更内容を確認・承認して完了。すべての修正がこの会話フローで進む。自分のビルドに合わせたカスタマイズがポイント。

対話で改良 / 変更は必ず自分で承認
エージェントと相談してハーネスを育てるの、なんか相棒とペアプロみたいで楽しそう！
03

#1 完成したと言うのに完成していない

DONE WHEN IT ISN'T

最も普遍的な悩み。実装を受け取ると「完全に構築・テスト済み」と言ったのに穴だらけ。解決策はエージェントと「悪魔の代弁者」を演じること。実装後に「これが動かなくなる要因は？依頼とのギャップは？」と問えば、エージェントは穴を特定するのが得意。さらに別エージェントに渡す reviewer スキルを作り、新しい目で批評させると効果が定まる。

悪魔の代弁者 / reviewerスキルで二重チェック
「本当に動く？」って聞き返すだけで穴がポロポロ出てくるの、地味に衝撃だった…！
04

#2 動作を何も証明しない

NEVER PROVES ANYTHING WORKS

標準では「10個中10個のテストが通りました」のような要約だけ。必要なのは本当のコマンドとその出力、アプリのスクリーンショットといった「証拠」。agent browser CLI で実際に機能を操作し、スクリーンショットをプルリクエスト本文に添付させよう。計画スキルに「実装前に集めるテスト成果物を決めさせる」の一手で、証拠付きの納品が常態化する。

テスト証拠の添付 / 計画段階で収集を明記
スクショ付きで納品してくれると、エージェントがほんとの同僚に感じるんだよね〜◎
05

#3 テストは通るのにアプリが壊れる

TESTS PASS BUT APP BROKEN

エージェントの自己採点テストは全部合格なのに、アプリを開くと壊れている。原因は「ユーザーと同じ使い方」でテストしていないこと。単体・結合テストだけでは足りず、ブラウザ自動化でボタンを実際にクリックし入力する検証が必要。計画スキルに検証計画を追加するか、「try it」スキルを作ってユーザー視点の操作テストを義務づけよう。

ユーザー視点の検証 / 検証は最弱点
自己採点で満点取るのズルいんだよ！ユーザーになりきって操作させるのが正解☆
06

#4 ルールを無視し続ける

IGNORING RULES

rules や skills は自然語の指示なので確率的で、無視されるリスクが常にある。対して hooks は唯一の「保証」：ツール呼び出し時や会話開始時に必ず走るコードで、.env の読み込みを機械的にブロックできる。「絶対に〜するな」「AならBせよ」の形のルールはすべて hooks に移行しよう。CLAUDE.md をエージェントに読ませて hook 化できる箇所を抽出してもらえる。

hooksで保証 / .env保護・bun強制など
「お願い」じゃなくて「仕組み」で縛るのが本当のガードレールなんだね、納得！
07

AIレイヤーの使い分けの掟

FACTS→RULES / PROCESS→HOOKS / WORKFLOW→SKILLS

何をどこに入れるかの判断基準：制約・規約といった「事実」は rules、絶対に守らせたい「プロセス・手順」は hooks、エージェントに段階的に案内したい「大きなワークフロー」は skills に入れる。この3つを使い分けるだけでAIレイヤーが整理され、ルール肥大化と無視問題の両方に効く。迷ったらこの分類に照らしてみよう。

3層の住み分け / 整理の基本原則
どこに書けばいいか毎回迷ってたけど、この軸があれば一発で決まるね！
08

#5 ルールを増やすほど結果が悪化

MORE RULES, WORSE RESULTS

CLAUDE.md や AGENTS.md のようなグローバルルールが肥大すると、エージェントが見落とす確率が上がる。LLMが高性能になるほど、昔必要だった記述は不要になっている。解決策はコンテキストの瘦身：残す・消す・hooks に移すを見極め、性能が落ちないか検証しながら削る。Cole の「ablate AI layer」スキルがこの全工程をガイドしてくれる。定期的なメンテが必須。

コンテキスト瘦身 / ablateスキルで検証
ルールは多いほど安心…じゃなかった！びっくり。たま断捨離が大事なんだ〜
09

#6 会話が長くなるほど劣化する

GETS WORSE MID-CONVERSATION

エージェントも人間と同じく「注意の欠落」に悩む。長い会話は記憶すべき量が増えて性能が落ち（context rot / dumb zone）、しかもLLMは予測機械なので、一度ミスを重ねた会話では修正済みでもミスを繰り返しやすい。解決策はシンプル：1会話1小タスクを徹底し、長くなったら「完了済み・詰まっている点・試したこと」を書いた handoff.md を作って新しいセッションに引き継ぐ。

こまめに新セッション / handoff.mdで引き継ぎ
ダラダラ続けるほどボケるの、人間とおんなじで親近感わく…笑 引き継ぎメモ必須！
10

#7 主導権を失っている感覚

LOSING CONTROL

エージェントが高性能でも、ハイレバーな意思決定は自分が握るべき。何を作るか・スコープ・製品の高レベルな振る舞いは人間が決める。解決の中心は計画スキルの調整：エージェントが自ら決める事項と、必ず相談してくる事項を明文化し、計画に「自分で決めること／あなたに聞くこと」をリストアップさせる。承認してから実装へ。市販スキルは出発点にして、自分用に仕立て直そう。

意思決定の分担表 / 計画スキル改造
「任せるとこ」と「聞いてほしいとこ」を決めておくの、夫婦みたいな信頼ルールだね☆
11

#8 小さい依頼が巨大変更になる

SMALL REQUEST → HUGE CHANGE

小さなバグ修正を頼んだだけなのに、認証・スキーマ・テストまで触る大改修が返ってくる。複雑なコードベースほど発生しやすく、原因はLLMが標準で冗長すぎること。解決策は「簡潔さ・集中した実装」をルールに明記し、頼んでいない新抽象・余計なファイル・リファクタリングを禁止。自分のコードベースで「簡潔とは何か」をエージェントと一緒に定義しよう。

簡潔さの明文化 / 余計な変更を禁止
「ちょっと直して」→全面改装、あるあるすぎて笑えた。お願いしてないっての！笑
12

#9 レート制限にすぐ到達する

HITTING LIMITS

Claude Code や Codex の利用制限がすぐ切れる問題で、一番効く対策はサブエージェントの制御。標準では文脈読み込み・Web検索・テスト・実装に何十個も起動され、トークンを百万単位で溶かすことがある。使うタイミングと数を明示し（「バックエンド調査に1個、Web検索に4個」）、軽いタスクには安い小さいモデルを指定。ルールに「明示的に言った時だけサブエージェント使用」と書くのも有力。

サブエージェント制御 / 小さいモデルで節約
制限切れの犯人は子分たちだったんだね！数と役割を自分で決めるのが鍵〜
13

#10 小さな変更でも永遠にテスト

FOREVER TESTING SMALL CHANGES

些細な修正にも深〜い検証を始めて時間を溶かすのは、LLMが変更の「爆心半径（blast radius）」を把握できないため。自分から聞けば、コードベースの文脈を読んで「軽い影響／通常／要深掘り」をちゃんと見極めてくれる。計画スキルに爆心半径の判定を前期に入れ、検証レベルを計画へ明記させよう。#3の「何を検証するか」と組み合わせれば完璧。

blast radius判定 / 検証レベルを計画に
影響範囲に合わせて検証の深さを変えるの、ベテランエンジニアの勘をスキル化したかんじ！
14

#11 脱線を追いかけて集中しない

CHASING TANGENTS

大きなコードベースで作業中、エージェントが他の問題に目を付けて並行修正を始めてしまう。かといって無視するのももったいない。解決策は「保留リスト」：見つけた脱線は notice.md や GitHub Issue に書き留めて別のビルドループで対応し、今は本命に集中させる。ただし「積極的に探して記録して」と頼むと件数が爆発するので、見つけた時の扱いだけルール化するのがコツ。

脱線はIssueへ / 本命中の徹底
気になったことはメモして後回し、先輩エンジニアの「あとでやるリスト」とおんなじだ〜！

実践例：CLAUDE.md から hooks へ抽出

RULES → HOOKS EXTRACTION DEMO

実演ではエージェントに「CLAUDE.md を読んで、『Xの時は絶対Yするな』『AならBせよ』の形の強制項目を全部見つけて」と依頼。.env を読ませない・特定フォルダのマイグレーションを編集させない・npm/node ではなく bun を使う、などの候補が抽出され、それぞれプログラム的に検知してブロック・誘導できる hooks になった。既存ルールの見直しから始めるのが一番の近道。

抽出の実演 / 既存ルールのhook化
ルールをコードに昇格させる作業、エージェントにやらせていいのが天才的すぎる…！

Arcade：エージェント認証の統治

SPONSOR: AGENT ACTION GOVERNANCE

本動画のスポンサー Arcade は MCP ランタイム。各アプリに自分として一度だけサインインすれば、トークンの保存・更新は Arcade が行い、モデルは決してトークンを見ない。夜間や定期実行の長時間タスクで真価を発揮し、すべてのツール呼び出しが呼び出しの瞬間に検査される：深夜にアクセスを取り消せば、午前2時のジョブは次の呼び出しで即失効。全呼び出しの履歴で完全な監査と可観測性を確保。無料で開始可能。

ワンタイムログイン / 呼び出し単位のガバナンス
不在でも安全に働かせられるの、まさにエージェント時代の鍵だよね〜！
