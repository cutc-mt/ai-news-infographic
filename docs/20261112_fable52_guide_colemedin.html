数日前に登場の新モデルANTHROPIC RELEASED CLAUDE FABLE 5.2

🚀 リリース概要

AnthropicがClaude Fable 5.2を公開して数日。あらゆる新モデルが「信じられないほどすごい」と言われる時代にありながら、Fable 5.2には決定的に違う点があるという。

  • 従来LLM特有の「機械っぽい摩擦」が激減し、自己認識（セルフアウェアネス）が一段向上した印象

02

「返信しないで」テストを通過THE "DON'T REPLY" TEST

🧪 変わった実演

従来のLLMは「このメッセージには返信しないで」と頼んでも、トークンを生成するよう設計されているため必ず何か返してしまう。ところがFable 5.2は——

  • 思考トークンは生成しつつ、実際の応答を空欄のまま返すことに成功
  • 例自体は実用性に乏しいが、LLMの常にあった「壁」を破ったことの象徴

「仕事を愚かな機械に丸投げしている感覚」を塗り替える最初のシグナルだとColeは強調する。

  • アプリのアーキテクチャ決定でOpus 5.5と行き詰まった長い対話ログをそのままFableに渡すと、約10分で「完璧に見える解」が返ってきた
  • 第三者ベンチマーク（Artificial Analysis等）でも現行最高クラスのスコアを確認

05

単純タスクならFableに勝ちなしNO ADVANTAGE ON WELL-DEFINED TASKS

⚖️ 使い分けの原理

Anthropic自身のリソースでも明言されている通り、単純なタスクや範囲が明確に定義された仕事では、高性能モデルの優位性がほぼ消える。

  • Fableほど強くなくても、多くの場面でOpus 5.5が「十分に良い」
  • 強くて高いモデルを何にでも使うのは金を捨てているのと同じ
「最高のモデル＝常に正解」ではない、というのがこのガイド全体の出発点だよ。

結論：プランナーとワークホースの分割THE PLANNER / WORKHORSE SPLIT

🧭 本動画最大の教訓

Coleがこの動画で最も強調するのは、「Fable 5.2で計画・検索・意思決定を、Opus 5.5で定義済みステップの実行を」という分割だ。

  • Fable 5.2＝プランナー：アーキテクチャ判断・リサーチ・大きな決断
  • Opus 5.5＝ワークホース：明確化されたタスクの実装・検証・反復
  • この「大きいモデルで計画、小さいモデルで実行」パターンは以前から存在したが、役割がさらに先鋭化（sharpened）した

調査記事でも「Fable 5.2は長時間のエージェント実行（ロングホライズン）に最適」という見方で一致している。

実践手順：plan.mdハンドオフHOW TO DO IT IN CLAUDE CODE

🛠️ 手順
セッション1（Fable）コードベースの文脈を読み込み、Web検索しながらアーキテクチャ等の大きな決定を下す
plan.md決定内容をシンプルなMarkdownのハンドオフ文書に書き出してセッション終了
セッション2（Opus）/model でOpus 5.5に切り替え、文書を読ませて実装・検証・反復

難しい判断はすべて最初のセッションで済ませているため、2つ目のセッションは「ただ実行するだけ」。品質を落とさずに高価なFableの使用を最小化できる。

ベンチマークが裏付ける分割WHAT THE DATA SHOWS

📊 データ検証

Artificial Analysisのベンチマークでは——

  • オープンエンドな複雑タスクではFable（紫）がOpus（青）を全テストで上回る
  • 一方、範囲が明確なタスクでは両者に差がほぼない。Anthropic自身のFrontier Code 2.0ではFable（High）とOpus（Max）がほぼ同等

にもかかわらずFableはほぼ2倍のコスト。「先にFableで計画してタスクを明確化 → Opusで完成」が合理的な根拠。

Fable 5.2のエフォートは「High」FABLE EFFORT LEVELS

🎚️ 推奨: HIGH

複雑コーディングベンチマークでのFable 5.2の平均スコアとコスト——

プロンプト術①：所有者として振る舞わせる"YOU ARE THE OWNER"

📝 Fable専用チューニング

ルールやプロンプトに「あなたはこのコードベースの所有者であり長期の保守担当者。設計はあなたに委ねられている」と明記するだけで成果が変わる。

70%この一文あり：重複コードを整理
<10%一文なし：整理されず

一見ばかげた一文に思えても研究で効果が確認されており、Fable 5.2の「オーナーシップを取れる」性質を引き出す。なおOpus側のビルドセッションでは不要（クリーンアップ方針は計画書で決めるため）。

14

プロンプト術②：サブエージェントのモデル指定SUBAGENTS DEFAULT TO FABLE

💸 罠と対策

Claude CodeでFableと会話していると、起動されるサブエージェントもデフォルトでFableを使ってしまう。

  • サブエージェントの仕事は主にコンテキストの読み込みで、高い推論力は不要 → Fableではトークンと金の無駄
  • カスタムサブエージェントならYAMLフロントマターでモデル（Sonnet / Opus）を指定
  • 会話中でも「このサブエージェントにはこのモデルを使って」と動的に指示可能
レート制限が予想より早く来るなら、まずこのサブエージェント問題を疑ってみてね！
15

プロンプト術③：手順ではなく結果を書くDESCRIBE OUTCOMES, NOT STEPS

🎯 開放性を活かす

LLMが高性能になるほど、私たちは具体的手順を詳細に書いて過剰に縛ってしまいがち。これはFable 5.2で特に損になる。

  • 手順に100%の確信があるなら明示的ガイドも有効
  • 少しでも不確かな部分があるなら、「望む成果（アウトカム）」だけを書いて道筋はエージェントに任せるのが正解

オープンエンドなタスクに最強のFableの能力を、ステップ指定で封印しない——という発想の転換だ。

プロンプト術④：ルールをアブレーションするABLATE YOUR RULES

✂️ 掃除のすすめ

CLAUDE.mdなどのコンテキストファイルから、古いモデル用のルールを刈り込むこと。

  • かつて必要だった誘導ルールの多くは、今のモデルには無駄なトークンになっている
  • 放っておくとモデルを意図せず制約してしまうことも
  • 新LLM登場のたびに監査を。Coleはablate AI layerスキル（説明欄リンク）で効率化
「ルールを足す」だけでなく「引く」メンテも、強いモデル時代の必須作業なんだね。お掃除大事！
