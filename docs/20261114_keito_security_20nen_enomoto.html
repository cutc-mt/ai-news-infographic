「もう全員来てる」——PHP脆弱性ショックと、これからのセキュリティの考え方

エンジニア歴20年のウェブ専門家・榎本さんに聞く／AI時代の攻撃と防御／パスキー・WordPress・MDash移行／予防・止血・アフターフォローの3段階

📅 2026年11月14日 / KEITO【AI&WEB ch】（@keitoaiweb）× 榎本さん

①ゲストはエンジニア歴20年のウェブ専門家

  • 榎本さんはウェブエンジニアとして20年間の受託開発が中心。会員サイトからWordPress、決済のある代理店管理システムまで幅広く構築。
  • マーケティングシステムやTwitter（X）APIを使った開発など、「ウェブのシステムといったら何でも」の経験値を持つ実務派。
  • 今回はセキュリティの考え方と、話題のPHP脆弱性についての特別コラボ対談。
現場を20年やってきた人だからこそ見える「今のヤバさ」を聞いた

②そもそもPHPとは何か

  • PHPはウェブサイトを作るためのプログラミング言語の一つ。HTML・CSS・JavaScriptなどと並ぶ選択肢の一つ。
  • 世界のサイトの約7割がPHP製。さらに日本では90数パーセントがPHPという、実は知られざる天下無双の言語。
  • 普段みんなが見ているサイトはほぼ全てPHPが裏側のエンジンとして動いている——一般の人はまったく意識しないだけで、見た目の下で動いている。
「PHPなんて聞かない名前」ではなく、実は日本のウェブの9割を支える言語

③「脆弱性」＝弱点。今回はコンクリートそのもの

  • 脆弱性とは弱点のこと。家に例えると「合鍵を持たれる」「ピッキングされる」ような、サイトやアプリ側の弱点。
  • しかし今回は経路が違った。家を建てるコンクリート（＝言語そのもの）に弱点が見つかり、PHP製の家は皆侵入されるレベル。
  • 榎本さんいわく「20年エンジニアをやってきて、ここまで衝撃的な脆弱性の発表は初めて」。
ドアの鍵の話ではなく、建材そのものの品質の話——それが今回の異常さ

④突かれると何が起きるか

  • 攻撃者はサーバーの中に入り込みコマンドを全部実行できる状態に。実害としてはデータベースの個人情報の窃取。
  • サイトにウイルスを仕込まれ、ユーザーがアクセスすると全然違う海外サイトに飛ばされ情報を抜かれる——改ざん・リダイレクトも可能。
  • 要は「何でもできてしまう状態」。ここまでの対象範囲と深刻度が、過去の脆弱性との違い。
サーバーの管理人権限を渡すようなもの。個人情報・改ざん・ウイルス、全部あり得る

⑤AIが攻撃の構図を変えた

  • AIの普及で攻撃の回数とレベルが急上昇。攻撃力は上がっているのに、防御側の皆さんは防御力そのまま。
  • かつては「金持ちの家だけ狙われる」時代。人が手作業なら回数が限られ、お宝のありそうな家だけが標的に。
  • 今はAI自動化で泥棒が全戸のドアノブをガチャガチャしまわっている状態。「狙われてる」ではなく「もう全員来てる」と考えるべき。
バイブコーディングの悪用版。大量生成ロボットが自動で全家屋を試す時代が既に現実

⑥漏洩は「連鎖」する

  • メールアドレス＋パスワードが漏れ、パスワードを使い回していると他サイトにもログインされる。
  • Aサイトから名前・メール・パスワード、Bサイトから電話番号・住所…と複数サイトの情報を複合して一人の人格が組み上がる。
  • 完成した情報はフィッシング詐欺や特殊詐欺の電話などに悪用される——「自分の情報くらい」という認識は危険。
一つ漏れると全部漏れる。使い回しが情報漏洩の威力を数倍に増幅する

⑦個人で絶対やるべき認証対策

  • パスワードの使い回しは絶対にやめること。これが最優先かつ最善の一手。
  • 安心度ランキングは榎本さん見解でパスキー ＞ 2段階認証 ＞ パスワードのみ。
  • 2段階認証のメールコードも、メールのID・パスワード自体が漏れていると突破される。顔・指紋を使うパスキーは「自分の顔がないと入れない」分だけ強い。
対応しているところ全部パスキーに。それが今の個人最強の鍵のかけ方

⑧パスキーも突破され得る？

  • 理論上あり得る。ただし指紋や顔の情報が全て漏れた前提の話で、ハードルは高い。
  • それよりサイト運営側のセキュリティの方が甘いことが多く、ハッカーは効率のいいそちらを狙う。
  • つまり「個人はできることをやりつつ、企業のセキュリティ体制をしっかりしてもらう」が現実的な分担。
個人の最強認証より、運営側の weakest link を狙われる——防御は全体の強度で決まる

⑨PHP以外でも起こり得る

  • ログイン機能などを作れるプログラミング言語——JavaScript・TypeScript・Node.jsなど——には脆弱性の可能性が常に潜む。
  • 実際、Node.jsでも新たな脆弱性が発表されており、大小さまざまな脆弱性は日々見つかっている。
  • 「これからもどんどん出てくると思った方がいい」——PHPだけの特殊な事件ではない。
機能を作れる言語ならどこでも起こる。特定言語の問題ではなく時代の問題

⑩しかも今回は「AIが見つけた」

  • 今回の脆弱性が隠れていたのはサーバーに負荷がかかった時のエラー処理など、人間が普段ほとんど見ない箇所。
  • コンクリートの材質や密度を誰も確認しないのと同じ。それをAIが発見した。
  • 人間が数十年見つけられなかったものをAIが数ヶ月で簡単に見つける時代に。善悪両方で発見スピードが跳ね上がった。
見つけたのもAI、悪用するのもAI——セキュリティの加速度が変わった

⑪バイブコーディングの落とし穴

  • AIで業務システムを作った人の「公開したいがセキュリティが大丈夫か見てほしい」という相談が榎本さんに何件も。
  • 実例：個人情報を扱うシステムをクラウドに自動アップロードし、URLを共有。URLを叩くだけで会員情報一覧がずらっと表示された。
  • AIは言語化されたことしかやらない。作る時に「セキュリティにも気をつけて」の一文を入れるだけで変わるが…
AI製システムの「なんとなく公開」が一番怖い。ハッキング未満の軽い操作で抜ける

⑫「気をつけて」の一文だけでは足りない

  • その一言でアプリのコード自体には気をつけてくれる。
  • しかしサーバーの設定やパスワードの管理など、セキュリティに必要な項目まではカバーできない。
  • コンピュータユースでポチポチ設定させるのも現実的でなく、一定の理解は人間側に必要。
プロンプト一句で安全にはならない。範囲外の設定こそプロかツールに任せる

⑬セキュリティに100点はもう取れない

  • 大企業ですら日々漏洩ニュースに出る通り、100点満点は今や取れる時代じゃない。
  • 発想の転換：「30点より90点」「90点のものを98点へ」と、できる限り積み上げる。
  • 絶対に侵入されない家はない——しっかり鍵をかけ、顔認証をかけ、防犯カメラを付ける。多層防御が基本。
満点を夢見るより、減点を積み重ねて防ぐ。現実的な防御設計

⑭サーバー事業者側のリスクも現実に

  • レンタルサーバー（エックスサーバー等）の設定やWordPressのセキュリティプラグインで防げる部分はあるが、一人のウェブ担当が全て網羅するのは難しい。
  • 実際にサーバー会社がハッキングされたり、古いPHPバージョンのままの業者が運営終了したりする事例も。
  • その場合昨日まで見れたサイトが一斉に閲覧不能に。消えたものは戻らないのでバックアップと即復元体制が必須——問題が起きる前の対策だけが効く。
「事故ってから」では遅い。バックアップは保険そのもの

⑮WordPressが狙われる構造的理由

  • 世界の約4割のサイトがWordPress。単純に数が多い＝標的としての価値が高い。
  • 本体＋誰が作ったか分からないプラグインやテーマの寄せ集め構造で、一つでも弱点があればサイト全体が乗っ取られる。
  • 現場では「制作会社に作ってもらって3年放置」のような案件もよく見る。PHP脆弱性と合わさって最悪の組み合わせに。
WordPress自体が悪いのではなく、数の多さと「つぎはぎ構造」がリスクの正体

⑯更新サボり＝勝手口の鍵開けっ放し

  • WordPress本体はバージョンアップを重ねるが、更新しないままの古い脆弱性は公開情報なので真っ先に狙われる。
  • PHP脆弱性が「コンクリート」なら、未更新のWordPressは「裏の勝手口の鍵が開いたまま」の状態。
  • 「この家は勝手口が開いている」とハッカーに即バレるので、鍵開けっ放しと同等の危険性。
更新ボタンを押すか押さないか。それだけで「侵入口あります」という看板の有無が決まる

⑰移行先として注目のMDash

  • WordPressはPHP製だが、MDashはTypeScript製。今回のPHP脆弱性とは一応おさらばできる。
  • 最大の違いはCloudflare Workers上でプラグインを一つずつ隔離できること。一つ脆弱性が出てもそのプラグインの範囲で済む。
  • ただしTypeScriptにも今後脆弱性は出てくる可能性は十分ある。移行＝永遠の安心ではない。
言語を変えることより「汚染が広がらない構造」に変えることの方が本質的に重要

⑱セキュリティは「予防・止血・フォロー」の3段階

  • ①予防：現状把握とバージョン更新、個人情報漏洩保険への加入も選択肢。
  • ②止血：早期発見が最重要。漏洩は自分以外（Google警告・取引先）から発覚することが大半。IPA統計では攻撃を受けた中小企業の約70%が取引先にも影響、復旧に平均6日、被害額平均約73万円。改ざん検知・アクセスログ監視は専門家へ。
  • ③アフターフォロー：万一の際の対応までパッケージで。まずは自分のサイトの現状把握と最新情報のキャッチアップ（動画概要欄のセキュリティニュースLINE）から。
