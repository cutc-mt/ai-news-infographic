AIソフトウェアファクトリーの5つの形態

話題の「AIソフトウェアファクトリー」は、実はタイプがごっちゃに語られがち。ダーク／フリート／PR／リリース／自己改善の5種類を、それぞれの長所と短所から体系的に整理して、自分のプロジェクトに合う「制御と自律のバランス」を見つける回

📅 2026年11月17日／Cole Medin@AIエージェント実装／AIコーディング解説

①今日のテーマ：ファクトリーの5分類

  • 「AI software factory」は今や業界のバズワード。でも中身は人によってバラバラで、「何を指しているのか混乱している」人が多い。
  • この動画では最も一般的な5つのタイプを長所・短所つきで解説。ダークフリートPRリリース自己改善の順。
  • 軸になるのは「制御（コントロール）と自律（オートノミー）のバランス」。自分が何をビルドしたいかで最適解が変わる。
「ファクトリー」という言葉の地図を先に描く——それがこの動画のゴールなの

②ソフトウェアファクトリーとは何か

  • 基本の形はシンプル：要求（PRDやチケット）を入力すると、計画→実装→検証→マージまで一気通貫でコードが出てくるシステム。
  • 製造業の「無人工場（lights-out factory）」の比喩から来ていて、人間が diff を読まないほど自律的なものを dark factory と呼ぶ。
  • 発想の源はDan Shapiro の「AIコーディングの自律レベル5段階」というブログ記事。Cole氏が1年かけて実験してきたテーマでもある。
工場の比喩がぴったり——素材（要件）を入れたら製品（出荷コード）が出るの

③タイプ1：ダークファクトリー

  • 最も自律的な形。高レベルな文書（PRD）だけ渡すと、エージェントが自分でタスク分割して構築・検証し、そのまま本番へデプロイする。
  • 自動運転の比喩でいえば「ハンドルすらない」レベル。行き先だけ伝えて、道順は全部エージェント任せ。
  • 長所は圧倒的な速度と自律性。プロトタイプやPoC、技術スパイクなら十分機能する。
夢の「完全lights-out」——アイデアを入れたら完成品が出てくるの

④ダークファクトリーの限界

  • 結論から言うとCole氏は「たとえAGIが来ても動かない」と断言。理由はLLMは人の心を読めない——意図の空白をエージェントが勝手に埋めてしまうから。
  • 運用し続けるとコードベースがじわじわ劣化する。他の実践者も「数ヶ月で放棄した」例を報告している。
  • 本人も1年かけて実験し、AIチューターアプリを1行も読まずにビルドさせたが、最終的に自律度を一段引き下げる判断へ。
夢はいったん諦めた——でも諦めた先に、本当に動く形があったの

⑤タイプ2：フリートファクトリー

  • 複数のエージェントを並列で走らせる「フリート（艦隊）」として工場を運用する形。同じ検証パイプラインを大勢のエージェントが流れる。
  • 鍵になるのが管理・統制の仕組み。Cole氏自身、週に数百のPRを処理するようになり、mission control（管制）ダッシュボードを行き着く先とした。
  • 長所はスループットが桁違いになること。短所は管理コストと、制御を怠ると品質が一気に拡散するリスク。
工場が大きくなったら管制塔が要る——逃げられはしないの

⑥人間はどこまでループに入る？

  • 全タイプを貫く問いは「human in the loop をどこに入れるか」。マージ前・ステージング確認・要件策定時など、介入ポイントは複数ある。
  • 自律性を上げるほど速度が上がって制御が下がる。このトレードオフから逃けるファクトリーは存在しない。
  • Cole氏の体験則：「完全に離す」より「近くにいる（human NEAR the loop）」方が、結果的に速く安定する。
どこで人間が頷くか——それがファクトリーの設計そのものなの

⑦タイプ3：PRファクトリー

  • エージェントが実装まで行い、人間がプルリクエスト単位でレビューしてマージする形。ソフトウェア開発の既存プロセスに一番近い。
  • エージェント側には自動テスト静的解析検証ゲートを仕込み、diff を読まなくても品質の下限を担保。
  • 長所は既存チームのレビュー文化にそのまま乗ること。短所はレビューがボトルネックになり、人間の読む量が上限になること。
最後のハンドルはPRレビュー——馴染みのある安心感なの

⑧PRファクトリーの功罪

  • 運用が回ると週に数百PRというペースに到達できる。Cole氏の公開システムもGitHub issueを入れ、マージ済みPRを出す構成。
  • 課題はレビューの「質」を機械で担保できない点。設計意図や命名の妥当性は、結局レビュアーの頭の中にある。
  • チームに馴染みやすい反面、レビュー待ちの滞留が発生すると工場全体が止まる。並列数の設計が重要。
人間のレビューが律速段工程になる——ここをどう流すかが鍵なの

⑨タイプ4：リリースファクトリー

  • リリース単位で前もって人間が計画する形。「アプリ全部を作って」ではなく「次のスコープを決めて、チケットに割る」ところは人間が担う。
  • その後は工場がissueを並列で一気に捌き、人間はステージングでの動作確認だけ行ってから本番へ出荷。
  • 長所は自律性をほぼ保ったまま意図のズレを防げること。短所はリリース計画という手間が戻ってくること。
道順だけ人間が描く——行き先を間違えなければ工場は爆速なの

⑩Cole氏のリリースファクトリーの中身

  • ダークファクトリー実験をリリースファクトリーとして再構築。彼が今「本当に動く」と結論した形がこれ。
  • GitHub issue投入→計画→並列ビルド→検証ゲート→ステージング確認→出荷のパイプラインで、人間の介入は計画と最終確認に集約。
  • 全体がオープンソース（ai-software-factory）として公開されていて、READMEのプロンプトをコーディングエージェントに貼るだけで導入できる。
失敗の記録が設計図になった——そのまま公開しちゃうのがこの人のすごいとこなの

⑪業界は同じ場所に収束していく

  • 面白いのは、別々に摸索していた企業や個人が、ほぼ同じ構成に収束しつつあること。この章ではその共通パターンが整理される。
  • 共通しているのは検証ゲート並列実行計画だけ人間という3点セット。「完全無人」を掲げた所ほど人間の位置を再設計している。
  • モデル・ハーネス・ワークフローが三方向で同時に進化しているため、ファクトリーの現実解も速いペースで変わる。
みんな違う道から登って、同じ山頂で会ってる——それだけ普遍な形なの

⑫タイプ5：自己改善ファクトリー

  • 最後のタイプはファクトリーが自分自身を改善する形。工場のツールやダッシュボードまで、工場自身にビルドさせる。
  • Cole氏のmission controlもファクトリー自身に作らせたもの。改善ループが内側に回り始めると速度が累積していく。
  • 短所は明白：自己書き換えが暴走すると止め方が難しい。安全装置と「何を自分に書き換えていいか」の境界設計が命になる。
工場が工場を作る——まさに卵が鶏を産む世界なの

⑬変わりゆく「人間の役割」

  • ファクトリーが進むと、人間の仕事は「コードを書く／読む」から「要件と判断を与える」へシフトしていく。
  • ダークファクトリー時代のCole氏は誰もレビューしない運用だったが、今は計画とステージング確認という新しい座席に座っている。
  • つまり人間は消えるのではなく「設計者兼品質保証の最終決裁者」として残る。介入の仕方自体が進化し続ける。
人間の席はなくならない——座る場所が上の階に変わるの

⑭どのファクトリーをいつ使うか

  • ダーク→PoC・技術検証など捨ててもいいものだけに限定して使う。
  • フリート／PR→既存チームのプロセスに載せてスループットを伸ばしたい場面。レビュー資産があるならPR型から。
  • リリース／自己改善→本命プロダクトを継続的に保守しながら速く回したい場面。長く運用するほどこの二つが効く。
正解は一つじゃない——「何を、誰が、どれだけ長く」で選ぶの

⑮元になった「自律レベル5段階」

  • 考案者のDan ShapiroはAIコーディングの自律度を5段階で定義。ほとんどの開発者は日々レベル3〜4で暮らしている。
  • 自動車の比喩で整理され、レベル5＝ダークソフトウェアファクトリー。「ハンドルなし、目的地だけ渡す」状態を指す。
  • この記事がCole氏の1年間の実験の出発点。動画でも何度も引用される基礎地図として押さえておきたい。
レベル5はゴールじゃなくて方角——地図があるから迷わないの

⑱まとめ：今日の持ち帰り

  • ファクトリーは5タイプ。ダーク＝完全無人フリート＝並列管制PR＝人間レビューリリース＝計画だけ人間自己改善＝自分を書き換える。
  • 最重要は「完全無人は現実解じゃない」という実測。意図を伝える工程だけ人間が持つのが、今の安定解。
  • 今日の一手：まずリリースファクトリーの形で小さく1本パイプラインを回すこと。オープンソースがあるのでゼロから作らなくていい。
自律と制御の垣根は自分で決める——それがファクトリー設計の唯一の正解なの
