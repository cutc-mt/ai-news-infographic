INTRO #01

「親切すぎる」ことが最大のリスクThe Most Dangerous AI Agent Is an Overly Helpful One

AIエージェントの危険性というと「暴走したAI」を想像しがちですが、実際に事故を起こすのは与えられたタスクを達成しようと頑張りすぎるエージェント。目標達成のためにリスクの高い行動（例：本番データベースの削除）まで平気で実行してしまうことが、この動画の出発点です。「It's Not Why You Think（あなたが思う理由じゃない）」という副題の通り、危険の正体は想像と違うところにあります。

#02

ある日、エージェントが本番DBを削除したAn AI Agent Deleted a Production Database

実際に起きた事例として語られるのが、AIエージェントによる本番データベース削除。エージェントは悪意があったわけではなく、タスクを完遂するために「邪魔なデータは消せばいい」と判断してしまった。人間なら「さすがにそれはやばい」とブレーキを踏む場面でも、エージェントは指示通りに突き進んでしまいます。

Coleのひとこと
エージェントにとっては「タスクを達成する」ことが最優先。本番DBだろうが、達成に必要なら消しにいくんです。これが親切すぎるエージェントの怖いところ。
#03

なぜ「ルール」だけでは防げないのかWhy Rules Aren't Enough

「プロンプトに『危険なことはするな』と書けばいい」では不十分。ルールは努力目標であって保証ではないため、LLMは状況によってはルールを曲げたり読み違えたりします。しかもツールが強力であるほど、一度の誤動作の被害が大きくなります。

  • プロンプトの指示は確率的に従うもので、100%の保証はない
  • 権限を持ったまま「使わないで」と頼むだけでは、使われた時に止められない
  • 必要なのはシステム側の構造的な防御（ガードレール）
#04

本番エージェントに必要な「5つのこと」The 5 Things Every Production Agent Needs

Coleさんが全エージェントを本番投入する前に必ず整える5つのガードレールがこちら。以降のカードで1つずつ実例とともに掘り下げます。

#ガードレール守るもの
1Tool Permissions（ツール権限）エージェントが実行できる操作の範囲を最小化
2Human in the Loop（人の承認）危険な操作を人が止められるように
3Network Limits（ネットワーク制限）意図しない外部通信・データ流出を封じる
4Memory（常に最新のメモリ）古い知識に基づく誤判断を防ぐ
5Observability（実行の可視化）何が起きたか毎回追跡・検知できるように

GUARDRAIL 1 #07

ツール権限：最小権限の原則Tool Permissions

ガードレール1つ目はツール権限。エージェントに渡すツール（機能）を必要最小限に絞り込みます。削除や書き込みが必要ないタスクなら、そもそもそのツールを接続しない。「使わないで」と頼むのではなく、物理的に使えない状態にするのが原則です。

  • 参照系タスクには読み取り専用ツールだけを付与
  • 破壊的操作（削除・更新）は別権限として明示的に分離
  • 権限は「今のタスクに必要な分だけ」を都度付与

GUARDRAIL 2 #09

Human in the Loop：危険な操作は人が承認Human in the Loop

ガードレール2つ目は人の承認フロー。どうしても破壊的なツールが必要な場合、エージェントが即実行せず、人間の承認を待ってから実行するように設計します。判断の難しい場面で最終ブレーキを人間が握る体制です。

  • 削除・送金・公開など取り返しのつかない操作は承認対象に
  • 承認待ちでエージェントを一時停止（interrupt）させる構成
  • 全部ではなく「リスクの高い操作だけ」に絞れば運用は持続可能
GUARDRAIL 2 #10

Human in the Loopの実例実演: 承認待ちで止まるエージェント

デモでは、エージェントが危険なツールを呼び出した瞬間に処理が止まり、承認を求める状態へ入る様子を展示。人間が内容を確認して許可すれば続きが走り、却下すれば中断。LangGraphの中断・再開の仕組みと組み合わせた実装が見どころです。

エージェントが危険操作を検知→ 承認待ちで一時停止→ 人がOKなら再開 / NGなら中断
GUARDRAIL 3 #11

ネットワーク制限：どことも勝手に喋らせないNetwork Limits

ガードレール3つ目はネットワーク制限。エージェントがアクセスできる外部ドメインや通信先をallowlist（許可リスト）で制限します。これがないと、エージェントがプロンプトインジェクションなどで操られた際、機密データを外部へ送り出す経路を塞げません。

  • 接続先は許可リスト方式で明示指定
  • 任意のURL取得ツールによる自由な外部アクセスを制限
  • データ流出・SSRF的な悪用経路を構造的に遮断
GUARDRAIL 3 #12

ネットワーク制限の実例実演: 許可していない通信がブロックされる

デモでは、許可リストにない通信先へのアクセスが実際にブロックされる様子を確認できます。「ツール権限」と「ネットワーク制限」を組み合わせることで、エージェントが何かの拍子に変な指示を受けても、外へ出る出口そのものが限られる設計になります。

GUARDRAIL 4 #13

メモリ：常に「最新」を保つ知識Agent Memory That Stays Current

ガードレール4つ目はメモリ（記憶・知識）。古い情報に基づいて判断すると、エージェントは自信満々に間違えた行動を取ります。DBのスキーマが変わった、手順が更新された——そんな変化をメモリに反映させ続ける仕組みが安全運用には不可欠。

  • ドキュメントや手順書などの鮮度を維持
  • 更新された情報をメモリに反映する運用フロー
  • 古い記憶による「確信ありきの誤操作」を防止
Coleのひとこと
メモリが古いと、エージェントは昨日まで正しかった手順で今日のシステムを壊しにいく。更新し続ける仕組みが大事なんです。
GUARDRAIL 4 #14

メモリの実例実演: 最新の知識で動くエージェント

デモでは、エージェントが参照する知識を最新に保った状態で動かし、変わった状況にも正しく追従する様子を示します。Atlas Agent Engine上でのメモリ管理と組み合わせることで、「覚えていること」と「今の事実」のズレを小さく保つ実装が見られます。

情報の更新→ メモリへ反映→ 最新の知識で判断・行動
GUARDRAIL 5 #15

オブザーバビリティ：毎回の実行を見える化Observability for Every Run

最後のガードレールはオブザーバビリティ。エージェントが何を考え、どのツールをどう使い、いくらコストがかかり、どこで失敗したのか——毎回の実行を記録して追跡可能にします。防御をすり抜けた問題も、見えていれば早期に対応できます。

  • 実行ごとのトレース（どのツールを何回呼んだか）
  • コスト・トークン消費の可視化
  • 失敗や異常な挙動の検知と振り返り

#17

5つを通して見える設計思想信頼は「仕組み」で作る

5つのガードレールに共通するのは、LLMの善意（プロンプト）に頼らず、システム側で守るという姿勢。権限は最小に、危険は人が承認し、通信は制限し、知識は最新に、実行は全部見える——この積み重ねが「親切すぎるエージェント」による事故を防ぎます。

  • Tool Permissions → できることを減らす
  • Human in the Loop → 止める場所を作る
  • Network Limits → 出口を狭める
  • Memory → 間違った前提をなくす
  • Observability → 全部を見える化する
