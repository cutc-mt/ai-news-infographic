INTRO #01

pxpipeとは：コンテキストを画像に変えるローカルプロキシText-to-Image Proxy for Coding Agents

pxpipeは、コーディングエージェントの入力トークンを削減するために作られたオープンソースのローカルプロキシ。かさばるコンテキストテキストを、高密度な5×8ピクセルのPNGページ画像にレンダリングしてAPIリクエストを書き換えます。コード生成CLIに一切変更を加えず、手元のプロキシとして動作するのが特徴です。

#02

なぜ画像トークンの方が安いのかImage Token Math vs Raw Text

画像のコストはピクセルサイズで決まるため、文字を小さく詰め込むほど1トークンあたりの情報量が増えます。動画の計算では、密集したコードやJSONで1画像トークンあたり約3.1文字保持できるのに対し、テキストトークンは約1文字。同じ内容を送るなら画像の方が圧倒的にトークン数が少なくて済みます。

画像コスト＝ピクセルサイズで固定→ 密集テキストを詰め込む→ 1トークン≈3.1文字を実現

#05

収益性ゲート：損な変換はしないThe Profitability Gate

画像化は常に得というわけではありません。pxpipeは内部に収益性ゲートを持ち、画像化してもトークンが減らない・むしろ増えるケース（短いテキストや疎な文章）は自動的にテキストのまま通します。判定はリクエスト単位で行われるため、ユーザーが閾値を意識する必要はありません。

  • 短すぎるコンテキストは画像化せず素通し
  • 密なコード・JSONだけが変換対象になる
  • ゲート判定は自動、設定不要

モデル3tier：使う・要約のみ・使うなFull Readers / Gist Readers / Do-Not-Image

動画では対応モデルを3つの階層に分類。画像化したコンテキストを正確に読めるフルリーダー、だいたいの要点は掴めるギストリーダー、そして画像化すべきでないモデルに整理されます。

#15

サイレントな捏造とファクトシート対策Silent Confabulations and the Text Factsheet Fix

モデルの「視覚」はOCRではありません。読み取れないピクセルがあると、エラーを返すのではなくもっともらしい文字を捏造（コンファビュレーション）してしまいます。そこでpxpipeは各画像の横に、正確なIDや数値を記した小さなテキストのファクトシートを添付。「0」と「8」のような字形の混同を防ぎます。

不鮮明なピクセル→ エラーではなく捏造が起こる→ テキストファクトシートで補正

結論：使うべきか？Verdict: Should You Use pxpipe?

動画の結論は、Gemini 4・Gemini Flash・オリジナルFable 5なら本当に試す価値あり。Opus 5.5でも通常のツール駆動コーディングには有用です。一方でPNGエンコードによるわずかなレイテンシがあること、Sonnet・Haiku・オープン系モデルでは使わないほうがよいこと、tier分類はリリースごとに変わるので注視が必要という注意も付きます。

  • おすすめ: Gemini 4 / Gemini Flash / オリジナルFable 5
  • 条件付き: Opus 5.5（通常のツール駆動コーディングなら有用）
  • 見送り: Sonnet・Haiku・オープン系モデル
  • PNGエンコードの軽微なレイテンシには注意

エージェントのコストを桁で下げる新発想

「テキストは文字数で、画像はピクセルで課金される」という課金体系の違いを突いたpxpipe。対応モデルを選べば、エンドツーエンドの請求額を59〜70%削減できる実力があります。モデルごとの読み取り能力とファクトシートの工夫など、危険側の対策まで押さえた上で、ぜひ本編で詳細を確認してください。
