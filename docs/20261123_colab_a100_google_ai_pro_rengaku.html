使わないまま400貯めていた特典BENEFIT・Google AI Pro × Colab ポイント

特典の正体
  • Google AI Pro には本当にいろんな特典が付いていて、その中に「Colab で強い GPU を借りられるポイント」がある
  • 正式名称はコンピューティング ユニット(CU)。毎月200が自動で付いてくる

Google Colab とはCOURSE・ブラウザだけで動く計算環境

基礎をおさらい
  • ブラウザ上のノートブックに Python を書いて、Google の計算機で動かせるサービス
  • 無料でも使えて、有料のポイントを使えば A100 などの強い GPU を借りられる
  • 自分で大きな計算機を用意しなくてよい——今回のプログラムも Claude Code に書ってもらった
  • Colab の操作自体も、Google 公式の Colab MCP を通して Claude Code に任せた
BASE
「GPUを借りる」って聞くと難しそうだけど、実態はブラウザで開くノートブック。ハードウェアの知識より、何をGPUに載せるかの設計が大事なんだ。

  • GPU に載せられる計算なら、使わない手はないというのが結論

何を計算したか: 渦の輪の再結合TOPIC・約1億3,400万点の3D流体計算

題材
  • 2つの渦の輪(トーラス)が近づいて、1つにつながる様子を3Dで数値計算
  • 格子の点は約1億3,400万点、時間方向に 8,192ステップ進める重い処理
  • 配置は Kida と Takaoka の計算(1989〜1991年)と同じ型。傾きや間隔は独自の値で、論文の再現ではない
  • 流体の計算はれん学長の専門ではない——それでも Claude Code に頼んだらできたのがポイント
れ
「1回で終わるがっかり動画」にしないために、時間がかかる重い題材をわざと選んだんだ。ギリギリ破綻しないギリギリを狙ったら、いいサイズになったよ。

Claude Code × Colab MCPWORKFLOW・セルを書いて流すのはAI

仕組み
  • Google 公式の Colab MCP サーバーを使うと、Claude Code がノートブックのセルを書いて実行できる
  • 1回目は A100 を選ぶ所などを自分で押し、2回目は画面の操作まで Claude Code に任せた
  • セルが次々に実行されていく様子は、見ていて結構面白かったとのこと
  • MCP でできるのはセルの操作まで——GPU の選び直しなど画面操作は範囲外
MCP
「Colab公式MCP + Claude Code」の組み合わせは、ノーコードで重い計算を回す最短ルートのひとつだよ。AIがセルを流して、人間は結果を眺めるだけ。

速さの差の正体は「データを運ぶ速さ」ANALYSIS・計算力4倍 × メモリ帯域12倍

なぜ11倍?
観点A100 の使い方Macとの差
計算の力GPU全体を使用: SM 108個 / CUDAコア 6,912個約4倍
データを運ぶ速さ
(メモリ読み書き)		HBM による大帯域約12倍
  • 実測の約11倍は、計算力の差(約4倍)ではなくメモリ帯域の差(約12倍)とほぼ一致
  • この手の格子計算は「データの運び」が効くタイプ——GPU選びの指標になる考え方
  • ただしコア数は会社ごとに数え方が違い、Macの「18コア」とはそのまま比べられない
WHY
「CUDAコアの数で比べればいい」ではないんだ。何がボトルネックかを考えると、GPU選びの失敗がぐっと減るよ。

結果2: 描画に25.5分の落とし穴PITFALL・A100 を借りているのに CPU で描く

発見した問題
  • 計算した結果を絵にする所で、GPU で描く設定になっていなかった——A100 はその間ずっと休んでいた
  • 計算の約6倍の25.5分が描画にかかってしまった
  • さらに悪いことに、ノートブックは「GPU で描く」と表示する作りだったため気づきにくかった
  • 何が原因で何を変えたら速くなるかは、動画後半で詳しく検証
れ
「強いGPUを借りたのに休ませていた」という、あるある落とし穴。表示を信用しすぎちゃダメといういい教訓になったんだ。

描き方を直すと 25.5分 → 1.0分FIX・約25倍の改善を支えた3つの手

修正の中身
  • GPU で描く: 描画を GPU に載せて CPU から解放
  • 立体の入れ物は1回だけ作る: 毎フレーム作り直さず、中の数字だけ入れ替える使い回し
  • 12個の処理で同時に描く(並列化): 同じ300コマの描画を並行処理
  • 結果、同じ300コマが25.5分 → 1.0分(約25倍)に。描画には PyVista を使用
FIX
働かせたいものをちゃんと働かせる「適材適所」。計算を速くするのと、描画を速くするのとでは、効く手がまったく違ったんだ。

結局、何が効いたかTAKEAWAY・計算と描画で答えが違う

効きめのまとめ
処理効いたもの
計算データを運ぶ速さ(メモリの読み書き)
描画同時に描くこと(並列化)と使い回し
  • 同じ「速くする」でも、計算と描画で効く所がまったく違ったのが最大の学び
  • まずどこがボトルネックかを見極めてから手を打つのが高速化の基本

GPU ごとの得意とランタイムの選び方SELECT・データ運び vs 計算の力

選び方の軸
  • GPU によって「データを運ぶ速さ」と「計算の力」の得意が違う——どちらが効く計算かで選ぶ
  • ランタイムのタイプから GPU を選べるが、上のプランほど強い GPU に入りやすい(上がどれだけ付くかの数字は非公開)
  • 急がなければ L4 のまま進める手もある(格子を448の3乗に下げる作り。L4では未計測)
TIP
「どのGPUが正解」ではなく「この計算はどっちの力が要るか」から逆算するのがコツだよ。

A100 を選んだのに L4 につながったTROUBLE・空き待ちのリアル

あるある現象
  • 2回とも最初は L4 につながった——A100 を選んでも空いていなければ割り当たらない
  • 数分おいて選び直すと A100 が入った。あせらず再選択が正解
  • 上位プランほど強い GPU に入りやすいが、確実ではない
  • 使い終わったらランタイムを削除——つないでいる間はポイントが減り続ける
れ
「A100のはずがL4」で慌てないで。数分待って選び直せば入ることが多いんだ。あと、使い終わったらランタイムを削除(つないでいる間はポイントが減り続ける)して、結果は先に保存——削除すると中のファイルは消えるからね。大量データを置きっぱなしにするか手元に持ってくるかは、次の実験テーマだよ。
