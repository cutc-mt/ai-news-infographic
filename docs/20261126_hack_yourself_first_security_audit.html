THREAT 02

Java4Shellとは何か3:19 Java4Shell: A Critical Bug Found in an Hour

動画が「AI攻撃の現実感」として持ち出すのがJava4Shell（CVE-2026-114938）です。OpenJDKのBase64デコーダに存在するメモリ破壊脆弱性で、CVSS 4.0では9.2（CRITICAL）。認証前のRCE（リモートコード実行）が可能な範囲は、Keycloak・Jira・Confluence・Jenkins・Artifactory・PingFederateなど、デフォルト構成の主要Javaアプリに及びました。最適化されたアセンブリコード（AVX-512 VBMI対応のx86-64 CPUのみ）が末尾のパディング処理を誤り、ヒープ境界を越えた書き込みが発生する、という根因です。

  • CVE-2026-114938／CVSS 4.0: 9.2（CRITICAL）
  • OpenJDK 17.0.6以降＋AVX-512 VBMI対応x86-64CPUが対象（ARM64は影響なし）
  • 悪用例：Keycloak・Jira・Confluence・Jenkinsなど認証前RCE
ゆい
これを発見したのはセキュリティ企業Califの研究者がOpenAIのCodexにJVM内部の監査をさせた結果で、発見まで約1時間、最初の動作するエクスプロイトまでさらに2時間、AIのトークンコスト合計は200ドル未満だったんだって。「メモリ安全」が売りのJavaでも、性能クリティカルな部分はまだ低レベル言語で書かれてて、そこをAIが集中的に掘ったのが勝因らしいよ。

IDEA 02

攻撃者はどうやって脆弱性を見つけるか2:31 How Attackers Find Vulnerabilities

この章では攻撃側の探索プロセスそのものが解説されます。AIエージェントを使った攻撃者は、コードベースや公開情報から入口（エントリーポイント）を洗い出し、信頼境界（トラストバウンダリ）をまたぐデータの流れを追い、入力が到達する危険な操作（シンク）を突き止めます。Java4Shellの事例で言えば「Base64という誰もが使う機能が、最適化コードという見落とされやすい層で境界を破っていた」のが発見の鍵でした。防御側も同じ地図で自分のコードを見直す必要がある、という流れです。

ゆい
攻撃者の地図と防御者の地図が同じものなら、先に歩いたほうが勝ちなんだね。入口→境界→シンクっていう流れは覚えておく価値がありそう。

Cloudflareのセキュリティ監査スキル6:28 Cloudflare's Security Audit Skill

動画の主役ツールは、Cloudflareが無料・オープンソースで公開している「security-audit-skill」。コーディングエージェントに組み込むと、エージェントをセキュリティ監査人に変えるスキルです。単発のプロンプトではなく、偵察から報告までを構造化された手順（後述の6フェーズ）で回し、出力は機械可読なJSONと人間向けレポートの両方で残ります。「実際の信頼境界を破る脆弱性だけを、ソース証拠付きで・安全に再現できる形で・最小の修正とともに報告する」という思想がドキュメントに明記されているのが特徴です。

スキルのインストール7:38 Installing the Skill

導入はSkills CLI（skills.sh）経由の1コマンドで完結します。監査したいリポジトリでコーディングエージェントを起動し、「security audit this codebase」「find security vulnerabilities in ./src」のように依頼するだけで、リクエストがスキルのトリガー（セキュリティ監査・脆弱性発見・ペンテスト等）に一致すると自動で有効化されます。フル監査モードでは出力先を明示しない場合、対象リポジトリの外（~/security-audit-skill/<repo>/run-N）に成果物が置かれ、対象ソースを汚さない設計です。

TOOL 03

6フェーズの監査プロセスReconから報告までのフルワークフロー

スキルの監査は6つの段階で実行されます。①偵察：アーキテクチャ・信頼境界・入力面のマップとカバレッジ台帳の作成、②カバレッジ主導のハンティング：独立したハンターに単位を割り当て、不足を指摘する批評者（カバレッジクリティック）がギャップを探す、③候補検証：全候補を「反証しようとする」新しいエージェントに渡す、④構造化出力：判定をJSONスキーマで検証、⑤独立記録検証：最終的な主張を別エージェントが再検証、⑥レポート生成。quick／standard／deepのプロファイルで深さを調整できます。

①偵察→ ②ハンティング→ ③候補検証→ ④構造化出力→ ⑤記録検証→ ⑥報告

TOOL 04

ハンターとベリファイアの敵対的検証8:52 Hunters and Verifiers in Action

このスキル最大の特徴が、AIエージェント同士の「敵対的検証（Adversarial validation）」です。脆弱性候補を見つけたエージェント（ハンター）と、その候補の検証を担当するエージェント（ベリファイア）は必ず別個で、検証役は「この発見を否定しよう」と試みます。検証役は引用されたソース箇所をすべて読み直し、再現可能な決定的なチェックは自分で安全に再実行します。1人のAIの出力を鵜呑みにせず、独立したエージェントが互相にチェックする構造は、ハルシネーションだらけになりがちな「AIセキュリティ監査」への一番の回答と言えます。

ゆい
「発見した子と検証する子は別」っていうルール、ほんとに肝なんだ。AIは自信満々に間違えるから、否定役がいたほうが信頼できるんだね。

TOOL 05

判定は3種類：確定・要検証・棄却confirmed / needs_validation / rejected

報告される判定は3つに厳格に分かれます。「confirmed」は完全なソース追跡と再現結果つきの確定発見、「needs_validation」は解決できない事実が正確に記録された未確定のリード（深刻度は付けない）、「rejected」は反証されて棄却された候補です。深刻度は「影響」があって初めて付き、チェックリストからの逸脱そのものには付きません。また「Layer Aが攻撃を防いでいるなら、Layer Bがないことは脆弱性ではなくハードニング備考に留める」といった、誇大報告を抑える規律も文書化されています。

  • confirmed：完全なソース追跡＋再現結果つきの確定
  • needs_validation：未解決事実を明示した要検証（深刻度なし）
  • rejected：反証済みの棄却記録

RUN 03

脆弱性を「証明」して「修正」する10:32 Proving and Fixing the Bug

検出された脆弱性は、そのまま直すのではなく、まず再現（証明）が行われます。スキルの設計思想にもある「安全に再現できる最小限のローカルチェック」で実際に問題が起きることを確認し、影響が本物であることを裏付けてから、最小の有効な修正（smallest effective fix）を適用します。Java4Shellのような実世界の脆弱性対応と同じ「再現→影響評価→修正」の型を、自分のプロジェクトにAIエージェント込みで回すところまでが実演されます。動画の締めくくりも「証明と修正までやることが防御になる」という点に集約されます。

脆弱性候補→ 安全に再現・証明→ 影響評価→ 最小修正の適用

PRAC 01

どのくらいの頻度で自分をハックすべきか11:55 How Often to Hack Yourself

「一度やれば終わり」ではない、というのがこの章の論点です。コードは変わり続け、依存関係は更新され、Java4Shellのような土台の脆弱性も後から現れます（影響を受けたバージョンの広さを考えれば、実は継続的な見直しこそが本質です）。スキル自体が過去の監視漏れ・変更されたソースの再チェックを優先順位の上位に置いているのも、監査が反復を前提に設計されているからです。推奨タイミングの具体的な考え方は本編で解説されていますが、大規模な変更時や依存の大幅更新時には少なくとも見直す、というのが無難な下限と言えます。

ゆい
セキュリティって「やった」で終わらないんだね。コードが動き続ける限り、監査も回し続けるものなんだ。

PRAC 02

自分のアプリだけをハックする12:49 Only Hack Your Own Apps

動画が明確に区切るのが「許可の境界」です。この手法は、あくまで自分が所有・管理するアプリと、テストの許可された対象にだけ使うものです。他人のサービスやアクセス権のないシステムに同じAI手法を向けることは、技術的に可能でも違法・不正にあたります。スキルの文書自体も「これは防御的でソース第一のワークフロー」とし、監査はローカルのソースと安全に再現可能なチェックに限定する設計になっています。13:08のFinal Thoughtsでは、この線を守りながら習慣として回すことの価値が改めて強調されます。

  • 対象は自分が所有・管理するアプリ＋テスト許可のある環境
  • 無許可の対象への適用は違法・不正行為
  • スキル設計も「防御的・ローカル完結」を明記
