SEND 01

利用記録が外部に送られていた1:31章 — 発覚した外部送信の実態

検証の結果、T3 Codeはユーザーの利用記録（テレメトリ）を外部サービスへ送信していました。送信されていたのは行動統計データが中心で、プロンプト本文やファイルの中身そのものが盗み出されていたわけではありません。しかし問題は「明示的な同意なしに送っていた」こと。送信先の解析基盤には、ユーザーの操作ログが記録されていました。

  • 利用記録（テレメトリ）を外部へ送信
  • プロンプト本文・ファイル中身の送信は確認されず
  • 「同意なしで送る」こと自体が最大の問題

SEND 02

「使っていないのに」通信は発生アイドル状態でも送られていた記録

より問題をややこしくしたのが、ユーザーが何も操作していないアイドル状態でも通信が発生していた点。起動するだけで利用記録が送られ、一見「オフにした」つもりの設定でも通信が止まらないケースが報告されました。便利なツールほど「裏で何を話しているか」は見えにくくなる、というセキュリティの難しさを突いた事象です。

PROMISE

「送らない」と言っていたのに3:15章 — 覆された言葉

炎上をさらに深刻にしたのが、開発側の過去の発言。かつてテレメトリは「同意した人のみに送る（opt-in）」方針だと表明していたのに、後にその文言が公式ページから削除されていたことが判明します。実装はデフォルトで送信ONのまま。「言っていたこと」と「やっていたこと」のズレが、信頼を決定的に損ないました。

「送らない」と表明→ 文言が削除される→ 実装は送信ONのまま→ 信頼の崩壊

AUTH 01

認証ファイルからIDを読み取っていた4:07章 — 問題の核心

最も衝撃的だったのが、T3 CodeがCodexやClaude Codeの認証（サインイン）ファイルを読み取り、そこからユーザーIDにあたる情報を取得していた実装。取得したIDは送信前にハッシュ化されていたものの、ソルトなしの変換だったため、理論上は元のIDを推測・突き合わせできる可能性がありました。「匿名化済み」と言い切れる程度の保護ではなかったのです。

認証ファイルを読む→ ユーザーIDを取得→ 弱いハッシュで変換→ 外部へ送信

AUTH 02

「匿名」ではなく「仮名」だったハッシュ化の落とし穴

ソルトなしのハッシュは、匿名化とは呼べません。IDを一方向に変換していても、突き合わせや総当たりで「どのユーザーか」を特定できる余地があるため、セキュリティ用語では「仮名識別」に分類されます。さらに同一インストールへ紐付ける実装も確認され、複数の記録が同じ利用者として繋がる可能性も指摘されました。

  • ソルトなしハッシュ＝仮名識別、匿名ではない
  • 総当たり・突き合わせで特定できる余地
  • 同一インストールへの紐付けも判明

LESSON 02

開発者側への教訓炎上を防ぐのは「先に説明する」こと

開発側の失敗を整理すると、①大事なデータ（ID）に触れる実装の説明不足、②「送らない」という表明と実装のズレ、③文言の静かな削除。どれも技術的な欠陥というより、コミュニケーションの欠陥でした。テレメトリ自体は悪ではなく、透明性を持って設計・開示されれば許容される。炎上の原因は「隠れていた」ことだったのです。

ナビ
テレメトリ＝悪じゃない。開発を続けるための貴重なデータでもあるんだ。許されるか許されないかを分けるのは、送る・送らないの中身じゃなくて「先に説明して同意を得たか」なんだよね。静かに文言を消すのが一番ダメ。全部ここから崩れた。
