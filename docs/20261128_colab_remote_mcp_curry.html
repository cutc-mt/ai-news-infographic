BACKGROUND

前提：Google Colab API & MCP Endpoint発表2026年11月17日 — Colabが外から動かせる

2026年11月17日、Googleは「Google Colab API」と「MCP Endpoint」を発表しました。従来はブラウザ上でノートブックを開いて使うしかなかったColabのCPU・GPU・TPU環境を、外部のアプリケーションやAIエージェントから操作できるようになったものです。実行環境の作成、コード実行、リソース管理が自動化でき、公式の「Colab for VS Code」拡張もこのAPI基盤を利用しています。REST APIは主にランタイム管理を担当し、Pythonコードの実行にはJupyter Serverを利用する設計です。

  • REST API（v1beta）は6メソッド：作成・一覧・取得・削除・契約照会・スペック一覧
  • 無料ユーザーを含むすべてのColabユーザーに提供

WHAT IS

MCP（Model Context Protocol）とは何かAIエージェントと外部ツールをつなぐ標準プロトコル

MCPは、AIエージェント（LLM）と外部ツール・サービスを接続するためのオープンな標準プロトコルです。MCPサーバーがツール一覧（tools/list）を公開し、エージェントは必要なツールを直接呼び出せます。Claude Code、Gemini CLI、Windsurfなど主要なエージェントが対応しており、「エージェントにColabのGPUを貸す」にもこの仕組みが使えます。

CORE 01

リモートMCPの接続先は1つcolaboratory.googleapis.com/mcp

今回の目玉は、GoogleがホストするMCPサーバー「colaboratory.googleapis.com/mcp」への直接接続です。ブラウザでノートブックを開く必要がなく、HTTP POSTでinitialize（初期化）→ tools/list（ツール一覧）→ tools/call（ツール実行）というMCPの標準的な流れで通信します。ローカル環境に何かを常駐させる必要もありません。

プロトコル合わせ→ tools/list
ツール一覧取得→ tools/call
ランタイム作成・実行

CORE 02

使えるツールは10種類ランタイム管理とコード実行のフルセット

MCP経由で公開される主なツールは、ランタイム管理系とセッション実行系の2群、計10種類。中でもエージェント活用の中心になるのが execute_code で、Colab上でPythonコードを実行して標準出力やエラーを取得できます。同じセッションを使い続ければ変数やライブラリの読み込み状態も維持されます。

CORE 03

ランタイム＝クラウドのJupyterサーバー作成は遅い＆クォータ制限つき

Colabの「ランタイム」の実体はクラウド上のJupyterサーバーで、接続情報（URL・短期トークン・有効期限）をConnectionInfoとして受け取ります。公式ドキュメントによれば、ランタイム作成は「遅くクォータ制限がある」ため、使い回しが推奨。状態を分離したいときはランタイムを作り直すのではなく、新しいセッション（create_session）を使うのが定石と明記されています。GPUスペックによっては容量不足（FAILED_PRECONDITION）やレート制限（RESOURCE_EXHAUSTED）が返ることもあります。

  • DEADLINE_EXCEEDED時は同じリクエストを再送すると「待ち」に切り替わる
  • RESOURCE_EXHAUSTED時は指数バックオフで再試行
  • requestIdには毎回新しいUUIDを渡す

HOW TO 02

認証の勘所：スコープは1つだけgoogleapis.com/auth/colaboratory

未認証のまま tools/list までは200が返りますが、自分のランタイムを問い合わせる list_runtimes を呼ぶと401になります。ここで要求されるスコープは「googleapis.com/auth/colaboratory」の1件だけ。毎回ブラウザで同意画面を開くのはエージェント運用に向かないため、デスクトップアプリ向けOAuthのリフレッシュトークンを保存しておけば、再起動後も同意画面なしにアクセストークンを取り直せるとの検証報告があります。ただしOAuth同意画面が「テスト中」のままだとリフレッシュトークンは7日で失効する点に注意です。

HOW TO 03

Claude Codeから使う方法headersHelperで動的登録の壁を回避

Claude CodeはリモートMCPサーバーに対してOAuthクライアントを動的に登録（dynamic client registration）しますが、Googleの認可サーバーはこれに対応していません。実践報告で確立された回避策が headersHelper —— 接続時にコマンドを実行し、そのJSON出力をリクエストヘッダーとして送る仕組みです。Colab CLIのログインで colaboratory スコープつきトークンを取得し、APIを有効化したクォータプロジェクトとともに headersHelper 経由で渡す構成が定番になっています。

  • 動的クライアント登録は「Incompatible auth server」で失敗
  • headersHelperがトークン＋クォータプロジェクトを供給
  • read-onlyツールだけ許可して安全に検証する使い方も可能

HOW TO 04

実践検証の指標TPUが4秒で使い始められる

COMPARE 01

3月のローカルMCPとの違い「ブラウザ接続型」と「Googleホスト型」

実はGoogleは2026年3月にも同名のオープンソース「Colab MCPサーバー（googlecolab/colab-mcp）」を公開していました。ただしこちらはローカルでサーバーを立ち上げ、開いているブラウザとWebSocketでつなぐ仕組み。Agent側で使えるのは最初 open_colab_browser_connection だけで、トークン検証後に tools/list_changed イベントで他のツールが解放される——と、クライアント側の対応度に左右される部分がありました。11月のリモートMCPはこの制約をまるごと回避し、ブラウザのタブを開かずに済みます。

3月版
ローカル起動・ブラウザ接続が必須
11月版
Google側でホスト・ノートブック不要

COMPARE 02

Colab CLIとの使い分け「コマンド」か「ツール呼び出し」か

2026年6月公開の「Colab CLI」との比較も重要です。CLIは colab exec 1コマンドでノートブック全体を実行でき、ワンオフのスクリプト向き。MCPエンドポイントは1セルごとの execute_code になりますが、ツールがエージェント向けに記述されており、list_runtimes と delete_runtime が自分のアカウントの全ランタイムに届く点でエージェント用途に有利です。CLIのログインは colaboratory スコープつきトークンを得る最短ルートでもあります。

  • ノートブック実行：CLIは一括／MCPは1セルずつ（長いセルは分割を）
  • エージェントからの呼び出し：シェル経由（CLI）vs ツール直接呼び出し（MCP）
  • CLIログインのトークンがそのままMCP認証に流用可能

USE CASE

エージェントの動きの具体例「GPUで学習して報告して」の分解

MCP対応エージェントに「Google ColabのGPUを使って機械学習モデルを学習し、結果を確認してください」と指示すると、(1)利用可能GPUの確認 → (2)GPUランタイム作成 → (3)Pythonセッション作成 → (4)ライブラリ導入と学習実行 → (5)結果の取得と報告 → (6)不要ランタイムの終了——という流れをエージェントが自律的に回せます。ローカルのマシンを占有せず、安全なクラウドサンドボックスで高速に試せるのが魅力です。

GPU確認→ ランタイム作成→ セッション作成→ 学習実行→ 報告→ 後片付け

TIPS

注意点と小ワザエージェント運用でハマりやすい所

実運用で押さえておきたいポイントをまとめます。ローカルMCPでランタイムが切れた場合、エージェント側からは再接続できない点（あらかじめGPU付きで起動しておく必要がある）、結果として直接返るのは主にテキストで、画像やファイルの取得には別途HTTP接続が必要な点、そしてローカル版の既存ノートブックを開くには、新規ノートブック側のトークンをコピーして「ローカルのMCPに接続」で張り付ける方法がある点などです。

  • ローカル版：ランタイム切断後はエージェントから復旧不能
  • MCPの実行結果は基本テキスト（画像は別経路で取得）
  • 3月版ローカルMCPは uvx git+github.com/googlecolab/colab-mcp で導入
  • 前提パッケージは Python・git・uv の3点
